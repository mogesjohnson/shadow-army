# Packet M1-R3-V1: M1, round 3, red team's findings (on v0.14, v2@02d5f84.md)

## R-M1-161

- severity: P1
  type: defect
  location: PO-5 (docs/spec/v2.md:244), with WSP-3 (docs/spec/v2.md:742) and Appendix D actors/residual 5 (docs/spec/v2.md:1746, 1778)
  claim: Nothing makes the post office refuse a symlinked `.shadow/v2`/`.shadow` path, so a malicious repository can redirect the army's log/instruction (and, from M3, credential) directory to an attacker-controlled, possibly world-readable location that it also controls the contents of.
  scenario: The owner clones a hostile repo that commits `.shadow/v2` (or `.shadow`) as a git-tracked symlink to `/tmp/evil` (a world-readable, attacker-writable dir) — a repo is not bound by v1's "never commit .shadow" convention, and git recreates the symlink on checkout on Linux/macOS (both supported, PO-21/VER-2) before the post office ever runs. PO-5 then "creates `.shadow/v2/`" (a no-op through the existing link) and "makes sure that `.shadow/v2/.gitignore` holds `*`", writing the session logs, the `--append-system-prompt-file` and `--settings` env file (CH-2), and the post office's own log through the link into `/tmp/evil`. Result (1): secrets a CLI writes into its session log — accepted by residual 5 only because logs are "the owner's alone (PO-5)" — now leak to any local user and to the attacker; from M3 the `--mcp-config` soldier credential (PO-4) leaks the same way. Result (2, worse): the attacker controls the bytes in `.shadow/v2/logs/`, so after a post office dies mid-turn, PO-1's recovery, which finishes a dead turn "trusting the snapshots and worktrees the last one's log says it made or removed, as WSP-10 does" (line 216, 767), can be fed forged log lines claiming a snapshot/worktree was made — making the checkout guard (boundary 6, which the threat model promises is at least "detected" against the untrusted "Repository content" actor) treat an attacker's metadata/checkout change as explained. WSP-3 link safety is M6, so there is no link guard in M1 at all.
  evidence: PO-5 line 244 ("On Linux and macOS, the post office creates `.shadow/v2/` and `~/.shadow-army/` readable only by the owner's user (0700) ... writes its own files there 0600") says nothing about refusing a symlink or using O_NOFOLLOW; WSP-3 (line 742) "(M6; I, F) Link safety everywhere" is not in M1; Appendix D actors row (line 1746) "Other local users ... the army's files are the owner's alone (PO-5)"; residual 5 (line 1778) accepts CLI-written secrets in logs on the premise they stay owner-only; PO-1 line 216 and WSP-10 line 767 trust the prior log's record of snapshots/worktrees during recovery. No ledger row mentions symlinks (grep: no matches); R-F-100 fixed only file permissions, not path-is-a-link or pre-existing dirs.
  fix: Add to PO-5 (and name it in WSP-11 for the snapshot root): before writing anything under `.shadow/v2/` or `~/.shadow-army/`, the post office MUST verify each path component is a real directory it owns, not a symlink or a path owned by another user, opening with O_NOFOLLOW on each component (or equivalent on Windows); a `.shadow/v2` or `.shadow` that is a symlink, or is owned by another user, fails the start with an error ("the army's folder is not a plain directory owned by you"), and no soldier starts. Add an M1-AC2 X case: a repo whose `.shadow/v2` is a committed symlink starts nothing and reports why.

## R-M1-162

- severity: P2
  type: contradiction
  location: PO-5 (docs/spec/v2.md:244) vs M1-AC2 (docs/spec/v2.md:1029)
  claim: PO-5 requires narrowing an over-permissioned pre-existing folder only on Windows, but M1-AC2 tests that narrowing on Linux/macOS too, so the Linux/macOS owner-only guarantee has no requirement behind its own test.
  scenario: On Linux/macOS, `.shadow/v2/` already exists at mode 0755 (left by a prior run, a different tool, or a group-writable shared checkout). PO-5's Linux/macOS sentence only says it "creates ... 0700, whatever the umask"; mkdir on an existing dir is a no-op and the 0755 stays, so another local user (an untrusted actor per the Appendix D actors table) can read the logs — which per residual 5 can hold secrets a CLI wrote. The narrowing-of-existing clause ("Where either folder already exists with more, the post office narrows it at start, and its log says so") is grammatically attached to the Windows sentence alone. Yet M1-AC2 asserts "on Linux and macOS, `.shadow/v2/` and `~/.shadow-army/` are 0700 ... a folder that existed with more is narrowed, and the log says so (PO-5)" — a behavior PO-5's Linux/macOS prose never states.
  evidence: PO-5 line 244 (narrowing stated only in the Windows clause); M1-AC2 line 1029 ("a folder that existed with more is narrowed, and the log says so"); Appendix D actors line 1746 ("the army's files are the owner's alone (PO-5)").
  fix: In PO-5, move the narrowing requirement out of the Windows clause so it applies on every system: "On Linux and macOS, the post office creates `.shadow/v2/` and `~/.shadow-army/` 0700 and writes its files 0600, whatever the umask; where either folder already exists with wider permissions or a different owner, it narrows the permissions (or refuses, per the symlink fix above) and its log says so."
