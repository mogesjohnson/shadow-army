# Packet M1-R3-V2: M1, round 3, enterprise operator's findings 1 to 6 (on v0.14, v2@02d5f84.md)

## R-M1-167

- severity: P1
  type: gap
  location: PO-19 (v2@02d5f84.md:436, 440), PO-13 (353), PO-14 (361-366), M1-AC15 (1089), M1-AC18 (1104)
  claim: If Group Policy sets PowerShell's execution policy to AllSigned or Restricted, the unsigned guardian script never runs, so no Windows soldier can start and the post office loses its DACL protection. PO-13's checksum blocks the administrator's only fix, which is signing the script. No message, test or non-goal covers this case.
  scenario: 200 Windows 11 laptops have the Group Policy "Turn on Script Execution: Allow only signed scripts" (MachinePolicy AllSigned). At `/army`, PO-3's DACL run of the script fails, and the log says `memory protection: none`. PO-14 step 1 fails, and none of PO-14's example messages fits this cause. The administrator signs the .ps1 with the company's certificate. Set-AuthenticodeSignature appends a signature block inside the file, so its SHA-256 no longer matches the one built into the post office. PO-13 then refuses it with "The containment helper doesn't match ... reinstall it". There is no way forward. M1-AC15 tests AllSigned only at the user scope, which `-ExecutionPolicy Bypass` overrides, so CI passes while every managed fleet fails.
  evidence: PO-19 436 "A Group Policy execution policy still overrides `Bypass`"; PO-19 440 says the DLL isn't signed; PO-13 353 "A file that has changed is refused"; M1-AC15 1089 "With the user's execution policy set to AllSigned, the job still starts". https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1 says of the `-ExecutionPolicy` parameter: "it doesn't take precedence over the execution policy set by using a Group Policy"; "If you disable Turn on Script Execution, scripts don't run"; and AllSigned "Requires that all scripts ... be signed by a trusted publisher". about_Signing (https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_signing) describes the signature block written into the script file.
  fix: "decision: (a) a requirement: PO-20's release workflow Authenticode-signs the script and the DLL with a project code-signing certificate before checksumming, so PO-13's SHA-256 covers the signed bytes. PO-14 gains `Windows PowerShell's Group Policy (AllSigned) doesn't trust Shadow Army's publisher. An administrator can add its certificate to Trusted Publishers. No soldier can start.` M1-AC18 adds MachinePolicy AllSigned and Restricted cases. The certificate is a recurring cost to the owner, as PO-18's Apple ID is. (b) A non-goal: 'Windows machines whose Group Policy sets AllSigned or Restricted run no soldier', with that PO-14 message and an M1-AC18 case."

## R-M1-168

- severity: P1
  type: gap
  location: HOST-2 (v2@02d5f84.md:112-115), §3 (98-101), CH-1 (473), M1-AC10 (1057), Appendix D row 9 (1760)
  claim: The spec never says which executable runs the post office or how it is found. CH-1's rule (an absolute path found on PATH alone, never in the folder) covers only the soldiers' CLIs and git (WSP-10). So the program that receives the Monarch's secret on standard input can come from the folder.
  scenario: Codex's draft starts the post office with `argv: ["node", entry, ...]` and `cwd` set to the folder (AIConnections-m1/plugins/shadow-army/hooks/register.ts:137-139). The owner's PATH holds `.` or `./node_modules/.bin`, the case M1-AC10 tests for claude and git. A cloned repository commits an executable `node_modules/.bin/node`. At the first `/army`, the repository's `node` runs as the owner, before any trust card (ARM-7), and receives the 32-byte secret and the session id. It can pass a real post office's stream through and keep the secret. On Windows, whether Claude Code's spawn also searches the current folder first is NEEDS-PROBE. Under managed `allowManagedHooksOnly`, with Shadow Army deployed as the organization's mod, the repository's own hooks are blocked, so this becomes the repository's one way to run code at first use.
  evidence: CH-1 473 "never in the folder ... never through a relative `PATH` entry", which governs only "An adapter starts its CLI"; M1-AC10 1057 plants only claude and git; Appendix D row 9 marks "The repository to the programs that start" as "prevented"; mod typings `ProcessSpawnRequest`: "`argv[0]` the executable", the host's environment (mod-api-2.1.294/claude-code.d.ts 8023-8050); allowManagedHooksOnly blocks project hooks (https://code.claude.com/docs/en/plugins/mods/admin).
  fix: Add to HOST-2: "The mod starts the post office with the Node.js executable found by its absolute path on `PATH` alone, as CH-1 finds each CLI: never in the folder, a worktree or a snapshot, and never through a relative `PATH` entry. On Windows the current folder is never searched." M1-AC10 adds `node`, `node.exe` and `node_modules/.bin/node` planted at the root, with `.` and `node_modules/.bin` on PATH. Appendix D row 9 names the post office.

## R-M1-169

- severity: P1
  type: gap
  location: PO-13 (v2@02d5f84.md:348-354), PO-20 (442-447), PO-21 (462), PO-17 (415)
  claim: The post office runs third-party npm packages that npm resolves by semver range when the package is installed. Nothing pins, bundles, audits or license-checks them, so the attestation and SHA256SUMS don't cover the code that holds the Monarch's secret and starts every soldier.
  scenario: Release 2.0.0 depends on `"execa": "^10.0.1"` and five other caret ranges (AIConnections-m1/package.json:32-39) and ships no `npm-shrinkwrap.json`. A week later, a compromised patch release of a transitive dependency is published, as in the 2025 npm package compromises. A developer runs `npm install -g` on 2.0.0, and npm resolves the new version. `gh attestation verify` and SHA256SUMS still pass, because they cover the tarball and the binaries only. The post office then loads the malicious code with the secret and, from M3, every soldier credential. Nothing lists the dependencies' licenses (PLAYBOOK §10.6).
  evidence: PO-13 351 "Nothing is downloaded at install or at run time" speaks of the helper only; PO-21 462 relies on "the package's dependencies" sitting in npm's cache; PO-17 415's "no third-party dependency" covers the C helper only. npm honours a published `npm-shrinkwrap.json` but never a dependency's `package-lock.json` (https://docs.npmjs.com/cli/v10/configuring-npm/npm-shrinkwrap-json).
  fix: "Add to PO-13: 'The release package fixes the exact version and integrity hash of every runtime dependency (an `npm-shrinkwrap.json`, or the dependencies bundled into the tarball), so installing a release installs exactly the code CI tested. CI fails on a dependency with a known advisory or a license outside an allowlist. Each release lists its dependencies and their licenses (an SBOM).' PO-21's install test adds a registry that holds a newer patch release, and checks that the pinned one is installed."

## R-M1-170

- severity: P1
  type: gap
  location: HOST-1 (v2@02d5f84.md:111), HOST-2 (112-113), PO-13 (349, 354), M1-AC22 (1123)
  claim: The spec never says how the mod and the release package get installed together. HOST-1's "installed from this repository" yields a checkout, which PO-13 says holds no binaries. Under the vendor's documented enterprise mod policy, only a plugin loaded in place from an administrator's directory marketplace runs, and the spec neither supports nor excludes that.
  scenario: (a) A developer installs the plugin from this GitHub repository. Claude Code copies a git checkout into its cache, with no `native/` binaries and no built post office (PO-13 354), so PO-14 gives "No containment helper", or nothing starts. Reading A (the plugin finds an npm-installed package: where, and which version?) and reading B (the plugin carries the whole package) build different products. Codex's draft reaches `${$.plugin.root}/../../dist` (register.ts:134). (b) The company sets the built-in guard's `allowManagedModsOnly` with `disableSideloadFlags`. A mod loaded with `--plugin-dir`, or copied from a GitHub, git or npm source, counts as a user's mod and is refused, so the army never starts. M1-AC22 installs "the package tarball" but never says how Claude Code loads the mod from it.
  evidence: https://code.claude.com/docs/en/plugins/mods/admin: "No mod a user brings runs its hooks: that covers ... a mod loaded with `--plugin-dir`"; "A plugin that Claude Code copies into its cache counts as a user's ... every plugin from a GitHub, git, URL, or npm source"; a mod is the organization's only when managed settings name "the plugin's marketplace as a directory on the user's machine, by absolute path" and it is listed "by a relative path, so Claude Code loads it in place". Settings reference: `disableSideloadFlags` rejects `--plugin-dir` at startup.
  fix: "A requirement in M1 (from HOST-1): 'The release package is also a plugin marketplace directory. Its `.claude-plugin/marketplace.json` lists the mod by a relative path, and the mod finds the post office, the helpers and the script inside the same installed package, never in a checkout. The owner loads it with `--plugin-dir <package>/plugin`. An administrator can deploy the installed package at a path only administrators can write, as an `extraKnownMarketplaces` directory with managed `enabledPlugins`, so it counts as the organization's mod.' Then decision: whether installing from the repository (a git source) stays supported, or HOST-1 drops it."

## R-M1-171

- severity: P2
  type: defect
  location: PO-1 (v2@02d5f84.md:209, 211), CH-2 (477-479), PO-4 (236, →M3)
  claim: When an organization's managed settings make claude refuse to start, PO-1 counts it as a crash. The soldier restarts three times and ends down with only the CLI's words, although no restart can succeed.
  scenario: Managed `disableSideloadFlags: true` is the vendor's own recommended organization policy. From M3, each claude soldier's `--mcp-config` file (PO-4's fallback) makes claude exit "with an error naming the rejected flags" before its first event. PO-1 counts a crash and restarts the channel after 1, 5 and 30 seconds, then leaves it down, for every soldier and every session. In M1, the same happens to a soldier at `full` under managed `permissions.disableBypassPermissionsMode` if claude exits on `--permission-mode bypassPermissions`. The docs say only that claude "rejects the `--dangerously-skip-permissions` flag" (NEEDS-PROBE).
  evidence: PO-1 209 "A start counts as a crash when it ends before the CLI's first event"; PO-1 211 "Any other error the CLI reports before it exits counts as a crash". https://code.claude.com/docs/en/settings-reference (`disableSideloadFlags`, `permissions.disableBypassPermissionsMode`). The same entry says claude "still accepts a `--mcp-config` whose servers are all in-process `type: "sdk"` entries", which bears on Q9.
  fix: "Add to PO-1: 'A start the CLI refuses because of a setting, such as an organization's managed `disableSideloadFlags` or `disableBypassPermissionsMode`, is not a crash. It is never restarted. The soldier shows down with the CLI's words, and its log and one line in Claude's transcript name the soldier, its autonomy and the refused flag, as in `Kaisel can't start at full: your organization's managed settings disable bypassPermissions · lower its autonomy`.' Add a CH-1 error kind, read from a contract fixture of the CLI's message (NEEDS-PROBE). PO-4 (M3) settles Q9 against `disableSideloadFlags`."

## R-M1-172

  type: gap

CI runs the oldest and the newest of each.'"
