# Packet M1-R3-V3: M1, round 3, enterprise operator's findings 7 to 14 (on v0.14, v2@02d5f84.md)

## R-M1-173

- severity: P2
  type: gap
  location: WSP-11 (v2@02d5f84.md:771, 774, 780), PO-5 (243-246), ARM-6 (702, 709), Appendix D assets (1723-1731)
  claim: Where the army stores the owner's code is spread across the spec. Full copies of HEAD go in the home folder with no way to move them, and the guard baseline's location and contents are never stated.
  scenario: A regulated company keeps source code only on an encrypted, DLP-monitored data volume (`D:\src`) and uses Windows roaming profiles. Each session's snapshot, a full checkout of HEAD, lands in `%USERPROFILE%\.shadow-army\snapshots\`. That folder roams, because only `AppData\Local` and `AppData\LocalLow` are excluded by default, so the source is copied to the profile server at logoff, off the approved volume. A crashed army's copy stays until the next post office in that folder (WSP-11 774). WSP-11 780 says only that the baseline is "written and flushed". A builder may put it in the temp folder, which PO-4 and CH-2 forbid for their own files but nothing forbids for this one. From M2 the card shows "each path and its diff" (ARM-6 709), so the baseline may hold the bytes of `.env*` files.
  evidence: WSP-11 771 "It goes in Shadow Army's own folder in the user's home"; PO-5 246 "with where its guard's baseline is kept". The roaming-profile default exclusions come from a third-party mirror of the policy text (https://gp.kapilarya.com/exclude-directories-in-roaming-profile) and from Citrix (https://docs.citrix.com/en-us/profile-management/2305/configure/include-and-exclude-items); I didn't find the official Microsoft Learn page.
  fix: "A requirement: a data inventory in PO-5 that lists, for each kind of file (logs, tree entries, guard baselines, start states, snapshots, trust records, instruction, settings and MCP config files, the macOS nonce file), where it is, its permissions, when it is removed and how the owner deletes it. The baseline goes beside the session's log under `.shadow/v2/`, never in the temp folder. Then decision: a setting in the owner's own config, never the folder's, that moves `~/.shadow-army/snapshots/`; or a non-goal that states the location and its roaming-profile exposure."

## R-M1-174

- severity: P2
  type: gap
  location: §1 non-goals (v2@02d5f84.md:52), PO-13 (351), PO-2 (221), WSP-10 (763)
  claim: No requirement says that Shadow Army makes no outbound connection of its own or sends no telemetry. Only the helper is said to need no network, and §1's "Any service reachable from the network" is about inbound connections.
  scenario: A security review asks what leaves the machine. Readers can't answer, and a builder who adds an npm update check or crash reporting breaks no rule. Harness git runs the owner's filters (WSP-10 763), so making a snapshot of an LFS or partial-clone repository does reach the network, and the spec doesn't say so.
  evidence: PO-13 351 "Shadow Army makes no network request of its own for the helper"; §1 52.
  fix: "A requirement (X): 'Shadow Army makes no network connection of its own, except on the loopback address (PO-2), and has no telemetry. Data leaves the machine only through the soldiers' CLIs, and through git commands that the owner's own config makes fetch, such as an LFS filter or a partial clone's missing objects while a snapshot is made. A test runs a session with outbound connections blocked and sees none attempted by the post office, the helper or the mod.'"

## R-M1-175

- severity: P2
  type: decision-needed
  location: PO-5 (v2@02d5f84.md:242, 245, 248), WSP-8 (753), SEC-4 (826)
  claim: Logs keep every tool result whole, including file contents and command output, until the owner deletes them. They have no levels, no schema version and no support bundle, so a developer can't send support a log without also sending the repository's content and any secret that `redact()` misses.
  scenario: A soldier keeps crashing, and support asks for logs. The soldier's log holds every file the soldier read and every command's output, such as a `printenv` showing an internal hostname and an `X_AUTH=...` value. That name doesn't end in key or token, so it isn't redacted (residual 5). There is no smaller diagnostic to send instead, and with no schema version, support tooling can't parse logs across releases.
  evidence: PO-5 245 "A log holds each message, thinking block, tool call and tool result whole"; PO-5 248 "Logs are kept until the owner deletes them"; SEC-4 826's stated residual.
  fix: "decision: (a) a requirement: a support bundle (`sa live doctor`, later `/army doctor`) that collects the versions, the containment check, the memory protection line and each log's events without message, thinking or tool-result text, and puts a schema version on each log line; (b) a non-goal for 2.0, stating that logs hold the repository's content and are to be handled like the repository itself."

## R-M1-176

- severity: P2
  type: gap
  location: WSP-10 (v2@02d5f84.md:760-769), WSP-11 (770, 773, 780), PO-8 (294)
  claim: Harness git has no time limit, and nothing stops git from waiting on a credential prompt. A snapshot or guard command that waits on the network or on a prompt therefore holds a soldier's start, or a turn's finishing, forever.
  scenario: A monorepo is cloned blobless (`--filter=blob:none`) or uses LFS. Making a snapshot runs `git worktree add`, so git fetches the missing blobs, or the owner's LFS filter downloads objects (WSP-10 763 runs filters set at start). The token has expired, so Git Credential Manager waits on a prompt no one sees, with no TTY and `GIT_TERMINAL_PROMPT` unset. The soldier never starts, and nothing reports it. An owner's clean filter that hangs during the guard's `git status` at a turn's end leaves PO-8's finishing waiting forever, with the queue stuck.
  evidence: WSP-10 lists the switches harness git sets, with no timeout and no prompt setting; WSP-11 773 handles only a snapshot that "can't be made".
  fix: "Add to WSP-10: 'Each harness git command runs with `GIT_TERMINAL_PROMPT=0` and `credential.interactive=false`, and is ended after <N> seconds on the monotonic clock (<M> for making a snapshot). A snapshot that times out is one that can't be made (WSP-11), with the reason `git took longer than <M> s`. A guard or audit command that times out holds harness git with its reason.' Add a fault test with a fake git that never exits."

## R-M1-177

- severity: P2
  type: gap
  location: PO-1 (v2@02d5f84.md:203), WSP-11 (770-773), ARM-1 (679), SES-1 (637)
  claim: Nothing says when a soldier's session opens, at the army's first use or at its first message, and nothing caps how many are open at once. Each session makes a full checkout of HEAD without checking free disk space, so a roster's disk and memory cost on a large repository is unbounded and unstated.
  scenario: Reading A, every roster soldier opens at `/army`: 7 claude processes, plus 7 snapshots of a 15 GB checkout, about 105 GB in the home folder. Reading B opens one at the first message. On Windows the snapshot prefix `C:\Users\<user>\.shadow-army\snapshots\<folder>-<12 hex>\<session id>\` adds about 80 characters. So a repository whose deepest path fits within 260 characters at `C:\src\r\` fails to check out without `core.longpaths`, and WSP-11 773 gives only "does not start".
  evidence: The words "first message", "opens when" and "on demand" appear nowhere in PO, CH or SES about a session's opening; WSP-11 770 makes a snapshot "when the session opens".
  fix: "A requirement: 'A soldier's session opens at its first message [or: at first use]. At most <N> sessions are open at once, and a later one waits in its queue with `waits · <N> soldiers open`. Before making a snapshot, the post office compares free space with the checkout's size, and refuses with `snapshot not made · 12 GB needed, 4 GB free`.' Whether the cap is fixed or a setting is a technical choice."

## R-M1-178

- severity: P2
  type: decision-needed
  location: ARM-7 (v2@02d5f84.md:720-722), CH-7 (526), Appendix D residual 4 (1777)
  claim: An organization can't set Shadow Army policy for its fleet. It can't cap autonomy, such as forbidding `full`, and it can't pre-accept a repository's committed policy files, because ARM-7 lets nothing but the card accept a file.
  scenario: The company's policy says no agent runs unsandboxed. A developer sets Kaisel to `full` in the folder's `shadow.config.json` and accepts the card, and claude runs in bypassPermissions. The organization's only lever is Claude Code's managed `disableBypassPermissionsMode`, which the PO-1 finding above shows leading to a crash loop. Separately, a monorepo's committed `shadow.config.json` changes weekly, so 200 developers each answer the card after every change. That card fatigue feeds residual 4.
  evidence: ARM-7 721 "No setting, flag, environment variable or file in the folder accepts a policy file"; ARM-7 722 keeps the record per user in `~/.shadow-army/trust/`.
  fix: "decision: (a) a requirement: an administrator file at a path the OS protects (as with Claude Code's managed settings), which Shadow Army reads first and the owner can't override. It can cap each CLI's autonomy and list accepted hashes of a repository's committed policy files. (b) A non-goal: Shadow Army has no administrator policy, and organizations use their vendors' managed settings, with PO-1's outcome for a refused start."

## R-M1-179

- severity: P2
  type: decision-needed
  location: PO-13 (v2@02d5f84.md:348-354), HOST-2 (115), PO-16 (384-390), ARM-7 (722)
  claim: Installation is specified, but upgrade, rollback and uninstall are not. No state file carries a format version, and nothing says what to remove when Shadow Army is uninstalled.
  scenario: IT rolls 2.0.1 back to 2.0.0. 2.0.0 reads trust records and `.shadow/v2/trees/` entries written by 2.0.1, and nothing says whether it can. A tree entry it misreads leaves a dead army's processes unswept (PO-16). After `npm rm -g`, `~/.shadow-army/` stays (trust records naming every repository, and crashed armies' snapshots, which are copies of source code). So do each working tree's `.shadow/v2/` logs and the `.git/worktrees/` entries for snapshots. An upgrade under a running session is defined, but only in scattered places (PO-13 353, HOST-2 115).
  evidence: The spec says nothing about upgrade, rollback or uninstall; no format version appears in PO-5, PO-16 or ARM-7.
  fix: "decision: (a) a requirement (an OPS area, as PLAYBOOK §10 proposes): each state file carries a format version, and a post office refuses a newer one with a message rather than misreading it. An uninstall step, or a documented list, removes `~/.shadow-army/`, each known folder's `.shadow/v2/` and Shadow Army's worktree entries, after listing them. What an upgrade does is stated in one place. (b) A non-goal for 2.0, with the leftovers listed in the setup guide."

## R-M1-180

- severity: P2
  type: readiness
  location: §1 (v2@02d5f84.md:36-54), PO-20 (448-454), PO-14 (369)
  claim: M1 ships security-critical native code built on Apple's private interfaces, plus a release workflow. Yet the spec has no vulnerability disclosure policy, no window of supported releases and no path for security patches, and the repository has no `SECURITY.md`.
  scenario: A researcher finds a pid-reuse flaw in the macOS helper and has no private channel to report it or response time to expect. An enterprise vendor-risk questionnaire asks how vulnerabilities are reported and patched, and nothing answers it. PO-14 369 says "the fix ships as a patch release" but not which releases receive patches.
  evidence: A glob of the review worktree finds `LICENSE` but no `SECURITY.md` or `CHANGELOG`; PLAYBOOK §10.1 and §10.8.
  fix: "A requirement (R, among the release criteria): 'The repository has a `SECURITY.md` naming a private reporting channel (GitHub private vulnerability reporting), a first response within <N> days, and the releases that get security fixes, the latest minor release.' Or state it as a non-goal."
