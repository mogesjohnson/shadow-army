## R-M1-206

- severity: P1
  type: gap
  location: WSP-10 (v2@785cc17.md:776, 779-780); PO-1 (:221); PO-7 (:258, :272-280); WSP-11 (:784, :791-792)
  claim: A turn whose guard can't run because harness git is held is never checked if the post office then shuts down cleanly. So a soldier can stop the guard from seeing its own write to the checkout by also changing the shared git config in the same turn.
  scenario: In M1, a claude soldier runs at auto in its snapshot. In one turn it edits `<folder>/src/app.ts` by absolute path and runs `git config core.autocrlf true` in the shared config. At the turn's end, the guard's first harness git command sees the config change and holds harness git. The turn "needs harness git to finish". The owner sees only `harness git is held · shared config changed`. In M1 the hold lasts "until the post office restarts", which happens only when Claude Code exits. That shutdown is a clean one, so it closes its channels. The next post office finishes leftovers only "after a post office that didn't close its channels". The deferred guard (and from M2 the claim audit) never runs, and `src/app.ts`'s change is never reported. The snapshot's writes are never reported either: reporting them needs harness git, and WSP-11 says "A snapshot is removed only after its writes are reported". So the snapshot, a full copy of the code, stays in `~/.shadow-army/snapshots/` with no outcome. A crash restart while harness git is held is just as undefined: the old snapshot can't be reported, the new one "does not start", and PO-1's 1/5/30-second schedule doesn't say whether that start counts as a crash. From M2, an n on the card or no answer before exit loses the turn the same way.
  evidence: :780 "A turn that needs harness git to finish ends interrupted … Once harness git goes on, that turn's guard and audit run before anything else"; :779 "In M1 … harness git stays held until the post office restarts"; :221 "After a post office that didn't close its channels. Before it opens any channel, a post office finishes what the last one left open"; :791 "A snapshot is removed only after its writes are reported"; :770 the guard's git commands are harness git. Precedent: ledger R-F-126 fixed this same loss for WSP-12's pending revert ("a later post office retries it … however the last one ended"), but not for a deferred guard or snapshot report. Appendix D row 6 (:1782) claims "detected".
  fix: In WSP-10 after :780 add: "A turn whose guard or audit waits on held harness git keeps its baseline and stays open in its log, and a snapshot whose writes can't yet be reported stays. Every later post office, however the last one ended, finishes each such turn and snapshot as PO-1 says before it opens any channel. At a shutdown with harness git held, the post office's log and one line in Claude's transcript name each turn whose guard hasn't run and each snapshot left, as in `Iron's turn at 14:02 not checked: harness git held · checked at the next start`." In PO-1 :221, replace "After a post office that didn't close its channels" with "After a post office that didn't close its channels, or left a turn's guard or a snapshot's report waiting (WSP-10)". Add an M1-AC10 case: a config change plus a checkout edit in one turn, then a clean shutdown, then the next start reports the edit.

## R-M1-207

- severity: P1
  type: ambiguity
  location: HOST-2 (v2@785cc17.md:115); PO-3 (:229-231); PO-7 (:262); PO-1 (:209-211); M1-AC8 (:1070)
  claim: The spec says `sa live` works "through the same post office", but it never says how a terminal tool reaches a post office whose secret exists only in the mod's memory. Each way of building it breaks a MUST elsewhere.
  scenario: Reading A: `sa live` attaches to the mod's post office. It has no secret, because PO-3 forbids the secret on disk, on a command line or in the environment, so every command is refused. Reading B (Codex's draft, `src/v2/client.ts:38,68` and `cli.ts:18-48`, which spawns its own post office with an optional lease): `sa live` starts its own post office. Then (1) PO-7 says "without [Claude's session id], the post office refuses to start", and `sa live` has none. (2) While the owner's `/army` post office runs, `sa live` is refused with "the army is already running in this folder", and if `sa live` starts first, `/army` is refused. (3) Every M1 notice that goes to "one line in Claude's transcript" (crash, containment, trust card, snapshot) has no transcript to go to. (4) M1-AC8's "`/clear` and `/resume` during a soldier's turn … the running turn go[es] on" tests nothing if the turn runs in `sa live`'s own post office. The trust card (ARM-7) needs `$.ui.ask`, which a terminal tool doesn't have.
  evidence: :115 "`sa live`, the dev tool that opens, messages, stops and reconnects a claude soldier through the same post office"; :230 "MUST NOT be written to disk, a command line, an environment variable"; :262 "without one, the post office refuses to start"; :1070 "Through `/army` and `sa live` … `/clear` and `/resume` during a soldier's turn". Also, "stops" in M1 has no meaning: the stop is CH-10 (→M2), and :280 says M1 has none.
  fix: decision: (a) `sa live` is a dev-only mod command, so it goes through the mod's post office, secret and lease. (b) `sa live` is a terminal tool that starts its own post office as the mod does: its own secret on stdin, its own process as the session id and as what the watch follows, notices printed on its terminal in place of Claude's transcript, the trust card asked on its terminal, and refused while the mod's army runs in the folder. Then M1-AC8's `/clear` and `/resume` cases go through `/army`. Either way, say what "stops" means in M1: close the session.

  scenario: The owner has an LSP plugin installed, such as a TypeScript language server, which a `claude -p` soldier loads. An M1 soldier at auto edits `src/x.ts` in its snapshot. claude starts the plugin's language server, which "joins the process tree during that turn" (the spec's own words at :294). The turn's `result` comes, but WSP-11 keeps the guard open "while a process that joined the process tree during the turn hasn't exited". The server never exits, so "the soldier's next message waits until then", which is only when the session closes. Meanwhile, every save the owner makes in the checkout fails that turn ("any other change it finds fails the turn"), for as long as the session lasts. Whether a stdio MCP server spawned during the first turn also joins "during the turn" depends on timing: NEEDS-PROBE.
  evidence: :792 "Until PO-8 (→M2), it also stays open past the end event while … a process that joined the process tree during the turn hasn't exited; it closes when that work ends or the session closes, and the soldier's next message waits until then"; :294 "claude, for example, starts a plugin's language server at the first edit of a matching file … so the server joins the process tree during that turn"; :297 "A session service never keeps a turn open" applies only from M2.   fix: In WSP-11 :792, after "hasn't exited", add: "other than a session service as PO-8 defines it, which never keeps it open". Make PO-8's session-services bullet and claude's table of declared servers (CH-8) part of M1 for claude, and add an M1-AC11 case in which a fake starts a declared language server mid-turn and its next message goes in. ## R-M1-209

- severity: P2
  type: gap
  location: PO-1 (v2@785cc17.md:221-226); PO-5 (:253)
  claim: Recovery reads only "the last one's logs" and doesn't log its own progress. A post office that dies during recovery therefore either loses its predecessor's open work or repeats it.
  scenario: Post office A is killed mid-turn, leaving an open turn, its baseline, and snapshot S_A holding a soldier's commit. At the next use, B starts and begins PO-1's finishing. Then Claude Code is killed after B has written the checkout-change line but before it has reported S_A, or before writing anything. C starts, and "the last one" is B, whose log shows nothing open. Reading 1: C reads only B's log, so A's turn, baseline and S_A are never finished, and S_A's read-violation is never reported. Reading 2: C walks back through older logs, so A's checkout line and S_A report are given twice, or once if B left markers the spec doesn't require. A related case: a post office killed during `git worktree add` leaves a partial snapshot that no log names, because PO-5 writes the made-line with "its metadata", that is, after the snapshot exists. PO-1 :226 doesn't say whether such a snapshot is found by scanning the army's subfolder or ignored.
  evidence: :221 "a post office finishes what the last one left open, as the last one's logs (PO-5) … show"; :253 "each snapshot … with the commit it was made at … and its metadata, written and flushed as it is made". In contrast, PO-16's tree entries persist until each tree has ended (:399), which makes the sweep idempotent.
  fix: In PO-1 :221, replace "the last one's logs" with "the logs of every earlier post office in this folder with an item not yet finished". Add: "Each item finished is logged as finished, so a recovery cut short is resumed by the next post office and never reported twice. A snapshot in this army's subfolder that no log names is reported with the HEAD it has, as unchecked, then removed."

## R-M1-210

- severity: P2
  type: gap
  location: WSP-10 (v2@785cc17.md:776); PO-9 (:312); PO-1 (:226)
  claim: Harness git is not contained, and only the live post office enforces its 5- and 30-minute limits. A post office that dies leaves its git commands, filters included, running with no limit, alongside the next post office.
  scenario: On a large repository with LFS, the post office starts a snapshot with `git worktree add`, and the LFS smudge filter starts fetching. Claude Code is killed, and the post office with it. If git registers its worktree metadata after the new post office took its trusted state, WSP-10 treats it as a change (it didn't come from the new post office's own command) and holds harness git. In M1 the hold lasts until Claude Code restarts. The owner sees `harness git is held` with no cause they made.
  evidence: :776 "Each command is ended … after 30 minutes on the monotonic clock … on Linux and macOS through its own process group, and on Windows with `taskkill /t /f`" (the post office ends it); :312 containment holds only "every soldier's CLI"; PO-16's sweep (:401-404) covers only CLI trees; :778 "anything else that changed while the command ran is a change".
  fix: In WSP-10 :776, add: "Each harness git command's pid and start time go into `.shadow/v2/trees/` before it starts, as a tree's entry does (PO-16), so the mod and the next post office end a command that outlived its post office, with every process it started, before PO-1's finishing begins." Add an M1-AC16 case: kill the post office during a snapshot's checkout.
