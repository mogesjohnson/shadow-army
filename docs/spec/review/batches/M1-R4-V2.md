# Packet M1-R4-V2: M1, round 4, chaos engineer's findings 7-13 (raised on v0.17, v2@785cc17.md; check them against v0.20, v2@4f481fc.md)

## R-M1-212

- severity: P2
  type: ambiguity
  location: PO-1 lock (v2@785cc17.md:209); PO-7 watch (:270); PO-16 sweep (:401)
  claim: The process start time that the lock, the watch and the sweep compare is "the one the OS reports", with no source or unit. If the implementation reads it as a wall-clock rendering, it changes when the clock or the time zone changes, and the lock, the watch and the sweep all misjudge a living process.
  scenario: On Linux, the implementer reads it the way `ps -o lstart` does, as the boot time plus ticks. After an NTP step or a resume, /proc/stat's btime is recomputed, so the value shifts (NEEDS-PROBE for the exact shift). On Windows, the implementer reads it as `Win32_Process.CreationDate`, a local time with the current offset, so a daylight-saving change or a new time zone changes the string (NEEDS-PROBE). Then: the watch decides Claude Code "ended" and the army shuts down mid-turn with "the process that started it ended". A second use finds the living post office's lock "stale" and replaces it, so two post offices run in one folder. The new one's sweep ends the living one's soldier trees.
  evidence: :209 "The start time is the one the OS reports for that pid, read the same way when the lock is written and when it is checked"; :270 "tells that process apart … by its start time"; :401 "judges that by the entry's pid and start time". The lease, in contrast, explicitly "MUST NOT use the wall clock" (:264). proc_pid_stat(5) field 22 is ticks since boot: https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html. M1-AC1 moves the wall clock only for the lease (:1039).
  fix: In PO-1 :209: "The start time is Linux's `/proc/<pid>/stat` field 22 (clock ticks since boot), macOS's process start from `proc_pidinfo`, or Windows's creation FILETIME from `GetProcessTimes`, compared exactly; never a time rendered in the local or wall clock." Add to M1-AC1: with a living post office, moving the wall clock an hour, and on Windows changing the time zone, leaves its lock live, its watch quiet and its trees alone.

## R-M1-213

- severity: P2
  type: gap
  location: PO-1 startup wait (v2@785cc17.md:214); PO-9 (:319); PO-10 (:333); PO-14 (:364); compare PO-7 (:266), WSP-10 (:776)
  claim: Only the lease and harness git leave out time the post office didn't run. Every other bound counts a sleep, since the monotonic clock "goes on through sleep" on Windows and macOS, so waking the machine can produce a false crash or a false containment failure.
  scenario: On a Windows or macOS laptop, the owner opens a soldier and closes the lid within 10 seconds, during PO-14's check, PO-9's "ready within 10 seconds" or a channel's close. On waking, the post office sees more than 10 seconds gone. The check "has failed", and Claude's transcript names a step still running. Or PO-10's "tree … isn't empty 10 seconds after the kill began", so "the containment has failed": the soldier is down, "won't restart by itself", and a running turn's guard stays open. A sleep during the `initialize` wait (MCP_TIMEOUT plus 30 seconds) counts as a crash and uses up one of the four restarts. The owner gets a containment-failure alarm for a lid closed at the wrong moment.
  evidence: :266 "Node's monotonic clock … goes on through sleep and hibernation on Windows and macOS"; :776 "Time the post office did not run, counted as PO-7 counts it, doesn't count toward a limit" (git only); :364 "A check that hasn't passed 10 seconds after it began, on the monotonic clock, has failed"; :333 "If it isn't, the containment has failed". §5.1 F (:948) tests sleep only for the lease.
  fix: Add to PO-1 a general rule: "Every time bound the post office measures leaves out time it did not run, counted as PO-7 counts it (at most 5 seconds of any one step), the lease and WSP-10's limits included." Add a §5.1 F case: a one-hour step taken as sleep during PO-14's check, during a tree's kill and during a start's `initialize` wait fails nothing and counts no crash.

## R-M1-214

  scenario: `claude` on `PATH` is a version-manager shim that waits on input, or sits on a network share that has stopped answering. `claude --version` never returns, so the soldier's open hangs: it isn't a crash (PO-1's startup wait starts with the CLI), isn't down, and nothing says why. ## R-M1-215

- severity: P2
  type: ambiguity
  location: PO-7 (v2@785cc17.md:269, :279, :283)
  claim: When the mod is stalled, the shutdown event can sit behind the post office's queue of unwritten events, and the spec doesn't say whether the post office flushes that queue before it exits. One reading never exits; the other shows the owner the wrong reason.
  scenario: Claude Code is stopped with ctrl+z for a minute, the case PO-7 :267 names. The lease ends, the post office shuts down, and its last events, the shutdown event included, are still in its own queue behind a full pipe. Reading A: it waits to write them, so with the mod stopped it never exits and keeps its lock. Reading B: it exits and drops them. The owner resumes Claude Code, the mod reads what was in the pipe, then reaches the end of the output with no shutdown event. Claude's transcript says `the post office stopped unexpectedly · exit code 0`, not "no renewal from the mod for 30 s". From M3, the brief rows show endings "as far as its events told it", which are wrong.
  evidence: :269 "writes its events without blocking its event loop … Past 16 MiB of events not yet written"; :279 "It doesn't wait for the mod to read its last events; the logs keep them"; :283 "output that ends with no shutdown event gives the reason `the post office stopped unexpectedly`, with its exit code".
  fix: In PO-7 :279: "It writes what it can of its queued events for at most 2 seconds, then exits. Its exit code names the shutdown's reason (a table of codes), so the mod shows that reason when the shutdown event didn't arrive, and says `stopped unexpectedly` only for another code or a signal."

## R-M1-217

  type: gap
  location: ARM-7 record (v2@785cc17.md:732); PO-1 (:209)
  claim: The trust record is one file per repository, shared by every working tree's army, and written by read-modify-write with no rule for two writers or for a copy read earlier. Two armies' acceptances can overwrite each other.
  scenario: Army X runs in the main working tree and army Y in a linked one, each with its own post office. X read the record at its start. The owner accepts `rules.md` in Y.   evidence: :732 "one file per repository … written whole. Open decision D-33 sets the shipped copy's autonomy.
  fix: Add to ARM-7 :732: "Each acceptance reads the record again just before writing it, adds to it and never removes from it, and replaces it in one rename. Two post offices that write at once both keep their entries: a rename that finds the record changed since it was read is retried from a new read." Add an M1-AC13 case with two armies accepting at once.
