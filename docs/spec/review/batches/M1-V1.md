# Unit M1, round 1, batch M1-V1 (security)

## R-M1-1

- severity: P1
  type: decision-needed
  location: PO-3 (docs/spec/v2.md:170-175); SEC-2 (docs/spec/v2.md:417); M1-AC2 (docs/spec/v2.md:547); lead B2 (docs/spec/v2.md:782)
  claim: PO-3's control keeps the Monarch secret out of files/argv/env but not out of process memory, which the same-user soldier it names as the adversary can read, so the Monarch/soldier credential separation (ADR-0012) does not hold.
  scenario: A prompt-injected claude soldier (red-team position 1, "runs commands as the owner's user") on default Windows (OpenProcess+ReadProcessMemory, same-user DACL) or Linux with yama ptrace_scope=0 reads the mod's or post office's memory, lifts the 32-byte secret, and then issues Monarch commands (send/assign a brief to another soldier, interrupt, close, shutdown) and from M2 answers its own approval requests — acting without the owner. SEC-2/M1-AC2 test only files/argv/env/output/log, so they pass while the secret is extractable; the test gives false assurance.
  evidence: PO-3:172 "MUST NOT be written to disk, a command line, an environment variable, or anywhere a soldier can read. Soldiers run as the same user, so a file only the owner can read is not enough." — but the secret must live in readable memory to be presented on every command, so on Windows/default-Linux it IS "somewhere a soldier can read"; the MUST NOT is unsatisfiable there. B2:782 states the same. ADR-0012 splits the two credentials precisely so "a soldier cannot act as the Monarch."
  fix: decision: how far PO-3 goes. At minimum require, where the OS allows, best-effort memory hardening (Linux: PR_SET_DUMPABLE=0 / rely on yama; name Windows same-user ReadProcessMemory as a residual that cannot be fully prevented), scope the "anywhere a soldier can read" clause to disk/argv/env + hardening, require the credential be revocable/rotatable so a lifted value is short-lived, and add an X test asserting the hardening is applied on supported platforms and stating the Windows residual. Note that because the lift cannot be fully prevented on Windows, the human-approval control (CH-6, SEC-3) must not rest on the Monarch secret alone.

## R-F-29

- severity: P1
  type: decision-needed
  location: §3 (docs/spec/v2.md:83-84); PO-3 (:172); PO-4 (:179, :181); SEC-5 (:420)
  claim: Soldiers run as the same user, so the credentials can't be hidden from them, and PO-3's "anywhere a soldier can read" and SEC-5's "cannot send under another soldier's name" can't hold as built.
  scenario: The claude soldier's credential goes in `--mcp-config` as a JSON string with an Authorization header (S4), so it sits on Kaisel's command line. Iron runs `ps -ef` or `Get-CimInstance Win32_Process`, reads it, and sends "review passed" as Kaisel. SEC-5's test (own credential, another sender named) still passes. On Windows, the Monarch secret sits in the memory of the post office and of Claude Code, which another process of the same user can open for PROCESS_VM_READ under the default DACL.
  evidence: ADR-0012:14 says "soldiers run as the same user and can read whatever the owner can", yet its consequences say "A soldier cannot act as the Monarch". m0-report.md:47. https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights ("The ACLs in the default security descriptor for a process come from the primary or impersonation token of the creator"). https://man7.org/linux/man-pages/man5/proc_pid_cmdline.5.html
  fix: Decision, one of: (a) state a threat model in §3 (credentials stop a confused soldier, not one that reads other processes) and narrow PO-3 and SEC-5 to it; (b) isolate soldiers at the OS level (another user or a sandbox); (c) keep credentials off command lines and files where each CLI allows, and record the rest as residual risk.

## R-M1-2

- severity: P1
  type: gap
  location: ARM-1 (docs/spec/v2.md:376); ARM-3 (docs/spec/v2.md:381); HOST-2 (docs/spec/v2.md:94); VER-5 (docs/spec/v2.md:506); M1-AC6 (docs/spec/v2.md:555)
  claim: The spec puts `cli`, `model` and `autonomy` in repo-resident `shadow.config.json` and defines no trust boundary, allowlist or binary-resolution rule for it, so opening a malicious repo and starting the army runs an attacker-chosen command.
  scenario: Owner opens an untrusted repo that ships `shadow.config.json`. Reading A (`cli` is a free-form command): it sets a soldier's `cli` to `/tmp/evil` (or adds flags); `/army open <soldier>` (M1) spawns it — code execution on open. Reading B (`cli` is an adapter selector claude|codex|grok|agy): the repo plants a `claude.cmd`/`claude.exe` in the repo root or `node_modules/.bin`, and because the post office spawns the CLI with the repo as cwd, Windows/Node binary resolution is unspecified and can prefer the planted file — same result. Either way, a repo-controlled `autonomy: auto` also quietly reduces the vendor's own approval prompts.
  evidence: ARM-1:376 "`cli`, `model` and `autonomy` live in `shadow.config.json`"; glossary:58 "Soldier: one configured CLI and model"; ARM-3:381 "They can be configured." Nothing in ARM-1/ARM-3/HOST-2/SET-1 restricts `cli` to the four adapters, fixes binary resolution, or states that config is trusted/owner-authored. VER-5:506 ("fakes chosen through configuration") confirms config selects executables. Section 1 non-goals (35-53) name no config-trust boundary.
  fix: decision: whether repo `shadow.config.json`/`orchestratorDelegate.md` are trusted. If launched from a freshly opened repo, require `cli` to resolve to one of the four known adapters, require an absolute/validated binary path (no cwd/repo-relative resolution), validate `autonomy` and refuse escalation from untrusted config, and add an X test for a repo-supplied config that names a foreign `cli` or an escalated autonomy.

## R-M1-39

- severity: P2
  type: ambiguity
  location: VER-5 (docs/spec/v2.md:506)
  claim: "Chosen through configuration" doesn't say which configuration, and one reading puts an executable path in a repository file.
  scenario: Reading A: a path key in shadow.config.json selects the fake. In a cloned repository, the first use of the army then runs that repository's own executable as "claude", with the owner's rights. Reading B (the draft): tests inject a `command` through ChannelOptions and ClientOptions, which ship in the product; VER-5 forbids that ("never through a code path that ships").
  evidence: draft src/v2/channel.ts:39-40; src/v2/client.ts:13-14; src/v2/fixture-main.testutil.ts:13.
  fix: decision: tests put `test/fakes/` first on PATH, or set a variable that only the test runner sets. Never a key in shadow.config.json.

## R-M1-24

- severity: P1
  type: gap
  location: CH-7 (docs/spec/v2.md:255); CH-2 (docs/spec/v2.md:221-224)
  claim: No table says which claude flags each autonomy level passes. If a level passes no flag, claude's starting mode comes from settings files or its built-in default, and either can be more permissive than "supervised".
  scenario: A soldier has no `autonomy`, so it is supervised. Reading A (pass no flag): `claude -p` starts in `default`. It starts in `auto` instead when the session doesn't fetch feature flags (for example with telemetry off, on v2.1.285+). It starts in `acceptEdits` when the snapshot's committed `.claude/settings.json` sets `defaultMode`. Either way, a "supervised" soldier acts without asking. Reading B (v1's mapping): plan for reads and acceptEdits for writes, but that needs a write flag, which M1 doesn't have. Reading C (the draft): always `plan`.
  evidence: https://code.claude.com/docs/en/permission-modes ("Which mode a session starts in"): for `claude -p`, "`default` in sessions that fetch feature flags. In sessions that don't, such as on a third-party provider or with telemetry off, `auto` with Claude Code v2.1.285 or later". A settings file's `defaultMode` values other than auto and bypassPermissions "apply from any settings file". 2.0 SAFE-10 (legacy spec :1048) has no table. v1: src/adapters/claude.ts:16-20. Draft: src/v2/claude.ts:30.
  fix: "Every adapter always passes its CLI's permission mode explicitly. For claude, supervised passes `--permission-mode plan` (decision: or `default`), auto passes `--permission-mode auto`, and full passes `--permission-mode bypassPermissions`." Give the same table for M2's CLIs.

## R-M1-56

- severity: P3
  type: editorial
  location: CH-7 (docs/spec/v2.md:254-255); M1-AC5 (docs/spec/v2.md:554)
  claim: CH-7's first bullet forbids "a flag that disables a safeguard", but the flag `full` maps to (`bypassPermissions`) disables the permission prompt. M1-AC5's flag test needs the exception stated.
  evidence: https://code.claude.com/docs/en/cli-reference, `--dangerously-skip-permissions`: "Skip permission prompts. Equivalent to `--permission-mode bypassPermissions`".
  fix: "…passes a flag that disables a safeguard, except the documented flag that the owner's autonomy level chooses."

## R-M1-53

- severity: P2
  type: gap
  location: PO-3 (docs/spec/v2.md:173)
  claim: "The refusal is reported" has no limit, and any local process can read the port from the lock.
  scenario: A soldier reads the port from the lock (PO-1) and sends 1,000 bad requests a second. The post office writes 1,000 log lines and 1,000 events a second, so the log grows without limit and the mod's event stream floods.
  evidence: PO-1 (:164) puts the port in the lock. The draft records every refusal (src/v2/postOffice.ts:260).
  fix: "The first refusal is reported in full. After that, at most one report a minute, with the count since the last one."

## R-M1-31

- severity: P2
  type: contradiction
  location: M1-AC2 (docs/spec/v2.md:547); PO-3 (docs/spec/v2.md:173)
  claim: M1-AC2 says the credential "travels only on the post office's standard input", while PO-3 and section 3 have every command present it over the loopback port.
  scenario: Reading A: each command carries the secret in a header (the draft sends `Authorization: Bearer`), which breaks AC2's literal wording. Reading B: AC2 is taken literally, so commands must prove they know the secret without sending it (for example an HMAC per request). That is a different protocol, with a different test.
  evidence: section 3 (:83): "The mod's commands present that secret". Draft: src/v2/server.ts:59-61; plugins/shadow-army/hooks/register.ts:57.
  fix: AC2: "The credential is handed over only on the post office's standard input. After that, each command presents it over the loopback connection. It appears in no file, command line, environment variable, output or log."
