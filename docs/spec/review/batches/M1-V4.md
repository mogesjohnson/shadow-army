# Unit M1, round 1, batch M1-V4 (records and logs)

## R-M1-11

- severity: P1
  type: untestable
  location: PO-5 (docs/spec/v2.md:183); 5.1 F "a failed log write" (:490)
  claim: A failed log write has a fault test but no defined outcome, and the readings run from carrying on to ending every soldier's turn.
  scenario: The disk fills while Beru and Iron are mid-turn, or on Windows an antivirus scan holds `.shadow/v2/logs/<id>.jsonl` open and the append fails with EBUSY. Reading A, Codex's draft ("A broken audit must stop further work"): the post office closes every session, cutting both turns short, and refuses every later command. Reading B: it reports the failure and carries on, leaving a gap in the only record of the turn until PO-6 arrives in M3. Under either reading, a failed append can leave a torn line that later writes follow. The F test can't pass or fail against a text that sets no outcome.
  evidence: :183 gives only the place and the redaction. :490 lists "a failed log write" with no expected result. In Codex's draft, record() in C:\Users\johns\projects\AIConnections-m1\src\v2\postOffice.ts reacts to any log error with `void this.close()`.
  fix: "PO-5: A failed log write is retried once. If it fails again, the post office keeps working, its state shows one line ('logs not written: <reason>'), and each later write tries again. A log never stops a soldier. A partly written line is ended before the next write, and readers skip any line that doesn't parse." M1 adds a fault test: log writes fail mid-turn, the turn completes, the failure is reported once, and the log resumes when writes succeed. (Stopping the army on an unwritable log instead: decision.)

## R-F-13

- severity: P1
  type: untestable
  location: §5.1 F "a failed log write" (docs/spec/v2.md:490); PO-5 (:183); PO-6 (:184); MSG-4 (:303)
  claim: No requirement says what a failed or partial write does (full disk, a crash mid-append). So this fault case can't fail, and MSG-4's promise never to send a message twice rests on a record write whose failure and durability are undefined.
  scenario: The disk fills. Reading A, as in Codex's draft: one failed log line closes the whole post office, so every soldier's turn is cut short. Reading B: keep running and deliver anyway. The "delivered" record never landed, so after a crash the message reads as queued and is sent again, which is the repeat MSG-4 forbids. A partial last JSONL line after a crash forks the same way: skipping it loses "delivered" and the message is sent twice; refusing it blocks every start. Also undefined: a snapshot or worktree that can't be made, and a report that wasn't written while the summary card shows its path.
  evidence: MSG-4:303 "records a message as delivered before it writes it to the CLI … never repeat one". Codex's draft: postOffice.ts:79-82 closes the post office on any log failure; logs.ts appends with no fsync.
  fix: Choosing between stopping the whole post office (as drafted) and keeping it running with delivery refused is a decision. Either way, state: "A message goes to its CLI only after its 'delivered' record is flushed to disk. With records unwritable, nothing is delivered, and the row says 'cannot write records · disk full'. On start, a partial last line is reported, and a message whose last whole record is 'delivered' ends interrupted. A snapshot or worktree that can't be made refuses the soldier's start; it never falls back to the folder." Add fault cases that check the chosen outcome.

## R-M1-7

- severity: P2
  type: untestable
  location: SEC-4 (docs/spec/v2.md:419); WSP-8 (docs/spec/v2.md:409)
  claim: SEC-4's absolute "Logs and records hold no secret, token or credential" is unverifiable and stronger than `redact()` can deliver, and the required match-set for redact is not defined in-spec.
  scenario: A soldier reads a repo `.env` and quotes `AWS_SECRET_ACCESS_KEY=...` in its session output; the post office writes the session log through redact(). redact (carried from 2.0 SAFE-6) is pattern-based; an arbitrary third-party secret that matches no known pattern is written verbatim, yet SEC-4 asserts the log holds no secret. An implementer cannot know which patterns are required, and the X test can only prove known patterns are removed, not the absolute.
  evidence: SEC-4:419 "Logs and records hold no secret, token or credential (WSP-8)." WSP-8:409 only says redact "runs on every write" and points to 2.0 SAFE-6, which (legacy/spec/shadow-army-2.0.md:1035) likewise only says "A single redact() runs on every write ... Logs are pruned after 30 days" — neither defines what redact matches.
  fix: Scope SEC-4 to the credentials Shadow Army controls (the Monarch secret, soldier credentials, Bearer/Authorization values) and define redact's required match-set there; state that third-party secrets in soldier output are out of redact's scope (or covered only by named patterns), so the test checks a concrete, provable property.

## R-M1-21

- severity: P2
  type: ambiguity
  location: PO-5 (docs/spec/v2.md:183); WSP-8 (:409); SEC-4 (:419); M1-AC2 (:547)
  claim: Redacting each log write can't catch a secret that is split across streamed fragments, and the text doesn't say whether fragments are logged.
  scenario: With `--include-partial-messages`, Iron's reply streams as text fragments. The flag is documented, Codex's draft adds it, and the pane's live view will want it. The model repeats an API key it read from `.env`, and the key arrives split across fragments: "…sk-ant", "-api03-AbC", "dEf…". redact() matches no pattern in any single line, so the pieces are written to `.shadow/v2/logs/<id>.jsonl`. The whole message logged afterwards is redacted, but the fragments stay. SEC-4 fails although every write "passes through redact()".
  evidence: :183 "Every write passes through redact()"; :419 "Logs and records hold no secret, token or credential". CH-2 :222 lists claude's flags without saying the list is complete. https://code.claude.com/docs/en/cli-reference documents `--include-partial-messages`. Codex's draft emits every frame as "raw" (C:\Users\johns\projects\AIConnections-m1\src\v2\claude.ts), and C:\Users\johns\projects\AIConnections-m1\src\v2\postOffice.ts logs each one.
  fix: "PO-5: A log holds each complete message, event or tool result. Streamed fragments are never written, and redact() runs on the complete text." M1-AC2 adds: a secret streamed across fragments appears in no log.

## R-M1-52

- severity: P2
  type: gap
  location: PO-5 (docs/spec/v2.md:183); WSP-8 (docs/spec/v2.md:409)
  claim: The logs have no format, file names, size limit or retention. WSP-8 narrows 2.0 SAFE-6 without saying whether its 30-day pruning and its coverage of "events, reports and fixtures" still apply.
  scenario: A six-hour session logs every thinking delta into one file that grows without limit and is never rotated or pruned. OBS-1 (M5) later has to find "the soldier's log" under a name nobody fixed. The text doesn't say whether the event stream to the mod is redacted; the draft redacts it.
  evidence: 2.0 SAFE-6 (legacy spec :1035): "…logs, events, briefs, reports and fixtures. Logs are pruned after 30 days." The spec's own rule (:31): "unless this spec restates it". Draft: src/v2/logs.ts:55-85.
  fix: "Logs are JSON Lines, one file per session (`<soldier>-<session>.jsonl`), plus `post-office-<start>.jsonl`. They are pruned after 30 days. redact() also runs on the event stream, reports and fixtures." decision: a size limit.

## R-M1-6

- severity: P2
  type: decision-needed
  location: WSP-8 (docs/spec/v2.md:409); SEC-4 (docs/spec/v2.md:419); lead H25 (docs/spec/v2.md:781); Appendix A (docs/spec/v2.md:722-741)
  claim: 2.0's SAFE-7 (strip C0/C1 controls and ESC/CSI/OSC sequences from strings shown in the UI) was not carried into v2, so terminal-escape/invisible-character injection from a malicious repo or a prompt-injected soldier has no control, and the drop is not recorded in Appendix A.
  scenario: A prompt-injected soldier (or a file in a malicious repo echoed by a soldier) emits ANSI escape/OSC/bidi sequences in its text or stderr. In M1 the mod surfaces soldier/CLI diagnostics to the owner's Claude Code UI and to on-disk logs; `redact()` targets secrets, not control characters, so the sequences pass through and can rewrite the owner's terminal, hide or forge output. H25 confirms "Nothing covers control characters, escape sequences or invisible characters."
  evidence: WSP-8:409 carries only 2.0 SAFE-6 (redact). 2.0 SAFE-7 (legacy/spec/shadow-army-2.0.md:1036) "Every model, vendor and config string shown in the UI is stripped of C0 and C1 controls ... and of ESC, CSI and OSC sequences" has no v2 equivalent and no row in Appendix A (722-741). H25:781 flags it as "Could add (v2.0)" touching MSG-1/HOST-4/HOST-11/SEC. New evidence beyond the Appendix C note: it is a dropped carry-over, i.e., a regression from the superseded spec's posture, not merely a new idea.
  fix: decision: restore SAFE-7 as a v2 requirement (strip/placeholder C0/C1, ESC/CSI/OSC and invisible/bidi characters wherever the mod draws text and before text reaches Claude), add it to Appendix A as a carry-over, and give it an X test. Rendering lives in M3/M5, but the requirement and the M1 log/`$.ui.log` surface should be named now.
