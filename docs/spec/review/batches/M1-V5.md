# Unit M1, round 1, batch M1-V5 (the claude channel)

## R-M1-12

- severity: P1
  type: vendor-fact
  location: CH-2 (docs/spec/v2.md:226); M1-AC3 (:548); VER-9 (:514)
  claim: "The turn totals come from `result`" is wrong for claude in stream-json input mode. The result's cost and per-model totals are running totals for the whole process (plus the restored spend after a resume), its `usage` leaves out subagents, and a result after a crash or a stop reports zeros.
  scenario: Iron answers three briefs in one process, each costing $0.10, and the third result reports a `total_cost_usd` of $0.30. If that is read as the turn's cost, the third turn shows $0.30, and SES-7 and HOST-15 add up $0.60 when $0.30 was spent. After a resume (CH-9), the first turn also carries the old session's spend. If the figures are read from `usage`, a turn whose subagent read 200k tokens shows only the main loop. A crash mid-turn (claude emits `error_during_execution` with zeroed fields, then exits) or a stop (S6: "its usage is all zeros") records a costly turn as 0 tokens and $0. VER-9's "tokens" inherit whichever reading the builder picked.
  evidence: https://code.claude.com/docs/en/agent-sdk/cost-tracking, on streaming input mode: "`usage`: covers only that turn, and within it only the main agent loop, not any subagents it ran. `total_cost_usd` and `modelUsage` ... carry the running total for the whole call so far, plus any spend restored when the call resumed a session". The same page: "When the Claude Code process crashes, it emits a final `error_during_execution` result and exits ... may carry zeroed `usage`, `total_cost_usd`, and `modelUsage`". It also says these figures "are client-side estimates, not authoritative billing data". C:\Users\johns\projects\AIConnections\.shadow\v2-tools\review\evidence\s6-results.md records that the interrupt result's usage "is all zeros". It also records the point it planned for the spec: "a turn's figure is the difference from the last report in the same session; a missing or zero report is 'not reported', never a new baseline". Issue #63, comment 6159653512, lists "Usage as each turn's own figures, never running totals" for v0.6, and the text doesn't have it.
  fix: "CH-2: A turn's main-loop tokens are its `result.usage`. Its cost and per-model totals are the difference between its `total_cost_usd` and `modelUsage` and those of the previous result from the same process, shown as claude's own estimate. A result whose fields are all zero after a crash or a stop is 'not reported'. Its input and cache tokens are summed from the turn's main-loop assistant messages, counting each message id once. Its output and cost read 'not reported', and it is never the baseline for the next difference. VER-9 compares the sums of these per-turn figures." M1-AC3 adds a three-turn recording whose per-turn figures add up to the last result's total, and a crashed turn shown as not reported.

## R-M1-16

- severity: P2
  type: gap
  location: CH-2 (docs/spec/v2.md:225); PO-8 (:193)
  claim: CH-2 ends a turn at any `result`, but claude also emits results for turns that no message started, and M1 has no rule tying a result to its message.
  scenario: Brief A's turn starts `npm test` in the background and ends with result A, and the post office sends brief B. The test finishes, and claude takes its follow-up turn (S6). That turn's result, with `origin.kind: "task-notification"`, arrives before B's reply. Under CH-2 it ends B's turn: B is "answered" with A's test outcome, and B's own result arrives later with no message to end. PO-8 (M2) says such a turn "belongs to the same message" but names no field, and M1 ships CH-2 without it.
  evidence: :225 "A turn ends with the result event." C:\Users\johns\projects\AIConnections\.shadow\v2-tools\review\evidence\s6-results.md: "claude then takes a follow-up turn by itself with the outcome." https://code.claude.com/docs/en/agent-sdk/typescript, SDKResultMessage. On `origin`: "When the SDK injects a synthetic follow-up turn, such as for a finished background task, the resulting SDKResultMessage carries origin: { kind: "task-notification" }". On `user_message_uuid`: "The uuid of the SDKUserMessage the turn is answering ... Claude Code echoes a uuid only if you set one on the message."
  fix: "CH-2: Each message is written with its own `uuid`. A `result` ends a message's turn only when its `user_message_uuid` names that message. A result whose `origin.kind` is `task-notification` belongs to the message whose turn started the task (PO-8). Any other result is recorded and ends nothing." M1-AC4's fake adds the background case.

## R-M1-17

- severity: P2
  type: vendor-fact
  location: CH-1 (docs/spec/v2.md:219-220); CH-2 (:221-226); M1-AC4 (:552)
  claim: CH-2 never names the claude fields that carry a rate limit, a context overflow, a login needed or a refusal, and claude retries rate limits by itself. M1-AC4's fake can pass while the real adapter misreads claude.
  scenario: A fake claude emits whatever the builder guessed, and the three-kinds test passes. (Codex's draft falls back to matching "prompt is too long" in the message text, and reads a `model_refusal_no_fallback` frame: NEEDS-PROBE.) Real claude marks a context overflow with `terminal_reason: "prompt_too_long"`, and its assistant `error` values have no overflow kind. On a 429 it emits `system/api_retry` events (`error: "rate_limit"`, `retry_delay_ms`) while it retries, with no reset time. If each retry becomes a CH-1 error event, the owner sees "rate limit" on a turn that then answers; the text doesn't say. The field that marks a refusal isn't among the result's documented fields (NEEDS-PROBE). And a retry after partly streamed text streams the reply again (simulation 4), so the reply has to come from `result.result`, never from joined fragments.
  evidence: :219 "read from the CLI's own fields: a rate limit (with its reset time where the CLI gives one), a context overflow, a login needed"; :220 covers a refusal. https://code.claude.com/docs/en/agent-sdk/typescript: SDKAssistantMessageError is one of authentication_failed, oauth_org_not_allowed, account_on_hold, billing_error, rate_limit, overloaded, invalid_request, model_not_found, server_error, max_output_tokens, cloud_credential_error or unknown. The same page: `terminal_reason` includes "prompt_too_long" and "api_error", and the result also has `api_error_status`. https://code.claude.com/docs/en/headless ("Handle API retries") documents `system/api_retry`. Fixture provenance (VER-4) only arrives in M2.
  fix: "CH-2: The error kinds come from these fields. A rate limit: `error: rate_limit`, or `api_error_status` 429 on the failing turn. A context overflow: `terminal_reason: prompt_too_long`. A login needed: `authentication_failed` or `oauth_org_not_allowed`. A refusal: the field a recording shows. A `system/api_retry` is shown as a retry, with its attempt and delay, never as an error. The reply is `result.result`. Each mapping names the CLI version it was read from (CH-8)." M1-AC4's fake copies its frames from recorded claude output.

## R-M1-18

- severity: P2
  type: ambiguity
  location: PO-1 (docs/spec/v2.md:166); CH-1 (:218); 5.1 F (:486)
  claim: The text doesn't say whether a line the claude channel can't parse is a lost connection (a crash) or an error the session survives. The two readings differ in restarts and in how the message ends.
  scenario: A plugin's hook or an MCP server prints a non-JSON line on claude's output mid-turn. Reading A, Codex's draft (any malformed frame is a lost connection): the tree is ended, the turn is cut short, and the restart counts toward the three. Reading B (CH-8, M2: "an error, never silently dropped"; Appendix C's H2: the session carries on): one error row, and the turn goes on. Also unsaid: a line split across two reads is normal and must be joined, and only a line still incomplete when the stream ends is broken.
  evidence: :166 defines a crash as the process ending or a lost connection. CH-8 :259 (M2): "A line that cannot be parsed is an error, never silently dropped". Appendix C H2 (:784): "Today CH-8 makes it an error without saying whether the session continues". :486 lists the test with no outcome. In Codex's draft, parseLine in C:\Users\johns\projects\AIConnections-m1\src\v2\claude.ts calls failTransport.
  fix: decision: (a) a malformed line is a lost connection: end the tree, finish the turn as cut short (PO-8) and restart (PO-1); (b) it's an error of the kind "another error", kept word for word, and the session continues. Either way: "A line split across reads is joined first; only a line still incomplete when the stream ends is malformed."

## R-M1-43

- severity: P2
  type: vendor-fact
  location: CH-2 (docs/spec/v2.md:224); SI-2 (docs/spec/v2.md:276)
  claim: `--append-system-prompt` can't carry SI-1's multi-line text through an npm-installed `claude.cmd` on Windows, and CH-2 names no other route.
  scenario: On Windows with claude installed by npm, Node has to run the `.cmd` shim through cmd.exe. cmd.exe can't pass a line break inside an argument, and limits a command line to 8,191 characters.   evidence: draft src/v2/claude.ts:92-98; https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows; https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation. The CLI reference documents `--append-system-prompt-file`: "Load additional system prompt text from a file and append to the default prompt".
  fix: "The instructions go in `--append-system-prompt`, or in `--append-system-prompt-file` where the command line can't carry them (a file in the session's folder, removed at close)."
