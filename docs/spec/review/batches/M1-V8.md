# Unit M1, round 1, batch M1-V8 (second, independent verification of the P1s, part 2)

## R-F-30

- severity: P1
  type: gap
  location: §3 (docs/spec/v2.md:82-83); HOST-2 (:94); PO-1 (:164); PO-7 (:186)
  claim: The secret and the event pipe live only in the mod instance that started the post office. Nothing says what happens when any other instance finds that post office's lock: after a reload or worker respawn, from a second session in the folder, or after a restart within the lease.
  scenario: `claude --plugin-dir ./mod` is running in this repository and Iron is mid-turn. Claude edits a file under `mod/`, and the hooks module reloads: session.start runs again with no secret and no stdout handle, and the lease timer stops. 30 s later PO-7 closes every soldier session, cutting off Iron's turn. The new instance finds a live lock it can't command: HOST-2 says to start a post office, PO-1 allows one per folder. `/reload-plugins`, a second `claude` in the folder, or `/exit` followed by `claude` within 30 s hit the same gap.
  evidence: The mods reference says session.start runs "again after a reload of that mod", `--plugin-dir` "reloads its hooks module when you save", and lists `/reload-plugins` (https://code.claude.com/docs/en/plugins/mods/reference). The mods API says "Timers stop when the module reloads" (https://code.claude.com/docs/en/plugins/mods/api). The types file adds "an enable, a worker respawn, or a reload". `$.store` survives reloads but is on disk, which PO-3 forbids for the secret. NEEDS-PROBE: whether a spawned process outlives a reload.
  fix: Decision, one of: (a) refuse with a defined message, plus a defined takeover that first finishes open turns (PO-8); (b) a reload-safe handover; (c) one post office per Claude session instead of per folder. Add the chosen case to §5.1 F.

## R-F-10

- severity: P1
  type: gap
  location: §3 Architecture (docs/spec/v2.md:82-87); HOST-2 (:94); PO-1 (:164, :168); M3-AC12 (:631); §5.1 F (:476-491)
  claim: The spec never says what happens when the post office itself dies. It doesn't say who notices or who restarts it. It doesn't say what becomes of the soldiers' CLIs, their open turns and guards, the queued and delivered messages, or the folder lock, or what the owner sees.
  scenario: Three soldiers are mid-turn and two briefs are queued when the post office is killed (OOM or a crash). Reading A, as in Codex's draft: every later `send` throws "post office is closed", and the lock stays until the owner deletes it by hand. Reading B: the mod restarts it with a new secret. Either way, five things are undefined: (1) whether the CLIs die or run on with no guard (a Linux subreaper's orphans go to init); (2) whether the cut-short turns are ever finished as PO-8 says, when the guard's baseline was only in memory; (3) whether "queued" records become "not delivered"; (4) what the pane shows: its spinners keep turning on stale "working" states, and no toast fires; (5) M3-AC12 tests behavior "after a restart", but no requirement defines a restart.
  evidence: HOST-2 starts the post office only "the first time the army is used in a session". PO-1:168 covers only "When a channel closes or restarts". The fault level has "a CLI killed mid-turn" but no post office kill. Codex's draft: client.ts:76 throws "post office is closed"; server.ts:33 says "remove its stale lock after checking the recorded PID".
  fix: Add to §3 and PO-1: "If the post office exits unexpectedly, the mod shows the army as down (strip, status entry, one transcript line). On start, a post office: reclaims a lock whose pid and start time match no living process; finishes each turn its records show open (PO-8: guard against a baseline kept on disk, then audit, then message interrupted); ends each queued message as not delivered, reason 'post office stopped'. Nothing the CLIs started outlives the post office (PO-1)." The restart policy is a decision: restart on the next use, or ask the owner. Add fault cases: the post office killed mid-turn, with a queue, and with an approval open. Add an integration case with a fake mod host.

## R-M1-11

- severity: P1
  type: untestable
  location: PO-5 (docs/spec/v2.md:183); 5.1 F "a failed log write" (:490)
  claim: A failed log write has a fault test but no defined outcome, and the readings run from carrying on to ending every soldier's turn.
  scenario: The disk fills while Beru and Iron are mid-turn, or on Windows an antivirus scan holds `.shadow/v2/logs/<id>.jsonl` open and the append fails with EBUSY. Reading A, Codex's draft ("A broken audit must stop further work"): the post office closes every session, cutting both turns short, and refuses every later command. Reading B: it reports the failure and carries on, leaving a gap in the only record of the turn until PO-6 arrives in M3. Under either reading, a failed append can leave a torn line that later writes follow. The F test can't pass or fail against a text that sets no outcome.
  evidence: :183 gives only the place and the redaction. :490 lists "a failed log write" with no expected result. In Codex's draft, record() in C:\Users\johns\projects\AIConnections-m1\src\v2\postOffice.ts reacts to any log error with `void this.close()`.
  fix: "PO-5: A failed log write is retried once. If it fails again, the post office keeps working, its state shows one line ('logs not written: <reason>'), and each later write tries again. A log never stops a soldier. A partly written line is ended before the next write, and readers skip any line that doesn't parse." M1 adds a fault test: log writes fail mid-turn, the turn completes, the failure is reported once, and the log resumes when writes succeed. (Stopping the army on an unwritable log instead: decision.)

## R-F-13

- severity: P1
  type: untestable
  location: §5.1 F "a failed log write" (docs/spec/v2.md:490); PO-5 (:183); PO-6 (:184); MSG-4 (:303)
  claim: No requirement says what a failed or partial write does (full disk, a crash mid-append). So this fault case can't fail, and MSG-4's promise never to send a message twice rests on a record write whose failure and durability are undefined.
  scenario: The disk fills. Reading A, as in Codex's draft: one failed log line closes the whole post office, so every soldier's turn is cut short. Reading B: keep running and deliver anyway. The "delivered" record never landed, so after a crash the message reads as queued and is sent again, which is the repeat MSG-4 forbids. A partial last JSONL line after a crash forks the same way: skipping it loses "delivered" and the message is sent twice; refusing it blocks every start. Also undefined: a snapshot or worktree that can't be made, and a report that wasn't written while the summary card shows its path.
  evidence: MSG-4:303 "records a message as delivered before it writes it to the CLI … never repeat one". Codex's draft: postOffice.ts:79-82 closes the post office on any log failure; logs.ts appends with no fsync.
  fix: Choosing between stopping the whole post office (as drafted) and keeping it running with delivery refused is a decision. Either way, state: "A message goes to its CLI only after its 'delivered' record is flushed to disk. With records unwritable, nothing is delivered, and the row says 'cannot write records · disk full'. On start, a partial last line is reported, and a message whose last whole record is 'delivered' ends interrupted. A snapshot or worktree that can't be made refuses the soldier's start; it never falls back to the folder." Add fault cases that check the chosen outcome.

## R-M1-12

- severity: P1
  type: vendor-fact
  location: CH-2 (docs/spec/v2.md:226); M1-AC3 (:548); VER-9 (:514)
  claim: "The turn totals come from `result`" is wrong for claude in stream-json input mode. The result's cost and per-model totals are running totals for the whole process (plus the restored spend after a resume), its `usage` leaves out subagents, and a result after a crash or a stop reports zeros.
  scenario: Iron answers three briefs in one process, each costing $0.10, and the third result reports a `total_cost_usd` of $0.30. If that is read as the turn's cost, the third turn shows $0.30, and SES-7 and HOST-15 add up $0.60 when $0.30 was spent. After a resume (CH-9), the first turn also carries the old session's spend. If the figures are read from `usage`, a turn whose subagent read 200k tokens shows only the main loop. A crash mid-turn (claude emits `error_during_execution` with zeroed fields, then exits) or a stop (S6: "its usage is all zeros") records a costly turn as 0 tokens and $0. VER-9's "tokens" inherit whichever reading the builder picked.
  evidence: https://code.claude.com/docs/en/agent-sdk/cost-tracking, on streaming input mode: "`usage`: covers only that turn, and within it only the main agent loop, not any subagents it ran. `total_cost_usd` and `modelUsage` ... carry the running total for the whole call so far, plus any spend restored when the call resumed a session". The same page: "When the Claude Code process crashes, it emits a final `error_during_execution` result and exits ... may carry zeroed `usage`, `total_cost_usd`, and `modelUsage`". It also says these figures "are client-side estimates, not authoritative billing data". C:\Users\johns\projects\AIConnections\.shadow\v2-tools\review\evidence\s6-results.md records that the interrupt result's usage "is all zeros". It also records the point it planned for the spec: "a turn's figure is the difference from the last report in the same session; a missing or zero report is 'not reported', never a new baseline". Issue #63, comment 6159653512, lists "Usage as each turn's own figures, never running totals" for v0.6, and the text doesn't have it.
  fix: "CH-2: A turn's main-loop tokens are its `result.usage`. Its cost and per-model totals are the difference between its `total_cost_usd` and `modelUsage` and those of the previous result from the same process, shown as claude's own estimate. A result whose fields are all zero after a crash or a stop is 'not reported'. Its input and cache tokens are summed from the turn's main-loop assistant messages, counting each message id once. Its output and cost read 'not reported', and it is never the baseline for the next difference. VER-9 compares the sums of these per-turn figures." M1-AC3 adds a three-turn recording whose per-turn figures add up to the last result's total, and a crashed turn shown as not reported.
