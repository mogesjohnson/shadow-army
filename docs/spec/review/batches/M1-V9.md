# Unit M1, round 1, batch M1-V9 (first verification of the findings verifiers raised)

These three were raised by verifiers in passing, not by a round-1 reviewer, so each gets a first verification here. R-M1-57 and R-M1-58 cite the snapshot `v2@be9deb0.md`; R-F-67 is about text that v0.7 added, so it cites v0.7 (`docs/spec/v2.md`).

## R-M1-57

- severity: P2
  type: decision-needed
  location: CH-2 (docs/spec/v2.md:221-226); CH-7 (:253-255); §2 Autonomy (v0.7 :60)
  claim: v1 maps the supervised autonomy level to claude's plan mode, but plan mode lets claude's classifier approve shell commands by itself whenever auto mode is available (`useAutoModeDuringPlan`, on by default), so a supervised claude soldier doesn't send every command to the owner.
  scenario: A supervised claude soldier, started with `--permission-mode plan` as v1 does (and as R-M1-24's pending fix makes explicit), runs a shell command outside the read-only set. Where auto mode is available, plan mode's classifier approves it, and no permission request reaches the owner, so "supervised" acts partly as auto.
  evidence: raised by verifier M1-V7 (`raw/M1-r1-verify-V7.md`, R-M1-24's side point), citing https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode; v1 `src/adapters/claude.ts:13-22`; Codex's draft `src/v2/claude.ts:30`.
  fix: decision: (a) keep `plan`, and say in CH-2 and the glossary what supervised then allows; (b) map supervised to `default`; (c) keep `plan` with `useAutoModeDuringPlan` off, through a documented setting, where one exists. Big if it changes v1's mapping, since that changes what runs without the owner.

## R-M1-58

- severity: P2
  type: gap
  location: ARM-1 (docs/spec/v2.md:376-378); SES-6 (:355-360); CH-2 (:221-226)
  claim: claude's automatic model fallback re-runs a flagged request on a fallback model, and the session goes on with that model, with no refusal; nothing in the spec covers a soldier's model changing mid-session.
  scenario: A request of Kaisel's (claude-opus) is flagged. claude re-runs it on its fallback model, and the session continues on that model. The roster, the pane's header (name · id · model), the meter, SES-6's model-change rule (another model makes the soldier cold) and the usage records still say claude-opus.
  evidence: raised by verifier M1-V5 (`raw/M1-r1-verify-V5.md`, R-M1-17's side note), citing https://code.claude.com/docs/en/model-config, "Automatic model fallback" ("the session continues on the fallback model"; "The refusal is shown as a normal error" when the fallback is blocked).
  fix: CH-2: when claude reports a fallback to another model, the model shown and recorded for the soldier is the one claude reports, its log says why, and SES-6 treats it as a change to another model; whether a soldier may fall back at all is a question for the verifier to classify.

## R-F-67

- severity: P2
  type: defect
  location: §5.1 L (v0.7 docs/spec/v2.md:561-565)
  claim: v0.7's parity measure counts claude's requests one by one, but claude's per-message output count is a placeholder, its headless `--output-format json` run gives no request ids, and its `--resume` follow-up reports the conversation's whole total, earlier runs' spend included.
  scenario: Measured as written, claude's live total uses placeholder output counts, and its headless follow-up's resumed total counts the first run again, so the 1.05 rule compares the wrong numbers.
  evidence: raised by verifier M1-V5 (`raw/M1-r1-verify-V5.md`, R-M1-12's v0.7 note), citing https://code.claude.com/docs/en/agent-sdk/cost-tracking and https://code.claude.com/docs/en/headless ("Pipe data through Claude").
  fix: for claude, the measure takes each turn's own figures as CH-2 defines them (R-M1-12's pending fix), and the headless follow-up's tokens are its total less the first run's.
