# F-R5-enterprise: F, round 5, enterprise operator (spec-reviewer, Opus, high; 2026-10-30, session 24, fork3)

- severity: P1
  type: gap
  location: PO-5, WSP-10, PO-1 "After a post office that didn't close its channels"; §1 non-goals (snapshot v2@1d99e92.md:258, 798, 222, 37-56)
  claim: Since D-38, a harness git hold, the trusted git state and the turns still open all reach the next start only through the last post office's log. But no log line, lock, `trees/` entry or copy carries a format version, and PO-5's rule that "a reader skips any line that doesn't parse" turns a line from another release into "no hold" and "no open turn". So an upgrade or a rollback, a routine fleet action, fails open. R-M1-179 parked the format version "to settle before M1's formats freeze". This is new evidence: since v0.22, the log carries security state.
  scenario: Release 2.0.1 renames the field of WSP-10's hold record, or adds a field to it. On a developer's machine, 2.0.0 ended with harness git held for a `filter.x.clean` that a soldier added to `.git/config`, and with Iron's turn still open. The fleet pushes 2.0.1, or rolls back from 2.0.2 to 2.0.1 after a bad release. At the next start, the new post office's reader skips the lines it can't parse (PO-5:258), or ignores fields it doesn't know. It finds no hold, so it "trusts the state ... when the post office started" (WSP-10:798), filter included. The first snapshot runs the soldier's filter as the owner. Iron's turn is never seen as open, so its guard never closes and its snapshot's writes are never reported (PO-1:222-227). Nothing in the spec says what a start does with a log, lock or `trees/` entry from another release. PO-13:369 covers only the binaries' checksums.
  evidence: PO-5:258 "A line cut short by a failed write is ended before the next one, and a reader skips any line that doesn't parse."; WSP-10:798 "A post office whose last one's log ends with harness git held ... trusts the state that log last trusted instead"; PO-5:257 (the records that keep a hold); a grep of the snapshot for "format version|schema version|older version|newer version" finds nothing on persisted state; ledger R-M1-179 "parked for X3 and M6; the format version to settle before M1's formats freeze"; PLAYBOOK §10.4 "install, upgrade, rollback and uninstall".
  fix: PO-5: "Every log line, the lock, each entry under `.shadow/v2/trees/` and the trust record carry the format version of the release that wrote them. A reader skips only a line cut short by a failed write: the last line of a log, or a line followed by the gap's count line. At start, a line among those PO-1 and WSP-10 read (a turn opened or closed, a snapshot or worktree made or removed, the trusted state, a hold and what ended it) that is of a format this release doesn't know, or that can't be parsed, is never taken as absent. Harness git stays held, no channel opens, and one transcript line names the file, the release that wrote it and the way out, as in `Shadow Army 2.0.1 can't read the log that 2.1.0 left · harness git held · use 2.1.0 or later in this folder`. Each release reads every earlier format." Add an M1 AC with a log, a lock and a `trees/` entry from a future format and from an older one.

- severity: P2
  type: defect
  location: PO-5 Disk; Appendix D residual 15 (snapshot v2@1d99e92.md:259, 258, 257, 1865)
  claim: PO-5 tells the owner to free disk space by deleting old logs, and warns only that this loses "what PO-1 would finish". It never says that the last post office's log, and the copies kept beside it, hold WSP-10's harness git hold and trusted state. So the spec's own disk-full advice silently releases a hold on a soldier-planted filter. Residual 15 states that risk only as tampering by the soldier's user, not as the owner following PO-5.
  scenario: A soldier at `auto` adds `filter.x.clean` to `.git/config`. The post office holds harness git, and its hold line's write fails because the disk is full. By PO-5:258 "a log never stops a soldier or a turn", so the hold lives on only in memory. Claude's transcript shows `logs not written · disk full`. Following PO-5:259 ("The owner frees space by deleting old logs under `.shadow/v2/logs/`"), or a help desk's runbook built from it, the developer deletes the logs, then quits Claude Code. Under PO-7, a normal exit ends the post office outright, so nearly every log comes from a post office "that didn't close its channels". The next start finds no hold, trusts the config as it is, and runs the filter as the owner at its first snapshot.
  evidence: PO-5:259 "The owner frees space by deleting old logs ... Deleting the logs of a post office that didn't close its channels, before the next one has started, loses what PO-1 would finish from them."; PO-5:257 "WSP-10's records ... each written and flushed before harness git runs again or goes on" (it doesn't say whether a failed write keeps harness git held); residual 15 (1865) "a log rewritten or deleted before the next start lets that start trust the config as it then is"; PO-7:262 (a normal exit ends the post office outright).
  fix: PO-5 Disk: "Deleting a log is safe once a later post office has started and finished (PO-1), except for the newest `po-*.jsonl` and the copies beside it while harness git is held: deleting those releases the hold (WSP-10, residual 15). The disk-full line says which logs are safe to delete, as in `Shadow Army: logs not written · disk full · logs older than the last start can be deleted`." And in PO-5:257: "A hold whose record can't be written keeps harness git held; the post office retries the write before harness git goes on." Alternatively, keep WSP-10's trusted state and holds in a state file outside `logs/` that the disk advice never names.

- severity: P2
  type: vendor-fact
  location: HOST-2 Versions (proxy check); HOST-1 (snapshot v2@1d99e92.md:119, 114)
  claim: In a regulated company the proxy usually comes from managed settings' `env`, often with a `NO_PROXY` that doesn't list `127.0.0.1`. A developer can't override a managed `env` key, so HOST-2's line "add 127.0.0.1 to NO_PROXY" asks for something only an administrator can do. HOST-1's administrator deployment path doesn't say the managed `env` must list `127.0.0.1`. A whole fleet then gets "nothing started" and a fix it can't apply.
  scenario: Managed settings set `env.HTTPS_PROXY=http://proxy.corp:8080` and `env.NO_PROXY=.corp.example`. All 200 developers run `/army`. HOST-2 reads the merged `env` and prints `HTTPS_PROXY would send the army's commands through a proxy · add 127.0.0.1 to NO_PROXY · nothing started`. A developer adds `NO_PROXY` to `~/.claude/settings.json` or exports it in the shell. The managed value still wins, so the next `/army` prints the same line. The developers open support tickets, and nothing in the spec tells the administrator what to change.
  evidence: https://code.claude.com/docs/en/env-vars: "a managed settings entry overrides the same variable in user or project settings"; "Claude Code writes each `env` entry into the process environment, replacing the value inherited from the shell." https://code.claude.com/docs/en/settings: "Nothing in your own settings files or `--settings` overrides a managed key". HOST-1:114 names only `extraKnownMarketplaces` and `enabledPlugins` for an administrator. NEEDS-PROBE: whether `$.settings.read()` tells which scope set a variable.
  fix: HOST-1: "An administrator who sets a proxy in managed `env` also lists `127.0.0.1` in its `NO_PROXY`." HOST-2: "Where the variable comes from managed settings, the line says so and names the administrator, as in `Shadow Army: your organization's managed settings send the army's commands through a proxy (HTTPS_PROXY) · ask your administrator to add 127.0.0.1 to NO_PROXY · nothing started`." Where the scope can't be told (probe), the line names both ways.

- severity: P3
  type: readiness
  location: §0 Reading this spec; header (snapshot v2@1d99e92.md:14-35, 3-12)
  claim: The spec has no conformance statement (what an implementation must do to claim it implements v2.0), no list of normative references with their dates (RFC 2119/8174 are named, but the vendor documents are cited inline and undated), and no change process after revision 1.0.
  scenario: After 1.0, Codex changes a requirement in a PR with no ADR. Nothing in the spec says whether that is allowed, and a vendor document cited inline changes without anyone noticing.
  evidence: a grep for "conformance|amendment|after 1.0" finds nothing; PLAYBOOK §10.9.
  fix: §0: "**Conformance.** An implementation conforms when it meets every MUST and every requirement of the milestones it claims, as Appendix B traces them. **References.** RFC 2119, RFC 8174 and each vendor document cited, with the date it was read, are normative. **Changes after 1.0.** A change to a requirement goes through a PR and an ADR, and the header's revision history names it."
