- id: R-M1-212
  verdict: CONFIRMED
  severity: P2
  evidence: v0.20 line 210 (PO-1 "One per folder": "The start time is the one the OS reports for that pid, read the same way when the lock is written and when it is checked"), still names no source or unit. Same words reused at 273 (watch), 340/401/408 (sweep, listing identity), and M1-AC1 1050 and 1056. Only the lease is shielded from the wall clock (267, 1052). No ledger row or Appendix D residual covers it. Linux field 22 of /proc/<pid>/stat is ticks since boot (https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html). `ps lstart` and similar tools add that to a recomputed boot time. NEEDS-PROBE only for the size of the shift, not for the fix.
  reason: "Read the same way" does not stop a wall-clock rendering from drifting, so the lock, watch and sweep can misjudge a live process. The text can fix this by naming the raw source.
  fix: |
    Replace the sentence at v0.20 line 210 ("The start time is the one the OS reports ... when it is checked.") with: "The start time is the process's own creation stamp, compared exactly and never rendered in the local or wall clock: on Linux field 22 of `/proc/<pid>/stat` (clock ticks since boot), on macOS the process start from `proc_pidinfo`, on Windows the creation FILETIME from `GetProcessTimes`. It is read the same way when the lock is written and when it is checked, and wherever PO-7's watch, PO-11's listing and PO-16's sweep compare it."
    Add at the end of M1-AC1's line-1056 case: "Moving the wall clock an hour either way, and on Windows changing the time zone, leaves a living post office's lock live, its watch quiet, and its soldiers' trees to the sweep unharmed (the sweep run by a second post office)."

- id: R-M1-214
  verdict: CONFIRMED
  severity: P2 (the ready-wait half is the real hang; a `--version` hang is a rarer cause)
  evidence: Line 119 (HOST-2 Versions: "running each ... with `--version`") and 497 (CH-2: "the adapter reads `claude --version`") have no limit. Line 238 (PO-3 Windows script "once ... before it reads the secret") and 456 (PO-19 DACL) have no limit. Line 268 starts the lease "when the post office reports that it is ready", and nothing bounds the wait for that report. Line 1127 bounds only the guardian's report (10 s), not the post office's report to the mod. 215 and 369 show other steps do have limits.
  reason: Several steps before a first event can hang with no limit, no crash, no state and no line, and a post office that never reports ready never starts its lease.
  fix: |
    Append to line 119, after the "Versions" sentence about running each with `--version`: "Each `--version` run, for Node.js, git and claude (CH-2), ends after 10 seconds on the monotonic clock, with every process it started. One that ends this way counts as missing, and the line says so, as in `claude --version gave no answer in 10 s`."
    Add to PO-7 line 268 (after "...reports that it is ready"): "The mod waits at most 60 seconds, on its own timer, for the post office's port and ready report. A post office that has not reported ready by then is ended by the mod with its process tree, and Claude's transcript gets one line naming the step it was in (the DACL script of PO-19 included), as in `the army did not start: the post office was not ready in 60 s · memory-protection script`. The DACL script of PO-19 is ended after 30 seconds with its processes, which the log reports as `memory protection: none` with that reason, and the post office goes on."
    The 60 seconds is my choice, longer than the 30 suggested by the reviewer, because the first run of the DACL script under Smart App Control or antivirus (line 237) can be slow. The owner can change the number.
    Add M1-AC1 and M1-AC4 cases: a fake `claude`, `node` or `git` whose `--version` never exits gives the missing line within 10 s and leaves no process behind. A fake post office that never reports ready is ended at 60 s with the transcript line, and the next use starts a new one.
