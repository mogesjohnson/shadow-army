# M1 round 1, red team (snapshot be9deb0)

Unit M1, round 1 — red team. Findings most severe first.

- severity: P1
  type: decision-needed
  location: PO-3 (docs/spec/v2.md:170-175); SEC-2 (docs/spec/v2.md:417); M1-AC2 (docs/spec/v2.md:547); lead B2 (docs/spec/v2.md:782)
  claim: PO-3's control keeps the Monarch secret out of files/argv/env but not out of process memory, which the same-user soldier it names as the adversary can read, so the Monarch/soldier credential separation (ADR-0012) does not hold.
  scenario: A prompt-injected claude soldier (red-team position 1, "runs commands as the owner's user") on default Windows (OpenProcess+ReadProcessMemory, same-user DACL) or Linux with yama ptrace_scope=0 reads the mod's or post office's memory, lifts the 32-byte secret, and then issues Monarch commands (send/assign a brief to another soldier, interrupt, close, shutdown) and from M2 answers its own approval requests — acting without the owner. SEC-2/M1-AC2 test only files/argv/env/output/log, so they pass while the secret is extractable; the test gives false assurance.
  evidence: PO-3:172 "MUST NOT be written to disk, a command line, an environment variable, or anywhere a soldier can read. Soldiers run as the same user, so a file only the owner can read is not enough." — but the secret must live in readable memory to be presented on every command, so on Windows/default-Linux it IS "somewhere a soldier can read"; the MUST NOT is unsatisfiable there. B2:782 states the same. ADR-0012 splits the two credentials precisely so "a soldier cannot act as the Monarch."
  fix: decision: how far PO-3 goes. At minimum require, where the OS allows, best-effort memory hardening (Linux: PR_SET_DUMPABLE=0 / rely on yama; name Windows same-user ReadProcessMemory as a residual that cannot be fully prevented), scope the "anywhere a soldier can read" clause to disk/argv/env + hardening, require the credential be revocable/rotatable so a lifted value is short-lived, and add an X test asserting the hardening is applied on supported platforms and stating the Windows residual. Note that because the lift cannot be fully prevented on Windows, the human-approval control (CH-6, SEC-3) must not rest on the Monarch secret alone.

- severity: P1
  type: gap
  location: ARM-1 (docs/spec/v2.md:376); ARM-3 (docs/spec/v2.md:381); HOST-2 (docs/spec/v2.md:94); VER-5 (docs/spec/v2.md:506); M1-AC6 (docs/spec/v2.md:555)
  claim: The spec puts `cli`, `model` and `autonomy` in repo-resident `shadow.config.json` and defines no trust boundary, allowlist or binary-resolution rule for it, so opening a malicious repo and starting the army runs an attacker-chosen command.
  scenario: Owner opens an untrusted repo that ships `shadow.config.json`. Reading A (`cli` is a free-form command): it sets a soldier's `cli` to `/tmp/evil` (or adds flags); `/army open <soldier>` (M1) spawns it — code execution on open. Reading B (`cli` is an adapter selector claude|codex|grok|agy): the repo plants a `claude.cmd`/`claude.exe` in the repo root or `node_modules/.bin`, and because the post office spawns the CLI with the repo as cwd, Windows/Node binary resolution is unspecified and can prefer the planted file — same result. Either way, a repo-controlled `autonomy: auto` also quietly reduces the vendor's own approval prompts.
  evidence: ARM-1:376 "`cli`, `model` and `autonomy` live in `shadow.config.json`"; glossary:58 "Soldier: one configured CLI and model"; ARM-3:381 "They can be configured." Nothing in ARM-1/ARM-3/HOST-2/SET-1 restricts `cli` to the four adapters, fixes binary resolution, or states that config is trusted/owner-authored. VER-5:506 ("fakes chosen through configuration") confirms config selects executables. Section 1 non-goals (35-53) name no config-trust boundary.
  fix: decision: whether repo `shadow.config.json`/`orchestratorDelegate.md` are trusted. If launched from a freshly opened repo, require `cli` to resolve to one of the four known adapters, require an absolute/validated binary path (no cwd/repo-relative resolution), validate `autonomy` and refuse escalation from untrusted config, and add an X test for a repo-supplied config that names a foreign `cli` or an escalated autonomy.

- severity: P1
  type: gap
  location: PO-1 (docs/spec/v2.md:163-164); HOST-2 (docs/spec/v2.md:94); M1-AC1 (docs/spec/v2.md:546)
  claim: PO-1 defines the lock's fields but never defines what happens when a lock already exists, so a stale lock after a crash (or a planted one) wedges the army with no defined recovery.
  scenario: The post office crashes (PO-7 only covers clean shutdown), leaving `.shadow/v2/post-office.lock`. Next army use: HOST-2 says "at most one post office per folder" and PO-1 finds a lock whose pid is dead or reused. The spec gives no action (reclaim? refuse? attach to the recorded port?), so an implementer guesses: refuse → permanent DoS until manual cleanup; blind-delete → unsafe reclaim; or trust the recorded port → a malicious same-user process pre-writes a lock pointing the mod at an attacker port. A malicious repo can also ship the lock file to deny the army outright.
  evidence: PO-1:164 "A lock in the folder holds the post office's pid, its process start time and its port. The start time tells the process that wrote the lock apart from a later one that reuses its pid." — states the discriminator but never the action for live/stale/pid-reused/forged. M1-AC1:546 only checks "Its lock holds its pid, start time and port"; no conflict/stale case is tested.
  fix: Specify, for each case at startup: recorded pid dead, or alive with a different start time (pid reuse) -> reclaim the lock; alive with matching start time -> refuse with a clear message and do not connect to the recorded port; unparseable/forged -> refuse and tell the owner. Add an F/X test for stale and forged locks.

- severity: P2
  type: gap
  location: CH-2 (docs/spec/v2.md:223); CH-6 (docs/spec/v2.md:241-252); HOST-12 (docs/spec/v2.md:145); M1-AC4 (docs/spec/v2.md:549-553)
  claim: M1 enables host-routed permission prompts (CH-2) but the answerer (CH-6) is M2, and no M1 requirement or AC defines what M1 does with a permission request, leaving an undefined, safety-adjacent outcome.
  scenario: A claude soldier in M1 (running in a HEAD snapshot) attempts a tool call that needs approval. CH-2 has set `--permission-prompts host --permission-prompt-tool stdio`, which per spike S5 turns OFF claude's safe self-deny and makes claude send `can_use_tool` and wait. In M1 there is no relay (CH-6, M2) and no owner answer path (pane M5, stop MSG-9/CH-10 M2). The turn hangs indefinitely (soldier DoS, queue stalls) unless an implementer adds an auto-answer — and an auto-approve would violate HOST-12/SEC-3.
  evidence: CH-2:223 "runs with `--permission-prompts host --permission-prompt-tool stdio` ... Without these flags claude denies the request by itself (spike S5)." CH-6 (relay) and SEC-3 are listed under M2 (561); M1's Implements (536-544) include CH-2 but not CH-6. M1-AC4 (549-553) covers brief/summary, crash, three error kinds, orphan child — no permission request.
  fix: State M1's behavior for a permission request before CH-6 exists: either do not set `--permission-prompts host` until the relay ships, or have the host deny-and-record (never approve), and add an M1-AC bullet for a claude request with no relay.

- severity: P2
  type: defect
  location: PO-1 (docs/spec/v2.md:166,168); M1-AC4 (docs/spec/v2.md:553); §5.1 fault tests (docs/spec/v2.md:479)
  claim: PO-1 claims process-tree termination means "nothing the CLI started keeps running," which is not true against a hostile child and is a weaker guarantee than the carried-over 2.0 SAFE-11 itself admitted, giving a persistence path.
  scenario: A prompt-injected soldier double-forks/`setsid`s, or registers a user systemd unit, a cron/at job, a launchd agent, or a Windows scheduled task/service. On channel close PO-1 ends the process tree, but a process re-parented to PID 1 or owned by the init/scheduler survives — the soldier persists past session end and hides activity. The fault test "a CLI that leaves a child process running" (479) and M1-AC4's orphan-child bullet (553) exercise only a cooperative in-tree child, never an escaping one.
  evidence: PO-1:168 "the post office ends the CLI's whole process tree, so nothing the CLI started keeps running." The carried-over predecessor, 2.0 SAFE-11 (legacy/spec/shadow-army-2.0.md:1049), states the opposite as a residual: "Vendor daemons outside the group (F34) are a stated residual risk." v2 dropped that admission while strengthening the claim. (D-3 decides how the containment helper ships; this finding is about the over-stated guarantee and the untested adversarial case, not the shipping mechanism.)
  fix: Soften PO-1 to a best-effort guarantee, name the residual (a child that re-parents to init or registers with the OS scheduler/init can survive), and rely on the checkout guard / a survivor check to detect it; add a fault test for a child that escapes the tree.

- severity: P2
  type: decision-needed
  location: WSP-8 (docs/spec/v2.md:409); SEC-4 (docs/spec/v2.md:419); lead H25 (docs/spec/v2.md:781); Appendix A (docs/spec/v2.md:722-741)
  claim: 2.0's SAFE-7 (strip C0/C1 controls and ESC/CSI/OSC sequences from strings shown in the UI) was not carried into v2, so terminal-escape/invisible-character injection from a malicious repo or a prompt-injected soldier has no control, and the drop is not recorded in Appendix A.
  scenario: A prompt-injected soldier (or a file in a malicious repo echoed by a soldier) emits ANSI escape/OSC/bidi sequences in its text or stderr. In M1 the mod surfaces soldier/CLI diagnostics to the owner's Claude Code UI and to on-disk logs; `redact()` targets secrets, not control characters, so the sequences pass through and can rewrite the owner's terminal, hide or forge output. H25 confirms "Nothing covers control characters, escape sequences or invisible characters."
  evidence: WSP-8:409 carries only 2.0 SAFE-6 (redact). 2.0 SAFE-7 (legacy/spec/shadow-army-2.0.md:1036) "Every model, vendor and config string shown in the UI is stripped of C0 and C1 controls ... and of ESC, CSI and OSC sequences" has no v2 equivalent and no row in Appendix A (722-741). H25:781 flags it as "Could add (v2.0)" touching MSG-1/HOST-4/HOST-11/SEC. New evidence beyond the Appendix C note: it is a dropped carry-over, i.e., a regression from the superseded spec's posture, not merely a new idea.
  fix: decision: restore SAFE-7 as a v2 requirement (strip/placeholder C0/C1, ESC/CSI/OSC and invisible/bidi characters wherever the mod draws text and before text reaches Claude), add it to Appendix A as a carry-over, and give it an X test. Rendering lives in M3/M5, but the requirement and the M1 log/`$.ui.log` surface should be named now.

- severity: P2
  type: untestable
  location: SEC-4 (docs/spec/v2.md:419); WSP-8 (docs/spec/v2.md:409)
  claim: SEC-4's absolute "Logs and records hold no secret, token or credential" is unverifiable and stronger than `redact()` can deliver, and the required match-set for redact is not defined in-spec.
  scenario: A soldier reads a repo `.env` and quotes `AWS_SECRET_ACCESS_KEY=...` in its session output; the post office writes the session log through redact(). redact (carried from 2.0 SAFE-6) is pattern-based; an arbitrary third-party secret that matches no known pattern is written verbatim, yet SEC-4 asserts the log holds no secret. An implementer cannot know which patterns are required, and the X test can only prove known patterns are removed, not the absolute.
  evidence: SEC-4:419 "Logs and records hold no secret, token or credential (WSP-8)." WSP-8:409 only says redact "runs on every write" and points to 2.0 SAFE-6, which (legacy/spec/shadow-army-2.0.md:1035) likewise only says "A single redact() runs on every write ... Logs are pruned after 30 days" — neither defines what redact matches.
  fix: Scope SEC-4 to the credentials Shadow Army controls (the Monarch secret, soldier credentials, Bearer/Authorization values) and define redact's required match-set there; state that third-party secrets in soldier output are out of redact's scope (or covered only by named patterns), so the test checks a concrete, provable property.
