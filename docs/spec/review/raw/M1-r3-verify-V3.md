- id: R-M1-173
  verdict: CONFIRMED (in part; the relocation half is a DECISION)
  severity: P2
  evidence: Current v2.md WSP-11 780 still gives only the baseline's contents ("holds the ignore rules the snapshot had then") and "written and flushed", with no location. PO-8 304 says only "That baseline is on disk". PO-5 246 logs "where its guard's baseline is kept", which assumes a location without setting one. WSP-12 795 places the start state "beside the turn's guard baseline", so it inherits the same gap. PO-5 244 makes only `.shadow/v2/` and `~/.shadow-army/` 0700/owner-only, so a baseline kept anywhere else (the temp folder, for example) gets neither those permissions nor a removal rule. PO-4 236 and CH-2 forbid the temp folder only for their own files. From M2, ARM-6 709's "each path and its diff" means the baseline must hold earlier bytes of hashed paths such as `.env*`, and WSP-8 753 does not redact baselines. Appendix D's asset table (1731-1739) has no row for copies of the owner's code (snapshots, baselines, start states). Relocation: WSP-11 771 hard-codes `~/.shadow-army/snapshots/`. For precedent, Claude Code itself offers `CLAUDE_CONFIG_DIR` to move its home-folder files (https://code.claude.com/docs/en/settings, "Find or create your settings files" note). Nothing in settled.md or the ADRs covers this, and it is not fixed in v0.15.
  reason: The baseline's place, permissions and lifetime are really unstated in an M1 requirement (WSP-11), so a builder can legally put source bytes and secrets outside the owner-only folders. Moving the snapshot folder off a roaming profile, however, is a new capability for the owner to decide.
  fix: WSP-11 780, after "Its baseline, which holds the ignore rules the snapshot had then,": "is kept beside the session's log under `.shadow/v2/logs/` (PO-5), never in a worktree, a snapshot or the system's temporary folder, and is removed once the turn's guard has closed (PO-8, →M2);". Appendix D assets, add a row: "Copies of the owner's code | each session's snapshot in `~/.shadow-army/snapshots/` (WSP-11), each turn's guard baseline and start state beside its log (WSP-11, WSP-12), and the logs, which hold every tool result whole (PO-5)". Put the data inventory, if wanted, as that informative row, not as a new requirement.
  options (relocation): (a) the owner's own setting, outside the folder (an environment variable like Claude Code's `CLAUDE_CONFIG_DIR`), that moves `snapshots/` only, never `trust/`; (b) a non-goal stating the location, and that a Windows roaming profile copies `%USERPROFILE%\.shadow-army` at logoff (only `AppData\Local` and `AppData\LocalLow` are excluded by default).
  big or technical: big (a new setting, or accepting a data-location risk).

- id: R-M1-174
  verdict: CONFIRMED
  severity: P2
  evidence: §1 52's "Any service reachable from the network" and Appendix D's actor row (1754) are about inbound connections. PO-13 352 and PO-17 408 restrict only the helper. No requirement states that the post office or the mod make no outbound connection, or that there is no telemetry. PLAYBOOK §10.2 requires "that nothing leaves the machine except through the vendors' own CLIs; and telemetry (none, or stated)" to end as a requirement or a non-goal. WSP-10 763 runs the owner's filters, and git lazily fetches a partial clone's missing objects on checkout (https://git-scm.com/docs/partial-clone), so making a snapshot can reach the network. ADR-0012 (local only) makes "none" the only sensible answer.
  reason: The gap is real and in an M1 requirement (PO-2), and stating it restricts nothing the design allows, so it is trivial rather than a decision for the owner.
  fix: Add to PO-2: "Shadow Army's own code, the mod, the post office and each guardian, opens no network connection except on the loopback address, and sends no telemetry, crash report or update check. Data leaves the machine only through the soldiers' CLIs and the owner's Claude Code, and through git where the owner's own config makes it fetch, as an LFS filter or a partial clone's missing objects do while a snapshot is made (WSP-10)." M1-AC1 adds: "every connection the post office and the mod open during these runs, as Node's `net.client.socket` diagnostics channel reports them, is to the loopback address." This is simpler and more portable in CI than a run with outbound connections blocked.

- id: R-M1-176
  verdict: CONFIRMED
  severity: P2
  evidence: WSP-10 760-769 lists every switch harness git sets, with no time limit and no prompt setting. WSP-11 773 handles only a snapshot "that can't be made". PO-8 295's finishing waits on the guard's git. No line in v2.md bounds a git command. v1's `src/workspace/git.ts` runs git with `stdin: "ignore"` and no timeout. That doesn't stop git's own prompt, which opens the terminal directly; for HTTP authentication it is controlled by `GIT_TERMINAL_PROMPT` (https://git-scm.com/docs/git, GIT_TERMINAL_PROMPT). Git Credential Manager's `credential.interactive` set to `false`/`never` "Never prompts... an error is returned" (https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/configuration.md). A partial clone fetches missing blobs on checkout (https://git-scm.com/docs/partial-clone), and WSP-10 763 runs the owner's LFS filter. WSP-10 762 turns fsmonitor off, so `git status` on a monorepo can legitimately take minutes.
  reason: A snapshot or guard command that waits on a credential prompt or a hung filter blocks a soldier's start, or a turn's finishing and its queue, with no outcome. That breaks the owner's "timeouts everywhere" rule (PLAYBOOK §10.3) in M1 requirements.
  fix: As proposed, with values. Add to WSP-10: "runs with `GIT_TERMINAL_PROMPT=0` and `-c credential.interactive=false`, and is ended, with every process it started, filters included, after 30 minutes on the monotonic clock for making or bringing a snapshot, and 5 minutes for any other command. A snapshot that times out is one that can't be made (WSP-11), with the reason, as in `snapshot not made · git took longer than 30 min`. A guard or audit command that times out holds harness git with its reason." The values are generous because fsmonitor is off and a 15 GB checkout can take minutes; the purpose is an outcome, not speed. M1-AC10 adds: a fake git on PATH that never exits ends at each limit under a fake monotonic clock. At a first start the soldier doesn't start and the reason is in its log and the transcript. During a turn's guard, harness git is held with the reason. Each harness git command's environment holds `GIT_TERMINAL_PROMPT=0`.

- id: R-M1-178
  verdict: DECISION
  severity: P3 (was P2): the scenario's premise that the organization's only lever is Claude Code's managed setting is wrong. Autonomy only chooses vendor flags (settled design rule; ADR-0010), so every vendor's admin-enforced policy already caps a soldier whatever Shadow Army's config says. What is left is card fatigue.
  evidence: ARM-7 720-722. CH-7. Residual 4 (1785). Claude Code managed settings outrank everything, `--settings` included ("Nothing in your own settings files or `--settings` overrides a managed key", https://code.claude.com/docs/en/settings), and `permissions.disableBypassPermissionsMode` "Prevent[s] anyone from entering bypassPermissions mode" (https://code.claude.com/docs/en/settings-reference). Codex's `requirements.toml` `allowed_sandbox_modes` / `allowed_approval_policies` are "admin-enforced constraints that users can't override" and block `danger-full-access` and `--yolo` (https://learn.chatgpt.com/docs/enterprise/managed-configuration). The crash-loop outcome of a refused start is R-M1-171's. Nothing in settled.md covers an administrator layer.
  reason: Pre-accepting a repository's committed policy files for a fleet would add a new way to cross ARM-7's trust boundary, which only the owner can choose. Parked for X3 (enterprise readiness), not M1-blocking.
  options: (a) an administrator file at an OS-protected path, read first, that caps each CLI's autonomy and lists accepted hashes of committed policy files; (b) a non-goal: Shadow Army has no administrator policy, organizations use their vendors' managed settings (named above), a refused start has R-M1-171's outcome, and card fatigue stays within residual 4.
  big or technical: big (a trust boundary).

- id: R-M1-179
  verdict: DECISION
  severity: P2
  evidence: Nothing in v2.md covers upgrade, rollback or uninstall. PO-5 242, PO-16 385 and ARM-7 722 define no format version. PO-1 215-220 and PO-16 393 read the last post office's logs and tree entries. An update between a crash and the next start is the likely case, and then a newer post office reads an older one's files. A line that doesn't parse is skipped (PO-5 247, PO-16 385), so a changed format can leave a dead army's processes unswept. On the other hand, a trust record that can't be parsed "counts as none" (ARM-7 722), which fails safe. The upgrade text is scattered across PO-13 354, PO-14 364 and HOST-2 115. PLAYBOOK §10 says a new area such as "an OPS area for install, upgrade and support" goes "to the owner as a decision first". §10.4 lists install, upgrade, rollback and uninstall.
  reason: The format version is technical and needed from the first release. A new OPS area, and an uninstall step that deletes the owner's files (like M9, which §14 calls big), are the owner's choice. Parked for X3 and M6, but the format version should be settled before M1's file formats freeze.
  options: (a) an OPS area: each file Shadow Army writes and reads back (lock, logs, tree entries, trust records) carries a format version, and a post office that finds a newer one leaves it as it is and says so, as in `tree entry from Shadow Army 2.1 · not read`; an uninstall step, or a documented list, that removes `~/.shadow-army/`, each known folder's `.shadow/v2/` and Shadow Army's worktree entries after listing them; and what an upgrade does, stated in one place. (b) a non-goal for 2.0, with the leftovers listed in the setup guide. The format-version half of (a) can be applied as technical whatever the owner picks for the rest.
  big or technical: big (a new area; the uninstall deletes files).
