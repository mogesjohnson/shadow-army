# P-16: does Claude Code's `$.http.fetch` send a loopback request through a proxy? (fork3, Opus; 2026-10-29)

For R-M1-235 and card D-37. Claude Code 2.1.312 on Windows 11 and on WSL 2 Ubuntu (POSIX). Harness and summaries are in `evidence/p16-p17/`.

## Result

**Listener B, the proxy, got the request.** On both systems, Claude Code's `$.http.fetch` to `http://127.0.0.1:<A>/probe` goes to the proxy, `x-probe` header included, whenever a proxy variable is set. That holds whether the variable is set in the shell or in the folder's `.claude/settings.json` `env`. `NO_PROXY=127.0.0.1,localhost` stops it. So D-37's recommendation holds: option (b).

| Case (same on Windows and WSL) | Who got the `x-probe` request | Request line at that listener |
|---|---|---|
| no proxy variable | A | `GET /probe?w=start HTTP/1.1` |
| `HTTP_PROXY=http://127.0.0.1:<B>` in the shell | **B** | `GET http://127.0.0.1:<A>/probe?w=start HTTP/1.1` |
| `HTTPS_PROXY=…<B>` in the shell (the URL is `http:`) | **B** | same, absolute form |
| `http_proxy=…<B>` (lower case) in the shell | **B** | same |
| `HTTP_PROXY=…<B>` in `.claude/settings.json` `env` | **B** | same |
| `HTTPS_PROXY=…<B>` in `.claude/settings.json` `env` | **B** | same |
| `HTTP_PROXY=…<B>` and `NO_PROXY=127.0.0.1,localhost` in the shell | A | `GET /probe?w=start HTTP/1.1` |

- Each case fetched twice, once in `session.start` before any prompt (`w=start`) and once from the mod's `/p1617` command (`w=command`). Both fetches went to the same listener every time. The mod saw B's answer (`text: "B"`), so a proxy can read the request and answer it too.
- In every proxy case B also got Claude Code's own traffic (`CONNECT api.anthropic.com:443`, `mcp-proxy.anthropic.com:443`, `http-intake.logs.us5.datadoghq.com:443`). That includes the `NO_PROXY` case, so the variable was in force there. B tunnelled those connections so Claude Code worked normally.
- `HTTPS_PROXY` alone also carries an `http:` URL. That matches the network-config page's "uses the first one that's set in the order `https_proxy`, `HTTPS_PROXY`, `http_proxy`, `HTTP_PROXY`".
- Interactive check (WSL, a real pseudo-terminal, no prompt sent, `HTTP_PROXY` in the shell): B got `GET http://127.0.0.1:<A>/probe?w=start`. The interactive and `-p` runs agree.

## `socketPath` (option (a))

- This build's typings (`.claude-plugin/types/claude-code/index.d.ts`, which Claude Code 2.1.312 writes into a `--plugin-dir` mod in an interactive session) list it: `init` is "`{ method, headers, body, auth, socketPath }` (… socketPath a Unix socket to go over instead of TCP)". On `HttpInit.socketPath`, the typings say: "The URL still gives path, query and Host; redirects stay on it; no proxy". The public docs still don't list it.
- WSL: a fetch with `socketPath` set to a Unix socket under the case folder reached it (status 200, the socket listener answered `SOCK`).
- Windows: a fetch with `socketPath: "\\.\pipe\p16-…"` was refused before any connection: `$.http.fetch: socketPath \\.\pipe\p16-888cf9f3 refused: a network location is not reached from here`. Not tried: a Windows AF_UNIX socket file. Neither Node nor Python here can listen on one, so option (a) has no Windows transport that this probe could show.

- No permission-mode flag was passed, so each session used the user's default; the WSL screen shows `auto mode on`. None used full autonomy, and no tool ran in any session.
