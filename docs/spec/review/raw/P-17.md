# P-17: how Claude Code ends a mod's spawned child at exit and at unload (fork3, Opus; 2026-10-29)

For R-M1-236 (PO-7). Claude Code 2.1.312 on Windows 11 and on WSL 2 Ubuntu (POSIX). Harness and summaries are in `evidence/p16-p17/`.

## Result

**At every normal exit the host ends the child outright, before `session.end` runs.** On POSIX it sends `SIGTERM`, then `SIGKILL` 500 ms later. On Windows it terminates the child with no signal. At unload, after a save under `--plugin-dir`, it does the same with a shorter gap. A post office spawned with `$.process.spawn` therefore gets at most about 0.5 s after `SIGTERM` on Linux and macOS, and nothing on Windows. PO-7's 30 s + 10 s shutdown can never finish at a normal exit. R-M1-236's **uncatchable-end draft holds**: keep PO-7 263 as it is, change 261 ("unless it is ended outright first"), and add the M1-AC8 line. Option (a), adding a termination signal as a fourth trigger, would buy 500 ms on POSIX only. Option (b), leaving the process group, would not help, because the host signals the child itself.

This build's typings say the same: `$.process.spawn`: "The loop is the child's life: leaving it, `return()` on the stream, `next.signal` aborting or the module unloading kills the child, and nothing else does, a hook's return included".

### WSL (POSIX): the child is a Python script that logs, because WSL has no Node.js

| How Claude Code ended | What the child saw | Child's end, as `$.process.spawn` reported it | Timing |
|---|---|---|---|
| `-p` run finishing | `SIGTERM` | `{code: null, signal: "SIGKILL"}` | SIGTERM → kill 509 ms; `session.end` 5 ms later |
| stream-json `-p`, stdin closed | `SIGTERM` | `SIGKILL` | 503 ms; `session.end` at the same ms |
| interactive `/exit` | `SIGTERM` | `SIGKILL` | 503 ms; `session.end` (`prompt_input_exit`) at the same ms |
| interactive ctrl+c twice | `SIGTERM` only (no `SIGINT`: the TUI reads ctrl+c as a key) | `SIGKILL` | 502 ms; `prompt_input_exit` |
| terminal closed (pty master closed, a hangup) | `SIGTERM` only (no `SIGHUP`) | `SIGKILL` | 503 ms; `session.end` (`other`) |
| `kill -TERM` to Claude Code (pipes or pty) | `SIGTERM` | `SIGKILL` | 503–504 ms; `other`; Claude Code exits 143 |
| `kill -HUP` to Claude Code | `SIGTERM` | `SIGKILL` | 503 ms; `other`; exits 129 |
| save under `--plugin-dir` (unload and reload; interactive, and stream-json with `CLAUDE_CODE_PLUGIN_DIR_WATCH=1`) | `SIGTERM`, about 6.5 s and 7.9 s before the session ended | dead within one 250 ms heartbeat of `SIGTERM` (about 50 and 160 ms); `session.start` runs again and starts a new child | — |
| `/reload-plugins` with the mod unchanged | nothing | child ran on until `/exit` | it printed `Reloaded: 1 plugin…` and didn't reload the hooks module |
| `kill -KILL` to Claude Code | nothing | **child kept running**, re-parented, and got `EPIPE` on stdout each second | no `session.end` |

- The child's process group and session are Claude Code's own: under the pty, child `pgid` = `sid` = Claude Code's pid. Even so, the terminal's own signals didn't reach it. Ctrl+c is a key to the TUI, and the hangup went to Claude Code as the session leader. Every signal the child got came from the host.
- In every case the child handled `SIGTERM`, logged it and carried on, and was then killed without another event. So the end is uncatchable (`SIGKILL`, which `$.process.spawn`'s result confirms).
- The child's stdin is a pipe that's at its end from the start (`stdin-end` right after start).

### Windows: the child is a Node.js script

| How Claude Code ended | What the child saw | `$.process.spawn`'s result | Timing |
|---|---|---|---|
| `-p` run finishing | nothing (no `SIGHUP`/`SIGBREAK`/`SIGINT`, no `exit` event) | `{code: 1, signal: null}`, which is a `TerminateProcess` | last heartbeat 213 ms before `session.end`; the result arrived 2 ms before it |
| stream-json `-p`, stdin closed | nothing | `{code: 1, signal: null}` | last heartbeat 142 ms before `session.end` |
| save under `--plugin-dir` (`CLAUDE_CODE_PLUGIN_DIR_WATCH=1`) | nothing | killed at the reload (last heartbeat 62 ms before the debug log's `plugin.register … admitted`); the old module's log write then failed with `the plugin's environment is unloaded` | new child from the reloaded `session.start` |
| `/reload-plugins` sent as a stream-json message | — | no reload happened in `-p` | — |
| `taskkill /pid` (no `/f`) | — | refused: `This process can only be terminated forcefully (with /F option)` | then forced |
| `taskkill /f /pid` of Claude Code | nothing | **child died with Claude Code** (gone 4 s later; last heartbeat 114 ms before Claude Code's exit was seen) | no `session.end` |

- On Windows nothing reaches the child that it could catch. Even a forced kill of Claude Code ends the child with it, which suggests a kill-on-close job object, not observed directly. On POSIX, a `SIGKILL` of Claude Code leaves the child running. PO-1's recovery and the lease must cover that orphan on Linux and macOS.

## Not run here: cases that need the owner at a real Windows terminal

`/exit`, ctrl+c twice, closing the window, and `/reload-plugins` in an interactive Windows session. Every automated Windows case ended the child with `TerminateProcess` and no signal, so these are expected to match. Steps for the owner, in PowerShell (about 3 minutes):

1. `cd $env:TEMP\sa-p1617; mkdir win-i; cd win-i`
2. `$env:ANTHROPIC_BASE_URL='http://127.0.0.1:9'; $env:P1617_MODE='p17'; $env:P1617_MODLOG="$PWD\mod.jsonl"; $env:P17_CHILD=(ConvertTo-Json -Compress @((Get-Command node).Source, "$env:TEMP\sa-p1617\child.mjs", "$PWD\child.jsonl"))`
3. `claude --plugin-dir $env:TEMP\sa-p1617\mod`, choose "Yes, I trust this folder", wait 3 s, type `/exit` and press Enter.
4. Check: `Get-Content child.jsonl | Select-String -NotMatch '"hb"'` should show only `start` and `stdin-end`, and `Get-Content mod.jsonl` should show `child-out-end` with `{"code":1,"signal":null}` just before `session.end`.
5. Repeat steps 3 and 4 three times after `del child.jsonl, mod.jsonl`: once ending with ctrl+c twice, once by closing the terminal window, and once by typing `/reload-plugins` first (the child should keep running) and then `/exit`.

## How it ran

- No model call: `ANTHROPIC_BASE_URL=http://127.0.0.1:9` in every session, and nothing was typed but slash commands. The mod spawns `[node|python3, child, log]` through `$.process.spawn({ argv })` from `session.start`, reading the stream in a detached loop, as the typings' "a child for the session's life" example does.
- Windows: `p17.mjs` (pipes and stream-json). WSL: `p17-wsl.py`, whose `i-*` cases run Claude Code on a real pseudo-terminal: `/exit`, ctrl+c as `\x03` twice, closing the master for the hangup. It answers the folder-trust dialog with Down and Enter.
- Times: the child logs a heartbeat every 250 ms and each event with a millisecond clock. The mod logs `session.start`, `session.end` and the spawn result. All times are on the same host clock.
- No permission-mode flag was passed; none of the sessions used full autonomy, and no tool ran.
