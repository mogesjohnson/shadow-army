## V17-FC1: fix check of v0.17 (lines cite v2@785cc17.md)

### The P1 repair

- **R-M1-182: NOT FIXED.** It is fixed for the current folder that cmd.exe searches by itself, and for launchctl. It is not fixed for relative entries on `PATH`.
  - Evidence: CH-1 483, PO-18 429, M1-AC10 1079, row 9 1785. Microsoft's page (https://learn.microsoft.com/en-us/windows/win32/api/processenv/nf-processenv-needcurrentdirectoryforexepatha) says that with the variable present, "cmd.exe uses the path %PATH%".
  - **What is fixed.** `cmd.exe` is now found by its absolute path, and the variable stops cmd.exe putting the current folder (`.`) ahead of `PATH`. `/bin/launchctl` is named in PO-18. No program Shadow Army starts itself is still found by name:
    - git and Node.js through `PATH`'s absolute entries (WSP-10 775, HOST-2 117);
    - `cmd.exe`, `taskkill` and `powershell.exe` from the Windows folder (CH-1, WSP-10 776, PO-19 445);
    - `launchctl` by its absolute path (PO-18, PO-17 415);
    - the helper and the script from the package (PO-13 360, HOST-1).
  - **What is left.** A `.cmd` shim still takes `node` from the snapshot through a relative `PATH` entry such as `.` or `node_modules\.bin`. The CLI inherits that `PATH` unchanged, and cmd.exe searches `%PATH%` exactly as it is given. M1-AC10 1079 puts these very entries on `PATH` in the same bullet. So CH-1's "no program a shim runs by name … is taken from the current folder" and row 9's "prevented" are still false whenever `PATH` holds `.`. See N1.
  - **CH-7 and ADR-0010.** The variable removes no vendor safeguard: it only narrows a search. But it reaches further than CH-1 says (N13).
  - **Minor, not raised as a finding.** The spec never says how "the Windows folder" is found. If it is read from `%SystemRoot%`, a settings `env` block can set that variable (WSP-11 783 already assumes such a block can set any variable). That adds little beyond residual 8.
