## Details

**1a. The log (798).** It records each file's hash at start, at a `y` and after each of Shadow Army's snapshot or worktree commands, plus each hold and what ended it. That is buildable. Yes, a restart can tell the last post office's own snapshot changes from a soldier's: the log records the trusted state after each such command, and the state gains only that command's metadata ("and nothing else").

The edge cases:
- **A hold line cut short by a crash:** a reader skips it (PO-5 258), so the hold is lost and the start trusts the config.
- **A cut trusted-state line:** the start falls back to an older trusted state, which can deadlock in M1 (N3).
- **A missing log:** residual 15 states it.
- **A log from an older version:** it has no hold record in this form, so it carries no hold. That only matters for pre-2.0 builds.

PO-5 257 lists none of these records and doesn't say they are flushed (N2). The card shown again from M2 must give "each path and its diff" (ARM-6 737), but the log keeps hashes only (N2).

**1c. Start order.** While a hold stands, no soldier starts before M6: every session needs a snapshot (WSP-11 801, ARM-8 760, WSP-10 800).
- In M1 the owner sees WSP-10 799's transcript line.
- From M2 the owner sees the card again (PO-1 225).
- PO-14 and PO-16 need no harness git, so they don't wait.
- PO-1 222-227 do need harness git: an open turn's guard, a snapshot's report and removal, and WSP-12's revert. Only items "its log records as waiting" are told to wait (228, 800), so whether these block start, or let channels open from M6, is unstated (N3).
- The ready point agrees: all of this comes after the report (270), so nothing touches the 60 s.

**1d. Guard timeout.** 798 carries only "held for a change", so a timeout hold doesn't carry, which is D-38's stated outcome. But D-38 says "the restart compares with that state". The text doesn't compare at all, and no harness git runs during a timeout hold, so a filter added in that time is trusted at the next start (N1).

**N9 inputs (783-784).**
- `postgres://u:p@ss@host/db` becomes `u:[redacted]@host/db`.
- `https://u:pw@host:8443/x?y=@z` has only `pw` redacted: the authority ends at `/x`, so the `@` in the query is outside it.
- `https://u@host/x` and `ssh://git@host:22/r` are kept: no `:` follows the user name before the last `@`.
- 784's word-start rule holds: the character before the password is `:`.
- An unencoded `/`, `?` or `#` in a password still leaks. Residual 5 covers secrets `redact()` doesn't match.

**Outside the packet's scope (pre-existing, not from v0.22).** HOST-2 120 counts `/reload-plugins` as a mod reload that ends the post office. P-17 line 23 saw `/reload-plugins` with the mod unchanged reload nothing, and the child ran on. A P3 vendor-fact if you want it filed.
