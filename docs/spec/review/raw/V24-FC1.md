- severity: P2 (P1 if harness git runs in a snapshot by plain discovery: then a soldier that can write only in its own snapshot, agy included, runs code as the owner)
  type: gap
  location: WSP-10 (docs/spec/v2.md:795, 798); M1-AC10 (:1109)
  claim: Two files decide which git folder and common folder harness git uses: the `.git` file at the root of a snapshot, worktree or linked-worktree folder, and a `commondir` file in the repository's own git folder. Neither is in "a worktree's metadata" (798), neither is compared, and neither is trusted only where it holds what Shadow Army's command wrote.
  scenario: A soldier mid-turn rewrites its snapshot's `.git` file as `gitdir: ./.g`. `./.g` is a git folder inside its own snapshot, with a `config` defining `filter.evil.clean` and an alternates file pointing at the real objects, and the soldier adds a `.gitattributes` naming that filter. When the turn's writes are found (WSP-11 811), or reported at the next start (PO-1 227), harness git runs in the snapshot, finds `./.g` and runs `filter.evil` as the owner. A builder who compares "the config git reads for that repository" as the repository's own files sees no change. The same works for the folder's guard when a soldier at `auto` writes `.git/commondir` naming a folder of its own. At a normal start, which trusts everything as it is, a redirect left in a leftover snapshot is trusted too.
  evidence: https://git-scm.com/docs/gitrepository-layout lists `commondir` as a top-level `$GIT_DIR` entry ("$GIT_COMMON_DIR … will be set to the path specified in this file if it is not explicitly set"), and describes the gitfile (`.git` holding "gitdir: <path> to point at the real directory"). https://git-scm.com/docs/git, GIT_COMMON_DIR ("non-worktree files that are normally in $GIT_DIR will be taken from this path instead"). 798: "A worktree's metadata is its `gitdir`, `commondir` and `config.worktree`". WSP-12 840 already handles a replaced `.git` file, but only for M6 worktrees ("put back before any harness git runs there"). WSP-11 has nothing like it.
  fix: |
    WSP-10 795 OLD: runs a git found by its absolute path on `PATH` alone, as CH-1 starts each CLI, never one in the folder, a worktree or a snapshot;
    NEW: runs a git found by its absolute path on `PATH` alone, as CH-1 starts each CLI, never one in the folder, a worktree or a snapshot, with `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR` in its environment naming the git folder, working tree and common folder Shadow Army knows for it: the repository's own, and, for one of this army's snapshots or worktrees, its own `worktrees/<id>` entry and folder as the log gives them. So no `.git` file and no `commondir` file decides which config or objects git reads;
    WSP-10 798 OLD: A worktree's metadata is its `gitdir`, `commondir` and `config.worktree`.
    NEW: A worktree's metadata is its `gitdir`, `commondir` and `config.worktree`, and the `.git` file in its folder; the folder's own also includes any `commondir` in the repository's own git folder, which git otherwise takes as its common folder.
    WSP-10 798 OLD: and a `gitdir` that is missing or names the `.git` file of that snapshot or worktree at the path the log gives.
    NEW: a `gitdir` that is missing or names the `.git` file of that snapshot or worktree at the path the log gives, and a `.git` file that names that snapshot's or worktree's own `worktrees/<id>` entry.
    M1-AC10 1109 OLD: and the filter never runs (WSP-10);
    NEW: and the filter never runs; and so it is when the soldier instead rewrites its snapshot's `.git` file to name a git folder of its own inside its snapshot, whose config defines such a filter: harness git run in that snapshot reads the repository's own config, and the filter never runs (WSP-10);
    (If N4 is applied first, this pair's OLD is N4's NEW ending "…into its snapshot's own `worktrees/<id>` entry (WSP-10);", and the new clause goes before "(WSP-10)".)
