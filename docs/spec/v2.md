## 0. Reading this spec

- **Requirement words.** MUST, MUST NOT, SHOULD and MAY mean what RFC 2119 and RFC 8174 say, and only when capitalized.
- **Requirement IDs.** Each requirement has an ID such as `PO-2`. IDs are stable and never reused. A dropped requirement stays in place as `- **ID** (withdrawn in v0.N: the reason)`, and Appendix B's rules 2 to 4 skip it.
- **Milestone and evidence.** Each requirement names the milestone that implements it and the kinds of evidence that verify it (section 5):

  | Code | Evidence |
  |---|---|
  | U | unit test |
  | C | contract test |
  | I | integration test |
  | X | security test |
  | F | fault test |
  | S | screen snapshot |
  | L | live check by the owner |
  | R | review |

- **Carried over.** A requirement carried over from v1 or 2.0 names its source as `(from …)`, and Appendix A lists it. This spec governs: a source's detail applies only where this spec says nothing on the point, and never against this spec, an ADR or the design rules. For a 2.0 source the detail is the archived 2.0 text, except 2.0 SAFE-10's "may add restrictions" (Shadow Army never adds or removes a vendor safeguard), SAFE-11's killing of the turn's process group at the end of each turn (CH-2, PO-8), and WS-1's detached worktree (each soldier works on its own branch). For a v1 source it is v1.0.1's code on `legacy/v1`.
- **Traceability.** Appendix B gives the rules, and a script checks them in CI (VER-7).
- **Ideas.** Appendix C sets each of the owner's 118 ideas, and each of the six v2.1 designs, beside what this spec says. It is a reference for review; nothing in it is a requirement.

## 1. Goals and non-goals

Goals:

- **G1 Claude is the Monarch.** The owner's own Claude Code session plans, assigns work and reads summaries. No separate Monarch CLI.
- **G2 Live soldiers.** Each soldier is one long-lived session of its own CLI, in its own worktree, with the vendor's harness exactly as installed.
- **G3 Short messages.** Only briefs and short summaries cross between models, by name. A message is one more turn in an open session, never a new session.
- **G4 Watch and steer.** The owner can watch any soldier's session as it runs, type into it, stop its turn, and change or cancel what waits in its queue.
- **G5 Visible cost.** Token use is visible and in the owner's hands: a meter per soldier, a cold-cache warning and the 200k handoff.
- **G6 Safe writes.** v1's workspace safety carries over: worktrees, claims, the guard, link safety, apply and undo.
- **G7 Verified.** Every requirement is verified, and the verification is traced in CI.

Non-goals:

- Removing or replacing any part of a vendor's harness to save tokens (ADR-0010).
- A full-screen Ink shell; v1's chat stays in `v1.0.x`.
- Any service reachable from the network.
- Answering a vendor's permission request on the owner's behalf.
- Cost figures beyond what each CLI reports.

## 2. Glossary

- **Owner:** the person whose Claude Code session is the Monarch.
- **Monarch:** the owner's Claude Code session, which leads the army.
- **Soldier:** one configured CLI and model, with a shadow name (Iron, Igris, Beru, Tusk, Kaisel, Bellion, Tank).
- **Autonomy:** a soldier's permission level in `shadow.config.json`: `supervised`, `auto` or `full`, as in v1. It chooses only that CLI's documented flags (CH-7).
- **Post office:** the local helper process that holds the soldiers' sessions and carries messages between them.
- **Channel:** the post office's connection to one soldier, through that CLI's own live-session interface.
- **Live session:** one open conversation in a soldier's CLI. Each message adds one turn, and any turn the CLI then takes by itself when that turn's background work ends (PO-8).
- **Queue:** the messages waiting for a soldier's next turn. A **held** queue waits for the owner instead of going by itself.
- **Stop:** ending a soldier's running turn while its session stays open with its history. Starting fresh, by contrast, closes the session.
- **Brief:** a message that assigns work.
- **Summary:** a reply of at most five lines of at most 120 characters each (MSG-5).
- **Tag:** a soldier's two-letter short name, unique in the army (VIS-6).
- **Report:** a soldier's full reply, kept on disk.
- **Standing instructions:** what a soldier is told once per session: who it is, the team, the rules and the reply format.
- **Context size:** every input token of the session's most recent main model request, whether uncached, written to the cache or read from it: the request that carries the conversation, never an auxiliary call such as a claude subagent's or agy's `checkpoint` step (SES-2).
- **Handoff line:** the context size at which a soldier hands off, 200,000 tokens by default.
- **Cold:** a session idle longer than its provider keeps the prompt cache, or one changed in a way its CLI documents as resetting the cache. Its next message likely pays full price for the whole history again. Cold is always an estimate, made before a message goes (SES-6).
- **Mod:** Shadow Army's Claude Code plugin: a pane, an army strip, a status entry, toasts, commands and tools.
- **Worktree:** a soldier's own git worktree and branch, one per soldier per Claude session (WSP-1).
- **Snapshot:** a throwaway copy of a base, whose writes are discarded and reported (ARM-6, WSP-11).
- **Checkout guard:** the check that every change to the checkout during a soldier's turn is explained by Shadow Army's records, or else goes to the owner (ARM-6, WSP-4).
- **Claims, claim audit:** the paths a writing turn may change, and the check, once the turn is over, of what it changed against them (WSP-2).
- **Attribution card:** the guard's decision on changes no record explains: y says they are the owner's, n fails the turn (ARM-6).

## 3. Architecture

```
owner ──► Claude Code (the Monarch) ──► the mod ──► the post office ──► channels ──► soldier CLIs
            transcript, prompt           pane, strip,    127.0.0.1 + secret    one per soldier  each in its own
                                         commands, tools                                        worktree
```

- **The mod starts the post office** and reads its event stream: every soldier's turns, states and usage. The mod draws those events in the pane and the strip.
- **The mod acts only in the owner's own Claude Code session.** In any other session, a soldier's included, it registers no tool or command, starts no post office, records nothing and draws nothing (HOST-2).
- **The post office decides every state.** Only the post office changes a message's or a soldier's state, one change at a time. Each mod action is a request whose result the mod shows only from the post office's event. A request that lost a race is refused with its reason, such as `already delivered`.
- **The mod gives the post office its secret through standard input at start.** The mod's commands present that secret, and the event stream comes back only over the post office's standard output.
- **Soldiers reach the post office through one MCP tool, `send`.** Each soldier holds its own credential, which allows nothing else. The tool is added to each soldier whose CLI allows it, through that CLI's own MCP configuration (PO-4).
- **Files travel only through worktree branches.** Shadow Army never puts a file's contents or a transcript into a message; a message carries only what its sender wrote.

**Why a separate process.** A mod can start a process and read its output for as long as it runs. But the process's input is written once and then closed, so a mod cannot hold a session open by itself. The post office holds the sessions, and the mod talks to it.

## 4. Requirements

### 4.1 The mod (HOST)

- **HOST-1** (M5; R) Shadow Army ships the mod as a plugin in this repository, loaded with `--plugin-dir` or installed from this repository. It MUST NOT depend on a marketplace plugin.
- **HOST-2** (M1; I, C, L) The mod starts the post office the first time the army is used in a session, and again at the first use after it has shut down (PO-7). It stops it when the session ends. There is at most one post office per folder (PO-1).
  - In M1 the first use is `/army`, which the mod registers from M1 in the list form that HOST-9 (→M5) gives it, or `sa live`, the dev tool that opens, messages, stops and reconnects a claude soldier through the same post office. From M3, Claude's `send` tool is a use too (HOST-10, →M3).
  - The mod acts only in the owner's own interactive session. In any other, such as a claude soldier's `-p` session, it registers no tool or command, starts no post office, records nothing and draws nothing. Claude Code's `session.start` marks such a run, with `isInteractive` false and no surface. The army runs only in the Claude Code CLI: elsewhere, such as the Desktop app, the mod can't start a process, so it offers no army.
  - A mod instance owns only the post office it started. When the mod reloads, as after a save under `--plugin-dir`, `/reload-plugins` or a lost hooks worker, that post office ends, with the module or by its lease within 30 seconds (PO-7), and its turns are cut short (PO-8, →M2). The new instance takes over no post office, since it has no secret: it starts its own at the next use, once the old lock is stale (PO-1), and Claude's transcript gets one line saying so.
- **HOST-3** (M5; S, I) **The pane** (spike S1).
  - In Claude Code's full-screen layout it docks beside the transcript from 110 columns. On the main screen it sits inline above the prompt, at most 72 columns wide.
  - It opens by itself only when a soldier needs the owner: from 144 columns, or from 110 once the owner has opened it before. Otherwise it waits undrawn until asked (`/pane`, or ctrl+x tab after a toast). When asked, it opens at any width.
  - Docked, it asks for 56 columns. A width the owner drags wins, and the pane reflows to whatever width Claude Code gives it.
- **HOST-4** (M5; S) **The pane's content**, top to bottom:
  - tabs, one per soldier;
  - a header with name · id · the model in use (CH-2), never dropped, the state with its word, and how many messages are queued. Below 50 columns it takes two lines: the name and the state, then the id and the model;
  - the meter;
  - the live session (thinking, tool calls, replies);
  - the message field;
  - the keys row, which wraps to a second row before any key is dropped.
- **HOST-5** (M5; I, S) **Keys in the pane:**
  - j and l switch tabs; i and k scroll the session, through `$.ui.scroll`. Tab and the arrow keys walk the pane's buttons, as Claude Code does in any pane, and the wheel scrolls too (spike S1).
  - Enter goes into the field, and Enter sends.
  - Esc leaves the field, and Esc again closes the pane.
  - The keys are button hotkeys, as the mod API provides; Claude Code's ctrl+x tab moves the keyboard into the pane.
  - j, l, i and k are reserved for moving in the pane. No other pane action, card or error uses them, because a repeated hotkey loses its binding.
  - The other pane keys:
    - o opens the log;
    - r reconnects or starts the soldier, and sends again a message that was not delivered. On an interrupted message it puts the text back in the field and sends nothing (MSG-4);
    - f starts fresh;
    - s stops the running turn (MSG-9);
    - q opens the queue, where 1 to 9 pick a message, x cancels it and c changes it (MSG-10);
    - g goes on: at the handoff card it keeps going, and after a stop it sends the held queue;
    - a and e answer the handoff card;
    - y and n answer the guard's attribution card (ARM-6);
    - d shows the soldier's changes (WSP-9, →M6);
    - 1 to 9 answer a vendor's approval request. An option that allows more than the one request, such as "allow for this session" or ACP's `allow_always`, takes its key twice: the first press marks it and says that the CLI decides what it covers, and the second sends it. Esc or another option's key clears the mark, and nothing is sent if the request closes first (CH-6).
  - No key is bound twice on one screen. The queue view replaces the session while it is open, so it and an approval request are never on screen together.
- **HOST-6** (M5; S) **The army strip** is one line above the prompt.
  - It lists every soldier in roster order, each with its state glyph and name in its colour, plus a five-cell meter and its tokens as the width allows.
  - Only a state that needs the owner (HOST-14), or error, shows a word in the strip, and it keeps it at every width: "waiting", "handoff" (handoff ready), "held", "log in", "down" and "error". Other states show by their glyph alone (VIS-2).
  - "error" shows from when a turn ends interrupted by what its CLI reported (PO-8), apart from a login needed, until the soldier's next turn starts or it starts fresh. It waits on nothing, so HOST-7's count, HOST-8's toasts and HOST-14's list leave it out.
  - The meters drop first, then the tokens, then names become tags (VIS-6). Glyphs never drop. If the line still does not fit, soldiers that need nothing fold into "+N more", and then the last ones that need the owner into "+N · /decisions".
- **HOST-7** (M5; U) **The status-line entry** is one plain-text entry, with the most urgent fact first. When more than one thing needs the owner, it gives their count and `/decisions`.
- **HOST-8** (M5; U) **Toasts** appear only while the pane is closed.
  - They are only for: a soldier waiting on the owner; a handoff ready; a disconnection; a CLI that needs a login; a message not delivered (MSG-4).
  - When a second decision opens while one is still open, one toast gives the count and points at `/decisions` (HOST-14). After that, new decisions get no toast until the list is empty.
- **HOST-9** (M5; U, S) **Commands:** `/army`, `/send <soldier> <message>`, `/pane [soldier]`, `/stop <soldier>`, `/queue [soldier]`, `/decisions`, `/fresh <soldier>`, `/handoff <soldier>`, `/sessions` and `/mode [ask|auto|plan|terminal|dark|light]`. `/diff` and `/apply` arrive with WSP-9 (→M6).
  - Each command's argument hint and one-line description, which Claude Code shows in its own slash menu:

    | Command | Argument hint | Description |
    |---|---|---|
    | `/army` | | every soldier, its tag and its connection |
    | `/send` | `<soldier> [--kind <kind>] <message>` | message a soldier yourself; Claude is told |
    | `/pane` | `[soldier]` | open or close the army pane |
    | `/stop` | `<soldier>` | stop its turn; its session and work stay |
    | `/queue` | `[soldier]` | what waits for each soldier |
    | `/decisions` | | everything waiting on you, oldest first |
    | `/diff` | `<soldier>` | the changes on its branch |
    | `/apply` | `<soldier\|undo>` | apply its changes to the folder, or undo |
    | `/fresh` | `<soldier>` | start its session fresh; its work stays |
    | `/handoff` | `<soldier>` | ask for its handoff summary now |
    | `/sessions` | | tokens, cache and cost per soldier today |
    | `/mode` | `[ask\|auto\|plan\|terminal\|dark\|light]` | how writing briefs go, and colours |

  - An unknown soldier name suggests the closest one and sends nothing.
  - `/send` takes an optional kind of work, `/send <soldier> --kind <kind> <message>`, checked as ARM-2 says. With or without a kind, a `/send` message is the owner's own (MSG-7); a kind only adds ARM-2's check.
- **HOST-10** (M3; I) **The mod gives Claude a `send` tool** (soldier, kind, brief, wantReply, wake).
  - `kind` is the kind of work the brief asks for: build, review, research or test. It is required, and the brief is checked against it before it is sent (ARM-2). The kind is checked and recorded (PO-6), never sent: the soldier receives only the brief's text.
  - It returns at once, with the brief's id and its state: delivered, or queued and what it waits for.
  - The summary arrives later as a summary card in Claude's conversation (MSG-5, MSG-8).
- **HOST-11** (M3; S) **The mod's rows in Claude's transcript:**
  - one row per brief, with its delivery state;
  - a summary card of at most five lines, plus the report's path, or `report not saved · <reason>` when the report can't be written;
  - one line for each soldier-to-soldier message and each message the owner typed directly.
  - Each one-line row starts with a bar, ▌ (ASCII `|`), in its soldier's colour. It is decoration: the row says everything in words and glyphs too (VIS-2, →M5).
- **HOST-12** (M5; R, U) The mod MUST NOT approve a tool call or a permission. It may only observe, or deny.
- **HOST-13** (M5; R) **The Monarch's own Claude Code permissions are the owner's.** The mod does not widen or narrow what Claude may do in the checkout. Soldiers' writes still go through their worktrees (WSP-2, →M6).
- **HOST-14** (M5; U, I, S) **One list of decisions, at the head of the army.**
  - Everything that waits on the owner, across all soldiers, is in one list, oldest first: approval requests, the guard's attribution cards (ARM-6), handoffs ready, queues held after a stop, logins needed, channels down and messages not delivered.
  - The list is the pane's first tab. Below the decisions the tab lists the rest of the army, in groups: working (stopping, background work and preparing handoff included), then error, then cold and idle, then starting, reconnecting and not started. Each row has the soldier's glyph, name and state word, and one fact: what it waits for and for how long, its current tool call, or its context size.
  - The tab is "needs you", with the count, and it shows while the list is not empty. `/decisions` prints the decisions in the transcript.
  - Choosing a row opens its card under the list, in the same tab, and the answer is given there with the card's own keys (HOST-5). The soldier's own tab shows the same card.
  - A new decision never replaces the card the owner is reading. It joins the list, and one line above the list names it, as in `↑ new: Iron · queue held · Tab`.
  - A row leaves the list once its decision is made, wherever it was made. An approval request also leaves when a stop cancels it (CH-6).
- **HOST-15** (M5; U, S) **While you were away.** When the owner has given no input for 10 minutes and the army has settled, with no soldier working, stopping, starting or preparing a handoff, the mod adds one digest to Claude's transcript:
  - a line with the time span;
  - one row per soldier whose state changed since the owner's last input, in HOST-11's words: answered (with the facts of MSG-11, →M6), interrupted with its reason (MSG-4), waiting on you, handoff ready, cold with its reason or cache unknown (SES-6), down, log in needed or error;
  - the cost the CLIs reported in that time, where they report one (SES-7).

  It comes once per absence. The 10 minutes are real time, counted as SES-6 counts idle time, from the owner's last input. The mod draws it as transcript notice rows, which are not added to Claude's conversation and wake nobody (MSG-8). It is not a toast (HOST-8).

### 4.2 The post office (PO)

- **PO-1** (M1; I, F) **Supervision.** The post office is one local process per folder, and it supervises every soldier session.
  - **One per folder.** The folder is the top level of the git working tree the owner's Claude Code session runs in. A lock there holds the post office's pid, its process start time and its port, and is written whole. The start time is the one the OS reports for that pid, read the same way when the lock is written and when it is checked. The mod learns the port only from the post office's standard output, never from the lock.
    - A start that finds a lock reads it. The lock is stale when no process has that pid with that start time, or when the file is empty or can't be read. A stale lock is replaced, and the new post office's log says so; of two starts that find the same stale lock, only one wins.
    - A lock whose owner is alive is never deleted or replaced. The start is refused, and the mod says why, as in `the army is already running in this folder (pid 4120, started 14:02)`, or `the army is still closing` while that post office shuts down (PO-7). The next use of the army tries again.
  - **Restarts.** A channel that crashes is restarted after 1 second, then 5 seconds, then 30 seconds. A fourth crash within 10 minutes of the first leaves it down until the owner reconnects it; a reconnect, or 10 minutes without a crash, resets the count. In M1 a restarted channel opens a fresh session, and the soldier's log says so; from M2 it resumes the previous one by id (CH-9, →M2).
  - **What a crash is.** Only the CLI's process ending, or the post office losing its connection to the CLI, is a crash; ten unparseable lines in a row count as a lost connection (CH-1). After a lost connection the post office ends the CLI's process tree before anything else. An error the CLI reports while it keeps running (CH-1) never restarts it.
    - A start counts as a crash when it ends before the CLI's first event, or gives no sign of life within its CLI's own startup wait plus 30 seconds. For claude the sign is its answer to the `initialize` control request, and the wait is `MCP_TIMEOUT`, 30 seconds unless the owner set it.
    - Silence is never a crash: a running CLI is not ended or restarted for sending nothing, and the owner can stop its turn (MSG-9, →M3).
    - A login needed never restarts the channel, whether the CLI keeps running or exits after it: the soldier shows "log in" until the owner reconnects it. Any other error the CLI reports before it exits counts as a crash, and keeps its kind and words (CH-1).
  - A message whose turn had started when the CLI crashed is never sent again by itself (MSG-4, →M3). Before the channel restarts, that turn is finished (PO-8, →M2).
  - **Containment.** When a channel closes or restarts, the post office ends the CLI's whole process tree: the CLI and every process that descends from it, one that starts a new session or forks twice included. If the post office's own process ends without closing a channel, however it ends, a kill or a crash included, that channel's whole process tree still ends within 10 seconds, through the containment that Q8 chooses, as far as it reaches.
    - Work the CLI hands to a service outside its tree keeps running: a systemd, launchd or cron job, a scheduled task, a process started through WMI, or a vendor's own background service, such as Claude Code's background sessions. That is a stated residual risk, and no guard or audit sees what such work changes after the turn.
  - **After a post office that didn't close its channels.** Before it opens any channel, a post office finishes what the last one's records left open (PO-6, →M3). Each turn still open is finished (PO-8, →M2): its guard is closed against the baseline kept on disk for it, any change goes on that turn's attribution card (ARM-6, →M2), or before M2 into one line in Claude's transcript, and its message ends as interrupted. Each queued message ends as not delivered. Both carry the reason `the post office stopped unexpectedly`, and nothing is sent again by itself (MSG-4, →M3).
- **PO-2** (M1; X) **Local only.** The post office and every port a channel opens MUST bind to the loopback address (127.0.0.1 or ::1). Any other address is refused at start, with an error that says so.
- **PO-3** (M1; X) **The Monarch's credential.**
  - The mod makes a secret of 32 random bytes each time it starts the post office, and passes it on the post office's standard input.
  - The secret MUST NOT be written to disk, a command line, an environment variable, or anywhere a soldier can read. Soldiers run as the same user, so a file only the owner can read is not enough.
  - Every command from the mod presents it. A wrong or missing secret is refused. The first refusal is reported in full; after that, at most one report a minute, with the count since the last one.
  - The event stream, with every soldier's turns, reaches the mod only on the post office's standard output.
  - The secret is never printed whole; at most its last four characters are shown.
- **PO-4** (M3; C, I, X) **The soldiers' tool and credentials.**
  - Each soldier session gets its own credential: 32 random bytes, made when the session opens and revoked when it closes or starts fresh.
  - That credential works only on the soldiers' MCP endpoint, which serves exactly one tool, `send(to, text)`, over local HTTP.
  - A soldier credential never appears on any process's command line. codex and grok take theirs over stdio, in `thread/start` and `session/new`; how claude takes its own, with nothing on its command line or on disk, is open question Q9.
  - The sender is always the soldier the credential belongs to; any sender named in the request is ignored.
  - A soldier credential MUST NOT issue a Monarch command, read the event stream, or read any session, log or record.
  - The tool is added to claude, codex and grok soldiers through each CLI's own MCP configuration, adding to it and never replacing it: claude's `--mcp-config`, codex's `thread/start` config, and grok's `session/new` `mcpServers` (spike S4).
  - agy has no per-session way to add it, so agy soldiers get no `send` tool in v2.0. They reply through summaries only.
- **PO-5** (M1; U, F) **Logs.** The post office keeps an append-only log for itself and one for each soldier's session, under `.shadow/v2/logs/`. Logs are JSON Lines: one file per soldier session, named by the soldier and the session id, and one per start of the post office, named by its start time. Every write passes through `redact()` (WSP-8).
  - A log holds each message, thinking block, tool call and tool result whole. The fragments a CLI streams are joined first, and `redact()` runs on the joined text. When a turn ends before a message is whole, what was joined so far is written.
  - Each decision (HOST-14, →M5) is logged when it opens and when it closes, so a post office ended outright loses none.
  - A log never stops a soldier or a turn. A write that fails is tried once more, 100 ms later. If that fails too, the post office carries on, reports it once on the event stream, and Claude's transcript gets one line, as in `Shadow Army: logs not written · disk full`. Each later write tries again, and the first line written after a gap says how many lines were lost. A line cut short by a failed write is ended before the next one, and a reader skips any line that doesn't parse. Records are not logs: what a record that can't be written does is in MSG-4 (→M3).
- **PO-6** (M3; U, F) **Records.** Every brief, summary and message is stored with its id, time, sender, recipient and delivery state, and a brief with its kind of work (HOST-10). Full reports go under `.shadow/reports/`.
- **PO-7** (M1; U, I, F) **Shutdown.** When the Claude session ends, the post office closes every soldier session through that CLI's own exit, and leaves the worktrees and branches in place.
  - **What starts it.** Three things start the same shutdown: the mod's release at `session.end`, the lease's end, and the watch. The first one starts it; the others then change nothing.
  - **The lease.** A living Claude process doesn't prove a living session: a mod can hang or be stopped. So the mod renews a lease with the post office every 10 seconds, and the post office ends the lease after 30 seconds of its own running time without a renewal. The 10 and 30 seconds are fixed; no setting changes them.
    - **Renewing.** The mod gives the post office Claude's session id (`$.session.id()`) with the secret at start (PO-3); without one, the post office refuses to start. Every 10 seconds, by its own timer (`$.clock.every`), the mod sends a renewal: a command that presents the secret and carries that session id. Only a renewal renews the lease. At most one renewal waits for its answer, and one that falls due meanwhile is skipped; a renewal unanswered after 5 seconds no longer counts as waiting. A renewal that fails is not retried early and stops nothing: the next one goes at its time.
    - **At `session.end`** the mod stops renewing before anything else, then sends a release that names the Claude session. The post office answers the release at once, then shuts down; a release that names another session is refused. If the release doesn't arrive within that hook's short time budget, the lease ends the post office instead.
    - **The clock.** The post office measures the lease on Node's monotonic clock (`performance.now()`). It MUST NOT use the wall clock for it, so a change of the system time, either way, changes nothing. Times it reports, such as when the lease ended, are wall-clock times for display only.
    - **The checks.** The gap starts at zero when the post office reports that it is ready, and goes back to zero with each renewal. Once a second, a check adds the time since the previous check, the last renewal or the start, whichever came last, but never more than 5 seconds. The lease ends at the first check that brings the gap to 30 seconds. Only a check ends it. Handling a renewal never measures time, so a renewal handled before that check renews the lease, however late it was sent.
    - **Sleep, suspension and stalls.** A step of more than 5 seconds between two checks means the post office did not run: the computer slept or hibernated (Windows' modern standby included), the post office was suspended by a debugger or a signal, or its event loop stalled. At most 5 seconds of it count, on every system. Node's monotonic clock stops while Linux is suspended, but goes on through sleep and hibernation on Windows and macOS, where the first check after waking sees one long step. Renewals sent while the post office was suspended wait at its port, and are handled when it runs again. The post office logs each such step with its length.
    - **The mod stopped or stalled.** Time in which the post office runs and the mod doesn't counts in full. That covers Claude Code stopped by job control (ctrl+z) or a debugger while the post office isn't, its event loop busy, and the mod's timer stopped. The lease ends once 30 seconds of it pass without a renewal.
    - **Refused renewals.** A renewal is refused, and renews nothing, when it carries another session id, when it comes from an earlier start of the post office (PO-3), or when the lease has ended. An ended lease never comes back. The refusal gives the reason. The post office logs the lease's start, each long step and each refusal, never a renewal one by one.
  - **The event stream never holds the post office.** Claude Code blocks a child of the mod on its next write once 1,048,576 characters of its output wait unread, and Node writes to a pipe synchronously on Windows. So the post office writes its events without blocking its event loop, and goes on reading its soldiers, serving `send` and taking renewals while they wait. Past 16 MiB of events not yet written, it stops reading its soldiers' output until the mod has read them.
  - **The watch.** Once a second the post office also checks that the process that started it is still running. It tells that process apart from a later one that reuses its pid by its start time, as the lock does (PO-1). Once that process has ended, the post office shuts down at once, without waiting for the lease.
  - **Containment.** The lease and the watch need a running post office. The post office may be ended outright before its shutdown finishes, for example by Claude Code when the mod unloads, or by a crash. Then no session closes through its CLI, and its process containment ends each soldier's whole process tree (PO-1).
  - **The shutdown,** whatever started it, for every soldier at once:
    - The post office records the reason and the time in its own log and in each soldier's (PO-5), and sends them as an event. The reason is one of `the session ended`, `no renewal from the mod for 30 s` and `the process that started it ended`.
    - From then on it refuses every command, renewals included, and every soldier's `send` (PO-4, →M3), giving that reason. No channel starts, restarts or resumes (PO-1; CH-9, →M2), and it never waits for background work.
    - Each queued message ends as not delivered, with the reason (MSG-4, →M3), and nothing more is sent.
    - A running turn is stopped as a stop stops it, background work included (MSG-9, →M3; CH-10, →M2), and each approval request it has open is closed as a stop closes it, and nothing is approved (CH-6, →M2). A turn not ended 30 seconds after the stop has its CLI's process tree ended (PO-1). The turn is finished (PO-8, →M2), and its message ends as interrupted, with the reason (MSG-4, →M3).
    - An attribution or handoff card still open is not answered, and doesn't hold up the shutdown (ARM-6, →M2; SES-4, →M4). It is kept in the records as unanswered, with its paths and hashes (PO-6, →M3), and the message whose summary waited for it ends as interrupted, with the reason `the session ended before the owner answered`.
    - Then each session closes through its CLI's own exit. Once the CLI has exited, or 10 seconds after it was asked to, the post office ends its whole process tree (PO-1) and revokes the soldier's credential (PO-4, →M3). A channel still starting has its process tree ended at once.
    - Once every session is closed, the post office releases its lock (PO-1) and exits. It doesn't wait for the mod to read its last events; the logs keep them.
    - Until M2, which brings the stop (CH-10, →M2) and the finishing of turns (PO-8, →M2), a running turn is not stopped first: closing its session cuts it short.
  - **What the owner sees.**
    - The soldier's log and the post office's log say when the army stopped and why. They also say what happened to each turn, queued message, approval request and card, as in `14:02:13 lease ended: no renewal from the mod for 30 s · turn stopped · 2 queued messages not delivered · session closed`.
    - The mod learns of the shutdown from the post office's last event, from a command refused for that reason, or from the end of the post office's output; output that ends with no shutdown event gives the reason `the post office stopped unexpectedly`, with its exit code or signal. A renewal that only fails tells it nothing. Then the mod stops renewing, and Claude's transcript gets one line, as in `the army stopped at 14:02:13: no renewal from the mod for 30 s · the next use starts it again`. From M5, while the pane is closed, a toast says so, as for a disconnection (HOST-8, →M5). The rows of the briefs it affected show how they ended, as far as its events told it (HOST-11, →M3). The records keep every ending (PO-6, →M3).
    - The next use of the army starts a new post office (HOST-2) once the old one has exited and released its lock. Until then, the mod says that the old one is still closing. The soldiers start new sessions. The old sessions' logs and reports, and every worktree and branch, stay.
- **PO-8** (M2; I, F) **A turn ends once, and only when its work has stopped.**
  - A turn's end event is its CLI's own: claude's and agy's `result`, codex's `turn/completed`, or the answer to grok's `session/prompt`.
  - **Work left running.** A turn is not over at its end event while something it started is still running: a background task the CLI reports, or a process that joined the CLI's process tree during the turn (PO-1) and is not a session service. claude reports its background tasks with `task_started`, `background_tasks_changed` and `task_notification` events, and stops one on a `stop_task` control request. Until that work ends:
    - the soldier shows it, as in `◐ 1 background task`, and the message stays delivered;
    - the turn's guard stays open, so whatever the work changes belongs to the turn and goes on its attribution card like any other change (ARM-6, WSP-4, →M6);
    - messages to the soldier wait in its queue (MSG-3, →M3), and harness git for that soldier waits too (WSP-7, →M6);
    - a turn the CLI takes by itself when the work ends belongs to the same message. claude takes one more turn with a background command's outcome.

    The work has ended when the CLI reports each task's end, each such process has exited, and each turn the CLI takes by itself with a task's outcome has ended; at the latest at the CLI's own time limit for background work. claude takes such a turn when a task completes or fails by itself, and marks its messages and `result` with the origin kind `task-notification`. It may answer several outcomes in one turn; then the others' `result`s come first, empty, with `num_turns` 0. A task stopped by s, or a process that is not a CLI task, starts no such turn. A task whose follow-up has sent no event 30 seconds after the task ended, on the monotonic clock, has none. s stops the work at any time (MSG-9, →M3): the adapter stops each task through its CLI and ends each such process, and the session stays open.
  - **Session services.** Some processes serve the whole session rather than one turn: the language servers and MCP servers declared by the configuration the CLI runs with, its plugins included (SET-2, →M4). The CLI starts each one itself, not through a tool's command, and keeps it between turns. claude, for example, starts a plugin's language server at the first edit of a matching file and keeps it for diagnostics, so the server joins the process tree during that turn.
    - The adapter recognizes a session service only as a process the CLI started with a command its configuration declares, plus any helper its table names for that server, such as the compiler server a language server starts. The table of where its CLI declares servers, and of their helpers, names the CLI version it was read from (CH-8).
    - Every other process that joins the tree during a turn is the turn's work, even one a session service started: a job an MCP server starts for a tool call, a process the adapter cannot tell, and one a tool started with a service's command. A tool call's ownership comes before the service it ran through.
    - A session service never keeps a turn open. Once the turn's own work has ended, the turn is over, the next message can go in and harness git can run (WSP-7, →M6), while the service keeps running. s leaves it running.
    - It ends with the session: closing or restarting the channel ends the CLI's whole process tree (PO-1).
    - A change it makes to the checkout during a turn goes on that turn's attribution card, like any other change (ARM-6, WSP-4, →M6).
  - **Cut short.** Sometimes the turn is not over yet when the CLI's process ends, its connection is lost, or a stop falls back to ending the process (CH-10). Then the turn is over once the post office has ended the CLI's whole process tree (PO-1), background work included. That covers a turn with no end event, and one whose background work was still running. The post office reads everything the CLI wrote before it decides whether an end event came.
  - **Finishing.** When a turn is over, either way, the post office finishes it before anything else. It closes the turn's checkout guard (ARM-6, WSP-4, →M6) and runs its claim audit (WSP-2, →M6), once each, on the files as they are then. Then the message ends by what the CLI's own fields say in the last end event; when the CLI took a turn by itself after background work ended, that turn's end event is the last. The message ends:
    - **answered**, with that turn's result as the summary, when the turn completed or the model refused (CH-1): claude's `result` with the subtype `success` and no `is_error`, codex's `turn/completed` with the status `completed`, or grok's answer with the stop reason `end_turn` or `refusal`;
    - **interrupted**, when the turn failed or stopped short of finishing: claude's `result` with an `error_…` subtype or `is_error`, codex's `turn/completed` with the status `failed`, or grok's answer that is an error or has the stop reason `max_tokens` or `max_turn_requests`. The CLI's own error or reason is kept word for word, with its kind when it is an error (CH-1), such as a rate limit or a context overflow. The changes made so far stay, and the message's row shows them (MSG-4, →M3);
    - **interrupted**, when the turn was cut short or the owner stopped it (MSG-9, →M3).

    The work done so far stays under the usual rules. Nothing is sent again by itself (MSG-4, →M3), and an error the CLI reports while it keeps running never restarts it (PO-1).
  - Only then is the session resumed (CH-9), the channel restarted (PO-1) or the next message sent. If the guard raises an attribution card, the soldier's queue is held until the owner answers it (MSG-3, →M3).
  - The guard and the audit run once per turn. An end event read after the turn is over is recorded and changes nothing.
  - A turn the CLI starts by itself after a message's work is over belongs to that message: it gets a guard and an audit of its own, the queue waits for its end event, and its result never ends a later message. Its result is recorded under that message and shown in the soldier's log, and Claude's transcript gets one line saying the soldier took a turn by itself after answering (HOST-11, →M3), with its changes (MSG-11, →M6). n on its card fails that turn as a read-violation, and the line says so; the message keeps the state it ended in.
  - A change made after the turn is over belongs to no turn, so the owner's own edits between turns stay exempt. The next turn's guard starts from the checkout as it is when that turn's message goes in. That baseline is on disk before the message goes in, so a post office that dies mid-turn leaves it for the next one (PO-1).
  - The guard and the claim audit run after a failed turn too (from v1 #22 and #16: `src/core/summon.ts` checks the guard and audits after a failed run).

### 4.3 Channels (CH)

- **CH-1** (M1; U, C) **One interface.** Each CLI has one adapter, and all adapters share one interface.
  - The interface: open a session in its snapshot or its worktree (WSP-11; WSP-1, →M6) with the standing instructions; send a message; interrupt the running turn; stream events; close.
  - Events: text, thinking, tool call, tool result, approval request, usage, turn end, error.
  - An error says which kind it is, read from the CLI's own fields: a rate limit (with its reset time where the CLI gives one), a context overflow, a login needed, or another error. Each keeps the CLI's message word for word.
  - A refusal is not an error: the turn ends with the model's own words, marked as a refusal.
  - A line the CLI writes that can't be parsed is recorded word for word, redacted (WSP-8), and shown as an error of the kind another error, and the session carries on; ten in a row count as a lost connection (PO-1) (from 2.0 SOLD-6). A line split across reads is joined first, and only one still incomplete when the stream ends is malformed.
  - `cli` in `shadow.config.json` names one of the four adapters; any other value is refused at start. An adapter starts its CLI from an absolute path found on `PATH` alone, never in the folder, a worktree or a snapshot, and never through a relative `PATH` entry. On Windows the current folder is never searched.
- **CH-2** (M1; C, L) **claude.**
  - One long-lived `claude -p --input-format stream-json --output-format stream-json --verbose` process per soldier.
  - It needs claude 2.1.277 or later: 2.1.259 brought `--permission-prompts`, and 2.1.277 the totals a resumed session restores (a turn's own figures, below). A later version is needed where a field this adapter reads needs one where a field this adapter reads needs one; each such need is named beside its rule, with the version it was read from (CH-8, →M2). Before it opens a session, the adapter reads `claude --version`. An older claude opens no session and never counts as a crash (PO-1): the soldier's log says `claude <found> is older than <oldest>; update claude`, and Claude's transcript gets that line.
  - From M2 it runs with `--permission-prompts host --permission-prompt-tool stdio`, so each permission request arrives as a `control_request` (`can_use_tool`) for the relay (CH-6, →M2). In M1, before the relay exists, it runs without `--permission-prompt-tool stdio`, so claude denies by itself whatever would need an answer (spike S5), and nothing waits. It never runs with `--permission-prompts none`, which removes tools such as AskUserQuestion (CH-7).
  - It passes the permission mode of the soldier's autonomy on every start and resume, as v1 does (`src/adapters/claude.ts`): `--permission-mode plan` for supervised, or `acceptEdits` for a writing turn (ARM-5, →M6); `--permission-mode auto` for auto; and `--permission-mode bypassPermissions` for full.
  - The instructions go in `--append-system-prompt`, or in `--append-system-prompt-file` where the command line can't carry them, as through a Windows `.cmd` shim. That file is written by the post office beside the session's record, never in a worktree or a snapshot, and removed when the process ends.
  - Each message goes in with its own `uuid`, and with `priority` `later`, so that claude never folds it into a turn already running. A `result` ends a message's turn only when its `user_message_uuid`, or its `user_message_uuids` list, names that message. A `result` with the origin kind `task-notification` that comes after claude's `task_notification` for a task a message's turn started belongs to that message (PO-8, →M2). Any other `result`, the zeroed one after a crash included, is recorded in the soldier's log and ends nothing; a crash still ends its turn (PO-1).
  - **Error kinds**, from claude's own fields (CH-1): a rate limit is a `rate_limit_event` whose `status` is `rejected`, with `resetsAt` as its reset time, or a failing turn's `error` `rate_limit` or `api_error_status` 429, and `allowed_warning` is not an error; a context overflow is `terminal_reason` `prompt_too_long`; a login needed is `authentication_failed`, `oauth_org_not_allowed` or `cloud_credential_error`; any other error is another error. A refusal is read from the field claude's recordings show (section 5.1, C). A `system/api_retry` event is shown as a retry, with its attempt and delay, and is not an error.
  - **The model in use** is the one claude reports for the main conversation: `system/init`'s `model`, then each main-conversation assistant message's `message.model`. When claude changes it by itself, as its automatic fallback does for a flagged request, the soldier's log records the change, and the pane's header (HOST-4, →M5) and the turn's usage record (OBS-3, →M4) name that model. The roster keeps the configured one (ARM-1). Such a switch is not a change made before a message (SES-6, →M4): the turn's later requests ran on the new model, so the timer runs from the last of them. No adapter passes a setting that changes claude's fallback (CH-7).
  - The context size is the usage of the last assistant message in the main conversation, whose `parent_tool_use_id` is null: its `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` together. A subagent's messages never set it.
  - **A turn's own figures.** claude's `result` gives `usage` for the turn's main loop only. Its `total_cost_usd` and `modelUsage` are running totals for its process, subagents included, plus the earlier spend of a session it resumed. A turn's tokens, by model, and its cost are its result's `modelUsage` and `total_cost_usd` less those of the result before it: nothing, for a new session's first turn; the previous result in the same process; or, for the first turn after a resume (CH-9, →M2), the last result of the process before it, if that process exited normally.
    - With no such result, the turn's cost reads "not reported", and its tokens are its main-loop ones: input and cache summed over its main-loop assistant messages, each message id counted once, and output from its `usage`, since an assistant message's own output count is a placeholder.
    - A zero or falling total is never a baseline: the next result's cost also reads "not reported", since its difference would include an earlier turn's spend, and that result's totals become the baseline.
    - A result whose `usage`, `total_cost_usd` and `modelUsage` are all zero, as after a crash or a stop (spike S6), reports nothing. That turn's input and cache are summed the same way, its output and cost read "not reported", and it is never the result before the next turn.
    - The cost is claude's own estimate. SES-7 (→M4), HOST-15 (→M5) and section 5.1's live checks use these turn figures, never running totals.
- **CH-3** (M2; C, L) **codex.**
  - `codex app-server` over stdio: `thread/start` with `developerInstructions`, then `turn/start` for each message.
  - A turn ends with `turn/completed`.
  - Usage and the context window come from `thread/tokenUsage/updated`.
- **CH-4** (M2; C, L) **grok.**
  - `grok agent stdio`, or `grok agent serve` bound to the loopback with a secret.
  - `session/new` carries the instructions in `_meta.rules`, and `session/prompt` sends each message.
  - Usage comes from the prompt result's `_meta.usage`.
- **CH-5** (M2; C, L) **agy.**
  - One long-lived `agy --input-format stream-json --output-format stream-json` process, whose messages are `{"event":"user",…}`.
  - agy's own modes do not stop it writing: in spike S5 it wrote a file even with `--mode plan`. It therefore always runs as ARM-6 says.
  - The instructions lead the first message, because agy has no slot for them.
  - A turn ends with the `result` event. Its usage is a running total, and its input excludes cached tokens.
  - The context size comes from its `agent_response` steps only (SES-2, →M4).
- **CH-6** (M2; C, I) **Approval relay.**
  - claude, codex and grok ask through their own protocols (spike S5): claude's `can_use_tool` control request (CH-2), codex's `item/commandExecution/requestApproval` and `item/fileChange/requestApproval`, and grok's ACP `session/request_permission`.
  - Each request is shown word for word, with the CLI's own options, and the owner's answer goes back unchanged.
  - No adapter answers a request by itself. An unanswered request stays pending (spike S5) until the owner answers it or stops its turn, or the post office shuts down (PO-7), which closes it as a stop does.
  - **A stop cancels the turn's requests.** Stopping a turn (MSG-9, →M3) is the owner's answer to every request that turn still has open, and it approves nothing: the tool does not run. Each request is closed the way its CLI's protocol closes a cancelled turn's requests:
    - grok's adapter answers each `session/request_permission` with the `cancelled` outcome, as ACP requires;
    - claude withdraws its request with a `control_cancel_request`;
    - codex clears its request and says so with `serverRequest/resolved`.

    Spike S6 confirms claude's and codex's. A request still open when its turn ends is closed then, and no answer is sent for it afterwards.
  - A closed request's card leaves the decisions list (HOST-14, →M5). An answer given after it closed, such as a key pressed as the card goes, is dropped and never reaches the CLI.
  - agy has no relay, and its adapter declares that it has none. Headless agy has no approval protocol: it soft-denies any tool that would need a confirmation and carries on, and a `control_request` or `control_response` sent to it ends its session with exit code 2. The adapter therefore never sends either. It shows each denial agy reports on its standard error word for word, as a tool call that agy denied.
- **CH-7** (M1; R, U) **The harness stays whole.**
  - No adapter replaces a system prompt or removes a tool, and none passes, on its own, a flag that disables a safeguard: such a flag, like claude's `bypassPermissions` for `full`, goes only where the owner's autonomy level chose it (ADR-0010).
  - Autonomy chooses only each vendor's documented flags (from 2.0 SAFE-10). Each adapter passes its CLI's permission mode at every autonomy level, on every start and resume, so the mode never comes from a settings file or the CLI's own default: claude's in CH-2, and codex's, grok's and agy's with their channels (CH-3 to CH-5, →M2).
- **CH-8** (M2; U) **Versions.**
  - Each adapter records the CLI version its contract fixtures were recorded with.
  - A newer version connects, with a warning card.
  - A line that cannot be parsed is an error, never silently dropped.
- **CH-9** (M2; C) **Resume.** After a crash, a channel reopens the soldier's previous session by id where the CLI supports it: claude `--resume`, codex `thread/resume`, grok `session/load`, agy `--conversation`.
- **CH-10** (M2; C, L) **Interrupt.**
  - Each adapter stops a running turn through its CLI's own interrupt, and the session stays open: claude's stream-json `interrupt` control request, codex `turn/interrupt`, and grok's ACP `session/cancel`. The stop also closes the turn's open requests (CH-6).
  - The turn has stopped only when its end event comes (PO-8): claude's `result`; codex's `turn/completed`, with the status `interrupted` unless the turn had already finished; or grok's answer to the original `session/prompt`, with the `cancelled` stop reason. Events that arrive before then belong to the stopped turn, and are shown and recorded. No message goes in until then.
  - A CLI whose turn has not ended within 30 seconds of the stop, on the monotonic clock, is stopped as one with no interrupt.
  - Spike S6 confirms each one, and looks for agy's.
  - A CLI with no interrupt is stopped by ending its process tree. The turn is finished as PO-8 says, and then the session is resumed by id (CH-9). The soldier's log says it was resumed, as does the pane (HOST-4, →M5).

### 4.4 Standing instructions (SI)

- **SI-1** (M1; U) **Content.**
  - The soldier's shadow name, model and roles.
  - The whole team with their roles, and Claude as the Monarch.
  - The hard rules (ARM-2, →M3), `rules.md`, and the soldier's `agent.md` section.
  - The reply format: at most five lines of at most 120 characters each (what was done, which files, what to check).
  - The handoff instruction: when asked for a handoff (SES-4, →M4), reply under working on, done, decided, files and open.
- **SI-2** (M1, M2; C) **Injection.** The instructions go in through each CLI's append slot (CH-2 to CH-5) and MUST NOT replace the vendor's prompt. agy's first-message fallback shows in the post office view.
- **SI-3** (M1; U) **Size.** The instructions stay under 1,500 tokens, counted offline as their UTF-8 bytes divided by 3 and rounded up, the same way in CI and at start; they measured about 1,000 on 2026-10-07. A soldier whose instructions count 1,500 or more does not open: its log, and one line in Claude's transcript, give the count and name `rules.md` or its `agent.md` section to shorten. The text is never cut (SI-1).
- **SI-4** (M4; I) **Fresh sessions.** A fresh session receives the instructions again, with the handoff summary when there is one.
  - The instructions are fixed for a session's life. The post office keeps the exact text each session started with, in that session's record.
  - A resumed session (CH-9) gets that same text wherever its CLI takes instructions on a resume, never a text rebuilt from the files. agy's led its first message, so nothing is sent again. claude also keeps the system prompt it recorded on the session's first request, until the session is compacted.
  - An edit to `rules.md` or a soldier's `agent.md` section reaches that soldier with its next fresh session. Claude's transcript gets one line per edit, naming the soldiers whose open sessions keep the older instructions.

### 4.5 Messaging (MSG)

- **MSG-1** (M3; R, I) **Only briefs and summaries cross between models** (from v1's isolation rule). A message never carries a transcript or a file's contents; files travel through branches.
  - What a soldier wrote reaches another model only as that soldier's quoted words, named as such. A summary, a soldier-to-soldier message or an error is never presented as the owner's or the Monarch's instructions. Only the Monarch's briefs assign work (ARM-4).
- **MSG-2** (M3; U) **Names.** A message is addressed by shadow name, case-insensitively. An unknown name suggests the closest one, and nothing is sent.
- **MSG-3** (M3; I, F) **One turn, and the queue.**
  - A message is one turn in the recipient's open session.
  - A message to a soldier that cannot take it now is queued: the soldier is mid-turn (background work included, PO-8), starting, reconnecting, disconnected, or needs a login. Each soldier's queue runs first in, first out.
  - A queued message goes by itself as soon as the soldier can take it, including after a reconnect. Its row says what it waits for, such as "sends when Bellion is back".
  - A held queue waits for the owner instead: after a stop (MSG-9), and while a handoff card (SES-4, →M4) or an attribution card (ARM-6) is open.
  - Nothing in a queue is dropped silently.
- **MSG-4** (M3; U, S) **Delivery states.** The state updates in place, always as a glyph and a word.
  - A message moves through queued, delivered and answered.
  - Otherwise it ends in one of three ways, each with its reason:
    - **interrupted:** it was delivered, but no summary came back: the owner stopped the turn, the CLI crashed, the CLI reported the turn as failed (PO-8), the post office shut down or stopped unexpectedly (PO-7, PO-1), or the owner answered n to the guard's attribution card (ARM-6). The turn may already have changed files, so the row shows the changes made since the turn began (MSG-11, →M6);
    - **not delivered:** it never reached the session, for example because the post office stopped first. Nothing was sent, so it is safe to send again;
    - **cancelled:** the owner cancelled it while it was queued (MSG-10).
  - "Failed" is not a state. Each ending says which of these happened.
  - **Sending again.** A message that ended not delivered may be sent again as it is (r): none of it reached the session.
    - An interrupted message is never sent again, by itself or by a single key, because its turn may already have changed files. The post office refuses to send it again, and says why.
    - The post office records a message as delivered, and flushes the record to disk, before it writes the message to the CLI. A crash between the two, the machine's included, can then only lose a send, which shows as interrupted, and never repeat one. If the record can't be written, the message isn't sent: it stays queued, and its row says why, as in `waits · records can't be written · disk full`. A record line cut off by a crash is skipped when the records are read; because of the flush, its message never reached the CLI.
    - r puts an interrupted message's text back in the field instead, above the changes its turn made (d). The owner edits it or keeps it, and Enter sends it as a new message with its own id. Its row says which message it repeats.
- **MSG-5** (M3; U, I) **Summaries.**
  - A summary has at most five lines of at most 120 characters each, counted the same at any width. A longer line or reply is cut with …, and the whole reply is saved as the report.
  - The summary goes back to whoever sent the message.
  - For the Monarch, it is added to Claude's conversation as a summary card. The card's title says "answered", and it also states the facts of MSG-11 (→M6).
- **MSG-6** (M3; I) **Soldier to soldier.** Soldiers message each other through `send` (PO-4). Both panes show the message in full; Claude's transcript gets one line. A soldier MUST NOT assign work to another; only the Monarch briefs.
- **MSG-7** (M3; I) **The owner, directly.** The owner types into a soldier through the pane's field or `/send`, as "you". Claude's transcript gets one line saying that soldier's context changed.
- **MSG-8** (M3; I, L) **Waking the Monarch.** When a summary arrives and Claude is idle, the mod starts a turn only if the brief asked for a reply. The `send` tool asks for one by default. Otherwise the card waits for Claude's next turn. If Claude is mid-turn, the card joins the running turn and no new turn starts. Summaries that arrive within a few seconds of each other, on the monotonic clock, share one wake (spike S2). Briefs that Claude sends in one turn wake it once, when the last of them has answered or ended; a brief that must be read on its own sets `wake: "own"`.
- **MSG-9** (M3; U, I, S) **Stop a turn.**
  - s in the pane, or `/stop <soldier>`, stops that soldier's running turn through its CLI's own interrupt (CH-10).
  - Until the stopped turn has ended, the soldier's state is "stopping": the pane shows `■ stopping the turn…`, s is not offered, and messages wait in the queue. This normally lasts a second or two. If the CLI is ended after 30 seconds instead (CH-10), the pane says so, as in `claude did not end the turn within 30 s, so it was ended and its session resumed`.
  - Any approval request the turn has open is cancelled, never approved, and its card closes (CH-6).
  - When the turn's end event has come but background work it started is still running (PO-8), s stops that work instead: each task through the CLI, such as claude's `stop_task`, and each process the turn left running. A session service, such as a plugin's language server, keeps running (PO-8).
  - The session stays open with its history, and the work done so far stays in the soldier's worktree. This is not starting fresh (SES-5, →M4).
  - The message ends as interrupted, with the changes made so far (MSG-4), unless its turn had already ended by itself; then it ends as PO-8 says.
  - The soldier's queue is then held, so older instructions do not run by themselves. g sends the held queue; a new message from the owner goes first. Either goes in only once the stopped turn has ended (CH-10, PO-8).
  - Claude's transcript gets one line, so Claude knows the turn was stopped.
- **MSG-10** (M3; U, I, S) **The queue is visible, and the owner controls it.**
  - The pane's header shows how many messages are queued, and q opens the queue: each message's sender, age and first line.
  - The owner can cancel a queued message, or change its text before it is delivered. A cancel or change that reaches the post office after the message was delivered is refused with `already delivered`, and Claude gets no line.
  - When the message was Claude's brief, Claude's transcript gets one line saying it was cancelled or changed.
  - `/queue [soldier]` prints the queues in the transcript.
- **MSG-11** (M6; U, I, S) **Facts on the summary card.** Beside "answered", the card states these, from the post office's own records and never from the summary's text:
  - **changes:** the files and lines the turn changed on the soldier's branch, or "none";
  - **tests:** whether a test command ran in the turn and whether it passed, by its exit code where the CLI reports one, or "not run". Test commands match the soldier's `tests` patterns in `shadow.config.json`, by default `npm test`, `npx vitest`, `pytest`, `cargo test` and `go test`;
  - **applied:** "not yet", or when the changes were applied to the folder (WSP-9);
  - the report's path, and the commands that act on the work (`/diff`, `/apply`).

### 4.6 Sessions (SES)

- **SES-1** (M4; I) **One session per soldier.** Each soldier has one open session per Claude session, and related work accumulates in it.
- **SES-2** (M4; U, S) **The meter.**
  - It shows the context size from the CLI's own events, as a bar up to the handoff line, with colour steps at 30, 50, 70 and 90%.
  - Its text names both measures, as in `142k / 200k handoff · 55% window`. The bar measures the first; the share of the window shows only where the CLI reports its window.
  - Where the context size comes from (spike S3):
    - claude: the last assistant message in the main conversation (CH-2);
    - codex: `thread/tokenUsage/updated` → `last`;
    - grok: the session's `signals.json`, `contextTokensUsed`;
    - agy: the latest `agent_response` step to reach `DONE`, its input tokens plus cache reads.
  - Usage from an auxiliary call, such as a claude subagent's or an agy `checkpoint` step's, is recorded (OBS-3) but never moves the meter.
- **SES-3** (M4; U) **Near handoff.** At 90% of the handoff line (180k by default), the soldier shows "near handoff".
- **SES-4** (M4; I, S) **Handoff.**
  - At the handoff line, the soldier is asked for a handoff summary covering: working on, done, decided, files, open.
  - While the soldier writes it, the state is "preparing handoff". Once the card is ready, the state is "handoff ready", which needs the owner: it shows in bold, keeps its word in the strip, and joins the decisions list (HOST-14, →M5).
  - A card in its pane offers three choices: a accepts (a fresh session starts with the summary), e edits it first, and g keeps going and asks again after 20k more.
  - Messages to that soldier are held until the owner chooses.
- **SES-5** (M4; I) **Start fresh.**
  - `/fresh` or f in the pane closes the session, keeps its log, and starts a new one with the standing instructions.
  - The soldier's work stays on its branch, and nothing is reverted.
  - A handoff first is optional.
  - Stopping a turn (MSG-9) is different: it keeps the session.
- **SES-6** (M4; U, S) **Cold.**
  - Cold is an estimate, made before a message is sent: the time since the soldier's last model request is longer than its cache lifetime. That time is real time, sleep included: the larger of the wall clock's and the monotonic clock's time since the request, so a sleep counts and a clock set back never keeps a soldier warm.
  - **A change to the soldier's model, effort or tools** (MCP servers included) moves the estimate only as its CLI's documentation says that change affects the cache, for the model and sign-in in use. Each adapter keeps these rules in a table, with the CLI version they were read from (CH-8). Standing instructions never change within a session (SI-4).
    - A change the table says resets the cache makes the soldier cold at once, whatever its idle time and even when its lifetime is unknown. For claude: another model; effort, on a model or sign-in where each effort level has its own cache; and tools added or removed while they load up front.
    - A change the table says keeps the cache leaves the estimate as it was. For claude: effort on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 with an API key or a Claude subscription; an MCP server connected or removed while tool search defers MCP tools, as it does by default; and a plugin's skills, commands, agents and hooks.
    - With any other change, or when the adapter cannot tell which case applies, the estimate is unknown until the soldier's next model request: the timer goes, and that spot says what changed, as in `cache unknown · tools changed`. The soldier is not shown as cold.
  - The lifetime comes from, in order:
    - the owner's `cacheLifetime` for that soldier (SET-1);
    - what the CLI reports with its usage: claude marks each cache write as lasting 5 minutes or 1 hour (`cache_creation`), and every write in the 2026-10-07 live probes was for 1 hour;
    - the provider's documentation for that model.

    With none of these, the estimate is "unknown": no timer, and the soldier is shown as cold only after a change that resets the cache.
  - **The timer.** While the soldier is warm and its lifetime is known, the right end of the pane's meter line counts down to the minute from its last model request: `cold in 12m`, then `cold in <1m`. It changes as a value once a minute, never as motion (VIS-4, →M5).
  - When the time runs out, that spot reads `❄ cold since 13:53`. After a change that resets the cache it says why, as in `❄ cold · model changed`.
  - **The quick message.** `the next message likely re-reads the full 142k context`, with the soldier's context size, shows once in the session when the soldier turns cold, and in the field while the owner is in a cold soldier's field. It says "likely" because cold is an estimate. It goes when the message is sent or the owner leaves the field. It is not a toast (HOST-8, →M5).
  - What actually happened is kept apart from the estimate. Each request's cache reads are recorded with its usage (OBS-3), and a request whose cache reads fall to about zero counts as a miss. A miss never sets or shortens a lifetime: a changed prefix, compaction or the provider's routing can cause one while the cache is still held.
- **SES-7** (M4; U, S) **Usage today.** `/sessions` lists, for each soldier: sessions, messages, input (cache writes and reads included), the cached share, output, and cost where the CLI reports one ("—" otherwise). A total row follows.
- **SES-8** (M4; U) **The handoff line is set per soldier** (`handoffAt`). Where the CLI reports a window, the line MUST stay below it.

It is listed after claude-opus in `orchestratorDelegate.md`, whose order is the roster order, as v1 reads it (`src/core/roster.ts`). v1's router breaks ties by that order, so v1 still ranks claude-opus first for reviews and hard builds.
- **ARM-2** (M3; U) **Hard rules** (from v1's design rules). Grok never reviews, and agy never writes. They are enforced when a brief is sent and by each adapter's capabilities. A delegate file can restrict a soldier, never widen it.
  - A brief carries its kind of work (HOST-10). One whose kind the hard rules forbid (a review for grok, a build for agy), or that is not among the soldier's roles, is refused before it is sent, and the refusal says why.
- **ARM-3** (M1; U) **Shadow names** default as 2.0 set them (from 2.0 CFG-3 and CFG-4): Bellion codex-astra, Igris codex-sol, Kaisel claude-opus, Tank claude-opus-build, Iron claude-sonnet, Beru grok and Tusk agy. They can be configured: `shadowName` in `shadow.config.json` sets a soldier's name, and a soldier with neither a default name nor a `shadowName` takes its key. Names are unique without regard to case, and no name is another soldier's key; a clash is refused at start, naming both soldiers.
- **ARM-4** (M3; R) **Only the Monarch plans and assigns work**; the owner may also send work directly (MSG-7). Soldiers answer, ask and report.
- **ARM-5** (M6; I) **Writes need the build role**, and happen only in the soldier's own worktree, under its claims (from v1's design rules).
- **ARM-6** (M2; I, X, F) **agy runs in a throwaway snapshot.**
  - Every agy session runs in a read-only snapshot of its base, never in a worktree that merges.
  - Any file it writes is discarded and reported as a read-violation (from 2.0 WS-3).
  - The checkout guard covers each agy turn, from the moment its message goes in until the turn is over (PO-8). That is its `result` once nothing the turn started is still running, or, when no `result` can come, the moment its process tree has been ended. Between turns agy is idle, and the owner and the Monarch edit the checkout freely (HOST-13, →M5).
  - The guard also hashes these paths, even where git ignores them or doesn't track them (from 2.0 GUARD-2, less its vendor home configs; the user's global git config is WSP-10's): the shared git config, `hooks/` and `info/`, and each worktree's metadata; `.githooks/`, `.claude/`, `.mcp.json` and `.env*`; and `AGENTS.md`, `CLAUDE.md`, `shadow.config.json`, `orchestratorDelegate.md`, `rules.md` and `agent.md`.
  - During a turn, a change to the checkout is trusted only when records explain it:
    - Shadow Army's journaled applies and undos (2.0 GUARD-3);
    - the Monarch's edits through Claude Code's file tools, which the mod records from Claude Code's tool hooks, with each file's hash before and after.

    A path is trusted only if these records explain every change to it during the turn. If anything else also changed it, it is not trusted, even though the Monarch edited it too.
  - Every other change goes to the owner on an attribution card, with each path and its diff (from 2.0 GUARD-4). The owner's own edits and the Monarch's shell commands leave no such record, so their changes come here too. y says the changes are the owner's, and trusts exactly the hashes shown; n fails the turn as a read-violation. The turn's summary waits for the answer.
  - This is enforced by Shadow Army, because agy's own modes do not stop it writing (spike S5).

### 4.8 Workspaces and safety, carried over (WSP)

- **WSP-1** (M6; I) One worktree per soldier per Claude session (from 2.0 WS-1).
- **WSP-2** (M6; I) Claims, and the claim audit at the end of every writing turn (from v1 #16 and 2.0 WS-7). The audit runs once, when the turn is over (PO-8): after any background work the turn left running, and also for a turn that was cut short. It always runs before the soldier's next message.
- **WSP-3** (M6; I, F) Link safety everywhere: nothing is deleted or reverted through a link (from 2.0 SAFE-8, SAFE-9 and SAFE-12, and v1 #36 and #58).
- **WSP-4** (M6; I) The checkout guard (from v1 #22, and 2.0 GUARD-1 to GUARD-4). It covers every soldier's turns, with the scope, the trusted records and the attribution card that ARM-6 gives agy.
- **WSP-5** (M6; I, F) Applying a soldier's work to the folder is all-or-nothing, and it can be undone (from 2.0 WS-8 and WS-9, v1 #28, and #53).
  - This holds even when a write fails after the check has passed. Before writing, the apply copies the bytes of every file it will touch, and the git index; on any failure it restores them exactly, and removes files it created.
  - Undo works the same way.
  - If the restore itself fails, the report names every file still changed and does not say the folder is unchanged.
  - v1's `src/workspace/apply.ts` assumes `git apply` is atomic, which this requirement does not.
- **WSP-6** (M6; I) Work starts from the folder as it is, so follow-up work sees changes applied earlier (from 2.0 WS-5 and #32).
- **WSP-7** (M6; I) No soldier code runs while the harness runs git (from 2.0 SAFE-11). Background work a turn left running counts as the soldier's code until it has ended or been stopped (PO-8). A session service does not: harness git never waits for one (PO-8).
- **WSP-8** (M1; U) `redact()` runs on every write to logs, records (reports included) and briefs, and on every event the post office sends the mod, where each streamed fragment is redacted on its own (from 2.0 SAFE-6). Fixtures are redacted as VER-4 (→M2) says. 2.0's pruning after 30 days is not carried: logs are kept until the owner deletes them.
  - It replaces with `[redacted]`: the Monarch's secret and each soldier credential, in any letter case; a `Bearer` token and an `Authorization` header's value; a private key block, from its `-----BEGIN` line to its `-----END` line; a key that starts `sk-` (`sk-ant-` included) or GitHub's `ghp_`, `gho_`, `ghu_`, `ghs_` or `ghr_`, followed by at least 12 more letters, digits, `-` or `_`; and the value given to a name that ends in `key`, `token`, `secret`, `password` or `credential`, in any case, with or without `_` or `-`, as in `AWS_SECRET_ACCESS_KEY=…` or `"access_token": "…"`, in `key=value`, `key: value` and JSON. A count such as `input_tokens` is kept. The unit test has one case for each kind, with its source.
- **WSP-9** (M6; I, S) **Diff and apply from the mod** (from v1 `sa apply`, #28).
  - `/diff <soldier>` and d in the pane show the soldier's changes on its branch since its base.
  - `/apply <soldier>` applies them to the folder as WSP-5 says, and `/apply undo` undoes the last apply.
- **WSP-10** (M1; X, F) **Harness git runs nothing the repository names** (from 2.0 GIT-1 to GIT-4, and GUARD-2). Every git command Shadow Army runs, such as the one that makes a snapshot or a worktree, the guard's and the claim audit's:
  - turns off hooks: `core.hooksPath` names an empty folder Shadow Army keeps (2.0 GIT-1), and `hook.<event>.enabled` is false for each hook event the command can fire, so hooks defined in git's config stay off too;
  - turns off the file system monitor (`core.fsmonitor`), the pager, signing, external diffs and text conversion, as 2.0 GIT-1 lists, with `--no-optional-locks`;
  - passes the owner's line-ending, link and `filter.*` settings as they were when the post office started (2.0 GIT-2): a filter set then is the owner's, and runs;
  - commits with `--no-verify` (2.0 GIT-4);
  - runs a git found by its absolute path on `PATH` alone, as CH-1 starts each CLI, never one in the folder, a worktree or a snapshot.

  Before and after each command, the config git reads for that repository (every scope but the command line, includes followed, and any `config.worktree`), the shared `hooks/` and `info/`, and each worktree's metadata are compared with the state Shadow Army last trusted: their state when the post office started, or as the owner last accepted it (2.0 GIT-3). Changes to `branch.*` and `remote.*`, such as `git push -u` makes, don't count.
  - Any other change holds harness git for that repository until the owner answers it on the guard's attribution card (ARM-6, →M2): y trusts the state shown, and harness git goes on; n keeps it held. In M1, before that card exists, the post office's log names the change, Claude's transcript gets one line saying harness git is held and why, and harness git stays held until the post office restarts.
  - While harness git is held, a soldier that needs a snapshot or a worktree does not start, and its log says why. A turn that needs harness git to finish ends interrupted, with the change named (MSG-4, →M3), and the soldier's queue is held (MSG-3, →M3). Once harness git goes on, that turn's guard and audit run before anything else (PO-8, →M2).
- **WSP-11** (M1; I, F) **Before a soldier has its worktree** (from v1's design rules). Until WSP-1 (→M6) gives each soldier its worktree, each session opens in its own throwaway snapshot of HEAD under `.shadow/v2/`, made by harness git (WSP-10) when the session opens and removed when it closes.
  - A restart that opens a fresh session (PO-1) gets a new snapshot. A resumed session (CH-9, →M2) keeps its snapshot, so the paths in its history still hold.
  - A soldier whose snapshot can't be made does not start, and its log says why; it never runs in the folder itself.
  - A file it writes in its snapshot is discarded before its next turn and reported as a read-violation, as ARM-6 (→M2) says for agy.
  - The checkout guard covers each of its turns, from the moment its message goes in until its end event, or until its process tree has been ended. It covers the checkout and the paths that ARM-6 (→M2) hashes. Until the attribution card exists, any change it finds fails the turn: the soldier's log names each path, and Claude's transcript gets one line.

### 4.9 Security (SEC)

- **SEC-1** (M1; X) A test proves that no listening socket is reachable on a non-loopback address (PO-2).
- **SEC-2** (M1; X) A test proves that a request without the Monarch's credential, or with a wrong one, reaches no soldier and is reported, and that the credential appears in no file, command line or environment variable (PO-3).
- **SEC-3** (M2; X, R) No code path answers a vendor's approval request without the owner (CH-6, HOST-12, →M5), except the cancellation that closes it when the post office shuts down (PO-7). A stop's cancellation is the owner's answer. Neither approves anything (CH-6).
- **SEC-4** (M1; X) Logs and records hold nothing that `redact()` matches (WSP-8): the secrets Shadow Army holds by value, the Monarch's secret (PO-3) and each soldier credential (PO-4, →M3), in any encoding it uses for them, and each kind WSP-8 lists. A test writes each kind and finds none of it in a log or a record. Any other secret a soldier's CLI writes into its session, such as a value it read from a file or its environment, is logged as the CLI wrote it, as the CLI's own transcript keeps it: a stated residual risk.
- **SEC-5** (M3; X) A test proves that a valid soldier credential cannot issue any Monarch command, read the event stream, read another soldier's session, log or record, or send under another soldier's name, and that no soldier credential appears on the command line of any process the post office starts (PO-4).
- **SEC-6** (M1; U, X) **Text the mod shows** (from 2.0 SAFE-7). In text from a soldier, a CLI or a config file, each character of Unicode's control (Cc) and format (Cf) categories, except newline and tab, shows as a visible placeholder such as `\u{1b}` or `\u{202e}` wherever the mod draws it, and reaches Claude escaped the same way. That covers ESC, and so every escape sequence, as well as the bidirectional controls and the zero-width characters. Every other character is kept, so an approval request is still shown word for word (CH-6, →M2). A test draws a line holding each kind and finds only placeholders.

### 4.10 Visual design (VIS)

- **VIS-1** (M5; S) The v2 design canvas is the visual reference. v1's foundations carry over (from v1's design canvas, its "v1 reference" pages): tokens, type, glyphs and the ASCII profile. The canvas illustrates this spec: where the two disagree, this spec wins, and the canvas is redrawn.

A state is never shown by colour alone. A state that needs the owner keeps its word wherever it shows, and in the strip it shows the short word below (HOST-6).
  - **Soldier states**, one at a time, in this order of precedence:

    | handoff ready | ⇥ | `>` | handoff | its handoff card waits for the owner |

    | preparing handoff | ⇥ | `>` | | it is writing its handoff summary |
    | stopping | ■ | `#` | | the owner stopped its turn, and its CLI is ending it (MSG-9) |
    | working | ◐ | `\|` | | a turn is running, its background work included (PO-8) |
    | near handoff | ⚠ | `!` | | its context size is at 90% of the handoff line or more (SES-3) |

    | not started | · | `.` | | configured, but not started in this Claude session |

    Near handoff and cold also show beside working or idle, as a second glyph. Working turns through ◐ ◓ ◑ ◒ (ASCII `| / - \`), and stays on ◐ with reduced motion (VIS-4).
  - **Connections:** live ● (`@`), connecting ◌ (`-`), reconnecting ◐ (`|`), down ✗ (`x`) after three failed tries, and log in needed ⚠ (`!`).
  - **Messages**, as MSG-4 names them: queued … (`~`), delivered → (`>`), answered ✓ (`+`), interrupted ■ (`#`), not delivered ✗ (`x`) and cancelled − (`-`). Held is a state of the queue, not of a message: a message in a held queue is still queued, and its row shows ⏸ held (`=`) in place of ….
  - The mod's transcript rows start with ▌ (`|`), and a meter marks the handoff line with │ (`|`).
- **VIS-3** (M5; S) Every surface is drawn for terminals of 144, 110 and 80 columns and 24 rows, at the width Claude Code gives it there (section 5.1, S). A card that asks for a decision keeps its question and its keys in view, and the session above it scrolls. The pane is assumed to be 56 columns when docked, and reflows down to 44. Names are never dropped where a soldier is shown; the strip shortens them to tags and folds them as HOST-6 says (from 2.0 UX-9, without its model in the strip).
- **VIS-4** (M5; S) Only the working spinner moves. With reduced motion it stays on ◐.
- **VIS-5** (M5; R) All text is original, with no Claude Code branding.
- **VIS-6** (M5; U, S) **Tags.** Each soldier has a two-letter tag, unique in the army, used where its name does not fit.
  - By default a tag is the name's first letter, then the earliest later letter of the name that no earlier soldier in roster order has used with that first letter. With Beru before Bellion: Iron Ir, Igris Ig, Beru Be, Bellion Bl.
  - `tag` in `shadow.config.json` pins a soldier's tag. A duplicate is refused at start.
  - `/army` lists every tag.

### 4.11 Settings (SET)

- **SET-1** (M4; U) `shadow.config.json` gains `handoffAt` and an optional `cacheLifetime` for each soldier. `handoffAt` has a documented default, and `cacheLifetime` overrides the lifetime SES-6 would otherwise use. Both are validated at start.

### 5.1 Levels

- **Contract tests (C).** For each CLI, the owner records real sessions:
  - the two-prompt task (L, below); for claude, followed in the same session by "Use a subagent to count the lines in package.json.", so that the recording has three turns and a subagent's messages (M1-AC3);

A fixture carries the CLI version it was recorded with (CH-8), and is recorded again when its adapter is changed for a newer version of its CLI. Until then, a newer CLI connects with CH-8's warning.
- **Integration tests (I).** Fake claude, codex, grok and agy executables speak each wire protocol with scripted turns. The post office runs end to end against them:
  - briefs, queueing and summaries;
  - stopping a turn, also while an approval request is open, and cancelling or changing a queued message;
  - sending again a message that was not delivered, and refusing to send again one that was interrupted;
  - soldier-to-soldier messages;
  - handoff and fresh sessions;
  - crash, restart and resume.
- **Security tests (X).**
  - Binding to a non-loopback address is refused.
  - A missing or wrong secret is refused and reported.
  - Logs are redacted.
  - The mod has no approval path.
  - A repository whose shared config names an fsmonitor command, a pager, a signing program and an external diff, with every hook present, as files and in the config: no harness git command runs any of them. A filter added after the post office started, in any config scope, never runs, because the change holds harness git first; one set at start is the owner's, and runs (WSP-10).
- **Fault tests (F):**
  - a CLI killed mid-turn, in the middle of a tool call;
  - a rate limit, a context overflow and a refusal, each told apart;
  - a CLI that leaves a child process running, and one whose child starts a new session and forks twice;
  - a turn that changes the checkout and ends without its end event, and an end event read after it ended;
  - a turn whose end event comes while a child it started keeps writing;
  - a queued message ready just as the CLI starts a turn by itself after background work;
  - a session service the CLI starts during a turn and keeps, and a job such a service starts for a tool call;
  - a turn its CLI reports as failed after it changed a file;
  - a CLI whose turn does not end after a stop;
  - the mod's renewals stopping; a sleep, a suspended or stalled post office, a stopped mod and a wall-clock change, on a fake clock (PO-7);
  - the lease lapsing, and the session ending, while an approval request, an attribution card and a queued message are open;
  - the post office killed mid-turn, with a message queued, an approval request open and a child running;
  - a mod reload mid-turn: the old post office ends, its turns are cut short, and the new mod instance starts its own at the next use;
  - a soldier disconnected with a message queued;
  - a malformed or split JSON line: a split line is joined, a malformed one is shown and the session carries on, and ten in a row count as a lost connection;
  - a slow first token: a CLI that answers 5 s inside its startup bound, and one silent for 10 minutes mid-turn, run on; one that never answers is restarted as after a crash;
  - an expired login: the channel is never restarted, whether the CLI keeps running or exits, and the soldier shows "log in" until r;
  - a cache going cold, on a fake clock, also across a sleep longer than its lifetime and with the wall clock set back and forward an hour;
  - a failed log write: the turn goes on, the failure is reported once, and the log resumes with the count of lost lines;
  - a record that can't be written as its message is about to go, and a record line cut off by a crash;
  - a broken link in a worktree.
- **Screen snapshots (S).** The mod's render trees are rendered for terminals of 144, 110 and 80 columns and 24 rows, and in the ASCII profile, and compared with committed snapshots that follow the canvas. Each tree is rendered at the size Claude Code gives it there (`bodyColumns`): the pane docked at 56 columns, inline at up to 72, and at 44 (VIS-3); the strip at its column's width less the band's five-column mark, both alone and beside the docked pane, where a terminal of 110 leaves it under 50 columns.
- **Live checks (L).** The owner runs the two-prompt task on each CLI, in a clean checkout of the commit under test, once through a live session and once through the CLI's own headless run, with the same model, effort and autonomy:
  - **The task.** First "Read README.md and package.json, and say what this project is.", then, in the same session, "Which of those two files has more lines?".
  - **The headless run.** The CLI's own one-shot command with JSON output, keeping its session: `claude -p --output-format json`, `codex exec --json`, `grok --prompt-file <file> --output-format json` and `agy -p --output-format json`. Its follow-up continues that session by id through the CLI's own option: claude `--resume`, codex `exec resume`, grok `--resume` and agy `--conversation`. The exact commands are recorded with the check (VER-8).
  - **The measure.** For each run, the sum over both prompts of every model request's input tokens, whether uncached, written to the cache or read from it, and its output tokens. Requests are counted one by one, by their ids where the CLI gives them, never from a running total: a running total is turned into each turn's share by taking off the total before it. For claude, whose per-message output count is a placeholder, each turn's own figures are taken as CH-2 defines them instead, and the headless follow-up's tokens are its resumed total less the first run's.
  - **A pass.** The live total is at most 1.05 times the headless total, and the live follow-up reads neither file: no tool call in it opens either one, a shell command such as `wc -l` included. A run that fails either test is repeated twice, both ways, and then passes if the median of the three live totals is at most 1.05 times the median of the three headless ones, and at most one of the three live follow-ups read a file.

  The budget is at most $2 of reported cost per release.
- **Review (R).** The PR reviewer confirms the requirement in the code, citing file and line.

### 5.2 Rules

- **VER-1** (M1; R) **No live model calls in CI.** Live checks are the owner's.
- **VER-2** (M1; R) **Three systems.** CI runs every test level except L and R on ubuntu, macos and windows.
- **VER-3** (M1; R) **Tests come with the change.** A requirement's tests land in the same PR as its code.
- **VER-4** (M2; R) **Fixture provenance.** Contract fixtures are recorded from real CLIs by the owner, and record their date, CLI version and model. They are redacted before they are committed.
- **VER-5** (M1; U) **Fake CLIs.** Fakes live in `test/fakes/` and are chosen through configuration: the test runner puts `test/fakes/` first on `PATH`, as an absolute path, so the product starts a fake exactly as it starts the real CLI (CH-1). No option or setting in the product names a fake, and `shadow.config.json` never names an executable.
- **VER-6** (M1; R) **Coverage.** CI fails unless both of these hold:
  - the post office and the channels keep at least 85% line coverage, counted over the three systems' runs together (VER-2): a line is covered when any system's run covers it;
  - the security code has every line and every branch covered: making, handing over and checking the Monarch's credential (PO-3), the loopback-only rule (PO-2), and `redact()` (WSP-8), in the post office and in the mod. That code sits in files of its own, so the rule covers exactly it.

  Code that a child process runs lives in a file of its own, never in a string, so its lines count like any other. Code in another language, such as a native helper or a PowerShell script, keeps the same bars through that language's own coverage tool, counted over the systems it runs on (VER-2). No code is left out of the count, and neither bar is lowered, to pass.
- **VER-7** (M1; U) **Traceability in CI.** `scripts/check-spec-trace.mjs` checks Appendix B in CI and fails the build on a gap. Each test names the requirement or AC IDs it verifies, in its title or a comment beside it, and the script also fails when a requirement of the current milestone or an earlier one, with U, C, I, X, F or S evidence, is named by no test, or when a test names an ID this spec doesn't have. CI names the current milestone. R and L evidence is recorded on the PR (VER-8, →M2, and section 6).
- **VER-8** (M2; R) **Live checks are recorded.** Each live check is written up on its milestone's PR: CLI version, tokens, pass or fail.
- **VER-9** (M1, M2; L) **Live parity.** For each CLI, the owner runs the two-prompt task through a live session. It passes as section 5.1's live checks say.
- **VER-10** (M6; L) **Live on every system.** Before v2.0.0, the owner runs the army live on Linux and on macOS, each in its own terminal, as well as on Windows: a brief answered, a turn stopped, and a change applied and undone, with the pane, the strip and the decisions list drawn. Each run is written up as VER-8 says.

### 5.3 Leaving v1 behind (LEG)

## 8. Open questions

- **Q1** Should the army offer an opt-in that keeps the Monarch from writing in the checkout? The default (HOST-13) leaves Claude's permissions to the owner.
- **Q2** (answered by spike S2) What does waking the Monarch cost, and should it be on by default? A wake is one request at the Monarch's context size, mostly cache reads. MSG-8 wakes Claude only when a brief asks for a reply, and `send` asks by default.
- **Q3** Grok's 500k window is an opt-in setting. Does Grok charge more per token for long requests?
- **Q4** Will agy gain an instructions slot, or an approval protocol in headless mode? CH-5 and CH-6 change if it does.
- **Q5** The official ACP adapters for Claude Code and Codex: do they keep the vendor harness as installed? If so, they could replace our inward adapters.
- **Q6** (answered by VER-10) POSIX and macOS terminals need a live check before v2.0.0.
- **Q7** codex can add to a running turn (`turn/steer`). Should v2 offer "redirect without stopping" where a CLI allows it? Spike S6 looks at each CLI.
- **Q8** M1's draft (#75) stops processes from escaping a closing session (PO-1) with a small C helper, compiled on the owner's machine the first time a session starts on Linux or macOS. It needs a C compiler there (on macOS, Xcode's command-line tools). On macOS it reads process details through structures Apple doesn't publish, so an update could break it; then it refuses to start a soldier rather than run one uncontained. Keep it, ship the helper prebuilt for each system and processor, or contain processes another way? Decide before v2.0.0.
- **Q9** How does a claude soldier take its `send` credential with nothing on its command line or on disk: `setMcpServers` over its stream-json input, or a `headersHelper`? A probe settles it before M3 (PO-4).

## Appendix B: Traceability rules

4. Every acceptance criterion cites at least one requirement ID, and every requirement in a milestone's Implements is cited by one of that milestone's ACs.

8. An acceptance criterion relies only on requirements of its own milestone or an earlier one. Where an AC, or a requirement an AC cites, cites a requirement of a later milestone than its own (for a requirement with two milestones, its last), the citation is marked `→Mx` with the cited requirement's milestone, as in `(CH-9, →M2)` or `CH-9 (→M2)`, and the part it governs is verified in that milestone. The check covers every ID an AC names and every ID named by a requirement the AC cites.
9. Every requirement of the current milestone or an earlier one with U, C, I, X, F or S evidence is named by at least one test, and every ID a test names is in this spec. This rule needs the code, so it is checked in CI only (VER-7).
