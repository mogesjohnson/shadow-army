## 0. Reading this spec

- **Requirement words.** MUST, MUST NOT, SHOULD and MAY mean what RFC 2119 and RFC 8174 say, and only when capitalized.
- **Requirement IDs.** Each requirement has an ID such as `PO-2`. IDs are stable and never reused. A dropped requirement stays in place, marked *withdrawn*.
- **Milestone and evidence.** Each requirement names the milestone that implements it and the kinds of evidence that verify it (section 5):

  | Code | Evidence |
  |---|---|
  | U | unit test |
  | C | contract test |
  | I | integration test |
  | X | security test |
  | F | fault test |
  | S | screen snapshot |
  | L | live check by the owner |
  | R | review |

- **Carried over.** Requirements carried over from v1 or 2.0 name their source. The archived 2.0 text is the reference for their detail, unless this spec restates it.
- **Traceability.** Appendix B gives the rules, and a script checks them in CI (VER-7).

## 1. Goals and non-goals

Goals:

- **G1 Claude is the Monarch.** The owner's own Claude Code session plans, assigns work and reads summaries. No separate Monarch CLI.
- **G2 Live soldiers.** Each soldier is one long-lived session of its own CLI, in its own worktree, with the vendor's harness exactly as installed.
- **G3 Short messages.** Only briefs and short summaries cross between models, by name. A message is one more turn in an open session, never a new session.
- **G4 Watch and type.** The owner can watch any soldier's session as it runs, and type into it.
- **G5 Visible cost.** Token use is visible and in the owner's hands: a meter per soldier, a cold-cache warning and the 200k handoff.
- **G6 Safe writes.** v1's workspace safety carries over: worktrees, claims, the guard, link safety, apply and undo.
- **G7 Verified.** Every requirement is verified, and the verification is traced in CI.

Non-goals:

- Removing or replacing any part of a vendor's harness to save tokens (ADR-0010).
- A full-screen Ink shell; v1's chat stays in `v1.0.x`.
- Any service reachable from the network.
- Answering a vendor's permission request on the owner's behalf.
- Cost figures beyond what each CLI reports.

## 2. Glossary

- **Monarch:** the owner's Claude Code session, which leads the army.
- **Soldier:** one configured CLI and model, with a shadow name (Iron, Igris, Beru, Tusk, Kaisel, Bellion, Tank).
- **Post office:** the local helper process that holds the soldiers' sessions and carries messages between them.
- **Channel:** the post office's connection to one soldier, through that CLI's own live-session interface.
- **Live session:** one open conversation in a soldier's CLI. Each message adds one turn.
- **Brief:** a message that assigns work.
- **Summary:** a reply of at most five lines.
- **Report:** a soldier's full reply, kept on disk.
- **Standing instructions:** what a soldier is told once per session: who it is, the team, the rules and the reply format.
- **Context size:** the input tokens of the session's most recent model request.
- **Handoff line:** the context size at which a soldier hands off, 200,000 tokens by default.
- **Cold:** a session idle longer than its provider keeps the prompt cache. Its next message re-sends the whole history at full price.
- **Mod:** Shadow Army's Claude Code plugin: a pane, an army strip, a status entry, toasts, commands and tools.

## 3. Architecture

```
owner ──► Claude Code (the Monarch) ──► the mod ──► the post office ──► channels ──► soldier CLIs
            transcript, prompt           pane, strip,    127.0.0.1 + secret    one per CLI    each in its own
                                         commands, tools                                       worktree
```

- **The mod starts the post office** and reads its event stream: every soldier's turns, states and usage. The mod draws those events in the pane and the strip.
- **The mod sends commands and messages over the post office's local endpoint**, which needs the secret.
- **Soldiers reach the post office through one MCP tool, `send`.** It is added to each soldier through that CLI's own MCP configuration.
- **Files travel only through worktree branches.** Messages carry words, never file contents.

**Why a separate process.** A mod can start a process and read its output for as long as it runs. But the process's input is written once and then closed, so a mod cannot hold a session open by itself. The post office holds the sessions, and the mod talks to it.

## 4. Requirements

### 4.1 The mod (HOST)

- **HOST-1** (M5; R) Shadow Army ships the mod as a plugin in this repository, loaded with `--plugin-dir` or installed from this repository. It MUST NOT depend on a marketplace plugin.
- **HOST-2** (M1; I) The mod starts the post office the first time the army is used in a session, and stops it when the session ends. There is at most one post office per folder.
- **HOST-3** (M5; S, I) **The pane.**
  - It opens by itself only when a soldier needs the owner, and only when the terminal is at least 144 columns wide; it then docks beside the transcript.
  - Below 144 columns it opens only when asked (`/pane`, or ctrl+x tab after a toast), inline above the prompt and at most 72 columns wide.
  - It reflows to the width Claude Code gives it.
- **HOST-4** (M5; S) **The pane's content**, top to bottom:
  - tabs, one per soldier;
  - a header with name · id · model (never dropped) and the state with its word;
  - the meter;
  - the live session (thinking, tool calls, replies);
  - the message field;
  - the keys row.
- **HOST-5** (M5; I, S) **Keys in the pane:**
  - j and l (or ← →) switch tabs; i and k (or ↑ ↓) scroll.
  - Enter or Tab goes into the field, and Enter sends.
  - Esc leaves the field, and Esc again closes the pane.
  - The keys are button hotkeys, as the mod API provides; Claude Code's ctrl+x tab moves the keyboard into the pane.
- **HOST-6** (M5; S) **The army strip** is one line above the prompt.
  - It lists every soldier in roster order, each with its state glyph and name in its colour, plus a five-cell meter and its tokens as the width allows.
  - The meters drop first, then the tokens, then names become initials. Glyphs never drop.
  - A soldier waiting on the owner shows the word "waiting" at every width.
- **HOST-7** (M5; U) **The status-line entry** is one plain-text entry, with the most urgent fact first.
- **HOST-8** (M5; U) **Toasts** appear only for these, and only while the pane is closed:
  - a soldier waiting on the owner;
  - a handoff ready;
  - a disconnection;
  - a CLI that needs a login;
  - a failed brief.
- **HOST-9** (M5; U, S) **Commands:** `/army`, `/send <soldier> <message>`, `/pane [soldier]`, `/fresh <soldier>`, `/handoff <soldier>`, `/sessions` and `/mode [ask|auto|plan|terminal|dark|light]`.
  - Their names, argument hints and descriptions are as on the canvas's Commands page.
  - An unknown soldier name suggests the closest one and sends nothing.
- **HOST-10** (M3; I) **The mod gives Claude a `send` tool** (soldier, brief, wantReply).
  - It returns once the brief is delivered.
  - The summary arrives later as a summary card in Claude's conversation (MSG-5, MSG-8).
- **HOST-11** (M3; S) **The mod's rows in Claude's transcript:**
  - one row per brief, with its delivery state;
  - a summary card of at most five lines, plus the report's path;
  - one line for each soldier-to-soldier message and each message the owner typed directly.
- **HOST-12** (M5; R, U) The mod MUST NOT approve a tool call or a permission. It may only observe, or deny.
- **HOST-13** (M5; R) **The Monarch's own Claude Code permissions are the owner's.** The mod does not widen or narrow what Claude may do in the checkout. Soldiers' writes still go through their worktrees (WSP-2).

### 4.2 The post office (PO)

- **PO-1** (M1; I, F) **Supervision.** The post office is one local process per folder, and it supervises every soldier session. A channel that crashes is restarted at most three times; after that it is down until the owner reconnects it.
- **PO-2** (M1; X) **Local only.** The post office and every port a channel opens MUST bind to the loopback address (127.0.0.1 or ::1). Any other address is refused at start, with an error that says so.
- **PO-3** (M1; X) **The secret.**
  - Every connection MUST present the session secret: 32 random bytes, new each start, held in memory and in a file only the owner can read.
  - A wrong or missing secret is refused, and the refusal is reported.
  - The secret is never printed whole; at most its last four characters are shown.
- **PO-4** (M3; C, I, X) **The soldiers' tool.** The post office serves soldiers one MCP tool, `send(to, text)`, over local HTTP with the secret as a bearer token. It is added to each soldier through that CLI's own MCP configuration, adding to it and never replacing it (spike S4).
- **PO-5** (M1; U) **Logs.** The post office keeps an append-only log for itself and one for each soldier's session, under `.shadow/v2/logs/`. Every write passes through `redact()` (WSP-8).
- **PO-6** (M3; U) **Records.** Every brief, summary and message is stored with its id, time, sender, recipient and delivery state. Full reports go under `.shadow/reports/`.
- **PO-7** (M1; I) **Shutdown.** When the Claude session ends, the post office closes every soldier session through that CLI's own exit, and leaves the worktrees and branches in place.

### 4.3 Channels (CH)

- **CH-1** (M1; U, C) **One interface.** Each CLI has one adapter, and all adapters share one interface.
  - The interface: open a session in a worktree with the standing instructions; send a message; stream events; close.
  - Events: text, thinking, tool call, tool result, approval request, usage, turn end, error.
- **CH-2** (M1; C, L) **claude.**
  - One long-lived `claude -p --input-format stream-json --output-format stream-json --verbose` process per soldier.
  - The instructions go in `--append-system-prompt`.
  - A turn ends with the `result` event.
  - The context size is the last assistant message's usage; the turn totals come from `result`.
- **CH-3** (M2; C, L) **codex.**
  - `codex app-server` over stdio: `thread/start` with `developerInstructions`, then `turn/start` for each message.
  - A turn ends with `turn/completed`.
  - Usage and the context window come from `thread/tokenUsage/updated`.
- **CH-4** (M2; C, L) **grok.**
  - `grok agent stdio`, or `grok agent serve` bound to the loopback with a secret.
  - `session/new` carries the instructions in `_meta.rules`, and `session/prompt` sends each message.
  - Usage comes from the prompt result's `_meta.usage`.
- **CH-5** (M2; C, L) **agy.**
  - One long-lived `agy --input-format stream-json --output-format stream-json` process, whose messages are `{"event":"user",…}`.
  - The instructions lead the first message, because agy has no slot for them.
  - A turn ends with the `result` event. Its usage is a running total, and its input excludes cached tokens.
- **CH-6** (M2; C, I) **Approval relay.**
  - A CLI's permission request is shown word for word, with the CLI's own options, and the owner's answer goes back unchanged.
  - No adapter answers a request by itself. An unanswered request stays pending (spike S5).
- **CH-7** (M1; R, U) **The harness stays whole.**
  - No adapter replaces a system prompt, removes a tool or passes a flag that disables a safeguard.
  - Autonomy chooses only each vendor's documented flags (from 2.0 SAFE-10).
- **CH-8** (M2; U) **Versions.**
  - Each adapter records the CLI version its contract fixtures were recorded with.
  - A newer version connects, with a warning card.
  - A line that cannot be parsed is an error, never silently dropped.
- **CH-9** (M4; C) **Resume.** After a crash, a channel reopens the soldier's previous session by id where the CLI supports it: claude `--resume`, codex `thread/resume`, grok `session/load`, agy `--conversation`.

### 4.4 Standing instructions (SI)

- **SI-1** (M1; U) **Content.**
  - The soldier's shadow name, model and roles.
  - The whole team with their roles, and Claude as the Monarch.
  - The hard rules (ARM-2), `rules.md`, and the soldier's `agent.md` section.
  - The reply format: at most five lines (what was done, which files, what to check).
  - The handoff instruction (SES-4).
- **SI-2** (M1, M2; C) **Injection.** The instructions go in through each CLI's append slot (CH-2 to CH-5) and MUST NOT replace the vendor's prompt. agy's first-message fallback shows in the post office view.
- **SI-3** (M1; U) **Size.** The instructions stay under 1,500 tokens; they measured about 1,000 on 2026-10-07.
- **SI-4** (M4; I) **Fresh sessions.** A fresh session receives the instructions again, with the handoff summary when there is one.

### 4.5 Messaging (MSG)

- **MSG-1** (M3; R, I) **Only briefs and summaries cross between models.** A message never carries a transcript or a file's contents; files travel through branches. This carries over v1's isolation rule.
- **MSG-2** (M3; U) **Names.** A message is addressed by shadow name, case-insensitively. An unknown name suggests the closest one, and nothing is sent.
- **MSG-3** (M3; I) **One turn.** A message is one turn in the recipient's open session. A message to a soldier that is mid-turn is queued, and the queue runs first in, first out for each soldier.
- **MSG-4** (M3; U, S) **Delivery states.** Every message moves through queued, delivered and answered, or ends as failed with a reason. The state updates in place.
- **MSG-5** (M3; U, I) **Summaries.**
  - A summary has at most five lines. A longer reply is cut with …, and the whole reply is saved as the report.
  - The summary goes back to whoever sent the message.
  - For the Monarch, it is added to Claude's conversation as a summary card.
- **MSG-6** (M3; I) **Soldier to soldier.** Soldiers message each other through `send` (PO-4). Both panes show the message in full; Claude's transcript gets one line. A soldier MUST NOT assign work to another; only the Monarch briefs.
- **MSG-7** (M3; I) **The owner, directly.** The owner types into a soldier through the pane's field or `/send`, as "you". Claude's transcript gets one line saying that soldier's context changed.
- **MSG-8** (M3; I, L) **Waking the Monarch.** When a summary arrives and Claude is idle, the mod starts a turn only if the brief asked for a reply. The `send` tool asks for one by default. Otherwise the card waits for Claude's next turn (spike S2).

### 4.6 Sessions (SES)

- **SES-1** (M4; I) **One session per soldier.** Each soldier has one open session per Claude session, and related work accumulates in it.
- **SES-2** (M4; U, S) **The meter.**
  - It shows the context size from the CLI's own events, as a bar up to the handoff line, with colour steps at 30, 50, 70 and 90%.
  - The share of the window shows only where the CLI reports its window.
- **SES-3** (M4; U) **Near handoff.** At 90% of the handoff line (180k by default), the soldier shows "near handoff".
- **SES-4** (M4; I, S) **Handoff.**
  - At the handoff line, the soldier is asked for a handoff summary covering: working on, done, decided, files, open.
  - A card in its pane offers accept (a fresh session with the summary), edit first, or keep going, which asks again after 20k more.
  - Messages to that soldier queue until the owner chooses.
- **SES-5** (M4; I) **Start fresh.**
  - `/fresh` or f in the pane closes the session, keeps its log, and starts a new one with the standing instructions.
  - The soldier's work stays on its branch, and nothing is reverted.
  - A handoff first is optional.
- **SES-6** (M4; U, S) **Cold.**
  - A session is cold once it has been idle longer than its provider's cache lifetime.
  - Before a message goes to a cold soldier, the field says how many tokens that message will re-send.
  - Cache lifetimes are set per CLI, with defaults from spike S3.
- **SES-7** (M4; U, S) **Usage today.** `/sessions` lists, for each soldier: sessions, messages, input (cached included), the cached share, output, and cost where the CLI reports one ("—" otherwise). A total row follows.
- **SES-8** (M4; U) **The handoff line is set per soldier** (`handoffAt`). Where the CLI reports a window, the line MUST stay below it.

### 4.7 The army and its rules (ARM)

- **ARM-1** (M1; U) **The roster carries over.** Roles, cost, `forbidden` and `write` live in `orchestratorDelegate.md`; `cli`, `model` and `autonomy` live in `shadow.config.json`. Both files list the same soldiers.
- **ARM-2** (M3; U) **Hard rules.** Grok never reviews, and agy never writes. They are enforced when a brief is sent and by each adapter's capabilities. A delegate file can restrict a soldier, never widen it.
- **ARM-3** (M1; U) **Shadow names** default as in 2.0's CFG-4: Bellion codex-astra, Igris codex-sol, Kaisel claude-opus, Tank claude-opus-build, Iron claude-sonnet, Beru grok and Tusk agy. They can be configured.
- **ARM-4** (M3; R) **Only the Monarch plans and assigns work.** Soldiers answer, ask and report.
- **ARM-5** (M6; I) **Writes need the build role**, and happen only in the soldier's own worktree, under its claims.

### 4.8 Workspaces and safety, carried over (WSP)

- **WSP-1** (M6; I) One worktree per soldier per Claude session (from 2.0 WS-1).
- **WSP-2** (M6; I) Claims, and the claim audit at the end of every writing turn (from v1 #16 and 2.0 WS-7).
- **WSP-3** (M6; I, F) Link safety everywhere: nothing is deleted or reverted through a link (from 2.0 SAFE-8, SAFE-9 and SAFE-12, and v1 #36 and #58).
- **WSP-4** (M6; I) The checkout guard (from v1 #22, and 2.0 GUARD-1 to GUARD-3).
- **WSP-5** (M6; I, F) Applying a soldier's work to the folder is all-or-nothing, and it can be undone (from 2.0 WS-8 and WS-9, v1 #28, and #53).
- **WSP-6** (M6; I) Work starts from the folder as it is, so follow-up work sees changes applied earlier (from 2.0 WS-5 and #32).
- **WSP-7** (M6; I) No soldier code runs while the harness runs git (from 2.0 SAFE-11).
- **WSP-8** (M1; U) `redact()` runs on every write to logs, records and briefs (from 2.0 SAFE-6).

### 4.9 Security (SEC)

- **SEC-1** (M1; X) A test proves that no listening socket is reachable on a non-loopback address (PO-2).
- **SEC-2** (M1; X) A test proves that a request without the secret, or with a wrong one, reaches no soldier and is reported (PO-3).
- **SEC-3** (M2; X, R) No code path answers a vendor's approval request without the owner (CH-6, HOST-12).
- **SEC-4** (M1; X) Logs and records hold no secret, token or credential (WSP-8).

### 4.10 Visual design (VIS)

- **VIS-1** (M5; S) The v2 design canvas is the visual reference. v1's foundations carry over: tokens, type, glyphs and the ASCII profile.
- **VIS-2** (M5; S) Soldier, connection and message states use the vocabularies on the canvas's v2 Foundations page. A state is never shown by colour alone, and every glyph has an ASCII fallback.
- **VIS-3** (M5; S) Every surface is drawn for 144, 110 and 80 columns; the pane is assumed to be 56 columns when docked. Names are never dropped (v1 UX-9).
- **VIS-4** (M5; S) Only the working spinner moves. With reduced motion it stays on ◐.
- **VIS-5** (M5; R) All text is original, with no Claude Code branding.

### 4.11 Settings (SET)

- **SET-1** (M4; U) `shadow.config.json` gains `handoffAt` for each soldier and `cacheLifetime` for each CLI. Both have documented defaults and are validated at start.
- **SET-2** (M4; I) **Plugins.**
  - Soldiers start without the owner's personal plugins and connectors, where the CLI can leave them out without touching a vendor tool.
  - The owner can attach one to a soldier: live where the CLI allows, otherwise by a restart that resumes the same session (CH-9).

### 4.12 Observability (OBS)

- **OBS-1** (M5; U) l in the pane opens the soldier's log; the post office's own log is in `/army`.
- **OBS-2** (M3; U) Every brief, summary and message has an id, shown in the expanded row (ctrl+o).
- **OBS-3** (M4; U) Each turn's usage is recorded with the CLI's raw fields kept beside the normalized ones.

## 5. Verification

### 5.1 Levels

- **Unit tests (U).** Pure logic, with vitest:
  - routing and the hard rules;
  - meter maths, thresholds and state precedence;
  - parsers and name matching;
  - `redact()` and config validation.
- **Contract tests (C).** For each CLI, the owner records real sessions once:
  - the two-prompt task;
  - an approval request;
  - an error;
  - a session that goes cold.

  The tests replay each recording through the channel adapter, and the adapter's events MUST match the expected events. A fixture carries the CLI version it was recorded with, and is recorded again when a CLI updates (CH-8).
- **Integration tests (I).** Fake claude, codex, grok and agy executables speak each wire protocol with scripted turns. The post office runs end to end against them:
  - briefs, queueing and summaries;
  - soldier-to-soldier messages;
  - handoff and fresh sessions;
  - crash, restart and resume.
- **Security tests (X).**
  - Binding to a non-loopback address is refused.
  - A missing or wrong secret is refused and reported.
  - Logs are redacted.
  - The mod has no approval path.
- **Fault tests (F):**
  - a CLI killed mid-turn;
  - a malformed or split JSON line;
  - a slow first token;
  - an expired login;
  - a cache going cold, on a fake clock;
  - a failed log write;
  - a broken link in a worktree.
- **Screen snapshots (S).** The mod's render trees are rendered at 144, 110 and 80 columns, and in the ASCII profile, and compared with committed snapshots that follow the canvas.
- **Live checks (L).** The owner runs the two-prompt task on each CLI. A run passes when:
  - the live session's tokens are within 5% of that CLI's own headless run;
  - the follow-up reads no file.

  The budget is at most $2 of reported cost per release.
- **Review (R).** The PR reviewer confirms the requirement in the code, citing file and line.

### 5.2 Rules

- **VER-1** (M1; R) **No live model calls in CI.** Live checks are the owner's.
- **VER-2** (M1; R) **Three systems.** CI runs every test level except L on ubuntu, macos and windows.
- **VER-3** (M1; R) **Tests come with the change.** A requirement's tests land in the same PR as its code.
- **VER-4** (M2; R) **Fixture provenance.** Contract fixtures are recorded from real CLIs by the owner, and record their date, CLI version and model. They are redacted before they are committed.
- **VER-5** (M1; U) **Fake CLIs.** Fakes live in `test/fakes/` and are chosen through configuration, never through a code path that ships in the product.
- **VER-6** (M1; R) **Coverage.** The post office and channels SHOULD keep at least 85% line coverage.
- **VER-7** (M1; U) **Traceability in CI.** `scripts/check-spec-trace.mjs` checks Appendix B in CI and fails the build on a gap.
- **VER-8** (M2; R) **Live checks are recorded.** Each live check is written up on its milestone's PR: CLI version, tokens, pass or fail.

## 6. Milestones

Each milestone is one or more PRs under #63, and each PR maps its ACs to evidence.

### M0: Spikes

Implements: none. It answers the questions the later milestones depend on, each with a short report on #63.

- **S1 The pane.** Pane width at 144, 110 and 80 columns; button hotkeys j, l, i and k; ctrl+x tab; inline placement.
- **S2 Waking the Monarch.** Adding a summary to Claude's conversation, then starting a turn: what it costs and when it is allowed.
- **S3 Usage and caches.** The context-size field and the cache lifetime of each provider, for grok and agy in particular.
- **S4 The send tool.** How each CLI accepts an extra MCP server for `send`: claude `--mcp-config`, codex configuration, grok `session/new` `mcpServers`, agy.
- **S5 Approval relay.** How each channel surfaces a permission request and takes an answer.

### M1: The post office and the claude channel

Implements:
- HOST-2;
- PO-1, PO-2, PO-3, PO-5, PO-7;
- CH-1, CH-2, CH-7;
- SI-1, SI-2, SI-3;
- ARM-1, ARM-3;
- WSP-8;
- SEC-1, SEC-2, SEC-4;
- VER-1, VER-2, VER-3, VER-5, VER-6, VER-7.

- **M1-AC1** The post office starts with the first use of the army and stops with the session. It binds only the loopback address and refuses `0.0.0.0` with an error (PO-1, PO-2, PO-7, HOST-2, SEC-1).
- **M1-AC2** A missing or wrong secret is refused and reported, and the secret never appears whole in output or logs (PO-3, SEC-2, SEC-4, PO-5, WSP-8).
- **M1-AC3** A contract test replays a recorded claude session. It shows two turns in one process, the instructions appended, and turn end, context size and turn usage parsed (CH-1, CH-2, SI-2).
- **M1-AC4** An integration test against a fake claude sends a brief and receives a summary of at most five lines. A crash restarts the channel at most three times (PO-1, CH-1).

- **M1-AC6** The roster and shadow names load from the two config files, and those files list the same soldiers (ARM-1, ARM-3).
- **M1-AC7** CI runs every level except live on three systems. The traceability script runs and passes, and no CI job calls a model (VER-1, VER-2, VER-3, VER-5, VER-6, VER-7).
- **M1-AC8** Live: the owner's claude parity check passes (section 5.1).

### M2: The codex, grok and agy channels

Implements: CH-3, CH-4, CH-5, CH-6, CH-8; SI-2; SEC-3; VER-4, VER-8.

- **M2-AC1** Contract tests replay recorded codex, grok and agy sessions through their adapters, with the instructions injected as CH-3 to CH-5 say (CH-3, CH-4, CH-5, SI-2, VER-4).

## 8. Open questions

- **Q1** Should the army offer an opt-in that keeps the Monarch from writing in the checkout? The default (HOST-13) leaves Claude's permissions to the owner.

- **Q3** Grok's 500k window is an opt-in setting. Does Grok charge more per token for long requests?
- **Q4** Will agy gain an instructions slot? CH-5 changes if it does.
