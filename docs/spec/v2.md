## 0. Reading this spec

- **Requirement words.** MUST, MUST NOT, SHOULD and MAY mean what RFC 2119 and RFC 8174 say, and only when capitalized.
- **Requirement IDs.** Each requirement has an ID such as `PO-2`. IDs are stable and never reused. A dropped requirement stays in place as `- **ID** (withdrawn in v0.N: the reason)`, and Appendix B's rules 2 to 4 skip it.
- **Milestone and evidence.** Each requirement names the milestone that implements it and the kinds of evidence that verify it (section 5):

  | Code | Evidence |
  |---|---|
  | U | unit test |
  | C | contract test |
  | I | integration test |
  | X | security test |
  | F | fault test |
  | S | screen snapshot |
  | L | live check by the owner |
  | R | review |

- **Carried over.** A requirement carried over from v1 or 2.0 names its source as `(from …)`, and Appendix A lists it. This spec governs: a source's detail applies only where this spec says nothing on the point, and never against this spec, an ADR or the design rules. For a 2.0 source the detail is the archived 2.0 text, except 2.0 SAFE-10's "may add restrictions" (Shadow Army never adds or removes a vendor safeguard), SAFE-11's killing of the turn's process group at the end of each turn (CH-2, PO-8), and WS-1's detached worktree (each soldier works on its own branch). For a v1 source it is v1.0.1's code on `legacy/v1`.
- **Traceability.** Appendix B gives the rules, and a script checks them in CI (VER-7).
- **Ideas.** Appendix C sets each of the owner's 118 ideas, and each of the six v2.1 designs, beside what this spec says. It is a reference for review; nothing in it is a requirement.
- **Threat model.** Appendix D sets out the assets, the actors and how far each is trusted, each trust boundary with the requirement that controls it, and the residual risks. Like Appendix C, it is informative.

## 1. Goals and non-goals

Goals:

- **G1 Claude is the Monarch.** The owner's own Claude Code session plans, assigns work and reads summaries. No separate Monarch CLI.
- **G2 Live soldiers.** Each soldier is one long-lived session of its own CLI, in its own worktree, with the vendor's harness exactly as installed.
- **G3 Short messages.** Only briefs and short summaries cross between models, by name. A message is one more turn in an open session, never a new session.
- **G4 Watch and steer.** The owner can watch any soldier's session as it runs, type into it, stop its turn, and change or cancel what waits in its queue.
- **G5 Visible cost.** Token use is visible and in the owner's hands: a meter per soldier, a cold-cache warning and the 200k handoff.
- **G6 Safe writes.** v1's workspace safety carries over: worktrees, claims, the guard, link safety, apply and undo.
- **G7 Verified.** Every requirement is verified, and the verification is traced in CI.

Non-goals:

- Removing or replacing any part of a vendor's harness to save tokens (ADR-0010).
- A full-screen Ink shell; v1's chat stays in `v1.0.x`.
- Any service reachable from the network.
- Answering a vendor's permission request on the owner's behalf.
- Cost figures beyond what each CLI reports.

## 2. Glossary

- **Owner:** the person whose Claude Code session is the Monarch.
- **Monarch:** the owner's Claude Code session, which leads the army.
- **Soldier:** one configured CLI and model, with a shadow name (Iron, Igris, Beru, Tusk, Kaisel, Bellion, Tank).
- **Autonomy:** a soldier's permission level in `shadow.config.json`: `supervised`, `auto` or `full`, as in v1. Among the CLI's flags it chooses only documented ones (CH-7); with `auto` or `full`, a soldier that can't write also runs in a throwaway snapshot (ARM-8); at every level, a read-only turn in a worktree is reverted (WSP-12).
- **Post office:** the local process that holds the soldiers' sessions and carries messages between them.
- **Folder:** the top level of the git working tree the owner's Claude Code session runs in. One post office serves a folder (PO-1). Each working tree of a repository is a folder of its own, a linked one included, and has its own army.
- **Channel:** the post office's connection to one soldier, through that CLI's own live-session interface.
- **Containment:** what holds a soldier's CLI and every process it starts, so that the post office can list them all and end them: a subreaper on Linux, a launchd job's coalition on macOS and a Job Object on Windows (PO-9).
- **Guardian:** the process that holds one session's containment, starts the CLI in it, and ends its tree by itself when the post office is gone: the containment helper on Linux and macOS, Shadow Army's PowerShell script on Windows (PO-9).
- **Containment helper:** the small native program that sets up containment on Linux and macOS. It ships prebuilt in Shadow Army's package: one Linux binary for each supported processor, and one universal macOS binary (PO-12, PO-13).
- **Live session:** one open conversation in a soldier's CLI. Each message adds one turn, and any turn the CLI then takes by itself when that turn's background work ends (PO-8).
- **Queue:** the messages waiting for a soldier's next turn, at most nine (MSG-3). A **held** queue waits for the owner instead of going by itself.
- **Stop:** ending a soldier's running turn while its session stays open with its history. Starting fresh, by contrast, closes the session.
- **Brief:** a message that assigns work.
- **Summary:** a reply of at most five lines of at most 120 characters each (MSG-5).
- **Tag:** a soldier's two-letter short name, unique in the army (VIS-6).
- **Report:** a soldier's full reply, kept on disk, up to 2 MiB (PO-6).
- **Standing instructions:** what a soldier is told once per session: who it is, the team, the rules and the reply format.
- **Context size:** every input token of the session's most recent main model request, whether uncached, written to the cache or read from it: the request that carries the conversation, never an auxiliary call such as a claude subagent's or agy's `checkpoint` step (SES-2).
- **Handoff line:** the context size at which a soldier hands off, 200,000 tokens by default.
- **Cold:** a session idle longer than its provider keeps the prompt cache, or one changed in a way its CLI documents as resetting the cache. Its next message likely pays full price for the whole history again. Cold is always an estimate, made before a message goes (SES-6).
- **Mod:** Shadow Army's Claude Code plugin: a pane, an army strip, a status entry, toasts, commands and tools.
- **Worktree:** a soldier's own git worktree and branch, one per soldier per Claude Code process, unless the soldier runs in a snapshot (WSP-1, ARM-8).
- **Snapshot:** a throwaway copy of HEAD (WSP-11), or of a soldier's base (WSP-6) for agy (ARM-6) and a soldier that can't write (ARM-8), whose writes are discarded and reported.
- **Harness git:** every git command Shadow Army runs itself, such as the one that makes a snapshot, and the guard's and the claim audit's (WSP-10).
- **Checkout guard:** the check that every change to the checkout during a soldier's turn is explained by Shadow Army's records, or else goes to the owner (ARM-6, WSP-4).
- **Claims, claim audit:** the paths a writing turn may change, and the check, once the turn is over, of what it changed against them (WSP-2). A read-only turn in a worktree is audited with no claims (WSP-12).
- **Writing turn, read-only turn:** a turn whose message has the kind build is a writing turn. Every other turn is read-only, and its writes are discarded or reverted (ARM-5).
- **Read-violation:** a write that a read-only turn made in its snapshot or worktree, which is discarded or reverted and reported (WSP-11, WSP-12). Answering n on the attribution card also fails a turn as a read-violation (ARM-6).
- **Attribution card:** the guard's decision on changes no record explains: y says they are the owner's, n fails the turn and leaves the files as they are (ARM-6).
- **Trust card:** the card that asks the owner to accept, by their hashes, the folder's own `shadow.config.json`, `orchestratorDelegate.md`, `rules.md`, `agent.md` and `.mcp.json`, before any soldier starts there (ARM-7).
- **Transcript line:** a notice row in the owner's transcript, which is not added to Claude's conversation and wakes nobody, unless its requirement says it goes to Claude's conversation.

## 3. Architecture

```
owner ──► Claude Code (the Monarch) ──► the mod ──► the post office ──► channels ──► soldier CLIs
            transcript, prompt           pane, strip,    127.0.0.1 + secret    one per soldier  each in its own
                                         commands, tools                                        worktree
```

- **The mod starts the post office** and reads its event stream: every soldier's turns, states and usage. The mod draws those events in the pane and the strip.
- **The mod acts only in the owner's own Claude Code session.** In any other session, a soldier's included, it registers no tool or command, starts no post office, records nothing and draws nothing (HOST-2).
- **The post office decides every state.** Only the post office changes a message's or a soldier's state, one change at a time. Each mod action is a request whose result the mod shows only from the post office's event. A request that lost a race is refused with its reason, such as `already delivered`.
- **The mod gives the post office its secret through standard input at start.** The mod's commands present that secret, and the event stream comes back only over the post office's standard output.
- **Soldiers reach the post office through one MCP tool, `send`.** Each soldier holds its own credential, which allows nothing else. The tool is added to each soldier whose CLI allows it, through that CLI's own MCP configuration (PO-4).
- **Files travel only through worktree branches.** Shadow Army never puts a file's contents or a transcript into a message; a message carries only what its sender wrote.

**Why a separate process.** A mod can start a process and read its output for as long as it runs. But the process's input is written once and then closed, so a mod cannot hold a session open by itself. The post office holds the sessions, and the mod talks to it.

## 4. Requirements

### 4.1 The mod (HOST)

- **HOST-1** (M5; R) Shadow Army ships the mod as a plugin in this repository, loaded with `--plugin-dir` or installed from this repository. It MUST NOT depend on a marketplace plugin.
- **HOST-2** (M1; I, C, L) The mod starts the post office the first time the army is used, and again at the first use after it has shut down (PO-7). It stops it when the owner's Claude Code process ends, or at a `session.end` that ends the army, such as `/logout`'s; `/clear`, `/resume` and `/branch` keep it running, with its soldiers' sessions (PO-7). There is at most one post office per folder (PO-1).
  - In M1 the first use is `/army`, which the mod registers from M1 in the list form that HOST-9 (→M5) gives it, or `sa live`, the dev tool that opens, messages, stops and reconnects a claude soldier through the same post office. From M3, Claude's `send` tool is a use too (HOST-10, →M3).
  - The mod acts only in the owner's own interactive session. In any other, such as a claude soldier's `-p` session, it registers no tool or command, starts no post office, records nothing and draws nothing. Claude Code's `session.start` marks such a run, with `isInteractive` false and no surface. The army runs only in the Claude Code CLI: elsewhere, such as the Desktop app, the mod can't start a process, so it offers no army.
  - The mod starts the post office with the Node.js executable it finds by its absolute path on `PATH` alone, as CH-1 finds each CLI: never one in the folder, a worktree or a snapshot, and never through a relative or empty `PATH` entry. On Windows the current folder is never searched. The mod passes that absolute path as the command it starts.
  - **Versions.** Shadow Army supports Node.js 22 or later, git 2.34 or later, and Claude Code 2.1.286 or later as the host, the first version with mods on by default; the package's `engines.node` field says `>=22`. A claude soldier's oldest version is CH-2's. Before it first starts the post office, the mod checks each one: the host's through `$.session.version()`, and Node.js's and git's by running each, found as above, with `--version`. One that is missing or too old starts nothing, and Claude's transcript gets one line naming what is needed, as in `Shadow Army needs Node.js 22 or later on PATH; none was found`. CI runs the oldest and the newest Node.js and git (PO-21).
  - A mod instance owns only the post office it started. When the mod reloads, as after a save under `--plugin-dir`, `/reload-plugins` or a lost hooks worker, that post office ends, with the module or through the shutdown its lease starts within 30 seconds (PO-7), and its turns are cut short (PO-8, →M2). The new instance takes over no post office, since it has no secret: it starts its own at the next use, once the old one has exited (PO-1), and Claude's transcript gets one line saying so.
- **HOST-3** (M5; S, I) **The pane** (spike S1).
  - In Claude Code's full-screen layout it docks beside the transcript from 110 columns. On the main screen it sits inline above the prompt, at most 72 columns wide.
  - It opens by itself only when a soldier needs the owner: from 144 columns, or from 110 once the owner has opened it before. Otherwise it waits undrawn until asked (`/pane`, or ctrl+x tab after a toast). When asked, it opens at any width.
  - Docked, it asks for 56 columns. A width the owner drags wins, and the pane reflows to whatever width Claude Code gives it.
- **HOST-4** (M5; S) **The pane's content**, top to bottom:
  - tabs, one per soldier;
  - a header with name · id · the model in use (CH-2), never dropped, the state with its word, and how many messages are queued. Below 50 columns it takes two lines: the name and the state, then the id and the model;
  - the meter;
  - the live session (thinking, tool calls, replies);
  - the message field;
  - the keys row, which wraps to a second row before any key is dropped.
- **HOST-5** (M5; I, S) **Keys in the pane:**
  - j and l switch tabs; i and k scroll the session, through `$.ui.scroll`. Tab and the arrow keys walk the pane's buttons, as Claude Code does in any pane, and the wheel scrolls too (spike S1).
  - Enter goes into the field, and Enter sends.
  - Esc leaves the field, and Esc again closes the pane.
  - The keys are button hotkeys, as the mod API provides; Claude Code's ctrl+x tab moves the keyboard into the pane.
  - j, l, i and k are reserved for moving in the pane. No other pane action, card or error uses them, because a repeated hotkey loses its binding.
  - The other pane keys:
    - o opens the log;
    - r reconnects or starts the soldier, and sends again a message that was not delivered. On an interrupted message it puts the text back in the field and sends nothing (MSG-4);
    - f starts fresh;
    - s stops the running turn (MSG-9);
    - q opens the queue, where 1 to 9 pick a message, x cancels it and c changes it (MSG-10);
    - g goes on: at the handoff card it keeps going, after a stop it sends the held queue, and after a mode couldn't be set or a revert failed it tries again first (CH-11, →M6; WSP-12, →M6);
    - a and e answer the handoff card;
    - y and n answer the guard's attribution card (ARM-6), and the card for an edit before a turn a CLI started by itself (WSP-12, →M6);
    - d shows the soldier's changes (WSP-9, →M6);
    - 1 to 9 answer a vendor's approval request. An option that allows more than the one request, such as "allow for this session" or ACP's `allow_always`, takes its key twice: the first press marks it and says that the CLI decides what it covers, and the second sends it. Esc or another option's key clears the mark, and nothing is sent if the request closes first (CH-6).
  - No key is bound twice on one screen. The queue view replaces the session while it is open, so it and an approval request are never on screen together.
- **HOST-6** (M5; S) **The army strip** is one line above the prompt.
  - It lists every soldier in roster order, each with its state glyph and name in its colour, plus a five-cell meter and its tokens as the width allows.
  - Only a state that needs the owner (HOST-14), or error, shows a word in the strip, and it keeps it at every width: "waiting", "handoff" (handoff ready), "held", "log in", "down" and "error". Other states show by their glyph alone (VIS-2).
  - "error" shows from when a turn ends interrupted by what its CLI reported (PO-8), apart from a login needed, until the soldier's next turn starts or it starts fresh. It waits on nothing, so HOST-7's count, HOST-8's toasts and HOST-14's list leave it out.
  - The meters drop first, then the tokens, then names become tags (VIS-6). Glyphs never drop. If the line still does not fit, soldiers that need nothing fold into "+N more", and then the last ones that need the owner into "+N · /decisions".
- **HOST-7** (M5; U) **The status-line entry** is one plain-text entry, with the most urgent fact first. When more than one thing needs the owner, it gives their count and `/decisions`.
- **HOST-8** (M5; U) **Toasts** appear only while the pane is closed.
  - They are only for: a soldier waiting on the owner; a handoff ready; a disconnection; a CLI that needs a login; a message not delivered (MSG-4).
  - When a second decision opens while one is still open, one toast gives the count and points at `/decisions` (HOST-14). After that, new decisions get no toast until the list is empty.
- **HOST-9** (M5; U, S) **Commands:** `/army`, `/send <soldier> <message>`, `/pane [soldier]`, `/stop <soldier>`, `/queue [soldier]`, `/decisions`, `/fresh <soldier>`, `/handoff <soldier>`, `/sessions` and `/mode [ask|auto|plan|terminal|dark|light]`. `/diff` and `/apply` arrive with WSP-9 (→M6).
  - Each command's argument hint and one-line description, which Claude Code shows in its own slash menu:

    | Command | Argument hint | Description |
    |---|---|---|
    | `/army` | | every soldier, its tag and its connection |
    | `/send` | `<soldier> [--kind <kind>] <message>` | message a soldier yourself; it writes only with `--kind build`; Claude is told |
    | `/pane` | `[soldier]` | open or close the army pane |
    | `/stop` | `<soldier>` | stop its turn; its session and work stay |
    | `/queue` | `[soldier]` | what waits for each soldier |
    | `/decisions` | | everything waiting on you, oldest first |

    | `/fresh` | `<soldier>` | start its session fresh; its work stays |

  - An unknown soldier name suggests the closest one and sends nothing.
  - `/send` takes an optional kind of work, `/send <soldier> --kind <kind> <message>`, checked as ARM-2 says. With or without a kind, a `/send` message is the owner's own (MSG-7). A kind adds ARM-2's check, and only `--kind build` makes a writing turn: without it the turn is read-only (ARM-5, →M6).
- **HOST-10** (M3; I) **The mod gives Claude a `send` tool** (soldier, kind, brief, wantReply, wake).
  - `kind` is the kind of work the brief asks for: build, review, research or test. It is required, and the brief is checked against it before it is sent (ARM-2). Only build makes a writing turn, so writing tests is a build, and a brief of any other kind is a read-only turn (ARM-5, →M6). The kind is checked and recorded (PO-6), never sent: the soldier receives only the brief's text.
  - It returns at once, with the brief's id and its state: delivered, or queued and what it waits for. A brief refused before it is sent (ARM-2; MSG-1's size; MSG-3's queue) returns the refusal and its reason instead, with no id.
  - Claude's briefs have no rate cap: each waits in a queue of at most nine (MSG-3), and the owner sees each one in Claude's transcript (HOST-11). A soldier's sends have a rate cap (MSG-6).
  - The summary arrives later as a summary card in Claude's conversation (MSG-5, MSG-8).
- **HOST-11** (M3; S) **The mod's rows in Claude's transcript:**
  - one row per brief, with its delivery state, and one per brief refused before it was sent, with the reason (MSG-3);
  - a summary card of at most five lines, plus the report's path, with `cut at 2 MiB` when the report was cut (PO-6), or `report not saved · <reason>` when the report can't be written;
  - one line for each soldier-to-soldier message and each message the owner typed directly.
  - Each one-line row starts with a bar, ▌ (ASCII `|`), in its soldier's colour. It is decoration: the row says everything in words and glyphs too (VIS-2, →M5).
- **HOST-12** (M5; R, U) The mod MUST NOT approve a tool call or a permission without the owner. For Claude Code's own tool calls and permissions it may only observe, or deny. A vendor's approval request it passes on only with the owner's own answer, unchanged (CH-6, SEC-3).
- **HOST-13** (M5; R) **The Monarch's own Claude Code permissions are the owner's.** The mod does not widen or narrow what Claude may do in the checkout. Soldiers' writes still go through their worktrees (WSP-2, →M6).
- **HOST-14** (M5; U, I, S) **One list of decisions, at the head of the army.**
  - Everything that waits on the owner, across all soldiers, is in one list, oldest first: approval requests, the guard's attribution cards (ARM-6) and the cards for an edit before a turn a CLI started by itself (WSP-12, →M6), the folder's trust card (ARM-7), whose row shows its dialog again when chosen, handoffs ready, queues held after a stop, after a turn's mode couldn't be set (CH-11, →M6) or after a read-only turn's revert failed (WSP-12, →M6), logins needed, channels down and messages not delivered.
  - The list is the pane's first tab. Below the decisions the tab lists the rest of the army, in groups: working (stopping, background work and preparing handoff included), then error, then cold and idle, then starting, reconnecting and not running. Each row has the soldier's glyph, name and state word, and one fact: what it waits for and for how long, its current tool call, or its context size.
  - The tab is "needs you", with the count, and it shows while the list is not empty. `/decisions` prints the decisions in the transcript.
  - Choosing a row opens its card under the list, in the same tab, and the answer is given there with the card's own keys (HOST-5). The soldier's own tab shows the same card.
  - A new decision never replaces the card the owner is reading. It joins the list, and one line above the list names it, as in `↑ new: Iron · queue held · Tab`.
  - A row leaves the list once its decision is made, wherever it was made. An approval request also leaves when a stop cancels it (CH-6). When the post office stops, however it stops, every row it raised leaves the list: a request as closed (CH-6), a card as left unanswered (PO-7). An answer given after that is dropped.
- **HOST-15** (M5; U, S) **While you were away.** When the owner has given no input for 10 minutes and the army has settled, with no soldier working, stopping, starting or preparing a handoff, the mod adds one digest to Claude's transcript:
  - a line with the time span;
  - one row per soldier whose state changed since the owner's last input, in HOST-11's words: answered (with the facts of MSG-11, →M6), interrupted with its reason (MSG-4), waiting on you, handoff ready, queue held with its reason (HOST-14), cold with its reason or cache unknown (SES-6), down, log in needed or error, and each message not delivered (MSG-4);
  - the cost the CLIs reported in that time, where they report one, marked as SES-7 marks it.

  It comes once per absence. The 10 minutes are real time, counted as SES-6 counts idle time, from the owner's last input. The mod draws it as transcript notice rows, which are not added to Claude's conversation and wake nobody (MSG-8). It is not a toast (HOST-8).
- **HOST-16** (M3; I) **The mod shows only what the post office decided** (section 3). The mod shows the result of each request it makes (a stop, an approval answer, y or n, g, a cancel, a change, a fresh start, a reconnect) only from the post office's event. A request the post office refuses leaves the mod showing what the post office's last event showed, with the refusal's reason.

### 4.2 The post office (PO)

- **PO-1** (M1; I, F) **Supervision.** The post office is one local process per folder, and it supervises every soldier session.
  - **One per folder.** The folder is the top level of the git working tree the owner's Claude Code session runs in. A linked worktree of the repository, such as one that `git worktree add` or `claude --worktree` makes, is a folder of its own, so a repository can have an army in each of its working trees. Each army leaves the other armies' snapshots, worktrees and files alone (WSP-10, WSP-11; WSP-1, →M6). Outside a git working tree the army doesn't start, and the mod says why, as in `the army runs only inside a git working tree`. A lock there holds the post office's pid, its process start time and its port, and is written whole. The start time is the one the OS reports for that pid, read the same way when the lock is written and when it is checked. The mod learns the port only from the post office's standard output, never from the lock.
    - A start that finds a lock reads it. The lock is stale when no process has that pid with that start time, or when the file is empty or can't be read. A stale lock is replaced, and the new post office's log says so; of two starts that find the same stale lock, only one wins.
    - A lock whose owner is alive is never deleted or replaced. The start is refused, and the mod says why, as in `the army is already running in this folder (pid 4120, started 14:02)`, or, when the mod's own last post office is still shutting down, `the army is still closing` (PO-7). The next use of the army tries again.
  - **Restarts.** A channel that crashes is restarted after 1 second, then 5 seconds, then 30 seconds. A fourth crash within 10 minutes of the first leaves it down until the owner reconnects it; a reconnect, or 10 minutes without a crash, resets the count. In M1 a restarted channel opens a fresh session, and the soldier's log says so; from M2 it resumes the previous one by id (CH-9, →M2). A channel whose containment failed, at its start or later, is not a crash and is never restarted by itself (PO-15).
  - **What a crash is.** Only the CLI's process ending, or the post office losing its connection to the CLI, is a crash; ten unparseable lines in a row count as a lost connection (CH-1). After a lost connection the post office ends the CLI's process tree before anything else. An error the CLI reports while it keeps running (CH-1) never restarts it.
    - A start counts as a crash when it ends before the CLI's first event, or gives no sign of life within its CLI's own startup wait plus 30 seconds. For claude the sign is its answer to the `initialize` control request, and the wait is `MCP_TIMEOUT`, 30 seconds unless the owner set it.
    - Silence is never a crash: a running CLI is not ended or restarted for sending nothing, and the owner can stop its turn (MSG-9, →M3).
    - A start the CLI refuses because of a setting, such as an organization's managed `permissions.disableBypassPermissionsMode` at `full`, is not a crash and is never restarted. The adapter knows it by the CLI's message, as its contract fixtures record it (section 5.1 C). The soldier is down with the CLI's words, and its log and one line in Claude's transcript name the soldier, its autonomy and the refused flag, as in `Kaisel can't start at full: your organization's managed settings refuse it · lower its autonomy`.
    - A login needed never restarts the channel, whether the CLI keeps running or exits after it: the soldier shows "log in" until the owner reconnects it. Any other error the CLI reports before it exits counts as a crash, and keeps its kind and words (CH-1).
  - A message whose turn had started when the CLI crashed is never sent again by itself (MSG-4, →M3). Before the channel restarts, that turn is finished (PO-8, →M2).
  - **Containment.** Every CLI runs in a containment that is set up before it starts (PO-9). A CLI whose containment can't be set up doesn't start, and nothing starts it uncontained (PO-14). When a channel closes or restarts, the post office ends the CLI's whole process tree: the CLI and every process that descends from it, one that starts a new session or forks twice included (PO-10). If the post office's own process ends without closing a channel, however it ends, a kill or a crash included, that channel's guardian ends its whole process tree within 10 seconds (PO-10). If the guardian ends with the post office, PO-16 says what ends the tree, and when.
    - Work the CLI hands to a service outside its tree keeps running: a systemd, launchd or cron job, a scheduled task, a process started through WMI, a container engine, a tmux or screen server already running, a session that `ssh localhost` opens, or a vendor's own background service, such as Claude Code's background sessions; and, on Windows, a process created with a parent outside the tree (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`), which takes that parent's job, not the soldier's. That is a stated residual risk, and no guard or audit sees what such work changes after the turn. So is a process on Linux that no listing of its tree found (PO-11) when the guardian is ended from outside, alone or together with the post office: it keeps running too (PO-15, PO-16).
  - **After a post office that didn't close its channels.** Before it opens any channel, a post office finishes what the last one left open, as the last one's logs (PO-5) and, from M3, its records (PO-6, →M3) show:
    - Each turn still open is finished (PO-8, →M2). Its guard is closed against the baseline kept on disk for it (WSP-11), trusting the snapshots and worktrees the last one's log says it made or removed, as WSP-10 does, and any change goes on that turn's attribution card (ARM-6, →M2), or before M2 into one line in Claude's transcript. That check can't tell the turn's changes from later ones, so the card or the line says that it compares the checkout now with the turn's start, gives the time the last post office's log ends, and says that changes made since then, the owner's own included, show on it too. A turn whose guard had already closed is not checked again (PO-8, →M2).
    - Each message still recorded as delivered ends as interrupted, and each queued message ends as not delivered. Both carry the reason `the post office stopped unexpectedly`, and nothing is sent again by itself (MSG-4, →M3).
    - Each attribution or handoff card left open is kept in the records as unanswered, with its paths and hashes from the log, as PO-7 says (ARM-6, →M2; SES-4, →M4; PO-6, →M3).
    - In a worktree where the last one left a read-only turn open, the turn is reverted from the start state kept on disk for it, once the start state has passed its hash check (WSP-12, →M6).
    - In each snapshot the last one left (WSP-11; ARM-6, →M2), every write as WSP-11 defines it, a HEAD that isn't the commit the log gives for it included, is reported as a read-violation, in the log and in one line in Claude's transcript. Then the snapshot is removed, and so is any instructions or settings file the last one left beside its logs (CH-2).
- **PO-2** (M1; X) **Local only.** The post office and every port a channel opens MUST bind to the loopback address (127.0.0.1 or ::1). Any other address is refused at start, with an error that says so. That includes the port a macOS guardian connects back to (PO-18). The containment helper listens on no port (PO-17). Shadow Army's own code, the mod, the post office and each guardian, opens no network connection except on the loopback address, and sends no telemetry, crash report or update check. Data leaves the machine only through the soldiers' CLIs and the owner's Claude Code, and through git where the owner's own config makes it fetch, as an LFS filter or a partial clone's missing objects do while a snapshot is made (WSP-10).
- **PO-3** (M1; X) **The Monarch's credential.**
  - The mod makes a secret of 32 random bytes each time it starts the post office, and passes it on the post office's standard input.
  - The secret MUST NOT be written to disk, a command line, an environment variable, the post office's output, Claude's transcript, or a log. Soldiers run as the same user, so a file only the owner can read is not enough.
  - Every command from the mod presents it. A wrong or missing secret is refused, and reported in the post office's log (PO-5): the first refusal in full, then at most one report a minute, with the count since the last one. Refusals not yet reported are reported when their minute ends, on the monotonic clock.
  - The event stream, with every soldier's turns, reaches the mod only on the post office's standard output.
  - The secret is never printed whole; at most its last four characters are shown.
  - **Memory.** The mod and the post office hold the secret in memory while the post office runs, and the post office also holds each soldier's credential (PO-4, →M3). Before it reads the secret from its standard input, the post office protects its own memory where the system allows, and its log's first lines name the protection it has, as in `memory protection: Yama ptrace_scope 1` or `memory protection: none · ptrace_scope 0`:
    - **Linux.** It reads Yama's `ptrace_scope` (`/proc/sys/kernel/yama/ptrace_scope`). At 1, only a process's ancestors, or a process with `CAP_SYS_PTRACE`, may attach to it or read its memory through `/proc/<pid>/mem`; at 2, only a process with `CAP_SYS_PTRACE`; at 3, none. Soldiers descend from both the post office and Claude Code, so at 1 or more they can read neither copy of the secret, nor another soldier's CLI. At 0, or where the file is missing because the kernel has no Yama, there is no protection.
    - **Windows.** Through the script of PO-19, which it runs once from the installed package before it reads the secret, it replaces its own process's DACL (`SetSecurityInfo`) with one that grants no one `PROCESS_VM_READ`, `PROCESS_VM_WRITE`, `PROCESS_VM_OPERATION`, `PROCESS_CREATE_THREAD`, `PROCESS_CREATE_PROCESS`, `PROCESS_DUP_HANDLE`, `WRITE_DAC` or `WRITE_OWNER`, and that holds an OWNER RIGHTS (`S-1-3-4`) entry, which takes away the owner's implicit right to change the DACL back. Without `PROCESS_CREATE_PROCESS`, no process can start a child with the post office as its parent. The same operation gives each of the post office's threads a DACL that grants no one `THREAD_SET_CONTEXT`, `THREAD_GET_CONTEXT`, `THREAD_SUSPEND_RESUME`, `WRITE_DAC` or `WRITE_OWNER`, with the same OWNER RIGHTS entry, and sets the default DACL of its token to it, so a thread it starts later gets it too. A handle opened before the change keeps its rights, as Claude Code's handle to the process it started does. Where the DACL can't be set, the log says `memory protection: none` with the reason, and the post office goes on. A thread whose DACL can't be set is named in the log line, as in `memory protection: process DACL · 1 thread open`.
    - **macOS.** It checks nothing, and the log says `memory protection: not checked`.
  - **What this doesn't stop** is a stated residual risk. A soldier that runs code as the owner can read the secret from the mod's copy, in Claude Code's own process, on Windows always and on Linux at `ptrace_scope` 0 or without Yama, where the post office's copy is open too. On Windows it can also read it from the post office where its DACL couldn't be set, and from any process through `SeDebugPrivilege` when Claude Code runs elevated. On macOS the post office checks nothing, and whether a soldier can read either copy is not assessed; that is accepted as part of the same risk. With the secret it can act as the Monarch: command and stop soldiers, read the event stream and, from M2, answer approval requests (CH-6, →M2). Shadow Army runs on a machine with no protection too; its log says which one it has. Another plugin in the owner's Claude Code session runs as the owner inside the Monarch's host: a `process.spawn` hook sees the secret in the post office's input, and every event on its output, and can change them. Shadow Army can't hand the secret over in a way such a hook doesn't see.
- **PO-4** (M3; C, I, X) **The soldiers' tool and credentials.**
  - Each soldier session gets its own credential: 32 random bytes, made when the session opens and revoked when it closes or starts fresh.
  - That credential works only on the soldiers' MCP endpoint, which serves exactly one tool, `send(to, text)`, over local HTTP.
  - A soldier credential never appears on any process's command line, and stays off disk wherever the CLI allows. codex and grok take theirs over stdio, in `thread/start` and `session/new`. claude takes its own over its stream-json input where it can (Q9). Until a probe shows it can, and wherever it can't, the post office writes the `send` server's entry, credential included, to an `--mcp-config` file that only the owner can read, beside the session's log under `.shadow/v2/logs/` (PO-5), as CH-2's instructions file is, never in a worktree, a snapshot or the system's temporary folder. It removes the file once claude has answered the `initialize` control request (PO-1), or when the process ends, whichever comes first. Each start or resume of the process writes it anew.
    - A soldier that runs code as the owner can still take another soldier's credential: from that CLI's memory, or the post office's, where nothing shields it (PO-3), or from claude's file while it exists. With it, it can send under that soldier's name. That is a stated residual risk.
  - The sender is always the soldier the credential belongs to; any sender named in the request is ignored.
  - A soldier credential MUST NOT issue a Monarch command, read the event stream, or read any session, log or record.
  - The tool is added to claude, codex and grok soldiers through each CLI's own MCP configuration, adding to it and never replacing it: claude's stream-json input or its `--mcp-config` file (Q9), codex's `thread/start` config, and grok's `session/new` `mcpServers` (spike S4).
  - agy has no per-session way to add it, so agy soldiers get no `send` tool in v2.0. They reply through summaries only.
- **PO-5** (M1; U, X, F) **Logs.** The post office keeps an append-only log for itself and one for each soldier's session, under `.shadow/v2/logs/`. Logs are JSON Lines: one file per soldier session, named by the soldier and the session id, and one per start of the post office, named by its start time. Every write passes through `redact()` (WSP-8).
  - **Out of git.** Before it writes anything under `.shadow/v2/`, the post office makes sure that `.shadow/v2/.gitignore` holds `*`, so git ignores the army's files there, as v1 does for `.shadow/`.
  - **The owner's alone.** On Linux and macOS, the post office creates `.shadow/v2/` and `~/.shadow-army/` readable only by the owner's user (0700), whatever the umask, so nothing under them is open to another user, and writes its own files there 0600. On Windows it creates the two folders with inheritance off and an ACL that grants only the owner's user, SYSTEM and Administrators. Where either folder already exists with more, the post office narrows it at start, and its log says so.
  - **Its own folders.** Before it writes anything, the post office checks `.shadow/`, `.shadow/v2/`, `~/.shadow-army/` and each folder it makes under them (`logs/`, `trees/`, `reports/`, `snapshots/`, `trust/`): each must be a plain folder, not a symbolic link or, on Windows, a junction or another reparse point, and must be owned by the owner's user. It creates each file it writes there new, and never follows a link to one (`O_NOFOLLOW` and `O_EXCL` on Linux and macOS; on Windows, no reparse point). It also checks that git tracks nothing under `.shadow/v2/`. If any check fails, no soldier starts and nothing is written there, and the mod says why in one line in Claude's transcript, as in `Shadow Army: the army's folder .shadow/v2 is a link, not a folder of yours · nothing started`.
  - A log holds each message, thinking block, tool call and tool result whole. The fragments a CLI streams are joined first, and `redact()` runs on the joined text. When a turn ends before a message is whole, what was joined so far is written.
  - Each decision (HOST-14, →M5) is logged when it opens and when it closes, so a post office ended outright loses none. So is each turn, when its message goes in and when it is over, with where its guard's baseline is kept (WSP-11) and, for a read-only turn in a worktree, where its start state is kept and that start state's hash (WSP-12, →M6), so the next post office finds a turn left open (PO-1). The line that opens a turn is written and flushed before its message goes in. So is each snapshot or worktree Shadow Army makes or removes, with the commit it was made at or, for a snapshot, brought to (ARM-8, →M6) and its metadata, written and flushed as it is made or removed (WSP-10).
  - A log never stops a soldier or a turn, except that a message whose turn's opening line can't be written isn't sent (WSP-11). A write that fails is tried once more, 100 ms later. If that fails too, the post office carries on, reports it once on the event stream, and Claude's transcript gets one line, as in `Shadow Army: logs not written · disk full`. Each later write tries again, and the first line written after a gap says how many lines were lost. A line cut short by a failed write is ended before the next one, and a reader skips any line that doesn't parse. Records are not logs: what a record that can't be written does is in MSG-4 (→M3).
  - **Disk.** Logs are kept until the owner deletes them (WSP-8). v2.0 sets no limit on their size and doesn't rotate them; that is H62, after v2.0 (Appendix C). A log holds every message, thinking block, tool call and tool result whole, so it grows with every turn, and together with the records and reports (PO-6, →M3) it can fill the disk. That is a stated residual risk. A full disk stops new messages from going in instead of losing them: a message whose turn's opening line can't be written isn't sent (above), and a message whose record can't be written stays queued (MSG-4, →M3), each with its reason. The owner frees space by deleting old logs under `.shadow/v2/logs/`. Each open session's snapshot is a full checkout of HEAD (WSP-11), so on a large repository each soldier's snapshot takes about as much disk as the checkout. Deleting the logs of a post office that didn't close its channels, before the next one has started, loses what PO-1 would finish from them.
- **PO-6** (M3; U, F) **Records.** Every brief, summary and message is stored with its id, time, sender, recipient and delivery state, and a brief, or a `/send` that gave a kind, with its kind of work (HOST-10; HOST-9, →M5). A message with no kind is stored as having none, and its turn is read-only (ARM-5, →M6). Full reports go under `.shadow/v2/reports/`.
  - **At most 2 MiB a report:** 2,097,152 bytes of UTF-8. A longer reply's report keeps its first 2 MiB, cut between two characters after `redact()` has run on the whole reply (WSP-8), and ends with one line saying that it was cut, how many bytes followed, and that the soldier's session log holds the whole reply (PO-5), as in `report cut at 2 MiB · 1,180,334 bytes more · whole in the soldier's log`. The summary card says so beside the report's path (HOST-11). The summary is still taken from the whole reply (MSG-5).
- **PO-7** (M1; U, I, F) **Shutdown.** When the owner's Claude Code process ends, the post office closes every soldier session through that CLI's own exit, and leaves the worktrees and branches in place.
  - **What it outlives.** `/clear`, `/resume` and `/branch` end Claude's conversation, but the process and its mod go on, as Claude Code's own background work does. So they don't end the army: the soldiers keep their sessions, and a summary for a brief sent before them arrives in the conversation Claude Code is in then (MSG-5, →M3). Claude Code's `session.end` says which happened in its `reason`: `clear` for `/clear`, and `resume` for `/resume` and `/branch`, a `/resume` that moves the conversation to a background session included. Any other reason (`prompt_input_exit`, `logout` or `other`) ends the army, `/logout` included.
  - **What starts it.** Three things start the same shutdown: the mod's release at a `session.end` that ends the army, the lease's end, and the watch. The first one starts it; the others then change nothing.
  - **The lease.** A living Claude process doesn't prove a living session: a mod can hang or be stopped. So the mod renews a lease with the post office every 10 seconds, and the post office ends the lease after 30 seconds of its own running time without a renewal. The 10 and 30 seconds are fixed; no setting changes them.
    - **Renewing.** The mod gives the post office Claude's session id (`$.session.id()`) with the secret at start (PO-3); without one, the post office refuses to start. That id stays the army's for its life, after `/clear`, `/resume` or `/branch` gives Claude's conversation another. Every 10 seconds, by its own timer (`$.clock.every`), the mod sends a renewal: a command that presents the secret and carries the army's id. Only a renewal renews the lease. At most one renewal waits for its answer, and one that falls due meanwhile is skipped; a renewal unanswered after 5 seconds no longer counts as waiting. A renewal that fails is not retried early and stops nothing: the next one goes at its time.
    - **At a `session.end` whose reason is `clear` or `resume`** the mod keeps renewing with the army's id, and nothing else changes. **At any other `session.end`** the mod stops renewing before anything else, then sends a release that names the army's id. The post office answers the release at once, then shuts down; a release that names another session is refused. If the release doesn't arrive within that hook's short time budget, the lease ends the post office instead.
    - **The clock.** The post office measures the lease on Node's monotonic clock (`performance.now()`). It MUST NOT use the wall clock for it, so a change of the system time, either way, changes nothing. Times it reports, such as when the lease ended, are wall-clock times for display only.
    - **The checks.** The gap starts at zero when the post office reports that it is ready, and goes back to zero with each renewal. Once a second, a check adds the time since the previous check, the last renewal or the start, whichever came last, but never more than 5 seconds. The lease ends at the first check that brings the gap to 30 seconds. Only a check ends it. Handling a renewal never measures time, so a renewal handled before that check renews the lease, however late it was sent.
    - **Sleep, suspension and stalls.** A step of more than 5 seconds between two checks means the post office did not run: the computer slept or hibernated (Windows' modern standby included), the post office was suspended by a debugger or a signal, or its event loop stalled. At most 5 seconds of it count, on every system. Node's monotonic clock stops while Linux is suspended, but goes on through sleep and hibernation on Windows and macOS, where the first check after waking sees one long step. Renewals sent while the post office was suspended wait at its port, and are handled when it runs again. The post office logs each such step with its length.
    - **The mod stopped or stalled.** Time in which the post office runs and the mod doesn't counts in full. That covers Claude Code stopped by job control (ctrl+z) or a debugger while the post office isn't, its event loop busy, and the mod's timer stopped. The lease ends once 30 seconds of it pass without a renewal.
    - **Refused renewals.** A renewal is refused, and renews nothing, when it carries another session id, when it comes from an earlier start of the post office (PO-3), or when the lease has ended. An ended lease never comes back. The refusal gives the reason. The post office logs the lease's start, each long step and each refusal, never a renewal one by one.
  - **The event stream never holds the post office.** Claude Code blocks a child of the mod on its next write once 1,048,576 characters of its output wait unread, and Node writes to a pipe synchronously on Windows. So the post office writes its events without blocking its event loop, and goes on reading its soldiers, serving `send` and taking renewals while they wait. Past 16 MiB of events not yet written, it stops reading its soldiers' output until the mod has read them.
  - **The watch.** Once a second the post office also checks that the process that started it is still running. It tells that process apart from a later one that reuses its pid by its start time, as the lock does (PO-1). Once that process has ended, the post office shuts down at once, without waiting for the lease.
  - **Containment.** The lease and the watch need a running post office. The post office may be ended outright before its shutdown finishes, for example by Claude Code when the mod unloads, or by a crash. Then no session closes through its CLI, and its process containment ends each soldier's whole process tree, as PO-1 and PO-16 say.
  - **The shutdown,** whatever started it, for every soldier at once:
    - The post office records the reason and the time in its own log and in each soldier's (PO-5), and sends them as an event. The reason is one of `Claude Code ended`, `the owner logged out`, `no renewal from the mod for 30 s` and `the process that started it ended`.
    - From then on it refuses every command, renewals included, and every soldier's `send` (PO-4, →M3), giving that reason. No channel starts, restarts or resumes (PO-1; CH-9, →M2), and it never waits for background work.
    - Each queued message ends as not delivered, with the reason (MSG-4, →M3), and nothing more is sent.
    - A running turn is stopped as a stop stops it, background work included (MSG-9, →M3; CH-10, →M2), and each approval request it has open is closed as a stop closes it, and nothing is approved (CH-6, →M2). A turn not ended 30 seconds after the stop has its CLI's process tree ended (PO-1). The turn is finished (PO-8, →M2), and its message ends as interrupted, with the reason (MSG-4, →M3).
    - An attribution or handoff card still open is not answered, and doesn't hold up the shutdown (ARM-6, →M2; SES-4, →M4). It is kept in the records as unanswered, with its paths and hashes (PO-6, →M3), and the message whose summary waited for it ends as interrupted, with the reason `the army stopped before the owner answered`.
    - Then each session closes through its CLI's own exit. Once the CLI has exited, or 10 seconds after it was asked to, the post office ends its whole process tree (PO-1) and revokes the soldier's credential (PO-4, →M3). A channel still starting has its process tree ended at once.
    - Once every session is closed, the post office releases its lock (PO-1) and exits. It doesn't wait for the mod to read its last events; the logs keep them.
    - Until M2, which brings the stop (CH-10, →M2) and the finishing of turns (PO-8, →M2), a running turn is not stopped first: closing its session cuts it short.
  - **What the owner sees.**
    - The soldier's log and the post office's log say when the army stopped and why. They also say what happened to each turn, queued message, approval request and card, as in `14:02:13 lease ended: no renewal from the mod for 30 s · turn stopped · 2 queued messages not delivered · session closed`.
    - The mod learns of the shutdown from the post office's last event, from a command refused for that reason, or from the end of the post office's output; output that ends with no shutdown event gives the reason `the post office stopped unexpectedly`, with its exit code or signal. A renewal that only fails tells it nothing. Then the mod stops renewing, and Claude's transcript gets one line, as in `the army stopped at 14:02:13: no renewal from the mod for 30 s · the next use starts it again`. From M5, while the pane is closed, a toast says so, as for a disconnection (HOST-8, →M5). The rows of the briefs it affected show how they ended, as far as its events told it (HOST-11, →M3). The records keep every ending (PO-6, →M3).
    - The next use of the army starts a new post office (HOST-2) once the old one has exited, its lock released or left stale (PO-1). Until then, the mod says that the old one is still closing. The soldiers start new sessions. The old sessions' logs and reports, and every worktree and branch, stay.
- **PO-8** (M2; I, F) **A turn ends once, and only when its work has stopped.**
  - A turn's end event is its CLI's own: claude's and agy's `result`, codex's `turn/completed`, or the answer to grok's `session/prompt`.
  - **Work left running.** A turn is not over at its end event while something it started is still running: a background task the CLI reports, or a process that joined the CLI's process tree during the turn (PO-1, PO-11) and is not a session service. claude reports its background tasks with `task_started`, `background_tasks_changed` and `task_notification` events, and stops one on a `stop_task` control request. Until that work ends:
    - the soldier shows it, as in `◐ 1 background task`, and the message stays delivered;
    - the turn's guard stays open, so whatever the work changes belongs to the turn and goes on its attribution card like any other change (ARM-6, WSP-4, →M6);
    - messages to the soldier wait in its queue (MSG-3, →M3), and harness git for that soldier waits too (WSP-7, →M6);
    - a turn the CLI takes by itself when the work ends belongs to the same message. claude takes one more turn with a background command's outcome.

    The work has ended when the CLI reports each task's end, each such process has exited, and each turn the CLI takes by itself with a task's outcome has ended; at the latest at the CLI's own time limit for background work. claude takes such a turn when a task completes or fails by itself, and marks its messages and `result` with the origin kind `task-notification`. It may answer several outcomes in one turn; then the others' `result`s come first, empty, with `num_turns` 0. A task stopped by s, or a process that is not a CLI task, starts no such turn. A task whose follow-up has sent no event 30 seconds after the task ended, on the monotonic clock, has none. s stops the work at any time (MSG-9, →M3): the adapter stops each task through its CLI and ends each such process, and the session stays open.
  - **Session services.** Some processes serve the whole session rather than one turn: the language servers and MCP servers declared by the configuration the CLI runs with, its plugins included (SET-2, →M4). The CLI starts each one itself, not through a tool's command, and keeps it between turns. claude, for example, starts a plugin's language server at the first edit of a matching file and keeps it for diagnostics, so the server joins the process tree during that turn.
    - The adapter recognizes a session service only as a process the CLI started with a command its configuration declares, plus any helper its table names for that server, such as the compiler server a language server starts. The table of where its CLI declares servers, and of their helpers, names the CLI version it was read from (CH-8).
    - Every other process that joins the tree during a turn is the turn's work, even one a session service started: a job an MCP server starts for a tool call, a process the adapter cannot tell, and one a tool started with a service's command. A tool call's ownership comes before the service it ran through.
    - A session service never keeps a turn open. Once the turn's own work has ended, the turn is over, the next message can go in and harness git can run (WSP-7, →M6), while the service keeps running. s leaves it running.
    - It ends with the session: closing or restarting the channel ends the CLI's whole process tree (PO-1).
    - A change it makes to the checkout during a turn goes on that turn's attribution card, like any other change (ARM-6, WSP-4, →M6).
  - **Cut short.** Sometimes the turn is not over yet when the CLI's process ends, its connection is lost, or a stop falls back to ending the process (CH-10). Then the turn is over once the post office has ended the CLI's whole process tree (PO-1), background work included. That covers a turn with no end event, and one whose background work was still running. The post office reads everything the CLI wrote before it decides whether an end event came.
  - **Finishing.** When a turn is over, either way, the post office finishes it before anything else. It closes the turn's checkout guard (ARM-6, WSP-4, →M6). Then it runs the turn's claim audit (WSP-2, →M6) or, for a read-only turn, discards the writes in its snapshot (WSP-11) or reverts its worktree (WSP-12, →M6). Each runs once, on the files as they are then. Then the message ends by what the CLI's own fields say in the last end event; when the CLI took a turn by itself after background work ended, that turn's end event is the last. The message ends:
    - **answered**, with that turn's result as the summary, when the turn completed or the model refused (CH-1): claude's `result` with the subtype `success` and no `is_error`, codex's `turn/completed` with the status `completed`, or grok's answer with the stop reason `end_turn` or `refusal`;
    - **interrupted**, when the turn failed or stopped short of finishing: claude's `result` with an `error_…` subtype or `is_error`, codex's `turn/completed` with the status `failed`, or grok's answer that is an error or has the stop reason `max_tokens` or `max_turn_requests`. The CLI's own error or reason is kept word for word, redacted (WSP-8), with its kind when it is an error (CH-1), such as a rate limit or a context overflow. The changes made so far stay, except in a snapshot (WSP-11) or after a read-only turn (WSP-12, →M6), and the message's row shows them (MSG-4, →M3);
    - **interrupted**, when the turn was cut short or the owner stopped it (MSG-9, →M3).

    The work done so far stays under the usual rules. Nothing is sent again by itself (MSG-4, →M3), and an error the CLI reports while it keeps running never restarts it (PO-1).
  - Only then is the session resumed (CH-9), the channel restarted (PO-1) or the next message sent. If the guard raises an attribution card, the soldier's queue is held until the owner answers it (MSG-3, →M3).
  - The guard and the audit run once per turn. An end event read after the turn is over is recorded and changes nothing.
  - A turn the CLI starts by itself after a message's work is over belongs to that message: it takes that message's kind (ARM-5, →M6), it gets a guard and an audit of its own (after a read-only message, the revert of WSP-12, →M6), the queue waits for its end event, and its result never ends a later message. Its result is recorded under that message and shown in the soldier's log, and Claude's transcript gets one line saying the soldier took a turn by itself after answering (HOST-11, →M3), with its changes (MSG-11, →M6). n on its card fails that turn as a read-violation, and the line says so; the message keeps the state it ended in.
  - A change made after the turn is over belongs to no turn, so the owner's own edits between turns stay exempt, except in a soldier's worktree, as WSP-12 (→M6) says for a read-only turn the CLI starts by itself. The next turn's guard starts from the checkout as it is when that turn's message goes in. That baseline is on disk before the message goes in, so a post office that dies mid-turn leaves it for the next one (PO-1).
  - The guard and the claim audit run after a failed turn too (from v1 #22 and #16: `src/core/summon.ts` checks the guard and audits after a failed run).
- **PO-9** (M1; I, F) **Containment.** Every soldier's CLI runs in a containment that is set up before the CLI starts. The containment holds the CLI, every process it starts and every process those start, so the post office can list them all (PO-11) and end them (PO-10). That includes a process that starts a new session or process group, forks twice, clears its environment or outlives its parent. Each session has a guardian: the process that holds its containment, starts the CLI in it, and ends the tree by itself when the post office is gone.
  - **Linux.** The guardian is the containment helper (PO-12). It marks itself a child subreaper (`PR_SET_CHILD_SUBREAPER`), leads a session and process group of its own, which the CLI joins, starts the CLI as its child, and stays its parent for the session. When a process in the tree loses its parent, the kernel hands it to its nearest living ancestor that is a subreaper: the guardian, or a process in the tree that marked itself one. So the process stays in the tree.
  - **macOS.** The guardian is the containment helper, run as a launchd job of its own in the owner's login session, with a label unique to the session. launchd starts the job in a coalition of its own. Every process started from the guardian, the CLI included, stays in that coalition, whatever its parent, process group or session. PO-18 says how the job starts and what it rests on.
  - **Windows.** The guardian is Shadow Army's PowerShell script (PO-19). It creates the CLI inside a Job Object, assigned as the process is created (`PROC_THREAD_ATTRIBUTE_JOB_LIST`). Every process the CLI creates joins the job too, except one created with a parent outside the job, as PO-1 states. Before it creates the job, the guardian gives its own process the DACL that PO-3 gives the post office (PO-19), so no process in the job can copy its handle to the job and keep the job alive after it, or start a child with the guardian as its parent. The job allows no breakaway, and it ends every process in it when its last handle closes (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`). Only the guardian holds a handle to it. Windows has no containment helper.
  - **Apart from the post office.** A guardian is never a Node.js process. On Linux and macOS it runs in a session and process group apart from the post office's. So a signal to the post office's process group, or a command that ends Node.js processes by name, doesn't reach it.
  - **As if started directly.** The guardian starts the CLI with exactly the program, arguments, environment and working directory that the post office gives it, and on Linux and macOS with the post office's resource limits. What the post office writes reaches the CLI's standard input. The CLI's standard output and error reach the post office byte for byte, each in order. Containment adds nothing to the CLI's command and removes nothing from it (CH-7).
  - The post office learns when the CLI's own process exits, with its exit code or signal, even while the rest of its tree runs on (PO-1).
  - **At start.** A session whose containment isn't ready within 10 seconds, or whose macOS coalition isn't new (PO-18), doesn't start its CLI. Anything already started is ended, and the containment has failed (PO-15).
  - **What it is not.** Containment is cleanup, not a sandbox: it sets no file, network or permission policy. What Shadow Army enforces is the checkout guard and the claim audit (ARM-6, →M2; WSP-2, →M6; WSP-4, →M6). PO-1 lists the work it doesn't reach.
- **PO-10** (M1; I, F) **Ending a tree.** The post office ends a CLI's tree when its channel closes or restarts (PO-1), and when a stop falls back to ending the CLI (CH-10, →M2).
  - **In order.**
    - The CLI is asked to exit through its own exit, as PO-7 closes a session.
    - On Linux and macOS, a CLI that hasn't exited 9.5 seconds later gets `SIGTERM`.
    - Once the CLI has exited, or 10 seconds after it was asked to, every process still in the tree is killed.

    A lost connection (PO-1), a stop that falls back to ending the CLI (CH-10, →M2), a CLI whose process has already ended, and a post office that is gone skip the first two steps: the tree is killed at once.
  - **Only the system's word counts.** A tree has ended only when the system reports it empty. A list that the system documents as unreliable while processes run is never the proof. Linux's `/proc/<pid>/task/<tid>/children` is such a list.
    - **Linux.** The guardian kills each of its children, and each process it adopts as their parents die, and reaps them. It goes on until `wait` reports that it has no child left, living or exited (`ECHILD`). It signals only its own children. The kernel keeps their pids until they are reaped, so the guardian never signals a reused pid.
    - **macOS.** First the session's launchd job is removed, because launchd keeps a job made with `launchctl submit` alive after a failure. Then every living member of the session's coalition is stopped (`SIGSTOP`). Once all are stopped, they are killed (`SIGKILL`). This repeats until the coalition has no living member. Each signal goes through the process's audit token, which carries its pid version, so a reused pid is never signalled (PO-18).
    - **Windows.** The guardian terminates the job (`TerminateJobObject`) and waits until the job holds no active process.
  - **When the post office is gone.** The guardian watches its connection to the post office. If that connection closes without a close command, the guardian kills the tree at once. On macOS it ends every other member of its coalition first, and then has launchd remove its own job. On Windows, if the guardian is gone too, the job's last handle has closed, and the system has ended every process in the job.
  - **The limit.** The tree is empty within 10 seconds after the kill began. If it isn't, the containment has failed (PO-15).
  - **What is logged.** After each tree is ended, the soldier's log lists each process that was ended besides the CLI, with its pid and its command line through `redact()` (WSP-8).
- **PO-11** (M1; I) **Listing the tree.** The post office can list the processes in a CLI's containment at any moment. Each comes with an identity that a reused pid can't match:
  - Linux: each process whose chain of parents, read from `/proc/<pid>/stat`, reaches the guardian. Its identity is its pid and start time.
  - macOS: each living member of the session's coalition. Its identity is its pid and the kernel's unique id for the process (PO-18).
  - Windows: each process in the job. Its identity is its pid and creation time.

  PO-8 (→M2) and WSP-11 compare two lists to tell which processes joined the tree during a turn. A process that both starts and exits between two lists can be missed. Whatever it changed in the checkout is still on the turn's guard (ARM-6, →M2; WSP-4, →M6). Before it ends one listed process, as a stop does (MSG-9, →M3), the post office checks that the process's identity still matches.
- **PO-12** (M1; U, I) **Systems and processors.** The post office chooses the containment from Node.js's `process.platform` and `process.arch`:

  | `process.platform` | `process.arch` | Containment |
  |---|---|---|
  | `linux` | `x64` | the helper `native/linux-x64/sa-contain` |
  | `linux` | `arm64` | the helper `native/linux-arm64/sa-contain` |
  | `darwin` | `arm64` or `x64` | the helper `native/darwin/sa-contain`: one universal binary, with `arm64` and `x86_64` code |
  | `win32` | `x64` or `arm64` | a Job Object, through the script of PO-19; no helper |
  | any other pair | | none, so no soldier starts (PO-14) |

  - Each Linux binary is statically linked, so it doesn't depend on the system's C library, and one binary per processor runs on glibc and musl distributions, old and new. It needs `/proc` and Linux 3.4 or later, which has `PR_SET_CHILD_SUBREAPER`.
  - The macOS binary runs natively on Apple silicon and on Intel, whichever processor Node.js reports. Its minimum macOS version is the oldest one CI tests.
  - **Supported** means that CI ran the containment tests on that system and processor for the release (PO-21). For macOS it also means the versions from the oldest to the newest that CI tested. Each release's notes list them. Linux distributions aren't listed: the check decides (PO-14).
  - On a macOS newer than any that CI tested, the check still decides, and the post office's log says that version is untested.
- **PO-13** (M1; I, R, L) **Packaging and installing.** Installing or running Shadow Army from its release package MUST NOT compile anything.
  - The release package is the npm package tarball that CI builds (PO-20). It holds every binary of PO-12, and the Windows script and its DLL (PO-19), beside the post office's code. The same tarball is attached to the release on GitHub. It is also what the npm registry serves, when the project publishes there.
  - The package has no install script (`preinstall`, `install` or `postinstall`) and no `binding.gyp`. So npm builds and runs nothing when it installs the package, and `--ignore-scripts` changes nothing. Its `os` and `cpu` fields stay open: it installs anywhere, and PO-14 refuses soldiers where there is no containment.
  - Nothing is downloaded at install or at run time. The helper comes inside the package from wherever npm gets the package: the registry, a mirror, npm's cache or a tarball. npm's own proxy and certificate settings apply (`proxy`, `https-proxy`, `cafile`). Shadow Army makes no network request of its own for the helper, so once installed it works offline.
  - **Dependencies.** The release package fixes the exact version and integrity hash of every runtime dependency, in the `npm-shrinkwrap.json` it carries or by bundling them into the post office's code, so installing a release installs exactly the code CI tested. CI fails on a runtime dependency with a known advisory of moderate severity or above (`npm audit --omit=dev --audit-level=moderate`), or with a license outside the allowlist kept in the repository. Each release's notes list its runtime dependencies, with their versions and licenses.
  - The post office runs the helper and the script from the installed package. It never runs a copy in a temporary folder, which may be mounted `noexec`, or one written from a string.
  - The SHA-256 of each binary, of the script and of its DLL is written into the post office's code when the package is built. The post office checks each file against it before each run. A file that has changed is refused, for example after Shadow Army was updated under a running post office. A run refused for its checksum is a failed containment (PO-15), at a session's start or during it, and the reconnect's check gives PO-14's message.
  - A checkout of the repository holds no binaries. There, `npm run build` compiles the helper for its own system with that system's C compiler, or on Windows the DLL with the .NET SDK, and writes its checksum into that build. That path is for contributors and CI only; nothing in the package compiles anything.
- **PO-14** (M1; I, F) **No containment, no soldier.** A soldier's CLI MUST NOT start without containment.
  - **The check.** The post office checks containment on the machine as it is then, within 10 seconds. A check that hasn't passed 10 seconds after it began, on the monotonic clock, has failed: anything it started is killed, and its message names the step still running. It does this when it starts, before any soldier starts, and again before a soldier is reconnected or started after a failed check or a failed containment (PO-15):
    1. there is a helper for this system and processor (PO-12), and the post office can run it. On Windows, the script and its DLL are there (PO-19);
    2. each file's SHA-256 matches the one in the post office's code (PO-13);
    3. on Linux, the helper sets the subreaper mark and reads it back. On macOS, the helper finds every call it looks up at run time, every structure has the size it expects, and a signal through its own audit token is delivered (PO-18). On Windows, the script runs in FullLanguage mode (PO-19);
    4. a probe, a script in Shadow Army's package, starts in containment exactly as a CLI does. It starts a child, which starts a new session, forks a grandchild and exits. The listing shows the probe and the grandchild (PO-11), and on macOS the coalition is new (PO-18). The tree is then killed with no grace. Only the probe and the grandchild hold a pipe open for writing; on macOS it is a named pipe. When that pipe reaches its end, both have ended. That is the proof, not the listing or the helper's report.
  - **When a step fails,** no soldier starts, and the post office keeps running. Its log, each soldier's log and one line in Claude's transcript say what failed. Each names the system and its version, the processor and Shadow Army's version. From M5, `/army` shows it on each soldier's row (HOST-9, →M5). For example:
    - `No containment helper for linux-riscv64, so no soldier can start. Supported: Linux x64 and arm64, macOS, Windows x64 and arm64.`
    - `The containment helper doesn't match Shadow Army 2.0.1. If Shadow Army was just updated, start Claude Code again; otherwise reinstall it. No soldier can start.`
    - `Containment failed its check on macOS 27.1 (arm64): a test process outlived its containment. No soldier can start. A newer Shadow Army may fix this.`
    - `Containment can't be set up on Windows 11 (arm64): PowerShell runs Shadow Army's script in ConstrainedLanguage mode, as under an AppLocker or App Control policy. An administrator can allow the installed script, and its DLL where DLLs are enforced, with a hash rule made from the installed files. No soldier can start.`
  - **Who decides.** This spec decides. No setting, flag, environment variable or command lets the owner or the Monarch start a soldier uncontained, and the owner is never asked to accept one. The owner's way forward is the message's: reinstall Shadow Army, update it, or have an administrator allow the script.
  - **A failure is not remembered.** A reconnect, or the next start of a soldier, runs the check again without restarting the post office.
  - **When it passes,** the post office's log names the containment (a subreaper, a coalition or a job) and the SHA-256 of each file it checked.
  - **An update of the system** can change what containment rests on, most likely on macOS (PO-18). The first check after such an update fails, and no soldier starts until the owner installs a release whose check passes on that version. Nothing else changes: records, logs, worktrees and branches stay as they are. The project finds the break through PO-21's weekly run, and the fix ships as a patch release.
- **PO-15** (M1; F) **When containment fails during a session.**
  - **A guardian ended from outside.** If a session's guardian ends while the session is open, and the post office didn't ask it to, the channel has crashed (PO-1). Before anything else, the post office ends what it can still reach:
    - **macOS.** It removes the session's launchd job, so launchd doesn't start the guardian again, and then ends the coalition by the id it recorded (PO-10, PO-16). Nothing escapes, and the channel restarts as after any crash (PO-1).
    - **Windows.** The job's last handle closed with the guardian, so the system has ended every process in the job. Nothing in the job escapes, except as PO-1 states, and the channel restarts as after any crash (PO-1).
    - **Linux.** The kernel has handed the guardian's descendants to a subreaper above it, or to init, out of Shadow Army's reach. The post office ends every process still in the guardian's process group, and each process of the tree's listings whose identity still matches (PO-11, PO-16). Others may still run, so the containment has failed.
  - **The containment has failed** when a Linux guardian was ended from outside, and on any system when:
    - the helper or the script reports an error;
    - a session's containment isn't ready at its start (PO-9);
    - a tree isn't empty 10 seconds after its kill began (PO-10). One cause is a process that runs as another user through `sudo`, which the owner's user can't signal.
  - **Then:**
    - The soldier is down. Its log and one line in Claude's transcript say what failed, and name each process left by its pid and its command line through `redact()` (WSP-8). For example: `Containment failed for Iron: 1 process couldn't be ended (4242 sudo make install). Iron is down and won't restart by itself.` Where the post office can't tell which processes remain, as after a Linux guardian was ended from outside, the error says that processes the CLI started may still be running.
    - The soldier isn't restarted by itself, whatever PO-1's count says. A reconnect runs the check first (PO-14), and starts the CLI only once no process the error named still runs.
    - A turn that was running isn't over while a process the post office named still runs (PO-8, →M2). The turn's guard stays open and the soldier's queue waits. The post office tries to end those processes again every 10 seconds, and once all have ended it finishes the turn as PO-8 (→M2) says. Where it can't tell which processes remain, it finishes the turn as cut short (PO-8, →M2), and the error says that what those processes change won't be on the turn's attribution card.
- **PO-16** (M1; I, F) **What a dead post office leaves.** A guardian can end together with the post office, for example when both are killed.
  - **The record.** Before a CLI starts, the post office adds an entry for its tree under `.shadow/v2/trees/`: one JSON Lines file per tree, each line flushed as it is written. A reader skips a line that doesn't parse, as for logs (PO-5). The CLI doesn't start until its entry is written. If the entry can't be written, the CLI doesn't start, the containment has failed (PO-15), and the soldier's log and one line in Claude's transcript say why. A listing line that can't be added is reported as PO-5 says for a log write that fails. The entry holds:
    - the post office's pid and start time;
    - the guardian's identity, and the CLI's once it has started (PO-11);
    - on macOS, the launchd job's label and the coalition's id, which the kernel never reuses;
    - on Linux, the identity of each process each listing of the tree finds (PO-11), added as the post office lists it.

    The entry is removed once the tree has ended. It holds no secret and no nonce.
  - **The mod.** The post office's output can end with no shutdown event (PO-7). Then the mod has every tree that the post office's entries name ended at once, through the same code as the sweep below. It starts no post office for that (HOST-2).
  - **The sweep.** Before it opens any channel, and before it finishes what the last post office left open (PO-1), a post office ends every tree whose entry belongs to a post office that is no longer running. It judges that by the entry's pid and start time, as the lock does (PO-1):
    - **Linux.** Every recorded process whose identity still matches is ended. A process is never ended for its session or process-group id alone, because that id may now belong to an unrelated process.
    - **macOS.** The recorded job is removed if launchd still has it, and every member of the recorded coalition is ended (PO-10).
    - **Windows.** Nothing in the job is left: the job ended when its last handle closed. What PO-1 states escapes it.
  - **macOS.** launchd starts a killed guardian again (PO-18). A guardian that can't reach its post office, at its start or later, ends every other member of its coalition and then has launchd remove its job. Spike S7 measures how soon.
  - Claude's transcript gets one line, as in `the post office stopped unexpectedly; 3 processes Iron and Igris started were ended`. The log names each process, with its command line through `redact()` (WSP-8).
  - **What is left running.** Until the mod or the next post office ends them, those processes keep running. If the mod ended too, as when Claude Code is killed, they keep running until a post office next starts in this folder. On Linux, a process that no listing found keeps running. Both are stated residual risks (PO-1).
- **PO-17** (M1; X, R) **What the containment helper may do.** It does only the operations below, each named on its command line. It refuses any other operation and does nothing.
  - **Linux.** As the guardian: mark itself a child subreaper, start the CLI, watch its pipe to the post office, and end and reap the tree (PO-9, PO-10). It also runs its part of the check (PO-14).
  - **macOS.** As the guardian: connect back to the post office, start the CLI, pass the CLI's standard streams, and end the rest of its own coalition (PO-18). As a tool the post office runs: read a process's coalition, unique id and status; list a coalition's members; stop and kill, by their audit tokens, the members of one coalition that the post office recorded for a session; and run its part of the check.
  - It reports each result to the post office as one line of JSON. The report goes on a pipe of its own, or, for the macOS guardian, on its connection, and never on the CLI's standard streams.

  It MUST NOT:
  - signal or change any process outside its session's containment, signal a process in the post office's own coalition or launchd's, or signal by a pid that may have been reused;
  - start any program except the CLI (or the check's probe in its place) and, on macOS, `/bin/launchctl remove` for its own session's job;
  - open a network connection, except the macOS guardian's one connection to the post office on the loopback address (PO-2), or listen on any port;
  - create or write a file;
  - look into, keep or log the CLI's arguments, environment or standard streams, beyond passing them to the CLI unchanged (CH-7);
  - receive the Monarch's secret (PO-3), in its arguments, its environment or its input;
  - run with more than the owner's user's rights. It has no setuid or setgid bit and never asks for administrator rights, and its macOS signature grants no entitlement;
  - load any code except its own and the system's libraries;
  - leave anything behind. No process, launchd job or file of a session outlives that session, except as PO-16 says.

  Its source is C. It uses only the system's C library and headers, and has no third-party dependency. Every change to it is reviewed as security code, against these lists and PO-18's. Tests enforce what they can:
  - on Linux, the tests trace the shipped helper's own system calls in every containment test, and fail on any call outside an allowlist. VER-6's coverage job runs a copy instrumented for coverage, which writes its counts and never ships (PO-21), and is not traced;
  - on macOS, CI fails if the binary imports a symbol outside an allowlist, or if its signature carries an entitlement.
- **PO-18** (M1, M6; R, I, L) **macOS: the guardian, what it rests on, and signing.**
  - **Start.**
    - The post office has launchd start the session's guardian as a job of its own, with `launchctl submit` and a label unique to the session. `launchctl submit` needs no configuration file, and Shadow Army writes none: no launch agent, no login item.
    - The guardian connects back to the post office over the loopback address (PO-2) with a one-time nonce. The label is on its command line. The nonce reaches it in a file that only the owner's user can read, in a folder outside the folder's directory tree, and the post office removes that file once the guardian has connected. The Monarch's secret is never in either (PO-3).
    - Before it sends the CLI's command, the post office checks two things. launchd must list the guardian's pid under the session's label (`launchctl list`). The guardian's coalition must be new: not the post office's, and with no member but the guardian.
    - The post office records the coalition's id (PO-16), and passes the helper no other coalition.
  - **End.** As PO-10 says, with the job removed first. Because launchd keeps a job made with `launchctl submit` alive after a failure, a guardian that can't reach its post office ends the rest of its coalition and then has its job removed (PO-16).
  - **What it rests on.** Of all this, only `launchctl submit`, `list` and `remove` are documented, in launchctl's manual page, among its legacy subcommands. Everything else is an interface that Apple doesn't publish:
    - `proc_pidinfo`, `proc_listallpids` and `proc_signal_with_audittoken` come from `libproc.h`. That header's own comment says it "contains private interfaces", which "are subject to change in future releases";
    - the flavours that read a process's coalition, unique id and pid version (`PROC_PIDCOALITIONINFO`, `PROC_PIDUNIQIDENTIFIERINFO`), and their structures, come from `proc_info_private.h` in Apple's open-source kernel. The helper declares the structures itself;
    - `__proc_info_extended_id` ties each of those reads to one process by its unique id. No Apple header declares it;
    - the helper fills in an audit token with a pid and its pid version. The token's layout appears in Apple's kernel tests, not in its documentation;
    - Apple documents coalitions nowhere. That launchd gives each job a coalition of its own, and that a process's children join its coalition, is how Apple's kernel source and launchd behave today.

    Apple can change any of these in an update, without notice. The helper looks up the private calls each time it runs, not when it is built, and checks the size of every structure it reads. A missing call, a size that differs or a coalition that isn't new fails the check (PO-14), and then no soldier starts.
  - **Signing.** The macOS binary is signed with the project's Developer ID Application certificate, with the hardened runtime and a secure timestamp. Apple's notary service notarizes it, as Apple requires for software distributed with a Developer ID. It claims no entitlement. A notarization ticket can't be stapled to a standalone binary, so M6-AC11 confirms that an installed helper runs with the network off. Signing and notarization come with M6, before the first release (PO-20); until then CI's containment tests run on the macOS binary as it is built. A Developer ID needs the project's Apple Developer Program membership. The signing and notary credentials are used only by the release workflow (PO-20).
- **PO-19** (M1; I, F, R) **Windows: the script.**
  - The guardian is a PowerShell script that ships in Shadow Army's package as a file at a fixed path. Beside it is a DLL, a .NET assembly that declares the Windows functions the script calls. CI builds the DLL from Shadow Army's C# source for the .NET Framework 4 that Windows PowerShell 5.1 runs on, then tests it and checksums it with the binaries (PO-20, PO-21).
  - The post office runs the script from there, never from a copy written elsewhere. It uses Windows PowerShell 5.1, which ships with Windows, found by its absolute path in the Windows folder, never on `PATH`: `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <script>`. A Group Policy execution policy still overrides `Bypass`.
  - The script loads the DLL with `Add-Type -Path`, which takes the types from an assembly file and compiles nothing. No code sits in a string (VER-6).
  - The script does on Windows what PO-9 and PO-10 say. When its connection to the post office closes without a close command, it ends the job. If its own process ends, the job's last handle closes, and Windows ends every process in the job.
  - **The DACL.** Run with its DACL operation, before the post office reads the Monarch's secret, the script replaces the post office's DACL, its threads' and its token's default DACL as PO-3 says, then exits. As a guardian, it gives its own process the same DACL before it creates the job (PO-9).
  - **ConstrainedLanguage mode.** An AppLocker or App Control for Business policy that doesn't allow the script makes PowerShell run it in ConstrainedLanguage mode. In that mode `Add-Type` can't load C# code or Win32 functions, and loads an assembly only if it is signed, as the DLL isn't; nor can the script use a type outside the mode's allowed list. The script checks its language mode before anything else, and in that mode it refuses with that reason. The check then fails (PO-14), and no soldier starts. An administrator decides whether soldiers run on that machine, by allowing the installed script and its DLL with a hash rule made from the files themselves, as `New-AppLockerPolicy` makes one. AppLocker's file hash is a file's Authenticode hash, not the SHA-256 that `SHA256SUMS` lists (PO-20), which is for checking the files first. The hashes change whenever the script or the DLL changes.
  - It needs Windows 10 or 11, or Windows Server 2016 or later.
- **PO-20** (M1, M6; R) **Built, checked and attested in CI.**
  - **Where.** CI builds every binary, the Windows DLL included (PO-19), from the commit it tests or releases, on GitHub-hosted runners. No binary that ships is built anywhere else.
  - **Pinned toolchains.** The Linux binaries are built in a container image named by its digest. The macOS binary is built with a named Xcode version on a named runner image, and the Windows DLL with a named .NET SDK version on a named runner image, built with the C# compiler's deterministic output and its source paths mapped, so that no checkout path reaches the DLL. Changing either is a reviewed change to the workflow.
  - **Reproducible.** Two jobs on separate runners build each binary from the same commit. Their outputs MUST be byte-identical, with the macOS one compared before signing, or the run fails.
  - **Checksums.** The SHA-256 of every binary that ships, the DLL included, and of the Windows script, goes into the post office's code (PO-13), into a `SHA256SUMS` file in the package, and onto the release.
  - **Provenance.** Each binary and the package tarball get a GitHub artifact attestation, which `gh attestation verify <file> -R <owner>/<repo>` checks. A package published to the npm registry is published with provenance, which `npm audit signatures` checks. Both need the repository to be public when the release is built: npm makes no provenance for a private repository, and GitHub attests a private repository's builds only on GitHub Enterprise Cloud. A release built without them says so in its notes, and still has the checksums and the reproducible builds.
  - **The release.** The release workflow runs only for a release tag. In this order, it:
    1. builds the binaries again, and checks them against those the commit's CI run built and tested;
    2. signs and notarizes the macOS binary (PO-18);
    3. runs the containment tests on the signed bytes, on every macOS runner of PO-21;
    4. attests and publishes, only after the first three steps pass.

    Signing and notarization, steps 2 and 3, come with M6, before the first release (PO-18); until then a dry run skips step 2 and runs step 3 on the bytes step 1 checked. The Apple credentials are secrets of a GitHub environment that only this workflow uses. For a private repository, environment secrets need GitHub Pro, Team or Enterprise. Where GitHub offers required reviewers (a public repository, or GitHub Enterprise), the owner approves each run.
- **PO-21** (M1; R) **CI on every system and processor.**
  - Every CI run builds the binaries first (PO-20), and every later job uses those bytes, except VER-6's coverage job, which runs copies instrumented for coverage that never ship.
  - The containment tests (PO-9 to PO-11, PO-14 to PO-17, PO-19) run on:
    - Linux x64 and arm64, on the oldest and the newest Ubuntu that GitHub hosts;
    - Alpine Linux (musl) in a container, on x64 and arm64;
    - macOS on Apple silicon and on Intel, each on the oldest and the newest version that GitHub hosts;
    - Windows x64 and arm64.
  - **Install test.** On each of these systems, CI installs the package tarball with npm, with `--ignore-scripts`, and with the network off once the package's dependencies are in npm's cache. It then starts a fake soldier through the installed helper or script. The test passes only if the helper is still executable and every checksum still matches. It installs once more from a local registry that also holds a newer patch release of a runtime dependency, and passes only if the pinned version is the one installed (PO-13).
  - **Versions.** The install test and the containment tests run on Node.js 22 and on the newest Node.js release, and M1-AC10's git cases on git 2.34, git 2.54 and the newest git (HOST-2).
  - **Weekly.** A scheduled run tests the latest release on the newest runner image of each supported system, so a new image is tested within a week of GitHub offering it. A failure opens an issue. GitHub turns off a public repository's schedules after 60 days without activity, so each release's checklist confirms that the schedule is on.

### 4.3 Channels (CH)

- **CH-1** (M1; U, C) **One interface.** Each CLI has one adapter, and all adapters share one interface.
  - The interface: open a session in its snapshot or its worktree (WSP-11; WSP-1, →M6) with the standing instructions; send a message; interrupt the running turn; stream events; close.
  - Events: text, thinking, tool call, tool result, approval request, usage, turn end, error.
  - An error says which kind it is, read from the CLI's own fields: a rate limit (with its reset time where the CLI gives one), a context overflow, a login needed, or another error. Each keeps the CLI's message word for word, redacted (WSP-8).
  - A refusal is not an error: the turn ends with the model's own words, marked as a refusal.
  - A line the CLI writes that can't be parsed is recorded word for word, redacted (WSP-8), and shown as an error of the kind another error, and the session carries on; ten in a row count as a lost connection (PO-1) (from 2.0 SOLD-6). A line split across reads is joined first, and only one still incomplete when the stream ends is malformed. An event of a type the adapter doesn't know, or a field it doesn't know in a known event, is recorded in the soldier's log and otherwise ignored.
  - `cli` in `shadow.config.json` names one of the four adapters; any other value is refused at start. An adapter starts its CLI from an absolute path found on `PATH` alone, never in the folder, a worktree or a snapshot, and never through a relative `PATH` entry. On Windows the current folder is never searched.
- **CH-2** (M1; U, I, C, L) **claude.**
  - One long-lived `claude -p --input-format stream-json --output-format stream-json --verbose` process per soldier.
  - **Auto memory off.** The adapter starts each claude process with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in its environment, over any value the post office inherited, and in the `env` of the `--settings` it passes: inline, or, where the command line can't carry it, as a file written and removed as the instructions file below is. A settings file's `env` replaces a variable the process inherited, and `--settings` outranks the user's, the shared project and the local settings files, so none of them sets the variable back to `0`. Only managed settings outrank `--settings`: an organization's managed `env` that sets the variable to `0` turns auto memory back on, a stated residual risk. So claude neither loads nor writes its auto memory. Claude Code keeps one auto-memory directory per git repository, shared by all its worktrees, so a soldier's snapshot (WSP-11) would share the one the owner's own sessions load at every start. A soldier would then read the Monarch's `MEMORY.md`, and could save a memory that the owner's next session loads, outside briefs and reports (MSG-1, →M3). This changes one vendor default; it removes no tool and disables no safeguard (CH-7). Until a live run confirms it (M1-AC14), the spec relies on Claude Code's documentation (https://code.claude.com/docs/en/memory; decisions.md, D-19), which says that with the variable set to 1 claude neither creates nor loads auto-memory files. `CLAUDE.md` files still load as the vendor intends.
  - It needs claude 2.1.277 or later: 2.1.259 brought `--permission-prompts`, and 2.1.277 the totals a resumed session restores (a turn's own figures, below). A later version is needed where a field this adapter reads needs one; each such need is named beside its rule, with the version it was read from (CH-8, →M2). Before it opens a session, the adapter reads `claude --version`. An older claude opens no session and never counts as a crash (PO-1): the soldier's log says `claude <found> is older than <oldest>; update claude`, and Claude's transcript gets that line.
  - From M2 it runs with `--permission-prompts host --permission-prompt-tool stdio`, so each permission request arrives as a `control_request` (`can_use_tool`) for the relay (CH-6, →M2). In M1, before the relay exists, it runs without `--permission-prompt-tool stdio`, so claude denies by itself whatever would need an answer (spike S5), and nothing waits. It never runs with `--permission-prompts none`, which removes tools such as AskUserQuestion (CH-7).
  - It passes the permission mode of the soldier's autonomy on every start and resume, as v1 does (`src/adapters/claude.ts`): `--permission-mode plan` for supervised, and from M6 `acceptEdits` for a writing turn (ARM-5, →M6), set inside the live session before its message goes in (CH-11, →M6); `--permission-mode auto` for auto; and `--permission-mode bypassPermissions` for full.
    - **What supervised lets claude run** in a turn that doesn't write. This is `plan` in a `-p` session, as claude's permission-mode documentation describes it (https://code.claude.com/docs/en/permission-modes, read 2026-10-23). claude reads, and runs the shell commands of its built-in read-only set, without asking. It edits no file, because plan mode keeps its blocks wherever claude runs without an interactive terminal. Every other shell command goes one of two ways:
      - Where auto mode is available to the session and `useAutoModeDuringPlan` is on, claude's classifier reviews the command instead of the owner. Auto mode is available as claude's permission-mode documentation lists it: on the Anthropic API and Claude Platform on AWS for Opus and Sonnet 4.6 or later, Haiku 5.5 and the Fable models, and on Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry and signed-in Claude apps gateway sessions for Sonnet 5 or later, Opus 4.7 or later, Haiku 5.5 (with claude 2.1.293 or later) and the Fable models, unless an organization's `disableAutoMode` or Anthropic turns it off. `useAutoModeDuringPlan` is on by default. A command the classifier approves runs without the owner, in the soldier's snapshot (WSP-11) or worktree (WSP-1, →M6), where its writes are discarded and reported as WSP-11 says in a snapshot, and reverted in a worktree as WSP-12 (→M6) says. A command it rejects is blocked. A write to a protected path, such as `.git/` or `.claude/`, goes to the classifier too. A removal of a critical path is handled as in auto mode, which denies it in a `-p` session from claude 2.1.281; an older claude may send it to the classifier instead. Where the environment the soldier inherits sets `CLAUDE_CODE_DISABLE_DANGEROUS_RM_TIMEOUT=1`, or `CLAUDE_CODE_DISABLE_INLINE_SHELL_RM_PROMPT=1` for a path typed in a `-c` script, such a removal goes to the classifier too; no adapter changes that (CH-7).
      - Where auto mode isn't available, or `useAutoModeDuringPlan` is off, the command asks, through the relay from M2 (CH-6, →M2). In M1, which has no relay, claude denies it by itself, as it does every request that would need an answer (spike S5), and nothing waits.
    - Only the owner turns the classifier off, by setting `useAutoModeDuringPlan` to false in their user settings (`~/.claude/settings.json`), in their local project settings (`.claude/settings.local.json`, which claude reads from the main checkout's root when it runs in a linked worktree such as a soldier's snapshot, except on Windows, where it reads the snapshot's own), or in managed settings. A false in `--settings` would turn it off too, and the `--settings` the adapter passes never sets it. A repository's `.claude/settings.json` can't turn it off, and a false in any file that may set it wins. No adapter passes or writes this setting (CH-7). So unless the owner has turned the classifier off, a supervised claude soldier's read-only turn runs the commands claude's classifier approves, without the owner.
  - The instructions go in `--append-system-prompt`, or in `--append-system-prompt-file` where the command line can't carry them, as through a Windows `.cmd` shim. That file is written by the post office beside the session's log under `.shadow/v2/logs/` (PO-5), never in a worktree, a snapshot or the system's temporary folder, and removed when the process ends.
  - Each message goes in with its own `uuid`, and with `priority` `later`, so that claude never folds it into a turn already running. A `result` ends a message's turn only when its `user_message_uuid`, or its `user_message_uuids` list, names that message. A `result` with the origin kind `task-notification` that comes after claude's `task_notification` for a task a message's turn started belongs to that message (PO-8, →M2). Any other `result`, the zeroed one after a crash included, is recorded in the soldier's log and ends nothing; a crash still ends its turn (PO-1).
  - **Error kinds**, from claude's own fields (CH-1): a rate limit is a `rate_limit_event` whose `status` is `rejected`, with `resetsAt` as its reset time, or a failing turn's `error` `rate_limit` or `api_error_status` 429, and `allowed_warning` is not an error; a context overflow is `terminal_reason` `prompt_too_long`; a login needed is `authentication_failed`, `oauth_org_not_allowed` or `cloud_credential_error`; any other error is another error. A refusal is an assistant message whose `message.stop_reason` is `refusal`, as section 5.1 C's synthetic recording has it. Probe P-14 settles whether Claude Code's stream-json passes that message through, or its automatic fallback answers instead (the model in use, below), and whether the `result` carries it; then this rule names the field the probe shows. A `system/api_retry` event is shown as a retry, with its attempt and delay, and is not an error.
  - **The model in use** is the one claude reports for the main conversation: `system/init`'s `model`, then each main-conversation assistant message's `message.model`. When claude changes it by itself, as its automatic fallback does for a flagged request, the soldier's log records the change, and the pane's header (HOST-4, →M5) and the turn's usage record (OBS-3, →M4) name that model. The roster keeps the configured one (ARM-1). Such a switch is not a change made before a message (SES-6, →M4): the turn's later requests ran on the new model, so the timer runs from the last of them. No adapter passes a setting that changes claude's fallback (CH-7).
  - The context size is the usage of the last assistant message in the main conversation, whose `parent_tool_use_id` is null: its `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` together. A subagent's messages never set it.
  - **A turn's own figures.** claude's `result` gives `usage` for the turn's main loop only. Its `total_cost_usd` and `modelUsage` are running totals for its process, subagents included, plus the earlier spend of a session it resumed. A turn's tokens, by model, and its cost are its result's `modelUsage` and `total_cost_usd` less those of the result before it: nothing, for a new session's first turn; the previous result in the same process; or, for the first turn after a resume (CH-9, →M2), the last result of the process before it, if that process exited normally.
    - With no such result, the turn's cost reads "not reported", and its tokens are its main-loop ones: input and cache summed over its main-loop assistant messages, each message id counted once, and output from its `usage`, since an assistant message's own output count is a placeholder.
    - A result whose `usage`, `total_cost_usd` and `modelUsage` are all zero, as after a crash, and after a stop where spike S6's recording shows it, reports nothing. That turn's input and cache are summed the same way, and its output and cost read "not reported".
    - A result whose `total_cost_usd` is zero is never a baseline: the next result has no result before it, so its cost reads "not reported", its tokens are its main-loop ones, and its totals become the baseline.
    - claude starts its totals over after a message that is `/clear`, `/reset` or `/new`: that turn's result's own totals are its figures, and it is the next baseline. A result whose `total_cost_usd` is above zero but below the baseline's has started over too, and is taken the same way.
    - The cost is claude's own estimate. SES-7 (→M4), HOST-15 (→M5) and section 5.1's live checks use these turn figures, never running totals.
- **CH-3** (M2; C, L) **codex.**
  - `codex app-server` over stdio: `thread/start` with `developerInstructions`, then `turn/start` for each message.
  - A turn ends with `turn/completed`.
  - Usage and the context window come from `thread/tokenUsage/updated`.
  - From M6, at `supervised` each `turn/start` carries its turn's `sandboxPolicy` (CH-11, →M6), because codex keeps a turn's overrides as the thread's defaults for later turns.
- **CH-4** (M2; C, L) **grok.**
  - `grok agent stdio`, over the CLI's standard streams. `grok agent serve` is not used.
  - `session/new` carries the instructions in `_meta.rules`, and `session/prompt` sends each message.
  - Usage comes from the prompt result's `_meta.usage`.
  - From M6, at `supervised` the adapter sets a turn's mode before `session/prompt` with ACP's `session/set_mode`, to a mode that `session/new` lists, and waits for the answer (CH-11, →M6).
- **CH-5** (M2; C, L) **agy.**
  - One long-lived `agy --input-format stream-json --output-format stream-json` process, whose messages are `{"event":"user",…}`.
  - agy's own modes do not stop it writing: in spike S5 it wrote a file even with `--mode plan`. It therefore always runs as ARM-6 says.
  - The instructions lead the first message, because agy has no slot for them.
  - A turn ends with the `result` event. Its usage is a running total, and its input excludes cached tokens.
  - The context size comes from its `agent_response` steps only (SES-2, →M4).
- **CH-6** (M2; C, I) **Approval relay.**
  - claude, codex and grok ask through their own protocols (spike S5): claude's `can_use_tool` control request (CH-2), codex's `item/commandExecution/requestApproval` and `item/fileChange/requestApproval`, and grok's ACP `session/request_permission`.
  - Each request is shown word for word, with the CLI's own options, and the owner's answer goes back unchanged.
  - In a read-only turn (ARM-5, →M6), each request has one more line under it, Shadow Army's own and not the CLI's: `read-only turn: whatever this writes is reverted`. The answer still goes back unchanged, and whatever the approved tool writes is reverted, or discarded in a snapshot (WSP-12, →M6; WSP-11).
  - No adapter answers a request by itself. An unanswered request stays pending (spike S5) until the owner answers it or stops its turn, or the post office shuts down (PO-7), which closes it as a stop does.
  - **A stop cancels the turn's requests.** Stopping a turn (MSG-9, →M3) is the owner's answer to every request that turn still has open, and it approves nothing: the tool does not run. Each request is closed the way its CLI's protocol closes a cancelled turn's requests:
    - grok's adapter answers each `session/request_permission` with the `cancelled` outcome, as ACP requires;
    - claude withdraws its request with a `control_cancel_request`;
    - codex clears its request and says so with `serverRequest/resolved`.

    Spike S6 confirms claude's and codex's. A request still open when its turn ends is closed then, and no answer is sent for it afterwards.
  - A closed request's card leaves the decisions list (HOST-14, →M5). An answer given after it closed, such as a key pressed as the card goes, is dropped and never reaches the CLI.
  - agy has no relay, and its adapter declares that it has none. Headless agy has no approval protocol: it soft-denies any tool that would need a confirmation and carries on, and a `control_request` or `control_response` sent to it ends its session with exit code 2. The adapter therefore never sends either. It shows each denial agy reports on its standard error word for word, redacted (WSP-8), as a tool call that agy denied.
- **CH-7** (M1; R, U) **The harness stays whole.**
  - No adapter replaces a system prompt or removes a tool, and none passes, on its own, a flag that disables a safeguard: such a flag, like claude's `bypassPermissions` for `full`, goes only where the owner's autonomy level chose it (ADR-0010).
  - Autonomy chooses only each vendor's documented flags (from 2.0 SAFE-10). Each adapter passes its CLI's permission mode at every autonomy level, on every start and resume, so the mode comes from the autonomy level, not from a settings file or the CLI's own default: claude's in CH-2, and codex's, grok's and agy's with their channels (CH-3 to CH-5, →M2). A CLI can still refuse the mode passed: claude starts in Manual when auto mode isn't available to the session, as when a settings file sets `disableAutoMode` or the model has none. Wherever the mode a CLI reports differs from the one passed (claude's `system/init` `permissionMode`), the soldier's log and one line in Claude's transcript name both.
  - The read-only rule (ARM-5, →M6; ARM-8, →M6; WSP-12, →M6) never depends on a vendor's mode. It works through where a session runs and through Shadow Army's own checks once each turn is over, so it holds whatever mode the CLI runs in, as it must for agy (spike S5). The one mode a turn's kind chooses is at `supervised`, between turns, as v1's flags do (CH-11, →M6); at `auto` and `full` no turn changes the CLI's mode. Apart from that, no adapter passes, drops or switches a vendor flag or mode to enforce the rule.
- **CH-8** (M2; U) **Versions.**
  - Each adapter records the CLI version its contract fixtures were recorded with.
  - A version newer than its fixtures connects. The soldier's log and one line in Claude's transcript say so once per CLI and version, as in `claude 2.1.294 is newer than its adapter's fixtures (2.1.293)`, and `/army` lists it. It waits on nothing, so it raises no card, toast or decision.
  - A line that cannot be parsed is an error, never silently dropped.
- **CH-9** (M2; C) **Resume.** After a crash, a channel reopens the soldier's previous session by id where the CLI supports it: claude `--resume`, codex `thread/resume`, grok `session/load`, agy `--conversation`.
- **CH-10** (M2; C, L) **Interrupt.**
  - Each adapter stops a running turn through its CLI's own interrupt, and the session stays open: claude's stream-json `interrupt` control request, codex `turn/interrupt`, and grok's ACP `session/cancel`. The stop also closes the turn's open requests (CH-6).
  - The turn has stopped only when its end event comes (PO-8): claude's `result`; codex's `turn/completed`, with the status `interrupted` unless the turn had already finished; or grok's answer to the original `session/prompt`, with the `cancelled` stop reason. Events that arrive before then belong to the stopped turn, and are shown and recorded. No message goes in until then.
  - A CLI whose turn has not ended within 30 seconds of the stop, on the monotonic clock, is stopped as one with no interrupt.
  - Spike S6 confirms each one, and looks for agy's.
  - A CLI with no interrupt is stopped by ending its process tree. The turn is finished as PO-8 says, and then the session is resumed by id (CH-9). The soldier's log says it was resumed, as does the pane (HOST-4, →M5).

- **CH-11** (M6; C, I, F) **At `supervised`, each turn runs in the mode its kind chooses, set between turns.**
  - The read-only rule never depends on a vendor's mode: it holds whatever mode the CLI runs in (ARM-8, WSP-12, CH-7). What this requirement sets is the mode at `supervised`, where v1 chooses a CLI's flags by its autonomy and by whether the task writes (`src/adapters/claude.ts`, `codex.ts`, `grok.ts`). From M6, a turn that doesn't write (ARM-5) and a writing turn each run in the mode v1 gives them:
    - claude: `plan` (CH-2), and `acceptEdits`;
    - codex: the `readOnly` sandbox policy, and `workspaceWrite`;
    - grok: `plan`, and `acceptEdits`.

    At `auto` and `full` no turn changes the CLI's mode: every turn runs in the mode its autonomy chose (CH-7).
  - **Set between turns.** The adapter sets a turn's mode after the turn before it is over (PO-8) and before its message goes in, so a mode never changes during a turn. It does so before every message, whatever mode it believes the CLI is in, because a CLI can leave a mode by itself (below). A turn the CLI starts by itself keeps its message's mode (PO-8).
    - claude: through the stream-json control request behind the Agent SDK's `setPermissionMode()`, which the SDK documents as taking effect immediately for all later tool requests.
    - codex: in the `sandboxPolicy` of the turn's own `turn/start`. codex keeps a turn's overrides as the thread's defaults for later turns, so every `turn/start` at `supervised` carries its turn's policy. The approval policy stays the autonomy's.
    - grok: through ACP's `session/set_mode`, to a mode that `session/new` lists.
  - **A message goes in only once the CLI has answered** the request that sets its turn's mode, which for codex is the `turn/start` that carries it. If the CLI refuses, or doesn't answer within 10 seconds on the monotonic clock, nothing is sent:
    - the message stays queued, and its row says why, as in `waits · mode not set · <the CLI's words>`;
    - the queue is held (MSG-3) and joins the decisions list (HOST-14);
    - the soldier's log and one line in Claude's transcript say so, and g tries again.
  - A CLI that has no way to set its mode in a live session, such as a grok that lists no modes, keeps the mode it opened in, and the soldier's log says so. The read-only rule still holds (WSP-12). A mode that the CLI reports and that differs from the one set is logged as CH-7 says.
  - **A plan approved in claude.** In `plan`, a soldier can call ExitPlanMode. From M2, approving it through the relay (CH-6) may switch the live session out of `plan`, as the vendor's documentation says approving a plan does in an interactive session; whether it does in a stream-json `-p` session is for a probe (R-M1-93). Because the adapter sets the mode again before every message, a mode left that way lasts until the next message, and the turn stays read-only (WSP-12).
  - **Cold.** A mode that differs from the one before is a change to the soldier's permission mode (SES-6).
  - **What the vendors document.** claude's `setPermissionMode()` is in the Agent SDK's permissions page, and codex's per-turn `sandboxPolicy` override in its app-server page. These are not documented: the control request that claude's CLI takes in stream-json for the first, and whether `grok agent stdio` lists modes and takes `session/set_mode` for the third, as ACP's session-modes page describes. A contract fixture shows each before M6 (section 5.1, C; VER-4).

### 4.4 Standing instructions (SI)

- **SI-1** (M1; U) **Content.**
  - The soldier's shadow name, model and roles.
  - The whole team with their roles, and Claude as the Monarch.
  - The hard rules (ARM-2, →M3), `rules.md`, and the soldier's `agent.md` section.
  - The reply format: at most five lines of at most 120 characters each (what was done, which files, what to check).
  - The handoff instruction: when asked for a handoff (SES-4, →M4), reply under working on, done, decided, files and open.
- **SI-2** (M1, M2; C) **Injection.** The instructions go in through each CLI's append slot (CH-2 to CH-5) and MUST NOT replace the vendor's prompt. agy's first-message fallback shows in the post office view.
- **SI-3** (M1; U) **Size.** The instructions stay under 1,500 tokens, counted offline as their UTF-8 bytes divided by 3 and rounded up, the same way in CI and at start; they measured about 1,000 on 2026-10-07. A soldier whose instructions count 1,500 or more does not open: its log, and one line in Claude's transcript, give the count and name `rules.md` or its `agent.md` section to shorten. The text is never cut (SI-1).
- **SI-4** (M4; I) **Fresh sessions.** A fresh session receives the instructions again, with the handoff summary when there is one.
  - The instructions are fixed for a session's life. The post office keeps the exact text each session started with, in that session's record.
  - A resumed session (CH-9) gets that same text wherever its CLI takes instructions on a resume, never a text rebuilt from the files. agy's led its first message, so nothing is sent again. claude also keeps the system prompt it recorded on the session's first request, until the session is compacted.
  - An edit to `rules.md` or a soldier's `agent.md` section reaches that soldier with its next fresh session. Claude's transcript gets one line per edit, naming the soldiers whose open sessions keep the older instructions.

### 4.5 Messaging (MSG)

- **MSG-1** (M3; R, I) **Only briefs and summaries cross between models** (from v1's isolation rule). A message never carries a transcript or a file's contents; files travel through branches.
  - What a soldier wrote reaches another model only as that soldier's quoted words, named as such. A summary, a soldier-to-soldier message or an error is never presented as the owner's or the Monarch's instructions. Only the Monarch's briefs assign work (ARM-4).
  - **At most 24,000 characters.** A message's text, whether a brief, a soldier's `send` or the owner's own, has at most 24,000 characters, counted as Unicode code points. 24,000 is v1's figure for a whole brief, which v1 counted in UTF-16 units. A longer one is refused before anything is queued (MSG-3), with its length and the cap, as in `the brief is 31,240 characters; the limit is 24,000`. A change to a queued message's text (MSG-10) past the cap is refused, and the old text stays queued.
- **MSG-2** (M3; U) **Names.** A message is addressed by shadow name, case-insensitively. An unknown name suggests the closest one, and nothing is sent.
- **MSG-3** (M3; I, F) **One turn, and the queue.**
  - A message is one turn in the recipient's open session.
  - A message to a soldier that cannot take it now is queued: the soldier is mid-turn (background work included, PO-8), starting, reconnecting, disconnected, or needs a login. Each soldier's queue runs first in, first out.
  - A queued message goes by itself as soon as the soldier can take it, including after a reconnect. Its row says what it waits for, such as "sends when Bellion is back".
  - A held queue waits for the owner instead: after a stop (MSG-9), while a handoff card (SES-4, →M4) or an attribution card (ARM-6) is open, after a turn's mode couldn't be set (CH-11, →M6), and after a read-only turn's revert failed (WSP-12, →M6).
  - Nothing in a queue is dropped silently.
  - **At most nine waiting.** A soldier's queue holds at most nine messages, held or not, so the queue view's keys 1 to 9 reach each one (HOST-5, →M5). A send that would make a tenth is refused, and so is sending again a message not delivered (MSG-4). What is already queued stays as it was. A summary going back to a soldier (MSG-5) is never refused, and doesn't count. The owner makes room by cancelling a queued message (MSG-10), and each message the soldier takes makes room too.
  - **A refused send** is not a message: it has no id, no record and no turn, and nothing is queued or sent. MSG-1's size, this cap and MSG-6's rate refuse a send as ARM-2's hard rules do. The refusal goes back to the sender at once, with its reason and the cap, as in `Iron's queue is full (9 waiting) · cancel one to make room`:
    - Claude's `send` returns it (HOST-10), and the brief's row says so (HOST-11);
    - a soldier's `send` returns it as the tool's result, which the soldier's pane shows (PO-4);
    - the owner's own message (MSG-7) is refused where it was typed, and the pane's field keeps its text.

    The post office's log keeps each refusal with its sender, recipient, size and reason (PO-5). MSG-8 doesn't wait for a refused brief. These caps are fixed in v2.0; no setting changes them.
- **MSG-4** (M3; U, S) **Delivery states.** The state updates in place, always as a glyph and a word.
  - A message moves through queued, delivered and answered.
  - Otherwise it ends in one of three ways, each with its reason:
    - **interrupted:** it was delivered, but no summary came back: the owner stopped the turn, the CLI crashed, the CLI reported the turn as failed (PO-8), the post office shut down or stopped unexpectedly (PO-7, PO-1), or the owner answered n to the guard's attribution card (ARM-6). The turn may already have changed files, so the row shows the changes made since the turn began, or for a read-only turn what was reverted (MSG-11, →M6; WSP-12, →M6);
    - **not delivered:** it never reached the session, for example because the post office stopped first. Nothing was sent, so it is safe to send again;
    - **cancelled:** the owner cancelled it while it was queued (MSG-10).
  - "Failed" is not a state. Each ending says which of these happened.
  - **Sending again.** A message that ended not delivered may be sent again as it is (r): none of it reached the session.
    - An interrupted message is never sent again, by itself or by a single key, because its turn may already have changed files. The post office refuses to send it again, and says why.
    - The post office records a message as delivered, and flushes the record to disk, before it writes the message to the CLI. A crash between the two, the machine's included, can then only lose a send, which shows as interrupted, and never repeat one. If the record can't be written, the message isn't sent: it stays queued, and its row says why, as in `waits · records can't be written · disk full`. A record line cut off by a crash is skipped when the records are read; because of the flush, its message never reached the CLI.
    - r puts an interrupted message's text back in the field instead, above the changes its turn made (d). The owner edits it or keeps it, and Enter sends it as a new message with its own id. Its row says which message it repeats, and it takes that message's kind (ARM-5, →M6).
- **MSG-5** (M3; U, I) **Summaries.**
  - A summary has at most five lines of at most 120 characters each, counted as Unicode code points, as MSG-1 counts them, the same at any width. A longer line is cut to 119 and …, never inside a code point, a longer reply to its first five lines, and the whole reply is saved as the report, up to PO-6's cap of 2 MiB.
  - The summary goes back to whoever sent the message.
  - For the Monarch, it is added to Claude's conversation as a summary card. The card's title says "answered", and it also states the facts of MSG-11 (→M6).
  - A summary for a brief Claude sent before a `/clear`, `/resume` or `/branch` arrives in the conversation Claude Code is in now, and its card says so, as in `answered · a brief from before /clear`. It wakes Claude as any summary does (MSG-8).
- **MSG-6** (M3; I) **Soldier to soldier.** Soldiers message each other through `send` (PO-4). Both panes show the message in full; Claude's transcript gets one line. A soldier MUST NOT assign work to another; only the Monarch briefs.
  - **At most five sends in 10 minutes.** The sends the post office accepts from a soldier, queued or delivered, count against that soldier across its sessions, on the post office's monotonic clock (PO-7). A sixth within any 10 minutes is refused as MSG-3 says, with when the next can go, as in `Beru has sent 5 messages in 10 min · next at 14:32`. A refused call doesn't count, and a summary going back to the sender (MSG-5) is not a send.
  - Each accepted send is a paid turn for its recipient (G5), so the owner is told of a soldier at the cap. Its pane shows each refused call, and Claude's transcript gets one line for each run of refusals, as in `Shadow Army: Beru's sends refused · 5 in 10 min · s stops its turn`. The next such line comes only after one of its sends has been accepted again. The owner can stop its turn (MSG-9) or start it fresh (SES-5, →M4); otherwise the cap lifts by itself as the 10 minutes pass.
- **MSG-7** (M3; I) **The owner, directly.** The owner types into a soldier through the pane's field or `/send`, as "you". Such a message is a read-only turn unless `/send` gave it the kind build (ARM-5, →M6). Claude's conversation gets one line saying that soldier's context changed.
- **MSG-8** (M3; I, L) **Waking the Monarch.** When a summary arrives and Claude is idle, the mod starts a turn only if the brief asked for a reply. The `send` tool asks for one by default. Otherwise the card waits for Claude's next turn. If Claude is mid-turn, the card joins the running turn and no new turn starts. Summaries that arrive within a few seconds of each other, on the monotonic clock, share one wake (spike S2). Briefs that Claude sends in one turn wake it once, when the last of them has answered or ended; a brief that must be read on its own sets `wake: "own"`.
- **MSG-9** (M3; U, I, S) **Stop a turn.**
  - s in the pane, or `/stop <soldier>`, stops that soldier's running turn through its CLI's own interrupt (CH-10).
  - Until the stopped turn has ended, the soldier's state is "stopping": the pane shows `■ stopping the turn…`, s is not offered, and messages wait in the queue. This normally lasts a second or two. If the CLI is ended after 30 seconds instead (CH-10), the pane says so, as in `claude did not end the turn within 30 s, so it was ended and its session resumed`.
  - Any approval request the turn has open is cancelled, never approved, and its card closes (CH-6).
  - When the turn's end event has come but background work it started is still running (PO-8), s stops that work instead: each task through the CLI, such as claude's `stop_task`, and each process the turn left running. A session service, such as a plugin's language server, keeps running (PO-8).
  - The session stays open with its history, and the work done so far stays in the soldier's worktree, except a read-only turn's writes, which are reverted (WSP-12, →M6). This is not starting fresh (SES-5, →M4).
  - The message ends as interrupted, with the changes made so far (MSG-4), unless its turn had already ended by itself; then it ends as PO-8 says.
  - The soldier's queue is then held, so older instructions do not run by themselves. g sends the held queue; a new message from the owner goes first. Either goes in only once the stopped turn has ended (CH-10, PO-8).
  - Claude's transcript gets one line, so Claude knows the turn was stopped.
- **MSG-10** (M3; U, I, S) **The queue is visible, and the owner controls it.**
  - The pane's header shows how many messages are queued, and q opens the queue: each message's sender, age and first line.
  - The owner can cancel a queued message, or change its text before it is delivered. A cancel or change that reaches the post office after the message was delivered is refused with `already delivered`, and Claude gets no line.
  - When the message was Claude's brief, Claude's transcript gets one line saying it was cancelled or changed.
  - `/queue [soldier]` prints the queues in the transcript.
- **MSG-11** (M6; U, I, S) **Facts on the summary card.** Beside "answered", the card states these, from the post office's own records and never from the summary's text:
  - **changes:** the files and lines the turn changed on the soldier's branch, or "none". For a read-only turn that wrote, it says "none", then `read-violation:` and each path reverted or discarded (WSP-12, WSP-11);
  - **tests:** whether a test command ran in the turn and whether it passed, by its exit code where the CLI reports one, or "not run". Test commands match the soldier's `tests` patterns in `shadow.config.json`, by default `npm test`, `npx vitest`, `pytest`, `cargo test` and `go test`;
  - **applied:** "not yet", or when the changes were applied to the folder (WSP-9);
  - the report's path, and the commands that act on the work (`/diff`, `/apply`).

### 4.6 Sessions (SES)

- **SES-1** (M4; I) **One session per soldier.** Each soldier has one open session per Claude Code process, and related work accumulates in it. `/clear`, `/resume` and `/branch` keep it open, since they keep the army (PO-7).
- **SES-2** (M4; U, S) **The meter.**
  - It shows the context size from the CLI's own events, as a bar up to the handoff line, with colour steps at 30, 50, 70 and 90%.
  - Its text names both measures, as in `142k / 200k handoff · 55% window`. The bar measures the first; the share of the window shows only where the CLI reports its window.
  - Where the context size comes from (spike S3):
    - claude: the last assistant message in the main conversation (CH-2);
    - codex: `thread/tokenUsage/updated` → `last`;
    - grok: the session's `signals.json`, `contextTokensUsed`;
    - agy: the latest `agent_response` step to reach `DONE`, its input tokens plus cache reads.
  - Usage from an auxiliary call, such as a claude subagent's or an agy `checkpoint` step's, is recorded (OBS-3) but never moves the meter.
- **SES-3** (M4; U) **Near handoff.** At 90% of the handoff line (180k by default), the soldier shows "near handoff".
- **SES-4** (M4; I, S) **Handoff.**
  - At the handoff line, the soldier is asked for a handoff summary covering: working on, done, decided, files, open.
  - While the soldier writes it, the state is "preparing handoff". Once the card is ready, the state is "handoff ready", which needs the owner: it shows in bold, keeps its word in the strip, and joins the decisions list (HOST-14, →M5).
  - A card in its pane offers three choices: a accepts (a fresh session starts with the summary), e edits it first, and g keeps going and asks again after 20k more.
  - Messages to that soldier are held until the owner chooses.
- **SES-5** (M4; I) **Start fresh.**
  - `/fresh` or f in the pane closes the session, keeps its log, and starts a new one with the standing instructions.
  - The soldier's work stays on its branch, and nothing is reverted, except a read-only turn's revert still pending, which is tried again (WSP-12, →M6).
  - A handoff first is optional.
  - Stopping a turn (MSG-9) is different: it keeps the session.
- **SES-6** (M4; U, S) **Cold.**
  - Cold is an estimate, made before a message is sent: the time since the soldier's last model request is longer than its cache lifetime. That time is real time, sleep included: the larger of the wall clock's and the monotonic clock's time since the request, so a sleep counts and a clock set back never keeps a soldier warm.
  - **A change to the soldier's model, effort, tools or permission mode** (MCP servers included; a mode set for one turn, CH-11, →M6) moves the estimate only as its CLI's documentation says that change affects the cache, for the model and sign-in in use. Each adapter keeps these rules in a table, with the CLI version they were read from (CH-8). Standing instructions never change within a session (SI-4).
    - A change the table says resets the cache makes the soldier cold at once, whatever its idle time and even when its lifetime is unknown. For claude: another model; effort, on a model or sign-in where each effort level has its own cache; and tools added or removed while they load up front.
    - A change the table says keeps the cache leaves the estimate as it was. For claude: effort on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 with an API key or a Claude subscription; an MCP server connected or removed while tool search defers MCP tools, as it does by default; and a plugin's skills, commands, agents and hooks.
    - With any other change, or when the adapter cannot tell which case applies, the estimate is unknown until the soldier's next model request: the timer goes, and that spot says what changed, as in `cache unknown · tools changed`. The soldier is not shown as cold.
  - The lifetime comes from, in order:
    - the owner's `cacheLifetime` for that soldier (SET-1);
    - what the CLI reports with its usage: claude marks each cache write as lasting 5 minutes or 1 hour (`cache_creation`), and every write in the 2026-10-07 live probes was for 1 hour;
    - the provider's documentation for that model.

    With none of these, the estimate is "unknown": no timer, and the soldier is shown as cold only after a change that resets the cache.
  - **The timer.** While the soldier is warm and its lifetime is known, the right end of the pane's meter line counts down to the minute from its last model request: `cold in 12m`, then `cold in <1m`. It changes as a value once a minute, never as motion (VIS-4, →M5).
  - When the time runs out, that spot reads `❄ cold since 13:53`. After a change that resets the cache it says why, as in `❄ cold · model changed`.
  - **The quick message.** `the next message likely re-reads the full 142k context`, with the soldier's context size, shows once in the session when the soldier turns cold, and in the field while the owner is in a cold soldier's field. It says "likely" because cold is an estimate. It goes when the message is sent or the owner leaves the field. It is not a toast (HOST-8, →M5).
  - What actually happened is kept apart from the estimate. Each request's cache reads are recorded with its usage (OBS-3), and a request whose cache reads fall to about zero counts as a miss. A miss never sets or shortens a lifetime: a changed prefix, compaction or the provider's routing can cause one while the cache is still held.
- **SES-7** (M4; U, S) **Usage today.** `/sessions` lists, for each soldier: sessions, messages, input (cache writes and reads included), the cached share, output, and cost where the CLI reports one ("—" otherwise), with claude's marked `est.` (CH-2). A total row follows; its cost is the sum of the costs shown, marked `est.` when one is, and followed by `+ N not reported` while any soldier shows "—".
- **SES-8** (M4; U) **The handoff line is set per soldier** (`handoffAt`). Where the CLI reports a window, the line MUST stay below it.

### 4.7 The army and its rules (ARM)

- **ARM-1** (M1; U) **The roster carries over** (from v1's design rules). Roles, cost, `forbidden` and `write` live in `orchestratorDelegate.md`; `cli`, `model` and `autonomy` live in `shadow.config.json`. Both files list the same soldiers.
  - v1's `monarch` block and `orchestrate` role mean nothing in v2: Claude is the Monarch (ADR-0008), and no brief asks for orchestration (HOST-10, →M3).
  - codex-astra (Bellion) takes review and hard builds (`build` with `buildFor: [hard]`), as claude-opus does, and keeps `orchestrate`, so v1's `monarch` block and v1's Monarch stay as they are until LEG-1 (→M6). It is listed after claude-opus in `orchestratorDelegate.md`, whose order is the roster order, as v1 reads it (`src/core/roster.ts`). v1's router breaks ties by that order, so v1 still ranks claude-opus first for reviews and hard builds.
- **ARM-2** (M3; U) **Hard rules** (from v1's design rules). Grok never reviews, and agy never writes. They are enforced when a brief is sent and by each adapter's capabilities. A delegate file can restrict a soldier, never widen it.
  - A brief carries its kind of work (HOST-10). A brief is refused before it is sent, and the refusal says why, when its kind is one the hard rules forbid (a review for grok, a build for agy), when it is a build for a soldier whose entry says `write: false` (ARM-1), or when its kind is not among the soldier's roles.
- **ARM-3** (M1; U) **Shadow names** default as 2.0 set them (from 2.0 CFG-3 and CFG-4): Bellion codex-astra, Igris codex-sol, Kaisel claude-opus, Tank claude-opus-build, Iron claude-sonnet, Beru grok and Tusk agy. They can be configured: `shadowName` in `shadow.config.json` sets a soldier's name, and a soldier with neither a default name nor a `shadowName` takes its key. Names are unique without regard to case, and no name is another soldier's key; a clash is refused at start, naming both soldiers.
- **ARM-4** (M3; R) **Only the Monarch plans and assigns work**; the owner may also send work directly (MSG-7). Soldiers answer, ask and report.
- **ARM-5** (M6; I) **Writes need the build role**, and happen only in the soldier's own worktree, under its claims, in a writing turn (from v1's design rules).
  - **A writing turn** is the turn of a message whose kind is build: the Monarch's brief (HOST-10), or the owner's `/send <soldier> --kind build` (HOST-9). ARM-2 has already refused such a message to any soldier that can't write.
  - **Every other turn is read-only.** That covers:
    - a brief whose kind is review, research or test;
    - a message with no kind: one the owner types in the pane's field or sends with `/send` and no `--kind` (MSG-7), a soldier's (MSG-6), and the request for a handoff summary (SES-4).

    So the owner's own writing turn always goes through `/send <soldier> --kind build`.
  - **The post office decides**, before the message goes in, from the kind recorded with the message (PO-6).
    - The soldier never receives the kind (HOST-10), and nothing it writes or does changes it.
    - A turn the CLI starts by itself takes the kind of the message it belongs to (PO-8).
    - A message the owner sends again with r takes the kind of the message it repeats, and ARM-2 checks it again (MSG-4).
  - A read-only turn's writes are discarded in a snapshot (WSP-11, ARM-8) and reverted in a worktree (WSP-12). A writing turn is audited against its claims (WSP-2).
- **ARM-6** (M2; I, X, F) **agy runs in a throwaway snapshot.**
  - Every agy session runs in a read-only snapshot of its base, never in a worktree that merges. From M6 the snapshot is brought to the base again before each turn (ARM-8, →M6).
  - Each write it makes there, as WSP-11 defines one, is discarded and reported as a read-violation; other output that git ignores is discarded and not reported (from 2.0 WS-3).
  - The checkout guard covers each agy turn, from the moment its message goes in until the turn is over (PO-8). That is its `result` once nothing the turn started is still running, or, when no `result` can come, the moment its process tree has been ended. Between turns agy is idle, and the owner and the Monarch edit the checkout freely (HOST-13, →M5).
  - The guard also hashes these paths, even where git ignores them or doesn't track them (from 2.0 GUARD-2, less its vendor home configs; the user's global git config is WSP-10's): the shared git config, `hooks/` and `info/`, and each worktree's metadata, as WSP-10 defines it, less what WSP-10 leaves out: another army's, and that of any working tree that is neither this army's folder nor one of its own snapshots and worktrees (WSP-10); `.githooks/`, `.claude/`, `.mcp.json` and `.env*`; and `AGENTS.md`, `CLAUDE.md`, `shadow.config.json`, `orchestratorDelegate.md`, `rules.md` and `agent.md`. Another working tree of the repository that lies inside the folder is not the checkout, and nothing under it is hashed or compared (WSP-11).
  - During a turn, a change to the checkout is trusted only when records explain it:
    - Shadow Army's journaled applies and undos (2.0 GUARD-3);
    - the Monarch's edits through Claude Code's file tools, which the mod records from Claude Code's tool hooks, with each file's hash before and after;
    - Shadow Army's own commands that made or removed a snapshot or a worktree, for the metadata of the one they made or removed (WSP-10).

    A path is trusted only if these records explain every change to it during the turn. If anything else also changed it, it is not trusted, even though the Monarch edited it too.
  - Every other change goes to the owner on an attribution card, with each path and its diff (from 2.0 GUARD-4). The owner's own edits and the Monarch's shell commands leave no such record, so their changes come here too. y says the changes are the owner's, and trusts exactly the hashes shown; n fails the turn as a read-violation and leaves the files as they are: the guard reverts nothing (Appendix D, row 6). The card says so beside its keys, as in `y mine · n not mine, fail the turn · the files stay as they are`. The turn's summary waits for the answer.
  - This is enforced by Shadow Army, because agy's own modes do not stop it writing (spike S5).

- **ARM-7** (M1; U, I, X) **The folder's own policy files need the owner's trust** (from 2.0 POL-1 and POL-2).
  - The policy files are `shadow.config.json`, `orchestratorDelegate.md`, `rules.md` and `agent.md`, and the folder's `.mcp.json`, whose servers a `claude -p` soldier connects with no trust dialog of its own (CH-2). One of the first four that the folder has at its top level is used in place of the copy Shadow Army ships, as in v1 (`src/core/config.ts`, `src/core/rules.ts`). A shipped copy needs no trust. Shadow Army ships no `.mcp.json`, so a folder without one needs no trust for it.
  - **Hashed when read.** Whenever the post office reads the folder's policy files, at its start and wherever it reads them again, as for a fresh session (SI-4, →M4), it reads each file once, hashes those bytes with SHA-256, and uses those same bytes. It compares each hash with the hashes the owner has accepted for that file in the folder's repository, in any of its working trees (PO-1). A file is untrusted when no hash accepted for it there matches, as when the repository is new to Shadow Army or the file is new or changed, or when a file that was trusted in this folder before is gone. A claude session connects the `.mcp.json` of the snapshot or worktree it opens in, which can differ from the folder's, so that copy is hashed too, when the session opens, and is untrusted in the same way; the card lists it with the soldier's name.
  - **Nothing starts on an untrusted file.** While any policy file is untrusted, no soldier's session opens in the folder, a restart (PO-1) or a resume (CH-9, →M2) included, and no snapshot is made for one. The soldier's log, and the use that needed it, say why, as in `the army waits for you to trust this folder's Shadow Army files`. A brief sent meanwhile waits in the soldier's queue (MSG-3, →M3). Sessions already open keep the instructions and autonomy they opened with (SI-4, →M4).
  - **The trust card.** The post office raises one card for the folder, however many soldiers wait on it, and the mod shows it, from M1:
    - as notice rows in Claude's transcript, which are not added to Claude's conversation: each untrusted file with `new`, `changed` or `gone` and the first 12 hex digits of its hash, and for `shadow.config.json` each soldier it sets above supervised, with its `cli`, `model` and `autonomy`, as in `Kaisel · claude · opus · full`, and for `.mcp.json` each server it declares, with its command or its URL. Text from the files is escaped as SEC-6 says. The card doesn't show the files' text; the owner reads them in the folder;
    - then in Claude Code's own question dialog (the mod API's `$.ui.ask`), which asks `Trust this folder's Shadow Army files?` with two options, `Not now` first, then `Trust these files`.

    `Trust these files` accepts exactly the hashes shown, for every working tree of the repository: the post office records them, and the waiting sessions open, each soldier at the autonomy the accepted file gives it. Only an answer that is exactly `Trust these files` accepts. `Not now`, any other answer, text typed under Other included, a dismissed dialog, or a dialog that can't open accepts nothing and starts nothing, and the next use shows the card again. A file that changed after the card was shown stays untrusted, and the card shows again with its new hash.
  - **Only the card.** The folder's files raise a soldier's autonomy above supervised only through an accepted card. No setting, flag, environment variable or file in the folder accepts a policy file.
  - **The record** of accepted hashes is kept in Shadow Army's own folder in the user's home, `~/.shadow-army/trust/`, one file per repository, named for the first 12 hexadecimal digits of the SHA-256 of the repository's common git directory, in UTF-8, as `git rev-parse --path-format=absolute --git-common-dir` prints it, with its letters lower-cased on Windows, as WSP-11 makes an army's mark, and written whole. It holds that directory's path, the hashes accepted for each policy file, and, for each working tree, the files last trusted there, so a file gone from one is found. It is never in the folder, so a repository can't ship its own acceptance. A record that can't be read or parsed counts as none, and the post office's log says so. If the record can't be written, nothing is accepted, and the use says why.
  - **Stated residual risks.** Claude Code passes the dialog through its hooks as an AskUserQuestion call, which a PreToolUse hook can answer, so a hook the owner installed, or one in the folder's own Claude Code settings, can accept the card. Any process of the owner's, a soldier that runs code included, can write the record. The files the card doesn't cover, such as `CLAUDE.md`, `AGENTS.md` and `.claude/`, steer a soldier's CLI as its vendor intends, with no card. Where the folder lacks a policy file, the shipped copy applies with its own autonomy levels. v1's own commands, kept until LEG-1 (→M6), still read the folder's files with no card.

- **ARM-8** (M6; I, F) **Under `auto` or `full`, a soldier that can't write runs in a snapshot** (from v1's design rules and 2.0 WS-3).
  - A soldier can never take a writing turn (ARM-5) when it lacks the build role, when its entry in `orchestratorDelegate.md` says `write: false` (ARM-1), or when it is agy (ARM-2). When such a soldier's autonomy is `auto` or `full`, it runs each session in its own throwaway snapshot, as agy does at every level (ARM-6). At `supervised`, any such soldier but agy runs in its worktree (WSP-1), and WSP-12 reverts whatever its turns write.
  - **Where a session runs** is decided when it opens, from the soldier's roles, its `write` setting and its autonomy as the post office reads them then (ARM-1, ARM-7), and holds for that session's life, a resumed one included (CH-9).
  - **The snapshot** is of the soldier's base as WSP-6 defines it, and is made, kept and removed as WSP-11 says. The soldier has no worktree and no branch (WSP-1): `/diff` and `/apply` refuse and say so (WSP-9), as in `Tusk has no branch · it runs in a snapshot`.
  - **Following the base.** Before each turn's message goes in, harness git (WSP-10) brings the snapshot to the soldier's base as WSP-6 defines it then, in the same folder, so the paths in the session's history still hold. The post office logs the commit (PO-5), and that is the HEAD WSP-10 expects there. So a review brief sent after the owner applied work (WSP-9) sees that work. If the snapshot can't be brought to the base, as on a full disk or while harness git is held (WSP-10), the message isn't sent: it stays queued, its row says why, as in `waits · snapshot not updated · disk full`, and it goes by itself once the snapshot can be brought.
  - **Every turn it takes is read-only.** Once the turn is over (PO-8), and before anything else, the snapshot is put back as it was before the turn: its files, ignored ones included, its index and its `HEAD`, so a commit made there goes too, and nothing a turn wrote reaches the next. What it wrote is reported as WSP-11 says. The checkout guard covers each of its turns (WSP-4).
  - **No snapshot.** A soldier whose snapshot can't be made, or is needed while harness git is held (WSP-10), doesn't start, whether it is a first start, a restart after a crash or a fresh start (WSP-11). Then:
    - it shows down (VIS-2) with the reason, and is among the channels down in the decisions list (HOST-14);
    - messages to it wait in its queue, and each row says why, as in `waits · snapshot not made · disk full` (MSG-3);
    - its log and one line in Claude's transcript say why, and r tries again.

    It never runs in the folder or in a worktree instead, and its autonomy is never lowered so that it can start.

### 4.8 Workspaces and safety, carried over (WSP)

- **WSP-1** (M6; I) One worktree per soldier per Claude Code process (from 2.0 WS-1). Its branch's name starts `shadow/<mark>/`, with its army's mark (WSP-11), so two armies on one repository never take the same branch name. An army never changes or removes another army's worktree or branch, whether that army is running or gone. At start, the log, and one line in Claude's transcript, name each such worktree whose army's folder is gone. It stays, with its branch, for the owner. A soldier that runs in a snapshot (ARM-6, ARM-8) has no worktree and no branch.
- **WSP-2** (M6; I) Claims, and the claim audit at the end of every writing turn (from v1 #16 and 2.0 WS-7). A read-only turn in a worktree is audited as well, with no claims and against its own start state rather than the base, and its writes are reverted (WSP-12). The audit runs once, when the turn is over (PO-8): after any background work the turn left running, and also for a turn that was cut short. It always runs before the soldier's next message.
- **WSP-3** (M6; I, F) Link safety everywhere: nothing is deleted or reverted through a link (from 2.0 SAFE-8, SAFE-9 and SAFE-12, and v1 #36 and #58).
- **WSP-4** (M6; I) The checkout guard (from v1 #22, and 2.0 GUARD-1 to GUARD-4 and GUARD-6). It covers every turn of every soldier, writing or read-only, at every autonomy level and in every mode, with the scope, the trusted records and the attribution card that ARM-6 gives agy.
  - Inside a soldier's own worktree, a turn is checked by its claim audit (WSP-2) or, for a read-only turn, by WSP-12. A `HEAD` that moved during a read-only turn is a write there.
  - Refs are covered too, as in v1 (`src/workspace/guard.ts`). Shadow Army's own branches (`shadow/*`) are exempt only for what harness git does to them and for moves of a soldier's own branch during that soldier's turn; WSP-12 reverts a read-only turn's moves of it. Any other ref move, such as another branch, a tag, or one soldier's commit on another soldier's branch, is a change like any other and goes on the card.
- **WSP-5** (M6; I, F) Applying a soldier's work to the folder is all-or-nothing, and it can be undone (from 2.0 WS-8 and WS-9, v1 #28, and #53).
  - This holds even when a write fails after the check has passed. Before writing, the apply copies the bytes of every file it will touch, and the git index; on any failure it restores them exactly, and removes files it created.
  - Undo works the same way.
  - If the restore itself fails, the report names every file still changed and does not say the folder is unchanged.
  - v1's `src/workspace/apply.ts` assumes `git apply` is atomic, which this requirement does not.
- **WSP-6** (M6; I) Work starts from the folder as it is, so follow-up work sees changes applied earlier (from 2.0 WS-5 and #32).
- **WSP-7** (M6; I) No code of a soldier runs while the harness runs git for that soldier (from 2.0 SAFE-11). Background work a turn left running counts as the soldier's code until it has ended or been stopped (PO-8). A session service does not: harness git never waits for one (PO-8).
- **WSP-8** (M1; U, I) `redact()` runs on every write to logs, records (reports included) and briefs, and on every event the post office sends the mod, where each streamed fragment is redacted on its own (from 2.0 SAFE-6). An approval request is the one exception. What its card shows (the command or tool input, a file change's diff, its title and reason, and its options) goes into its event twice: whole, taken from whichever of the CLI's messages carries it, such as codex's `item/started` item or grok's `tool_call` update, for the card to show word for word (CH-6, →M2); and redacted, for anything that reaches Claude, as when `/decisions` prints it (HOST-14, →M5). So the mod never redacts, and needs no soldier's credential. The post office's log of the request is redacted. Fixtures are redacted before they are committed, and VER-4 (→M2) adds their provenance. 2.0's pruning after 30 days is not carried: logs are kept until the owner deletes them.
  - It replaces with `[redacted]`: the Monarch's secret and each soldier credential, in each encoding Shadow Army uses for them and in any letter case (SEC-4); a `Bearer` token and an `Authorization` header's value; a private key block, from its `-----BEGIN` line to its `-----END` line; a key that starts `sk-` (`sk-ant-` included) or GitHub's `ghp_`, `gho_`, `ghu_`, `ghs_` or `ghr_`, followed by at least 12 more letters, digits, `-` or `_`; and the value given to a name that ends in `key`, `token`, `secret`, `password` or `credential`, in any case, with or without `_` or `-`, as in `AWS_SECRET_ACCESS_KEY=…` or `"access_token": "…"`, in `key=value`, `key: value` and JSON.
  - A match never starts inside a word: the character before it, if any, is not a letter, a digit or `_`. A name is an identifier, with no spaces. Its value has at least 8 characters and no space, and ends at whitespace, a quote, `,`, `;`, `}` or the end of the line. So `input_tokens: 5`, `primary key: id` and the `sk-` inside `task-notification` are kept.
  - The unit test has one case for each kind, with its source, and for each kind a case that must be kept.
- **WSP-9** (M6; I, S) **Diff and apply from the mod** (from v1 `sa apply`, #28).
  - `/diff <soldier>` and d in the pane show the soldier's changes on its branch since its base.
  - `/apply <soldier>` applies them to the folder as WSP-5 says, and `/apply undo` undoes the last apply.
- **WSP-10** (M1; X, F) **Harness git runs nothing the repository names** (from 2.0 GIT-1 to GIT-4, and GUARD-2). Every git command Shadow Army runs, such as the one that makes a snapshot or a worktree, the guard's and the claim audit's:
  - turns off hooks: `core.hooksPath` names an empty folder Shadow Army keeps (2.0 GIT-1), `hook.<event>.enabled` is false for each hook event the command can fire, and `hook.<name>.enabled` is false for each hook the config git reads defines (`hook.<name>.command`), since git 2.54 runs hooks defined in its config but has no per-event switch. So hooks defined in git's config stay off too;
  - turns off the file system monitor (`core.fsmonitor`), the pager, signing, external diffs and text conversion, as 2.0 GIT-1 lists, with `--no-optional-locks`;
  - passes the owner's line-ending, link and `filter.*` settings as they were when the post office started (2.0 GIT-2): a filter set then is the owner's, and runs;
  - commits with `--no-verify` (2.0 GIT-4);
  - runs a git found by its absolute path on `PATH` alone, as CH-1 starts each CLI, never one in the folder, a worktree or a snapshot;
  - runs with `GIT_TERMINAL_PROMPT=0` in its environment and `-c credential.interactive=false`, so no credential prompt waits for an answer, and is ended, with every process it started, filters included, after 30 minutes on the monotonic clock when it makes or brings a snapshot or a worktree, and after 5 minutes for any other command. A snapshot that times out is one that can't be made (WSP-11), with the reason, as in `snapshot not made · git took longer than 30 min`. A guard or audit command that times out holds harness git, with that reason.

  Before and after each command, the config git reads for that repository (every scope but the command line, includes followed, and any `config.worktree`), the shared `hooks/` and `info/`, and each worktree's metadata are compared with the state Shadow Army last trusted: their state when the post office started, or as the owner last accepted it (2.0 GIT-3). After Shadow Army's own command that makes or removes a snapshot or a worktree, the trusted state gains the metadata of the one it made, or loses that of the one it removed, and nothing else: anything else that changed while the command ran is a change. That command passes `-c worktree.useRelativePaths=false`, so it writes nothing to the repository's config, where git would otherwise set `extensions.relativeWorktrees`. A worktree's metadata is its `gitdir`, `commondir` and `config.worktree`. Another army's snapshots and worktrees (PO-1) are left out, whether that army is running or gone. Their metadata is neither compared nor trusted, so making or removing one is no change, during Shadow Army's own command or at any other time. So is the metadata of any other working tree of the repository that is neither this army's folder nor one of this army's own snapshots and worktrees, such as one that `git worktree add`, `claude --worktree` or a subagent's `isolation: worktree` makes, or their own cleanup removes. The post office's log names each one it finds added or removed, and Claude's transcript gets one line for it, as in `Shadow Army: a working tree was added at .claude/worktrees/fix-1 · not this army's`; nothing is held. A snapshot or worktree is this army's own when it lies in this army's subfolder of `~/.shadow-army/snapshots/` (WSP-11), or when this army's logs name it (PO-5). Any other snapshot or worktree is another army's in two cases: its `gitdir` lies in a subfolder there that carries another army's mark, or its HEAD names a branch under another army's mark (WSP-1, →M6). Only worktree metadata is left out: the config git reads, and the shared `hooks/` and `info/`, are compared whoever changed them. The HEAD of each of Shadow Army's own snapshots and worktrees is not hashed but checked against the commit Shadow Army expects there (2.0 GIT-3); in a soldier's snapshot, a HEAD that moved is a write there (WSP-11). Changes to `branch.*` and `remote.*`, such as `git push -u` makes, don't count.
  - Any other change holds harness git for that repository until the owner answers it on the guard's attribution card (ARM-6, →M2): y trusts the state shown, and harness git goes on; n keeps it held. In M1, before that card exists, the post office's log names the change, Claude's transcript gets one line saying harness git is held and why, and harness git stays held until the post office restarts.
  - While harness git is held, a soldier that needs a snapshot or a worktree does not start, and its log says why. A turn that needs harness git to finish ends interrupted, with the change named (MSG-4, →M3), and the soldier's queue is held (MSG-3, →M3). Once harness git goes on, that turn's guard and audit run before anything else (PO-8, →M2).
- **WSP-11** (M1; I, F) **Before a soldier has its worktree** (from v1's design rules). Until WSP-1 (→M6) gives each soldier its worktree, each session opens in its own throwaway snapshot of HEAD, made by harness git (WSP-10) when the session opens and removed when it closes. A soldier's session opens at its first use, `sa live`'s open in M1 and, from M3, the first message to it (HOST-10, →M3); `/army` opens none. From M6 the same holds, with a snapshot of the soldier's base (WSP-6, →M6), for every soldier that runs in a snapshot: agy at every level (ARM-6, →M2), and a soldier that can't write, under `auto` or `full` (ARM-8, →M6). ARM-8 (→M6) also says how the snapshot follows the base from turn to turn.
  - The snapshot is made outside the folder's directory tree, because claude also loads `CLAUDE.md` and `CLAUDE.local.md` from every folder above its working directory. It goes in Shadow Army's own folder in the user's home, `~/.shadow-army/snapshots/`: in a subfolder for each folder, named for the folder's name and its army's mark, and there in a folder of its own for each session. The army's mark is the first 12 hexadecimal digits of the SHA-256 of the folder's path, in UTF-8, as `git rev-parse --show-toplevel` prints it, with its letters lower-cased on Windows. So each folder's army has its own mark, and keeps it across restarts. A file in the subfolder holds the folder's path.
  - A restart that opens a fresh session (PO-1) gets a new snapshot, and the old one's writes are reported as below before it is removed. A resumed session (CH-9, →M2) keeps its snapshot, so the paths in its history still hold.
  - A soldier whose snapshot can't be made does not start: its log and one line in Claude's transcript say why. It never runs in the folder itself.
  - **Another army's snapshots.** While another army's folder is still a working tree of the repository, this army never reports, changes or removes that army's snapshots (WSP-10), whether that army is running or not: its own next post office does (PO-1). When a post office starts, it checks each other subfolder that holds snapshots of this repository. If that subfolder's folder is gone, no longer on disk or no longer listed by `git worktree list`, the post office handles each snapshot in it:
    - It writes the snapshot's changed files and its HEAD's commit in its log, and in one line in Claude's transcript. The line names the gone folder, and says that the HEAD can't be checked, since that army's log went with its folder.
    - Then it removes the snapshot, and the subfolder once it is empty. A removal that finds the snapshot already gone is no error.

    A subfolder whose path file can't be read is left as it is, and the log says so.
  - A file it writes in its snapshot that git doesn't ignore, by the ignore rules the snapshot had when its turn began, a write to the snapshot's own copy of a path that ARM-6 (→M2) hashes, even where git ignores it, or a commit that moves the snapshot's HEAD, is a write there. Other output that git ignores, such as build output, caches and installed packages, is discarded with the rest and not reported (from 2.0 WS-3). Its writes are found once each turn is over, when the turn's guard closes, and reported then as a read-violation, as ARM-6 (→M2) says for agy; they are discarded before its next turn. A snapshot is removed only after its writes are reported.
  - The checkout guard covers each of its turns, from the moment its message goes in until its end event, or until its process tree has been ended. Until PO-8 (→M2), it also stays open past the end event while a task the turn started is running (claude's `task_started` with no `task_notification` for it yet), or while a process that joined the process tree during the turn hasn't exited; it closes when that work ends or the session closes, and the soldier's next message waits until then. Its baseline, which holds the ignore rules the snapshot had then, is kept beside the session's log under `.shadow/v2/logs/` (PO-5), never in a worktree, a snapshot or the system's temporary folder, and is removed once the turn's guard has closed. The baseline and the log line that opens the turn (PO-5) are written and flushed before the message goes in, so a post office that dies mid-turn leaves both for the next one (PO-1). If either can't be written, the message isn't sent, and Claude's transcript gets one line with the reason; from M3 the message stays queued instead, as for a record that can't be written (MSG-4, →M3). It covers the checkout and the paths that ARM-6 (→M2) hashes, with each worktree's metadata as WSP-10 defines and trusts it, so another soldier's snapshot made or removed during the turn is no change, and neither is another army's snapshot or worktree, or any other working tree of the repository, whose metadata WSP-10 leaves out. Shadow Army's own snapshots and worktrees, and its files under `.shadow/v2/`, are not the checkout, and nor is another working tree of the repository that lies inside the folder, as `git worktree list` gives it when the turn's guard opens or closes, such as one `claude --worktree` makes under `.claude/worktrees/`, with everything under it, another army's lock and logs there included (PO-1, PO-5). A change in the soldier's own snapshot is a write there. Until the attribution card exists, any other change it finds fails the turn: the soldier's log names each path, and Claude's transcript gets one line.

- **WSP-12** (M6; I, X, F) **A read-only turn's writes in a worktree are reverted** (from v1's design rules, v1 #16 and 2.0 WS-3).
  - Every read-only turn (ARM-5) that runs in a worktree is audited with no claims, at every autonomy level and whatever mode the CLI is in. That covers a builder's review, research and test briefs and its other read-only messages, and each turn of a soldier that can't write and runs in its worktree at `supervised` (ARM-8). Such a turn is one more turn of the soldier's one session (SES-1), in its one worktree.
  - **What is audited.**
    - Every path in the worktree that git tracks or lists as untracked, with everything under a working tree nested in it. ARM-6's and WSP-11's exception for a working tree nested in the folder covers the folder only.
    - The worktree's own copies of the paths ARM-6 hashes, such as `.claude/`, `.mcp.json` and `.env*`, even where git ignores them.

    What git ignores is read from the start state's ignore rules. Other ignored paths, such as build output, caches and installed packages, are not audited. Whatever a read-only turn leaves there stays for the soldier's later turns, though never on its branch or in `/diff` or `/apply` (WSP-9). That is a stated residual risk (Appendix D, residual 11).
  - **The start state.** Before the turn's message is recorded as delivered (MSG-4), the post office saves the worktree as it is. The start state holds:
    - the soldier's branch tip, the worktree's `HEAD`, its index and its `.git` file;
    - the bytes and mode of each audited file that differs from `HEAD` or that git doesn't track;
    - the ignore rules git reads there: its `.gitignore` files, `info/exclude` and the global excludes file. So an ignore rule that the turn adds hides nothing.

    It is written whole and flushed, beside the turn's guard baseline (PO-8) and outside every worktree and snapshot, and is kept until the turn's revert has run. The post office hashes it with SHA-256, and keeps the hash in memory and in the line that opens the turn (PO-5), written and flushed with that line. If the start state can't be written, or harness git is held (WSP-10), the message isn't sent: it stays queued, and its row says why, as in `waits · start state not written · disk full`.

    A turn the CLI starts by itself after its message's work is over (PO-8) has no message to wait for. It starts from the state that the post office saves, in the same way, once the message's own turn has been reverted. An edit that the owner makes in that worktree after that point is the owner's to keep or revert (D-24):
    - when the turn's first event comes, the post office saves the bytes and mode of each audited path that then differs from that start state, beside it and in the same way, with the copy's SHA-256 hash in the log line that records the event (PO-5);
    - when the turn is over, and before its revert, those paths go to the owner on a card, each with its diff from the start state, as in `Iron took a turn by itself after a review · 2 files changed before it began · y keep as yours, n revert`. y keeps each as it was at the first event: the copy becomes part of the start state, and the revert brings the path back to it. n reverts them with the turn. y and n are the attribution card's keys (ARM-6), and the soldier's queue is held until the owner answers (MSG-3);
    - a change made after the first event is the turn's, and is reverted like any other;
    - with no such path, no card shows.

    The card lists what changed before the post office read the turn's first event, so a write the turn made in that moment can be on it, and y keeps it (Appendix D, residual 11). A card still open when the post office ends leaves the revert pending, as below, and the next post office shows the card again before that revert runs.
  - **The audit** runs once, when the turn is over (PO-8), after the turn's guard has closed and before anything else goes to the soldier. First the post office hashes the saved start state and compares the hash with the one it kept. Then it compares the worktree with the start state, never with the base. With no claims, every difference is a write.
  - **Reverted** means that the worktree goes back to the start state:
    - each audited path the turn created is removed, and each one it changed or deleted gets back its bytes and mode, from `HEAD` or, where it wasn't committed then, from the saved copy;
    - the soldier's branch, the worktree's `HEAD` and its index go back to where they were, so a commit the turn made leaves the branch. A ref the turn moved outside its own branch is the guard's (WSP-4);
    - everything the turn didn't change stays as it was: the soldier's earlier work, committed or not, the owner's edits made between turns, except those the owner answers n for on the card above, for a turn the CLI starts by itself, and ignored output;
    - nothing is removed or restored through a link (WSP-3). A link the turn left is removed without being followed. A worktree folder or `.git` file the turn replaced is put back before any harness git runs there;
    - an edit that the owner makes in that worktree during the turn can't be told from the soldier's, so it is reverted too, and no copy is kept.
  - **Apply.** While a read-only turn of a soldier is open, and while its revert is pending or has failed, `/apply <soldier>` refuses and says why, as in `apply waits · Kaisel's review turn is still open`. So nothing the turn committed reaches the folder (WSP-9).
  - **Each CLI.** This depends on no vendor's mode (CH-7), so it works the same way for claude, codex and grok. agy never takes a writing turn (ARM-2) and always runs in a snapshot (ARM-6), so this requirement doesn't apply to it.
    - claude reloads its settings files when they change, so a `.claude/` settings file that a read-only turn writes in the worktree is live for the rest of that turn, until the revert puts it back.
    - On Linux and macOS, except in the other cases claude's settings documentation names, claude keeps `.claude/settings.local.json` for a linked worktree at the main checkout's root, not in the worktree (CH-2); on Windows it keeps it in the worktree, where the revert takes it back. A write at the main checkout's root, such as the rule that an approval's "don't ask again" saves, is outside the worktree: the revert doesn't undo it, and the checkout guard sees it only where that checkout is the folder (ARM-6, WSP-4).
    - An approval that the owner gives during the turn (CH-6) answers only the CLI's request. The turn stays read-only, and whatever the approved tool wrote in the worktree is reverted too. That holds if the approval leaves claude's `plan` mode (CH-11).
  - **What the owner sees.** A read-violation is not an ending: the message ends as PO-8 says.
    - The soldier's log names each reverted path and what the turn did to it (created, changed or deleted), and each commit taken off the branch.
    - The summary card's changes fact says "none", then `read-violation:` and the paths (MSG-11).
    - Claude's transcript gets one line, as in `Kaisel · review turn wrote 2 files · reverted (read-violation) · src/a.ts, src/b.ts`. Paths are shown as SEC-6 says.
    - A turn that changed nothing audited adds no line.
  - **Failures.** Whatever ends the turn, the audit and the revert run once, before the session is resumed, the channel restarted or the next message sent.
    - A stop (MSG-9), a crash in the middle of a tool call, or a turn cut short (PO-8) is reverted once the CLI's process tree has been ended (PO-1).
    - A post office that dies mid-turn leaves the start state on disk and its hash in the log. Before it opens any channel, the next one checks the hash and reverts the turn from the start state (PO-1), and the message ends as interrupted with `the post office stopped unexpectedly`.
    - While harness git is held (WSP-10), the revert waits. The message ends as interrupted, with the change named, and the queue is held. Once harness git goes on, the revert runs before anything else, as WSP-10 says.
    - A revert that fails, as when another process holds a file open, holds the soldier's queue (MSG-3), which joins the decisions list (HOST-14). The soldier's log and one line in Claude's transcript name each path still changed. The revert is tried again before any message goes in to that soldier, also after a fresh start (SES-5), which doesn't drop it, and `/apply` stays refused until it succeeds. A revert still pending or failed is recorded in the soldier's log (PO-5), and so is a revert that succeeds, so a pending one outlives the post office however that ends, a shutdown (PO-7) or a mod reload included. When a later post office starts, before it opens any channel or serves `/diff` or `/apply`, it finds each such record of this army's, checks the start state's hash, and tries the revert again, with the soldier held and `/apply` refused until it succeeds, or held as the next bullet says where the hash fails. A worktree that it won't use again, such as one a Claude Code process that has exited kept (PO-7), and one whose revert still fails, are named in its log and in one line in Claude's transcript each.
    - A start state whose hash doesn't match the one kept, or that is gone, is never restored from. The revert counts as failed, as in the previous bullet, and the log and Claude's transcript say that the start state changed. Trying again can't clear it: the soldier stays held, and the owner decides what to do with its worktree outside Shadow Army.

### 4.9 Security (SEC)

- **SEC-1** (M1; X) A test proves that no listening socket is reachable on a non-loopback address (PO-2).
- **SEC-2** (M1; X) A test proves that a request without the Monarch's credential, or with a wrong one, reaches no soldier and is reported, and that the credential appears in no file, command line, environment variable, output or log (PO-3). A test on each of the three systems (VER-2) proves that the post office's log names the memory protection it has, and that where it has one, a fake soldier can neither read its memory nor change its DACL, and on Windows can neither open its threads to read or change their context nor start a process with the post office as its parent. Neither proves that the secret can't be read where PO-3 states the residual risk.
- **SEC-3** (M2; X, R) No code path answers a vendor's approval request without the owner (CH-6, HOST-12, →M5), except the cancellation that closes it when the post office shuts down (PO-7). A stop's cancellation is the owner's answer. Neither approves anything (CH-6).
- **SEC-4** (M1; X) Logs, and records (PO-6, →M3), hold nothing that `redact()` matches (WSP-8): the secrets Shadow Army holds by value, the Monarch's secret (PO-3) and each soldier credential (PO-4, →M3), in any encoding it uses for them, and each kind WSP-8 lists. A test writes each kind and finds none of it in a log, and from M3 in a record. Any other secret a soldier's CLI writes into its session, such as a value it read from a file or its environment, is logged as the CLI wrote it, as the CLI's own transcript keeps it: a stated residual risk.
- **SEC-5** (M3; X) A test proves that a valid soldier credential cannot issue any Monarch command, read the event stream, read another soldier's session, log or record, or send under another soldier's name, and that no soldier credential appears on the command line of any process the post office starts, or on disk beyond the file PO-4 allows claude while it exists (PO-4). It proves what the post office lets a credential do, not that a credential stays with its soldier: a soldier that runs code as the owner can take another's, as PO-4's stated residual risk says.
- **SEC-6** (M1; U, X) **Text the mod shows** (from 2.0 SAFE-7). In text from a soldier, a CLI or a config file, each character of Unicode's control (Cc) and format (Cf) categories, except newline and tab, shows as a visible placeholder such as `\u{1b}` or `\u{202e}` wherever the mod draws it, and reaches Claude escaped the same way. That covers ESC, and so every escape sequence, as well as the bidirectional controls and the zero-width characters. Every other character is kept, so an approval request is still shown word for word (CH-6, →M2). A test draws a line holding each kind and finds only placeholders.

## 5. Verification

### 5.1 Levels

- **Unit tests (U).** Pure logic, with vitest:
  - routing and the hard rules;
  - meter maths, thresholds and state precedence;
  - parsers and name matching;
  - `redact()` and config validation.
- **Contract tests (C).** For each CLI, the owner records real sessions:
  - the two-prompt task (L, below); for claude, followed in the same session by "Use a subagent to count the lines in package.json.", so that the recording has three turns and a subagent's messages (M1-AC3);
  - an approval request, or for agy a tool it soft-denies (CH-6);
  - one session for each error kind of CH-1 that the CLI can be made to produce, such as a login needed and a context overflow. A kind that can't be produced on purpose, such as a rate limit, is built from the vendor's documented shape (for claude, `SDKRateLimitEvent` with `rate_limit_info.resetsAt`) and marked synthetic in its fixture. So is a refusal, which CH-1 doesn't count as an error: for claude, an assistant message whose `message.stop_reason` is `refusal`, with `stop_details`;
  - a turn stopped through the CLI's own interrupt, then the next message (CH-10);
  - a session resumed by id (CH-9);
  - a `send` call through the added MCP server, except for agy (PO-4);
  - for claude, a soldier session with the mod installed (HOST-2);
  - a session that goes cold;
  - for claude, codex and grok at `supervised`, one session with a writing turn and a read-only turn, each in the mode CH-11 sets: for claude the control request and its answer, for codex both turns' `turn/start`, and for grok `session/set_mode` where `session/new` lists modes.

  The tests replay each recording through the channel adapter, and pass only when the adapter's events match the expected events. A fixture carries the CLI version it was recorded with (CH-8), and is recorded again when its adapter is changed for a newer version of its CLI. Until then, a newer CLI connects with CH-8's notice.
- **Integration tests (I).** Fake claude, codex, grok and agy executables speak each wire protocol with scripted turns. The post office runs end to end against them:
  - briefs, queueing and summaries;
  - stopping a turn, also while an approval request is open, and cancelling or changing a queued message;
  - sending again a message that was not delivered, and refusing to send again one that was interrupted;
  - soldier-to-soldier messages;
  - handoff and fresh sessions;
  - crash, restart and resume;
  - a read-only turn that writes, at `auto`, both in a builder's worktree and in the snapshot of a soldier that can't write, and a turn's mode set between turns at `supervised` (ARM-8, WSP-12, CH-11);
  - containment on each system and processor, with the binaries and the script that ship: a CLI's detached child is listed and then ended, and the post office is killed with and without its guardian (PO-9 to PO-11, PO-16, PO-21).
- **Security tests (X).**
  - Binding to a non-loopback address is refused.
  - A missing or wrong secret is refused and reported.
  - Logs are redacted.
  - The mod never approves by itself: none of its Claude Code hooks allows a tool call or a permission (HOST-12), and it passes on a soldier's approval request only with the owner's own answer, unchanged (CH-6, SEC-3).
  - A read-only turn does each of these: commits on its own branch, moves another soldier's branch, adds an ignore rule over a file it writes, replaces a file with a link to a checkout file, and writes `.claude/settings.local.json` in its worktree. None of it reaches `/diff`, `/apply` or a later turn, the checkout file is unchanged, and the other branch's move is on the attribution card (WSP-12, WSP-4). A start state that the turn rewrote is not restored from (WSP-12).
  - The post office names its memory protection in its log, and where it has one, a soldier can't read its memory (PO-3).
  - A folder's new or changed `shadow.config.json`, `orchestratorDelegate.md`, `rules.md`, `agent.md` or `.mcp.json` starts no soldier until the owner trusts it (ARM-7).
  - The containment helper makes only the system calls and imports its allowlists name, signals nothing outside its session's containment, and never receives the Monarch's secret (PO-17, PO-3).
  - A repository whose shared config names an fsmonitor command, a pager, a signing program and an external diff, with each hook its commands can fire present, as files in `hooks/` and defined in the config (M1-AC10): no harness git command runs any of them. A filter added after the post office started, in any config scope, holds harness git at the next check, so no harness git command that starts after that check runs it. One added between a command's check and git's own reading of the config can run once; the check after the command finds it if it is still there, and holds harness git (Appendix D, residual 7). One set at start is the owner's, and runs (WSP-10).
- **Fault tests (F).** Every time bound the post office measures, in these tests and in section 6's ACs, runs on a fake monotonic clock, and on a fake wall clock where the bound reads one. The post office takes its clocks in code, so a test that runs it in-process gives it fakes; that is no product setting (VER-5). Bounds that a guardian or the system keeps, as in the containment tests (PO-9, PO-10, PO-16), and M1-AC1's SIGSTOP and unread-output cases, run in real time:
  - a CLI killed mid-turn, in the middle of a tool call;
  - a rate limit, a context overflow and a refusal, each told apart;
  - a CLI that leaves a child process running, and one whose child starts a new session and forks twice;
  - a turn that changes the checkout and ends without its end event, and an end event read after it ended;
  - a turn whose end event comes while a child it started keeps writing;
  - a queued message ready just as the CLI starts a turn by itself after background work;
  - a session service the CLI starts during a turn and keeps, and a job such a service starts for a tool call;
  - a turn its CLI reports as failed after it changed a file;
  - a CLI whose turn does not end after a stop;
  - the mod's renewals stopping; a sleep, a suspended or stalled post office, a stopped mod and a wall-clock change, on a fake clock (PO-7);
  - the lease lapsing, and the session ending, while an approval request, an attribution card and a queued message are open;
  - the post office killed mid-turn, with a message queued, an approval request open and a child running;
  - a mod reload mid-turn: the old post office ends, its turns are cut short, and the new mod instance starts its own at the next use;
  - a soldier disconnected with a message queued;
  - a malformed or split JSON line: a split line is joined, a malformed one is shown and the session carries on, and ten in a row count as a lost connection;
  - a slow first token: a CLI that answers 5 s inside its startup bound, and one silent for 10 minutes mid-turn, run on; one that never answers is restarted as after a crash;
  - an expired login: the channel is never restarted, whether the CLI keeps running or exits, and the soldier shows "log in" until the owner reconnects it;
  - a cache going cold, on a fake clock, also across a sleep longer than its lifetime and with the wall clock set back and forward an hour;
  - a failed log write: the turn goes on, the failure is reported once, and the log resumes with the count of lost lines. A turn whose opening line or guard baseline can't be written is not started, and Claude's transcript says why;
  - a record that can't be written as its message is about to go, and a record line cut off by a crash;
  - a broken link in a worktree;
  - a read-only turn that writes in a worktree holding uncommitted work, and is then stopped, killed in the middle of a tool call, or cut short when the post office dies (WSP-12);
  - a start state that can't be written, a revert that fails, a start state that fails its hash, a mode the CLI refuses or doesn't confirm, and a snapshot that can't be made or brought to its base (ARM-8, WSP-12, CH-11);
  - a containment helper or Windows script that is missing, can't be run, has changed or fails its check; a guardian killed during a session, and one killed together with the post office; and a process the owner's user can't signal (PO-14 to PO-16).
- **Screen snapshots (S).** The mod's render trees are rendered for terminals of 144, 110 and 80 columns and 24 rows, and in the ASCII profile, and compared with committed snapshots that follow the canvas. Each committed snapshot names the canvas frame it follows, or the spec's table, or the requirement's own text, where the two differ (VIS-1), and the PR reviewer confirms the match whenever a snapshot is added or changed. Each tree is rendered at the size Claude Code gives it there (`bodyColumns`): the pane docked at 56 columns, inline at up to 72, and at 44 (VIS-3); the strip at its column's width less the band's five-column mark, both alone and beside the docked pane, where a terminal of 110 leaves it under 50 columns.
- **Live checks (L).** The owner runs the two-prompt task on each CLI, in a clean checkout of the commit under test, once through a live session and once through the CLI's own headless run, with the same model, effort and autonomy, and the same standing instructions (SI-1). The headless run takes them through the slot its command offers for appended instructions, and agy's ahead of its first prompt, as its channel gives them (SI-2); the write-up says how (VER-8):
  - **The task.** First "Read README.md and package.json, and say what this project is.", then, in the same session, "Which of those two files has more lines?".
  - **The headless run.** The CLI's own one-shot command with JSON output, keeping its session: `claude -p --output-format json`, `codex exec --json`, `grok --prompt-file <file> --output-format json` and `agy -p --output-format json`. Its follow-up continues that session by id through the CLI's own option: claude `--resume`, codex `exec resume`, grok `--resume` and agy `--conversation`. The exact commands are recorded with the check (VER-8).
  - **The measure.** For each run, the sum over both prompts of every model request's input tokens, whether uncached, written to the cache or read from it, and its output tokens. Requests are counted one by one, by their ids where the CLI gives them, never from a running total: a running total is turned into each turn's share by taking off the total before it. For claude, whose per-message output count is a placeholder, each turn's own figures are taken as CH-2 defines them instead, and the headless follow-up's tokens are its resumed total less the first run's.
  - **A pass.** The live total is at most 1.05 times the headless total, and the live follow-up reads neither file: no tool call in it opens either one, a shell command such as `wc -l` included. A run that fails either test is repeated twice, both ways, and then passes if the median of the three live totals is at most 1.05 times the median of the three headless ones, and at most one of the three live follow-ups read a file.

  **The budget.** A release is a version tag, such as `v2.0.0`. Every live check run toward it since the tag before it counts: every milestone's, on every system, repeats included. Shadow Army never estimates a cost (section 1), so the budget has two limits, and each run counts against exactly one of them:
  - **$2 of reported cost**, over the runs whose CLI reports a cost for them: claude's live turns, with the cost CH-2 gives each turn, and a headless run's `total_cost_usd` where its JSON has one, as claude's and grok's do. A headless follow-up's cost is its resumed total less the first run's. claude's cost is its own estimate (CH-2), and it is counted as reported.
  - **1,000,000 tokens for each CLI**, over that CLI's runs that report no cost: every codex and agy run (CH-3, CH-5), and any other run whose cost reads "not reported", such as a claude turn after a crash (CH-2). Their tokens are those of the measure above: input, whether uncached, written to the cache or read from it, plus output, with each turn's share of a running total taken as the measure says.
    - codex: from `thread/tokenUsage/updated`, its input tokens, with its cached input counted once, plus its output tokens, with its reasoning counted once; a headless run's come from `turn.completed`'s `usage` the same way. The contract fixtures (VER-4) show which field holds which.
    - agy: `input_tokens`, which leaves out cached input, plus `cache_read_tokens`, plus `output_tokens`, from its usage (CH-5) and from a headless run's JSON `usage`.
    - grok: a live turn's input, cached input and output come from its prompt result's `_meta.usage` (CH-4), each counted once; a live turn whose `_meta.usage` gives a cost counts against $2 instead. The contract fixtures (VER-4) show which field holds which.
    - A run that reports no tokens counts as reaching its CLI's limit, as when codex sends no usage for an interrupted turn (spike S6).
  - **Why 1,000,000.** On 2026-10-07, one live and one headless run of the task used about 152k tokens on codex and 91k on agy (ADR-0009). A check that fails runs three times both ways, about 455k tokens on codex. The rest leaves room for VER-10's runs and for the two files growing. The figure comes from those token counts, never from a price.
  - **Going past.** Before a check runs, the figures from its last run (VER-8) are added to the release's spend so far. For the parity task's first run, ADR-0009's token figures stand in for the runs that count against a token limit. A run that counts against $2 and has no earlier cost figure makes its check one with no earlier figures. Three kinds of check wait for the owner's go, given with the spend so far in front of them: a check whose sum passes either limit, a check with no earlier figures, and any check once a limit has been reached. A check that has started is never cut short: one that passes a limit while it runs finishes and is recorded, and the next one waits. Each check's write-up gives each run's cost or tokens as counted here, the release's spend against each limit, and any go the owner gave (VER-8).
- **Review (R).** The PR reviewer confirms the requirement, citing the file and line in the code, or, for a rule about the PR, CI or a live check, the PR's file list, the workflow's line or the write-up.

### 5.2 Rules

- **VER-1** (M1; R) **No live model calls in CI.** Live checks are the owner's.
- **VER-2** (M1; R) **Three systems.** CI runs every test level except L and R on ubuntu, macos and windows. The containment tests also run on every system and processor that PO-21 lists, with the binaries and the script that ship.
- **VER-3** (M1; R) **Tests come with the change.** A requirement's tests land in the same PR as its code.
- **VER-4** (M2; R) **Fixture provenance.** Contract fixtures are recorded from real CLIs by the owner, and record their date, CLI version and model. They are redacted before they are committed.
- **VER-5** (M1; U, R) **Fake CLIs.** Fakes live in `test/fakes/` and are chosen through configuration: the test runner puts `test/fakes/` first on `PATH`, as an absolute path, so the product starts a fake exactly as it starts the real CLI (CH-1). No option or setting in the product names a fake, and `shadow.config.json` never names an executable.
- **VER-6** (M1; R) **Coverage.** CI fails unless both of these hold:
  - the post office and the channels keep at least 85% line coverage, counted over the three systems' runs together (VER-2): a line is covered when any system's run covers it;
  - the security code has every line and every branch covered: making, handing over and checking the Monarch's credential (PO-3), the loopback-only rule (PO-2), and `redact()` (WSP-8), in the post office and in the mod. That code sits in files of its own, so the rule covers exactly it.

  Code that a child process runs lives in a file of its own, never in a string, so its lines count like any other. Code in another language, such as a native helper or a PowerShell script, keeps the same bars through that language's own coverage tool, counted over the systems it runs on (VER-2). The containment helper's C counts as the post office's: its lines are measured on a build of the same source instrumented for coverage, run by the same containment tests in a job of its own (PO-21), and join the same count. PO-17's system-call trace and import check apply to the shipped build only. The instrumented build writes its counts only under a folder the test names, before each step that can end its own process, so a helper ended by a signal, as every macOS guardian is (PO-10), still counts its lines. The Windows script counts the same way, and so does the DLL's C#: an ordinary .NET coverage tool measures its lines in the same tests, on the DLL that CI built or a copy of it instrumented for coverage (PO-19). No code is left out of the count, and neither bar is lowered, to pass.
- **VER-7** (M1; U) **Traceability in CI.** `scripts/check-spec-trace.mjs` checks Appendix B in CI and fails the build on a gap. Each test names the requirement or AC IDs it verifies, in its title or a comment beside it. An ID has one of this spec's prefixes (HOST, PO, CH, SI, MSG, SES, ARM, WSP, SEC, VIS, SET, OBS, VER, LEG), or the form `Mn-ACn`; other text, such as `UTF-8` or `SHA-256`, is no ID. An AC's ID names only that AC: a requirement is named only by its own ID. A committed file, `docs/spec/implemented.txt`, gives the milestone being built and the requirements implemented so far; each PR adds those it implements, and removes none. Its first line is the milestone being built, as `M2`, and each further line is one requirement ID. A requirement with two milestones is of an earlier milestone once both are earlier than the one the file gives. The script also fails when a requirement that file lists, or one of an earlier milestone than the one it gives, with U, C, I, X, F or S evidence, is named by no test, or when a test names an ID this spec doesn't have. So a milestone built over several PRs is checked on each of them. The script doesn't check a test's kind: the PR's AC-to-evidence mapping (section 6) says which test gives which kind of evidence, and the PR reviewer checks it. R and L evidence is recorded on the PR (VER-8 and section 6).
- **VER-8** (M1, M2; R) **Live checks are recorded.** Each live check is written up on its milestone's PR: CLI version, tokens, the cost where the CLI reports one, the release's spend against section 5.1's budget with any go the owner gave past it, and pass or fail.
- **VER-9** (M1, M2; L) **Live parity.** For each CLI, the owner runs the two-prompt task through a live session. It passes as section 5.1's live checks say, and its runs count toward their budget.
- **VER-10** (M6; L) **Live on every system.** Before v2.0.0, the owner runs the army live on Linux and on macOS, each in its own terminal, as well as on Windows: a brief answered, a turn stopped, and a change applied and undone, with the pane, the strip and the decisions list drawn. Each run is written up as VER-8 says.

## 8. Open questions

- **Q1** Should the army offer an opt-in that keeps the Monarch from writing in the checkout? The default (HOST-13) leaves Claude's permissions to the owner.
- **Q2** (answered by spike S2) What does waking the Monarch cost, and should it be on by default? A wake is one request at the Monarch's context size, mostly cache reads. MSG-8 wakes Claude only when a brief asks for a reply, and `send` asks by default.
- **Q3** Grok's 500k window is an opt-in setting. Does Grok charge more per token for long requests?
- **Q4** Will agy gain an instructions slot, or an approval protocol in headless mode? CH-5 and CH-6 change if it does.
- **Q5** The official ACP adapters for Claude Code and Codex: do they keep the vendor harness as installed? If so, they could replace our inward adapters.
- **Q6** (answered by VER-10) Linux, macOS and Windows terminals need a live check before v2.0.0.
- **Q7** codex can add to a running turn (`turn/steer`). Should v2 offer "redirect without stopping" where a CLI allows it? Spike S6 looks at each CLI.
- **Q8** (answered by D-3) How does the helper that contains each CLI's processes (PO-1) ship: compiled on the owner's machine at first use, as M1's draft (#75) does, prebuilt, or not at all? Prebuilt. There is one Linux binary for each supported processor and one universal macOS binary, built, tested, checksummed and attested in CI, inside Shadow Army's package, so nothing is compiled or downloaded on the owner's machine (PO-12, PO-13, PO-20). On macOS it still rests on interfaces Apple doesn't publish, so an update can stop every macOS soldier until a release fixes it. It never runs one uncontained (PO-14, PO-18). Windows needs no helper: a script that ships with Shadow Army holds each CLI in a Job Object, through a DLL that CI builds, tests and checksums beside it, so nothing compiles there either (PO-19).
- **Q9** Can a claude soldier take its `send` server and credential over its stream-json input, through the control request behind the Agent SDK's `setMcpServers`, which leaves the servers claude's own configuration declares in place? And under PO-4's fallback, has claude read its `--mcp-config` file by the time it answers `initialize`? A probe settles both before M3. Until it does, and if the first answer is no, claude takes them from PO-4's owner-only file (PO-4).

## Appendix B: Traceability rules

1. Every requirement ID appears exactly once as a requirement, in section 4, 5.2 or 5.3.
2. Every requirement names its milestone and at least one evidence code.
3. Every requirement is in the Implements line of the milestone it names.
4. Every acceptance criterion cites at least one requirement ID, and every requirement in a milestone's Implements is cited by one of that milestone's ACs.
5. IDs are never reused. A withdrawn requirement keeps its ID and its place, in the form §0 gives, and rules 2 to 4 skip it.
6. A requirement is carried over exactly when it names a source as `(from …)`, and every carried-over requirement appears in Appendix A.
7. `scripts/check-spec-trace.mjs` checks rules 1 to 6 and 8, and in CI rule 9 (VER-7). Rule 5 is checked through rule 1, since withdrawn entries stay in place, and against the IDs of the spec on the PR's base branch or, on a push, at the commit before the push, which CI fetches, so a deleted entry is caught too.
8. An acceptance criterion relies only on requirements of its own milestone or an earlier one. Where an AC, or a requirement an AC cites, cites a requirement of a later milestone than its own, the citation is marked `→Mx` with the cited requirement's milestone, as in `(CH-9, →M2)` or `CH-9 (→M2)`, and the part it governs is verified in that milestone. A requirement with two milestones may be cited without a marker by an AC of either one, and that AC verifies the part its own milestone implements; that requirement's own citations are checked against its last milestone. The check covers every ID an AC names and every ID named by a requirement the AC cites.
9. Every requirement that VER-7's committed list names as implemented, and every requirement of an earlier milestone than the one it gives, with U, C, I, X, F or S evidence, is named by at least one test, and every ID a test names is in this spec. This rule needs the code, so it is checked in CI only (VER-7).

In short, Shadow Army prevents crossings through its own interfaces (rows 1 to 3, 5, 7 to 10, and 12 to 16). It only detects a soldier's direct change to the checkout (row 6), a git config change made while harness git runs (residual 7), and a working tree added inside the folder (residual 13). It neither prevents nor detects what a CLI takes from the repository by itself (row 11), or what a soldier does elsewhere on the machine (row 17).

**Residual risks.** Each is accepted by the owner's decision, or stated by the requirement named beside it. The ones marked (for the owner to accept) await that acceptance.

1. **The Monarch's secret in memory** (D-9). A soldier that can run code as the owner can read the Monarch's secret from the mod's copy, in Claude Code's own process, on Windows always and on Linux at `ptrace_scope` 0 or without Yama; from the post office's copy where PO-3 names no protection: on Linux at `ptrace_scope` 0 or without Yama, and on Windows where its DACL, or a thread's, couldn't be set; and on Windows from any process through `SeDebugPrivilege` when Claude Code runs elevated. It can then act as the Monarch: issue any command and read the event stream. At `ptrace_scope` 1 or more, soldiers can't, since they descend from both. On macOS the post office checks nothing, and whether a soldier can read either copy is not assessed; it is accepted with the rest. The post office logs which protection each machine has (PO-3). A soldier credential that a CLI holds in its memory is open to the same read, and so is claude's credential file while it exists; either allows only `send` as that soldier (PO-4). Another plugin in the owner's Claude Code session runs as the owner inside the Monarch's host: a `process.spawn` hook sees the secret in the post office's input and every event on its output, and can change them, on every system and at any `ptrace_scope` (PO-3).
2. **What remains of shared memory** (D-19). With auto memory off, a claude soldier neither loads nor saves the owner's auto memory, and a subagent's own memory is off too. An organization's managed settings outrank the `--settings` that keeps it off, so a managed `env` that sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY` to `0` turns auto memory back on for every claude soldier (CH-2). Each claude soldier still loads the owner's user instructions (`~/.claude/CLAUDE.md` and `~/.claude/rules/`), as Claude Code does for any session, and the `CLAUDE.md` files in its snapshot or worktree. A soldier that can write in the owner's home folder can still edit the memory files directly (the paragraph below).
3. **Work outside the process tree** (D-3, PO-1). Work a CLI hands to a service outside its tree keeps running, as PO-1 lists: a systemd, launchd or cron job, a scheduled task, a process started through WMI, a container engine, a tmux or screen server, a session that `ssh localhost` opens, or a vendor's own background service; and, on Windows, a process created with a parent outside the tree, which takes that parent's job. No guard or audit sees what it changes after the turn. A guardian killed together with the post office leaves its tree running until the mod or the next post office sweeps it, except on Windows, where the job ends with it. On Linux, the processes no listing found escape for good, as they do when a guardian alone is ended from outside (PO-15, PO-16). macOS containment rests on interfaces Apple doesn't publish, so an update can stop every macOS soldier until a release; it fails closed (PO-18). On Windows under AppLocker or App Control, no soldier starts until an administrator allows the containment script and its DLL: the DLL ships prebuilt, so nothing compiles, but ConstrainedLanguage mode blocks loading it too (PO-19).
4. **The folder's own files, once trusted** (D-10). After the owner accepts a trust card, those files act as the owner's own until they change again. Bytes accepted in one working tree are trusted in every working tree of the repository, and an older version accepted once stays trusted after a newer one is accepted (ARM-7). The card shows a change; it doesn't judge it.
5. **Secrets that `redact()` doesn't match** (SEC-4). Any other secret a soldier's CLI writes into its session, such as a value it read from a file or its environment, is logged as the CLI wrote it. An approval request's card shows what the request holds, secrets included (WSP-8).
6. **What a vendor approves by itself** (CH-7, D-16). Shadow Army adds no command filter, and removes no vendor safeguard (ADR-0010). At `auto`, each vendor's own classifier or sandbox decides. A `supervised` claude soldier runs in claude's plan mode, where claude's classifier may approve a shell command outside the read-only set without the owner, unless the owner's own settings turn `useAutoModeDuringPlan` off (CH-2). What such a command writes in a read-only turn is discarded in a snapshot or reverted in a worktree (ARM-8, WSP-12), but not what it does outside them (the paragraph below).
7. **A git config change while harness git runs** (WSP-10; for the owner to accept). A soldier can change the shared git config, adding a filter for example, between WSP-10's check before a harness git command and git's own reading of the config. Whatever git then runs has run. The check after the command finds the change if it is still there, and holds harness git. WSP-10's command-line settings still keep hooks, the file system monitor, the pager, signing, external diffs and text conversion off. On git 2.54, which has no per-event hook switch, a hook defined in the config within that window, under a name the check didn't see, runs too.
8. **Repository files a CLI reads by itself** (row 11; for the owner to accept). Each CLI uses the repository's own configuration as its vendor's rules say. For a `claude -p` soldier, that includes hooks, the `env` block and helper commands, with no trust dialog, which the owner's own trusted session runs too. Its `.mcp.json` servers connect only once the owner has accepted the file on the trust card (ARM-7), and as it was accepted.
9. **Logs without a limit** (D-5). Log size and rotation come after 2.0 (H62). Logs are kept until the owner deletes them (WSP-8), so they can fill the disk; a failed write is handled as PO-5 says.
10. **The trust card's own gaps** (ARM-7). A PreToolUse hook, the owner's or one in the folder's own Claude Code settings, can answer the card's dialog. Any process of the owner's user, a soldier that runs code included, can write the record in `~/.shadow-army/trust/`. v1's commands, until LEG-1, read the folder's files with no card.
11. **What a read-only turn leaves, and what its revert takes** (D-7). WSP-12 reverts a read-only turn's writes in a soldier's worktree, except where git ignores files. So:
    - what a read-only turn writes where git ignores files (build output, caches, installed packages) stays in a soldier's worktree for its later turns, though never on its branch or in `/apply`;
    - an edit the owner makes in a soldier's worktree during its read-only turn is reverted, and no copy is kept;
    - a `.claude/` settings file that a read-only turn writes takes effect until the revert;
    - an edit the owner makes in that worktree after the revert, before the CLI then starts a turn by itself, goes on WSP-12's card, and the owner keeps or reverts it (D-24). A write the turn makes before the post office reads its first event shows on that card as if it were the owner's, and y keeps it;
    - a rule that the owner saves with an approval's "don't ask again" during a read-only turn is the owner's own choice, and goes where claude puts it: on Linux and macOS, outside the cases claude's settings documentation names, to the main checkout's `.claude/settings.local.json`, where it stays; on Windows, to the worktree's, where the revert takes it back and reports it as the turn's read-violation (WSP-12, CH-2).
12. **The start state and the guard's baseline are files the soldier's user can write** (WSP-12; for the owner to accept). Soldiers run as the owner. The post office checks the start state against a hash that it keeps in memory and in the log line that opens the turn, so a rewrite while the post office runs is found, and the revert restores nothing from it. A post office that died has only the log's hash to check against, and the log is a file the soldier can write too. The guard's baseline (PO-8) has the same exposure and no hash. A turn that rewrites both could get its own copy restored as the builder's work.
13. **The repository's other working trees** (D-23). Another working tree of the repository inside the folder, such as one `claude --worktree` makes under `.claude/worktrees/`, is not this army's checkout, so this army's guard sees nothing written there (WSP-11, ARM-6), and adding or removing one holds no harness git (WSP-10). A soldier that runs git can add one and write in it unseen; only the transcript line that names each working tree added or removed shows it, and a tree added and removed between two harness git commands shows no line at all. The metadata of any working tree that is neither this army's folder nor one of its own snapshots and worktrees, wherever it lies, its `config.worktree` included, is compared by neither the guard nor harness git; only an add or a removal is logged. The nested tree's own army, whenever one runs there, guards it during that army's turns.

**Writes outside the snapshot, the worktree and the checkout** (D-4, D-19). Under `auto` or `full`, Shadow Army neither prevents nor detects what a soldier writes outside its snapshot, its worktree and the checkout, such as in the home folder or another repository, as in v1. The guard covers only the checkout and the paths ARM-6 hashes (ARM-6, WSP-11). Only the vendor's own sandbox, where its CLI has one at that level, or a container or VM that the owner provides, confines such writes. A read-only turn's snapshot and its revert don't reach them either (ARM-8, WSP-12).
