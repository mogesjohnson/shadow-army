# M1: the post office and Claude channel

This is the first implementation of the existing M1 plan under [#63](https://github.com/mogesjohnson/shadow-army/issues/63), based on spec v0.3. It introduces a local post office and a persistent native Claude Code channel. The existing v1 commands continue to work.

This partially implemented milestone remains draft until the missing M1 integration and the owner's live evidence are recorded. Offline tests use synthetic protocol traffic and fake executables; they are not recordings from a real provider. The later mod pane belongs to M5. The launcher accepts the documented one-shot stdin bootstrap; actual HOST-2 mod session start/stop integration and M1-AC1 acceptance remain pending M1 work.

## Try the persistent channel

Build with `npm run build`. From the target repository, run:

```console
sa live claude-sonnet
```

Type two related prompts in this interactive session. They use the same Claude process and native conversation until you exit. `/stop` interrupts a turn; `/exit` closes the session. When a native approval request appears, the owner can enter `/answer <request_id> <native JSON response>` in the interactive session. The adapter forwards that explicit response and never grants approval by itself.

The first M1 runtime opens a private detached worktree for the soldier and permits read-only work, including for a configured build soldier. A detected write fails the turn, and its snapshot remains available for inspection. Work is not applied to the checkout.

The snapshot starts from committed `HEAD`. Uncommitted checkout edits and untracked files are not included in M1; the working-state behavior of WSP-6 remains M6 work. Keep this limit in mind when asking a soldier to read or review current work.

A single task can be run with:

```console
sa live claude-sonnet "Read README.md and package.json; describe the project." --json
```

The single-task caller closes its post office afterwards. Use the interactive form when checking that history survives into a follow-up or when entering native approval responses.

Claude must already be installed and authenticated. Its vendor system prompt, native tools and permissions remain in place. Shadow Army appends standing instructions through `--append-system-prompt` on POSIX and `--append-system-prompt-file` on Windows, preserving the same full instruction text across the native executable boundary. Only the Claude channel ships in M1; the other configured soldiers' native channels belong to M2.

## Launcher and logs

`sa post-office --cwd <repository>` is the internal process boundary. The launching process generates the Monarch credential, writes one bootstrap JSON line on standard input, then closes that input. Bootstrap EOF does not stop the helper. Commands use a loopback HTTP connection; events return on standard output as JSONL. A normal caller session ends through the authenticated shutdown command. The helper also watches for its launching process to disappear, and the client has a forced shutdown deadline for a wedged helper. Actual integration with the mod's session hooks remains pending M1 work under HOST-2 and M1-AC1.

The Monarch credential must never go in arguments, environment variables, a temporary file, or a log.

The draft has an open P2 in POSIX session cleanup: a descendant that explicitly detaches into another process group can survive `close()`, even while the channel reports successful containment. An offline WSL protocol simulation reproduced continued writes after a mid-tool native crash and close. This blocks complete PO-1/PO-7 acceptance; it is separate from M2's per-turn background-job completion. Windows uses a Job Object and is unaffected by this escape. The PR review records the reproduction and requested fix.

Normal shutdown gives the native CLI two seconds to finish after stdin EOF before forced containment cleanup. POSIX also gives a nonresponsive native CLI a short SIGTERM grace. This preserves the default Claude SessionEnd cleanup budget, while longer custom hooks can exceed the shutdown deadline.

The post office and each soldier session have separate append-only JSONL logs under `.shadow/v2/logs/`. All values pass through redaction before logging or crossing the caller-facing output boundary. Redaction removes the configured secrets, all hex case spellings of a known 32-byte credential, common credential fields, bearer values, private keys and recognizable API-token strings. Token counts come from native provider usage. Claude's `total_cost_usd` is a cumulative client estimate; its delta is marked `costSource: native_cli_estimate`, with the original total retained. It is not a billing record. The instructions' size estimate is never logged as provider usage or cost.

Standing instructions contain the soldier's shadow name, configured model and roles, the actual team, Claude as Monarch, the hard rules, all of `rules.md`, that soldier's `agent.md` section, the five-line report and the 200k handoff instruction. Another soldier's private instructions are excluded. Instructions are preserved in full: an oversized set fails before launch, rather than losing rules through truncation.

The offline size guard uses `ceil(UTF-8 bytes / 3)` and rejects estimates of 1,500 tokens or more. This is a conservative heuristic for these shipped instructions, not the provider's tokenizer or a mathematical upper bound. SI-3's exact native token limit remains pending owner verification.

## Owner's live check

Use a clean checkout at the same commit, with the same committed file contents for the native headless baseline and the M1 snapshot. Use the same two files and prompts: first ask Claude to read the files and describe the project, then ask which has more lines. Keep model, permission mode and project conditions the same. Save the native events with CLI version, model and date, redact them before committing, and record the evidence on the M1 PR.

For acceptance, native reported token usage must be within 5% of the baseline, and the persistent follow-up must read no file. The release budget is at most $2 of reported cost. Also verify the assembled standing instructions against the native tokenizer before accepting SI-3. The implementation never substitutes estimated text tokens for native usage.

Pending #69 clarifies background-job lifetimes and native failed terminal outcomes. Any M1 lifecycle behavior touched by those final rules must be checked against the agreed spec before approval; a draft M1 PR does not resolve or supersede that review.
